# Глава 10. Открытые вопросы и трейдоффы

Честная карта того, что не решено — ни в этом руководстве, ни в индустрии. Каждый пункт: формулировка, почему это важно, текущая позиция и честный компромисс. Это не слабость руководства, а его часть: процесс, делающий вид, что вопросов нет, хрупок.

## 10.1. Нерешённые проблемы устойчивости AI

**Круг «модель проверяет модель».** Квалификацию расхождений спека↔код делает модель; размыкают круг только проверки исполнением; всё непокрытое держится на доверии к модели. Позиция: машинная проверка исполнением там, где дёшево ([принцип дешёвой формы](02-principles.md)); признание, что полного размыкания нет. Компромисс: не формализовать всё — validation (намерение) остаётся за человеком.

**Неполнота ведомости допущений.** Машина перечисляет, где спека молчала и она выбирала сама — но список заведомо неполон. Позиция: ведомость как обязательный артефакт приёмки, понимание его неполноты.

**Экономика спек при высокой неопределённости.** Когда требования меняются быстрее, чем их успевают зафиксировать, затраты на спеки могут не окупиться. Позиция: уровни процесса ([глава 5](05-process-at-scale.md)) — лёгкие формы для зон неопределённости; «не могу сначала всё придумать, а потом получить программу целиком» — итеративное уточнение, не BDUF.

**Ориентация человека при сотнях параллельных агентов.** При масштабировании от 5 агентов к сотням — как находить минимум мест, где внимание человека даёт максимум эффекта? («product-shaped hole», Nadeem). Решения нет — ни у нас, ни в индустрии.

## 10.2. Процессные трейдоффы

**Полнота vs дешевизна формализации.** Формализовать можно многое, но не всё дёшево. Компромисс: формализуем там, где дёшево (типы, контракты, PBT); словами — причины решений, разрешение конфликтов, триггеры пересмотра (ADR). Нет общего ответа, где граница — это инженерное суждение.

**Понижение уровня процесса.** Модель уровней ([глава 5](05-process-at-scale.md)) описывает только продвижение вверх; понижение не определено ни в одном источнике. Позиция: если инициатива «сдулась», артефакты остаются, уровень не пересматривается задним числом — но это конвенция, не правило.

**Молчание: lazy consensus vs «молчание ≠ согласие».** В review-практиках lazy consensus (молчание = согласие за 3 дня) конфликтует с принципом явной приёмки из феноменологии деградации. Позиция: молчание допустимо для **minor** артефактов (где цена ошибки мала); для **accepted-решений** (ADR, архитектура) — только явная приёмка. Это сознательное разграничение, а не противоречие.

**Граница Git-Native.** Принцип «всё в репо» упирается в upstream requirements work (discovery, scope, stakeholder alignment), которая идёт с не-инженерными ролями вне репозитория (кейс Talk Think Do). Позиция: репо — source of truth для артефактов решений; upstream-работа может жить в доступных всем ролям системах с **зеркалированием** в репо. Граница — по доступности ролям, не по догме.

**Multi-repo спеки.** Фича фронт+бэк в разных репо — где живёт спека? Открытая проблема индустрии (OpenSpec issue #725, кластер без решения). Позиция: hybrid-модель (каноническая спека в одном месте + cross-repo traces), но готового ответа нет.

## 10.3. Технологические трейдоффы

**Готовое vs собственное.** Принцип «использовать готовое, своё — только при необходимости» — но граница необходимости не всегда очевидна. Критерии, когда собственное оправдано: нужны механизмы, которых нет у готовых (cross-mission learnings, topic-views, cross-tool handoff); нужна независимость от bus factor / форк-модели; нестандартный пайплайн. Иначе — adopt/adapt. → `../research/kb/landscape/spec-kitty-research.md` (варианты A–D).

**Блокирующие gate vs скорость итерации.** Жёсткие gate (Spec Kit phase gates, Spec Kitty guards, SpecWeave evidence-gate) повышают устойчивость, но замедляют итерацию и могут воспроизводить waterfall. Компромисс: блокирующие gate для accepted-зон (invariants, evidence), advisory — для исследовательских; уровень строгости — по цене ошибки.

**Markdown vs machine-readable.** Единый формат для человека и агента (Markdown) против машинной обработки (YAML/schema). Позиция: человек читает Markdown, машина получает auto-generated производные (requirements.json, _index.md, evidence-log.csv) — source of truth один, проекции генерируются в CI.

## 10.4. Как жить с открытыми вопросами

1. **Фиксировать, не прятать.** Открытый вопрос, записанный в `docs/ideas/` или ADR с `Conditions for Revision`, лучше молчаливого компромисса.
2. **Калибровать по своему контексту.** Пороги и таргеты в этом руководстве — эвристики из источников, не законы; калибровать по метрикам своей команды ([глава 9](09-operations.md)).
3. **Пересматривать регулярно.** Ландшафт меняется быстро; quarterly review инструментов и переоценка необходимости SDD-инструментов (Thoughtworks Radar, категория Assess).
4. **Итеративно, не BDUF.** Процесс сам по себе — живой артефакт: начать с минимального, добавлять по мере необходимости, пересматривать по данным.

**Заключение.** Процесс разработки через документацию и AI-агентов — не продукт, который покупают, а инженерная дисциплина, которую проектируют под свой контекст: на принципах ([гл. 2](02-principles.md)), с реалистичными ожиданиями ([гл. 4](04-sdd-and-ai-agents.md)), под масштаб задачи ([гл. 5](05-process-at-scale.md)), с честным признанием нерешённого (эта глава). База знаний `../research/kb/` — фактура для углубления; `ideas/` — направления развития собственной системы.
