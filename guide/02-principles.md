# Глава 2. Принципы

Принципы — слой, инвариантный к инструментам: они остаются верными при смене любого tooling и определяют, устойчив процесс или нет. Сначала — базовые принципы проектирования процесса (что ценим), затем — принципы устойчивости, выведенные из критики AI-процессов (что ломается без них). Каждый принцип даётся с тем, как его проверить.

## 2.1. Базовые принципы проектирования

Пять декларативных принципов (`../research/kb/principles/process-design-goals.md`):

1. **Documentation-First** — документация создаётся до кода и является source of truth; код — производная от спецификаций.
2. **Open Formats & Tools** — артефакты в открытых форматах (Markdown, YAML, JSON, PlantUML, Mermaid); инструменты заменяемы без конвертации.
3. **Git-Native** — все артефакты в репозитории; версионирование, code review, ветвление и merge для документов.
4. **Human + AI Collaboration** — агенты генерируют и верифицируют, люди принимают финальные решения; clear handoff.
5. **Scalability** — процесс работает для проектов любого размера; минимальный набор на старте, структура добавляется по мере роста.

Операционное усиление — 10 принципов со следствиями (P1–P10): Git — единственный source of truth; формат важнее инструмента; один артефакт — одно решение; структура предсказуема; автоматизируй проверку доков; минимальный overhead по умолчанию; пишем для будущего читателя; человек утверждает, агент исполняет; обратная совместимость масштаба; инструмент можно выкинуть.

**Как проверить:** пять success-тестов — Traceability (от коммита до идеи по цепочке артефактов), Onboarding (новый участник/агент понимает проект по репо без устных объяснений), Vendor-exit (замена инструмента без конвертации), Scale (L1-задача ≤ 15 минут на доки), AI (агент без истории чатов имплементирует L1–L2 по спеке).

## 2.2. Принципы устойчивости (из критики AI-процессов)

Эти принципы выведены не из «как должно быть», а из задокументированных поломок. Каждый закрывает конкретный класс проблем (карта проблем — [глава 4](04-sdd-and-ai-agents.md)).

### Дешевая форма требования
Требование живёт в самой дешёвой форме, способной его удерживать: инвариант домена → тип; граница систем → схема + контрактный тест; обобщённое намерение → property-based тест; конкретное поведение → пример (unit-тест); причины решений → ADR. Словами — только то, что формализуется дороже, чем нарушается. Проверка: текстовая спека сжата до минимума; всё формализуемое дёшево — проверяется машиной. → `../research/kb/principles/cheapest-form.md`

### Явные инварианты и блокирующие gate
То, что нельзя нарушать, явно зафиксировано **с обоснованием** и проверяется исполнением; проверки **блокируют** продвижение, а не advisory. Агент минимизирует «трение» и обходит проверки, которые можно обойти — enforcement должен быть машинным и вне его досягаемости (CI, hooks, permissions). Проверка: инвариант нельзя нарушить флагом; «don't do X because Y, and instead do Z». → `../research/kb/principles/invariants-and-gates.md`

### Экономика внимания
Человек — самое медленное звено. Ограничивать нужно не объём артефактов, а объём человеческого внимания для их проверки. Машина хранит версии и сравнивает состояния; человек решает только по квалифицированным расхождениям. Сложность процесса = f(сложность задачи, цена ошибки), не константа. Проверка: лёгкая задача проходит с малым overhead; человек не читает сплошняком машинный вывод. → `../research/kb/principles/attention-economy.md`

### Молчание ≠ согласие
По отсутствию замечания невозможно отличить просмотренное от непросмотренного. Приёмка явная: фриз фиксирует область принятого; остальное — непросмотренное с неизвестным статусом. Машина ведёт **ведомость допущений** — места, где спека молчала и она выбирала сама. Проверка: «не заметил» и «принял» — разные статусы; допущения фиксируются и поднимаются в спеку. → `../research/kb/principles/ai-degradation-phenomena.md`

### Процесс важнее инструмента
Процесс проектируется владельцем; инструмент — заменяемая реализация. Инструмент оборачивается в собственную абстракцию (свои команды, свои форматы, свои review gates); есть план миграции. Vendor-lock принимает 4 формы: лицензионный, знаниевый, экосистемный, форматный. Проверка: смена инструмента не ломает процесс и привычки команды. → `../research/kb/principles/process-over-tool.md`

### Контент стабилен, структура виртуальна
Файлы не перемещаются; статус — данные (frontmatter), а не местоположение (директория); навигация — через виртуальные структуры (индексы, теги, симлинки). Перемещение ломает diff и дорого для агента; ссылка дешевле файла. Проверка: смена статуса/темы артефакта — без перемещения файла и с чистым diff. → `../research/kb/principles/content-stays-virtual-structure.md`

## 2.3. Чек-лист принципов

| Принцип | Быстрый тест |
|---|---|
| Documentation-First | PR без связанного артефакта не принимается (кроме trivial) |
| Open Formats | Все артефакты — Markdown/YAML/diagram-as-code |
| Дешевая форма | Формализуемое дёшево — проверяется машиной |
| Блокирующие gate | Проверка нарушения нельзя обойти флагом |
| Экономика внимания | Лёгкая задача — малый overhead |
| Молчание ≠ согласие | Явная приёмка + ведомость допущений |
| Процесс > инструмента | Смена инструмента не ломает процесс |
| Контент стабилен | Статус/тема меняются без перемещения файла |
