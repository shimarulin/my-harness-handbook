# Глава 4. SDD и AI-агенты: что работает, что нет

Честный разбор Spec-Driven Development на основе корпуса критики (60+ первоисточников, `../content/kb/landscape/sdd-criticism.md`). Не «за» и не «против»: что реально ломается, почему, что подтверждённо работает, и какие принципы из этого следуют.

## 4.1. Главный тезис

SDD-инструменты решают задачу «точных инструкций агенту», которая быстро устаревает по мере роста моделей, но **не решают главную проблему: расхождение спеки и кода — дефолтный исход при отсутствии блокирующего машинного enforcement**. Спека на естественном языке недоопределена по построению: машина молча заполняет пробелы, а обратная связь асимметрична (мы видим и правим спеку только там, где машина промахнулась) — доверие к спеке растёт быстрее её определяющей силы.

## 4.2. Что ломается: карта проблем

**Спек-дрейф.** Спеки не обновляются сами; синхронизация — конвенция, не принуждение. «If nothing blocks on spec/code divergence, divergence is the default outcome over time». Историческая аналогия: «Памяти усопшего Rational Rose… Модель и код всегда расходятся».

**Advisory verification.** У OpenSpec `validate` проверяет только структуру, `verify` не блокирует archive, `archive --no-validate` отменяет проверку. «Контракт подписан, но исполнение — на совести агента». Агент обходит проверки флагом (issue #194: `--skip-specs`).

**Плоскость и масштабирование.** «Миллион папочек со спеками, которые хз как организовывать». Multi-repo: фича фронт+бэк в разных репо — где живёт спека? (issue #725 открыт).

**Требования — upstream от репозитория.** Кейс Talk Think Do: 84% AI-authored code → отказ через 2 месяца. «Requirements work is not just an engineering activity. Discovery, refinement, scope conversations sit upstream of the repository» — репо не workspace для BA, delivery, QA, клиента.

**Экономика.** Полный цикл BMAD — 6 дней/$200 против лёгкого — 1 день. Кейс dev.to: простой Instructions.md победил OpenSpec по скорости, цене и удобству. «Будущее AI-assisted development — не тяжёлые фреймворки, а более лёгкие workflow с лучшими инструкциями».

**Waterfall в Markdown.** Spec Kit «в 10 раз медленнее ожиданий» (Scott Logic), «too opinionated», 8 файлов на один spec, iteration = регенерация.

**Провал planning-first.** «Plan Mode Is Dead» (Ayman Nadeem, постмортем Nuanced): планирование ≠ план; модели съели ценность план-артефактов снизу; никто не хочет читать AI-текст; waterfall-пайплайн против итеративного мышления.

**Феномены деградации (инструменто-независимые).** Умолчание (спека молчит — машина заполняет), дрейф (спека определяет — машина отклоняется), эрозия (деградация содержания при правках), наплыв (перенос структуры/стиля из соседнего кода). Зазор творчества: скрытые выборы машины, осевшие в коде. → `../content/kb/principles/ai-degradation-phenomena.md`

**Multi-agent ловушки.** «Process multiplier, not process creator» — без существующих процессов BMAD воспроизводит хаос на 19 агентах. «The 19-Agent Trap»: 19 system prompts конкурируют за внимание в одном окне.

## 4.3. Что подтверждённо работает

- **OpenSpec**: переделки кода −~1/3 после трёхфазного workflow; `verify` выявляет проблемы в ~1/3 случаев; «cleanest delta model in this category»; «the one you'll still be using in week three».
- **Spec Kit**: constitution как shared contract для распределённых команд; артефактная цепочка лучше чат-транскрипта для нового агента.
- **BMAD**: adversarial code review «поймал вещи, которые standard review бы пропустил»; самое здоровое сообщество (94.3% issue close rate).
- **Spec Kitty Research Mission**: evidence-gated research (guard «минимум 3 источника») — блокирующий, не advisory.
- **SpecWeave**: cross-tool handoff (перенос работы между вендорами/аккаунтами) и блокирующий evidence-gate (`task done --run` отказывает при fail) — прямые ответы на зафиксированные дефициты.

**Рынок подтверждает тезис критики**: инструменты с блокирующим enforcement (Spec Kitty guards, SpecWeave evidence-gate) появились как ответ на дефицит advisory verification. «Судьба SDD решится не качеством спек, а появлением дешёвого машинного enforcement».

## 4.4. Реалистичные ожидания (когда SDD помогает, когда нет)

| Сценарий | Вердикт |
|---|---|
| Сложная фича, много сессий агентов, greenfield | ✅ SDD помогает (durable context, трассировка) |
| Correctness > скорость (auth, money, data retention) | ✅ Стоимость спеки окупается |
| Простая задача, один context window | ❌ Overhead не окупается — lightweight spec или Instructions.md |
| Требования не определены upstream | ❌ SDD в репо не решает upstream-работу |
| Зрелая команда со своим процессом | ⚠️ Готовый фреймворк «из коробки» скорее навредит — нужна адаптация |
| Ожидание «спека = гарантия корректного кода» | ❌ Недетерминизм LLM; нужен machine enforcement |

## 4.5. Принципы, выведенные из поломок

Дешевая форма требования; явные инварианты и блокирующие gate; экономика внимания; молчание ≠ согласие; процесс важнее инструмента. Полный разбор — [глава 2](02-principles.md) и `../content/kb/principles/`.

## 4.6. Открытые вопросы

Круг «модель проверяет модель»; неполнота ведомости допущений; полнота vs дешевизна формализации; экономика спек при высокой неопределённости; ориентация человека при сотнях параллельных агентов; multi-repo спеки. Подробно — [глава 10](10-open-questions.md).
