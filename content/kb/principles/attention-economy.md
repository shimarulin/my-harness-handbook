# Принцип: экономика внимания человека и масштаб процесса

| Параметр | Значение |

## Что это

Человек в связке «человек–машина» — самое медленное и немасштабируемое звено. Принцип: **ограничивать нужно не объём машинно хранимого состояния, а объём человеческого внимания** для проверки изменений (Шапиро). Средства тем бесполезнее, чем больший объём артефактов в единицу времени создаётся: их объём растёт, предельная ёмкость внимания человека — нет. Сплошное ручное сличение замедляет пару до скорости человека.

Следствие: сложность процесса должна соответствовать сложности задачи и цене ошибки — а не быть константой.

## Ключевые концепции

### Масштаб процесса по цене ошибки

«Сложность процесса должна соответствовать сложности задачи и цене ошибки» (q1):

| Задача | Процесс |
|---|---|
| Простая (багфикс, мелкая фича) | Instructions.md + прямое исполнение |
| Средняя (новая фича) | Дельта-спека + ревью |
| Высокая (архитектурное изменение) | Полная спека + ADR + ревью |
| Легаси/рефакторинг | OpenSpec-like подход (дельты) |

Superpowers — та же идея, три пути с явным human approval перед кодингом (лёгкие пути снижают ceremony, не убирая checkpoint): **Spike** (вопрос + короткий подход, результат exploratory) / **Bounded change** (компактный дизайн в чате, без отдельных документов) / **Architectural change** (письменная спецификация и план).

Экономические данные (Ran Isenberg, 2026-04-13): планирование BMAD Full — 2 дня/$50, Spec-Kit — 4 ч/$30, OpenSpec — 3 ч/$25; полный flow BMAD — 6 дней/$200 против 1 дня у OpenSpec/Spec Kit. Overhead полного цикла для простых задач не окупается — «хирургия вилочным погрузчиком».

### Разделение труда человек/машина

Машина хранит версии, прогоняет проверки, сравнивает состояния; человек решает **только там, где изменение не укладывается в уже принятую норму и заказ** (Шапиро). Механическая разница предъявляется квалифицированно: «вы просили изменить А; вместе с ним изменилось Б, которое удерживало основание В; Б — необходимое следствие или отдельное решение?»

### Планирование ≠ план (Nadeem, «Plan Mode Is Dead», 2026-09-24)

Постмортем продукта Nuanced (HN: 538 points, 469 комментариев). Четыре причины провала planning-first:

1. **Планирование сконфлиировано с планом** — мышление до кода ценно, длинный артефакт никому не нужен; процесс был точкой, артефакт — нет.
2. **Модели стали очень хорошими** — model capability конкурировала с interface design; модель съела ценность продукта снизу.
3. **Никто не хочет читать AI-сгенерированный текст** — «если нужна короткая выжимка (Spec Tour), чтобы документ был юзабельным, зачем был документ?»
4. **Разрыв непрерывного процесса** — waterfall chat→disambiguate→spec→review→approve→implement против реального итеративного мышления; продукт заставлял заканчивать мышление преждевременно.

Замена: цикл **understand → act → inspect → clarify → adjust → act**; clarify — только там, где результат поднял реальное решение. Подтверждение (Gromilo): «Отношение к плану сменилось с "инструкции, которые агент должен сделать" на "вот как агент понял задачу". Можно свериться» — план стал зеркалом понимания, не контрактом.

**Когда план всё же писать** (чеклист Nadeem): blast radius — production (миграции БД, auth, деньги); результат нельзя проверить иначе (approve — единственный quality gate); requirements contested (несколько стейкхолдеров с разногласиями — документ как продуктивный формат несогласия); работа днями, не минутами (durable-артефакт переносит решения между сессиями).

### Контекстная инженерия (Chesbrough, 2026-05-28)

Наблюдение: деградация (повторы, галлюцинации) начинается при заполнении **50–60% контекстного окна**. Четыре стадии управления контекстом: понимание (что модель видит: системный промпт, AGENTS.md, skills, MCPs, tools) → мониторинг (программная проверка заполнения, пример `context-monitor check --threshold 60%`) → планирование (оценить «размер» задачи, большую разбить, ненужные MCPs выгрузить) → прунинг (`/clear` — дорогая перезагрузка; `/compact <instructions>` — сжатие с сохранением важного). Тезис статьи: SDD — это не про спеки («Why SDD is NOT about the Specs»).

### Итеративность вместо BDUF

«Не могу я сначала все придумать, а потом получить программу целиком» (Gromilo). Workflow: минимальная спека → итерация 1 → уточнение спеки по узнанному → итерация 2 → повторять; менять спеку, когда реальность её опровергает. Анти-паттерны применения SDD (Torres Bermon): 50-страничная спека, замороженная до имплементации (BDUF в Markdown); трёхстраничная спека без edge cases («шипите демо, ломается в первый день продакшена»); зелёные тесты при неправильном поведении (acceptance criteria — прокси интента; лечение — «Why this matters» и «Non-goals» в каждой спеке); framework shopping (четыре недели реального использования научат быстрее, чем сравнение фреймворков).

### Открытая проблема: ориентация при масштабе

При масштабировании от 5 параллельных агентов к сотням агенты должны находить минимум мест, где внимание человека даёт максимум эффекта — «product-shaped hole» (Nadeem). Решения нет.

## Сильные и слабые стороны

Сильные: снимает главный риск SDD (overhead без окупаемости); сохраняет контроль там, где он дешевле всего; объясняет провалы «тяжёлых» внедрений.

Слабые / риски: адаптивный процесс требует дисциплины маршрутизации задач (кто и как оценивает сложность/цену ошибки); «лёгкий» путь легко становится отсутствием процесса; молчание ≠ согласие остаётся в силе и на лёгких путях (см. `ai-degradation-phenomena.md`).
