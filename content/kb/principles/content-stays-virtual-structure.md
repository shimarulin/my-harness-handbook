# Принцип: контент стабилен, структура виртуальна (notes/ + views/, симлинки vs MOC)

| Параметр | Значение |
|---|---|
| Статус | draft |
| Обновлено | 2026-09-30 |

## Что это

Архитектурный принцип организации базы знаний, выведенный из семи инсайтов пользователя: **контент стабилен (файлы не перемещаются), структура виртуальна (индексы, теги, симлинки), статус — данные (frontmatter), а не местоположение (директория)**. Это принцип-претендент на ядро собственной системы (см. журнал идей STATUS.md) — описывает, как хранить и навигировать любые эволюционирующие артефакты, а не только research-заметки.

## Семь инсайтов (основание, дословно)

1. **Иерархия файловой системы работает как оглавление** — древовидная структура каталогов естественна для человека; не нужен отдельный индекс, файловая система уже им является.
2. **Статус должен быть и в структуре, и в frontmatter** — поиск (grep/rg) ищет по содержимому, но не по путям; статус только в директории не находится поиском, только в frontmatter не виден в tree.
3. **Перемещение файла в git вместе с изменением ломает diff** — rename detection ломается: «удалён + создан» вместо «перемещён + изменён».
4. **Перемещение агентом — дорого по токенам** — файл в 1000 строк = 2000+ токенов на перемещение (прочитать + переписать); скрипт делает то же за O(1) токенов.
5. **Один файл — много тем** — жёсткая иерархия не позволяет поместить файл в несколько каталогов.
6. **Плоская структура + симлинки** — вариант: файлы в одном месте, симлинки для организации (риски потерять связность).
7. **Перемещать ссылку, не файл** — если «перемещается» только ссылка (в индексе), diff чистый: файл не тронут, изменился только индекс.

Мета-процесс для самих инсайтов: журнал `research/meta/insights.md` (статусы `raw → confirmed → promoted`) → практическая проверка → правило в CONVENTIONS.md. Тот же pipeline, что inbox → active → decided, но для знаний о самом процессе.

## Архитектура

```
research/
├── notes/                          # РЕАЛЬНЫЕ ФАЙЛЫ. Source of truth. Не перемещаются никогда.
│   └── YYYY-MM-DD-<slug>/          # Один research = одна директория (дата создания + slug)
│       ├── README.md               # frontmatter: status, topics, author + TL;DR
│       ├── question.md
│       ├── findings/
│       └── comparison.md
├── views/                          # СИМЛИНКИ. Виртуальные коллекции. Не редактируется вручную.
│   ├── by-status/<status>/<slug> -> ../../notes/YYYY-MM-DD-<slug>
│   └── by-topic/<topic>/<slug> -> ../../../notes/YYYY-MM-DD-<slug>
├── indexes/                        # (опционально) MOC и автогенерируемые индексы
├── meta/insights.md                # Журнал инсайтов о процессе
├── scripts/                        # research-status.py, research-index.py, research-link.py
├── templates/
└── learnings.md
```

Frontmatter (обязательный в README.md): `status` (draft|active|review|decided|archived), `topics` (через запятую), `author` (human:/agent:), `created`, `updated`, опционально `decision` (ссылка на ADR).

Поток данных: `notes/` (frontmatter) — source of truth → `research-link.py sync` → `views/` (материализация для навигации). «Три "виртуальные директории" — один реальный файл. Ноль перемещений.»

### Правила (CONVENTIONS.md)

- **P1: Файлы не перемещаются** — создаётся в notes/YYYY-MM-DD-<slug>/ и остаётся навсегда.
- **P2: Статус — в frontmatter, не в директории** — меняется скриптом, не перемещением.
- **P3: Темы — через теги и MOC, не через директории** — `topics:` в frontmatter для автоиндексации; ручные MOC для сложных тем.
- **P4: Иерархия — для человека, поиск — для машины** — статус дублируется: frontmatter (поиск) + индекс/views (навигация).

Правила views: (1) только симлинки на директории в notes/; (2) всегда относительные пути; (3) никаких симлинков на симлинки; (4) не редактируется вручную — только `sync`; (5) frontmatter — единственный source of truth; (6) CI запускает `verify`.

## Симлинки vs MOC vs frontmatter-only (честный разбор)

Критика MOC: дополнительный шаг навигации (открыть документ, чтобы навигировать); требует поддержки (вручную — забывают, скриптом — ещё одна генерация); не интегрируется с инструментами (`ls`, `fzf`, IDE tree, `find` работают с ФС, не с Markdown); «MOC — это документ, а не структура».

| Аспект | Симлинки (views/) | MOC (индексные файлы) | Только frontmatter |
|---|---|---|---|
| Навигация человеком | ✅ Нативная: tree, IDE, ls | ❌ Через чтение Markdown | ❌ Только поиск |
| Навигация агентом | ✅ `ls views/by-topic/orm/` | ✅ Чтение MOC | ⚠️ rg + парсинг |
| Поиск (grep/rg) | ⚠️ Не следует (и это фича: notes/ — для поиска, views/ — для навигации) | ✅ | ✅ |
| Git diff | ✅ 1 строка на изменение | ⚠️ Несколько строк | ✅ Только frontmatter |
| Windows | ❌ Требует настройки | ✅ | ✅ |
| Файл в 2+ темах | ✅ Два симлинка | ✅ Две записи | ✅ Тег topics |
| Требует генерации | ⚠️ Sync | ⚠️ Генерация/вручную | ✅ Нет |
| Source of truth | Frontmatter (sync) | MOC-файл | Frontmatter |
| Нулевой overhead чтения | ✅ ФС = UI | ❌ Открыть MOC | ❌ Искать |

Риски симлинков и купирование: (1) Windows без Developer Mode — `core.symlinks=true`, WSL нативно, fallback CI-генерируемые indexes/; (2) абсолютные пути — запрещены, скрипт гарантирует относительные; (3) grep не следует симлинкам — «это фича, а не баг»: нет дублирования находок, notes/ для поиска; (4) циклы — правило «только на реальные директории notes/» + CI verify; (5) инструменты агентов — `cat`/`read_text` прозрачны, `ls`/`iterdir` видят ссылку; (6) merge conflicts — git хранит симлинк как однострочный blob, конфликт тривиален; (7) копирование вне git — не сценарий (git — единственный носитель).

**Вердикт**: симлинки — основной механизм навигации (человек через tree, агент через ls); frontmatter — source of truth (поиск + генерация views); MOC — опционально для аннотированных обзоров с контекстом (это документация, не навигация).

## Скрипты

| Скрипт | Назначение | Интерфейс |
|---|---|---|
| `research-status.py` | Смена статуса без перемещения (O(1) токенов) | `<path> --status <draft\|active\|review\|decided\|archived> [--author "agent:claude"]` |
| `research-index.py` | Генерация indexes/by-status.md и topic-*.md из frontmatter | `[--root research/]` |
| `research-link.py` | Управление симлинками views/ | `add <note-path> --topic <t> \| --status <s>`; `remove …`; `sync` (идемпотентный: rmtree views/ + перестройка из frontmatter); `verify` (битые → exit 1) |

Дизайн sync: после любого изменения frontmatter → sync → views актуальны; git diff после sync — только изменённые симлинки; CI = sync + verify.

## Переносимость принципа за пределы research/

Принцип применим к любому эволюционирующему корпусу артефактов: KB-статьи (эта база — кандидат), спеки, ADR-коллекции, ideas/. Инвариант: никогда не перемещать контент ради статуса/темы; статус и темы — данные; навигация — материализация. Расходится с моделью `inbox/ → active/ → decided/` через физическое перемещение (см. `../methods/research-knowledge.md` — там эта модель зафиксирована как допустимая для малых корпусов S, где цена перемещения мала; notes/+views/ — рекомендуемая для M+).
