# Экосистема Pi

**Статус:** черновик | **Дата:** 2026-09

## Ядро: Pi (earendil-works/pi)

Pi — минималистичный agent harness от Mario Zechner (создатель libGDX).
Ключевая философия: **«Adapt Pi to your workflows, not the other way around»**.

**Репозиторий:** https://github.com/earendil-works/pi  
**Сайт:** https://pi.dev  
**Stars:** 108k (сентябрь 2026)  
**Лицензия:** MIT

> ⚠️ Не путать метрики: **Pi** (earendil-works) — базовый runtime,
> ~108k звёзд. **pi-fabric** — стороннее расширение, ~245 звёзд.
> **senpi** — fork, ~443 звезды. **omp** — fork с Rust core, ~32.8k звёзд.

### Архитектура

```
┌─────────────────────────────────────────────────┐
│ pi-coding-agent (CLI)                           │
│  ├── Interactive TUI                            │
│  ├── Sessions (tree-structured, JSONL)          │
│  └── Extensions system                          │
├─────────────────────────────────────────────────┤
│ pi-agent-core (agent runtime)                   │
│  ├── Tool calling + state management            │
│  └── Event streaming                            │
├─────────────────────────────────────────────────┤
│ pi-ai (unified LLM API)                         │
│  └── 15+ providers, один API                    │
├─────────────────────────────────────────────────┤
│ pi-tui (terminal UI library)                    │
│  └── Differential rendering                     │
├─────────────────────────────────────────────────┤
│ pi-durable (durable runtime)                    │
│  └── Checkpointing, restore                     │
├─────────────────────────────────────────────────┤
│ pi-telemetry (vendor-neutral contracts)         │
│  └── OTLP export                                │
└─────────────────────────────────────────────────┘
```

### Ключевые особенности

- **4 инструмента из коробки**: read, write, edit, bash
- **Tree-structured sessions**: `/tree` для навигации, branching
- **15+ провайдеров**: Anthropic, OpenAI, Google, Groq, Ollama, ...
- **5 режимов**: interactive, print/JSON, RPC, app-server (Codex-compatible app integrations), SDK
- **Минимальный system prompt**: token-efficient
- **Extension-first**: всё добавляется через TypeScript модули

### Почему Pi как база

1. **Чистая архитектура** — каждый пакет можно использовать отдельно
2. **Extension-first** — всё добавляется через TypeScript модули
3. **Не opinionated** — не навязывает workflow
4. **Активная разработка** — ежедневные коммиты, большое сообщество
5. **RPC-режим в ядре** — ACP-адаптеры (pi-acp) строятся поверх него;
   сами адаптеры — сторонние (см. ниже)

## Расширение: pi-subagents (nicobailon/pi-subagents)

Добавляет мультиагентность через **delegation tool**.

**Репозиторий:** https://github.com/nicobailon/pi-subagents  
**Stars:** 3.7k

### Builtin агенты

| Агент | Роль | Когда использовать |
|---|---|---|
| `scout` | Codebase recon: files, entry points, data flow | Перед планированием |
| `researcher` | Web/docs research с источниками | Когда нужны внешние данные |
| `evidence-auditor` | Проверка claims против источников | Перед доверием research |
| `worker` | Implementation: edits files, validates | Для выполнения |
| `reviewer` | Code review + small fixes | После implementation |
| `oracle` | Second opinion, challenge assumptions | При рискованных решениях |
| `delegate` | Lightweight general delegate | Прочее |

### Архитектура subagents

```
Parent Session (Pi)
    │
    ├─ Foreground Subagent (in-process, streaming)
    │
    └─ Background Subagent (detached runner, async)
```

### Scripted Workflows

```javascript
// Через SubagentWorkflow tool
workflow.agent("scout", { task: "find auth flow" })
  .then(r => workflow.parallel([
    workflow.agent("reviewer", { task: "check security", ctx: r }),
    workflow.agent("oracle", { task: "challenge", ctx: r })
  ]));
```

### Common workflows

- **Scout before planning**: «Use scout to inspect the auth flow before planning»
- **Implementation then review**: «Implement this, then review it»
- **Review loop**: «Run a review loop on this change with a max of 3 rounds»
- **Parallel reviewers**: «Run reviewers for correctness, tests, and cleanup»
- **Council for decisions**: `/council` with model-based advisors

### Ограничения
- Оркестрация по умолчанию **LLM-driven** (родитель решает, когда делегировать)
- Нет workflow snapshots (только session trees)
- Нет observability для production
- Лимит `maxSubagentSpawnsPerRun` (default 64), watchdog, missions/schedules.
- Лимит `maxSubagentSpawnsPerRun` (default 64), watchdog, missions/schedules.

## Расширение: pi-fabric (monotykamary/pi-fabric)

Добавляет **code mode**: один программируемый tool `fabric_exec`.

**Репозиторий:** https://github.com/monotykamary/pi-fabric  
**Stars:** 245

### Как работает

1. LLM пишет TypeScript программу
2. Программа статически проверяется
3. Выполняется в изолированном QuickJS sandbox
4. Результат возвращается в conversation

> **Ядра выполнения:** по умолчанию TypeScript (QuickJS, sandboxed). Также доступно
> Python-ядро (**Monty** — sandboxed Python subset с VM-лимитами, без FS/network/process).
> CPython 3.10+ — explicit escape hatch с macOS sandbox-exec / Linux bwrap (fail closed).
> Выбор ядра — эксклюзивный (`executor.kernel`), per-call селектора нет.

```typescript
// Пример программы
const [manifest, sources] = await Promise.all([
  pi.read({ path: "package.json" }),
  pi.find({ pattern: "**/*.ts", path: "src" }),
]);

return {
  package: JSON.parse(manifest).name,
  sourceCount: sources.split("\n").filter(Boolean).length,
};
```

### Возможности

- **Capability routing**: вызов Pi tools, MCP servers, extension tools
- **Guardrails**: approvals, timeouts, concurrency limits, recursion depth
- **Cost budgets**: ограничение расходов на цепочку
- **Durable mesh**: topics, compare-and-swap state, actor restoration
- **Skills**: готовые паттерны (fabric-workflow, fabric-council, ...)
- **Live dashboard** (`/fabric`): Activity + Topology

**Требования:** Node 24+, Pi ≥0.80.6+. **Лицензия:** MIT.

### Ограничения

- **Маленькое сообщество** (~245 звёзд на момент анализа)
- Зависимость от одного мейнтейнера
- Интеграция с pi-web не документирована

> ⚠️ Заявление проекта: 100% ARC-AGI-3 (25 сред, 22.4 часа, 4 минуты человека, $1,349).
> Приводится как заявление проекта, не как независимый факт.

## Web UI: pi-web (jmfederico/pi-web)

Web control plane для Pi сессий.

**Репозиторий:** https://github.com/jmfederico/pi-web  
**Сайт:** https://pi-web.dev

### Архитектура

```
Browser (laptop/phone/tablet)
    ↓ HTTP/WS
PI WEB gateway (localhost:8504)
    ↓
Session daemon (долгоживущий)
    ↓
Pi Coding Agent сессии
    ↓
Реальные workspace
```

### Возможности

- **Persistent sessions**: переживают закрытие браузера
- **Multi-device**: один и тот же live session с любого устройства
- **Workspaces**: projects, git worktrees (auto-discovery)
- **Terminals**: встроенные в web UI
- **Fleet**: multi-machine federation

### Установка и требования

**Требования:** Node ≥22.19.0, Pi ≥0.87.0, npm.

```bash
npm install -g @jmfederico/pi-web --allow-scripts=node-pty
pi-web install
pi-web doctor
```

> На npm 12 флаг `--allow-scripts=node-pty` необходим, чтобы `node-pty`
> подготовил нативный модуль. Без флага install не воспроизводится.

### Ограничения

- Молодой проект, маленькое сообщество
- Не sandbox (trusted users only; для доступа извне — reverse proxy с auth)
- Нет observability для LLM calls

## ACP: pi-acp (сторонние адаптеры)

Адаптеры Agent Client Protocol для IDE-интеграции поверх RPC-режима Pi:

```
ACP-клиент (Zed, JetBrains) ↔ JSON-RPC 2.0 via stdio ↔ pi-acp ↔ pi --mode rpc
```

### Доступные реализации

| Адаптер | Статус |
|---|---|
| `svkozak/pi-acp` (npm `pi-acp`) | Upstream-адаптер, MVP-статус, фокус Zed |
| `@geohar/pi-acp` | Форк upstream: subagents как ACP-tasks (plan-канал), MCP auto-config через pi-mcp-adapter, multi-root workspaces, шаги к ACP v2 |

> `regadas/pi-acp` и `gsd-pi-acp` в первоисточниках не подтверждены —
> удалены из таблицы. Обсуждение #4444 в earendil-works/pi предлагает
> нативный `pi --mode acp` поверх AgentSession — сигнал, что сторонний
> адаптер может стать ненужным.

> В отличие от omp, где ACP реализован в самом бинарнике, у Pi это
> сторонний слой. RPC-режим в ядре — стабильно поддерживается.

## Fork: senpi (code-yeongyu/senpi)

> «pi had nothing (nothing), so I made something (something)»

Opinionated fork pi-mono с builtin extensions. Создан под влиянием OmO,
но легче — single CLI binary, не opencode plugin.

**Репозиторий:** https://github.com/code-yeongyu/senpi  
**Stars:** 443 | **Статус:** Experimental

### Что добавляет к Pi (18 builtin extensions)

| # | Extension | Что делает |
|---|---|---|
| 1 | `permission-system` | opencode-style permissions |
| 2 | `gpt-apply-patch` | Codex-style apply_patch для GPT |
| 3 | `prompt-preset` | Per-model system prompt presets |
| 4 | `todowrite` | Todo tools + continuation loop |
| 5 | `compaction` | Adaptive thresholds, emergency compaction |
| 6 | `bash-timeout` | Timeout enforcement |
| 7 | `tool-pair-guard` | Anthropic compaction safety |
| 8-18 | `websearch`, `webfetch`, `rules`, `goal`, ... | Utility extensions |

### Что НЕ содержит (в отличие от OmO)

- Discipline Agents (Sisyphus, Hephaestus, ...)
- Team Mode
- ultrawork / ulw
- Hashline
- Skill system

### Позиционирование

> «Think of senpi as a light version of OMO that runs as a single pi
> CLI binary instead of an opencode plugin.»

## Инструменты для работы с кодом

### Встроенные tools (концептуальный пример)

```typescript
// Read file
const content = await pi.tools.read({
  path: "src/auth/service.py",
  maxLines: 1000
});

// Grep search
const matches = await pi.tools.grep({
  pattern: "refresh_token",
  path: "src/",
  include: "*.py"
});

// Edit file
const result = await pi.tools.edit({
  path: "src/auth/service.py",
  oldText: "def old_function():",
  newText: "def new_function():"
});

// Bash command
const output = await pi.tools.bash({
  command: "npm test"
});
```

### Рекомендации по расширению

Для production harness рекомендуется добавить:

**1. Code intelligence** — tree-sitter для AST, LSP для symbol search
(готовые расширения: pi-ast-grep, pi-lsp-client от code-yeongyu).

**2. Semantic search** — embeddings + vector DB.

**3. Repo map** — дерево директорий + основные модули.

## Containerization patterns

Pi документирует три паттерна изоляции:

### Pattern 1: Gondolin Extension

```
Host: Pi + provider auth
    │
    │ micro-VM
    ▼
Gondolin: built-in tools + ! commands
```

**Когда:** нужна сильная изоляция, но provider auth на host.

### Pattern 2: Plain Docker

```
Docker container:
├─ Pi process
├─ All tools
└─ Network isolation
```

**Когда:** простая изоляция без сложной настройки.

### Pattern 3: OpenShell

```
OpenShell sandbox:
├─ Pi process
├─ Policy-controlled tools
└─ Restricted permissions
```

**Когда:** нужна policy-based security.

См. также раздел [01.sandbox](../01.sandbox/README.md) — там эта тема
раскрыта подробнее.

## Сильные стороны Pi

- Заточен под coding agents, чистая модульная архитектура
- RPC/SDK-режимы для встраивания
- Extension-first: всё добавляется без fork ядра
- Большое сообщество и активная разработка
- База для целой экосистемы (senpi, omp, pi-subagents, pi-fabric)

## Слабые стороны Pi

- Из коробки — почти ничего: 4 инструмента, никаких workflow-паттернов
- Нет автоматической оптимизации стоимости
- Observability ограничена session trees
- Встроенного web UI нет (только сторонний pi-web)

## Когда выбирать Pi

### Выбирайте Pi, если:

- ✅ Нужна модульность и полный контроль над стеком
- ✅ Планируется строить собственный harness поверх чистой основы
- ✅ Нужны RPC/SDK-режимы для встраивания в другие системы
- ✅ Важна близость к upstream (минимум чужих opinionated решений)

### Не выбирайте Pi, если:

- ❌ Нужен быстрый старт с готовыми patterns
- ❌ Нужна автоматическая оптимизация стоимости
- ❌ Нужен встроенный web UI или ACP без настройки
- ❌ Не хочется собирать стек из расширений самому
