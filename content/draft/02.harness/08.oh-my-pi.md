## Позиционирование

Oh My Pi (omp) — это форк Pi, расширенный до состояния
"batteries included" coding agent. Позиционируется как
"the most capable agent surface that ships".

**Ключевая идея:** Взять отличную основу (Pi от Mario Zechner)
и добавить всё, чего не хватает для реальной разработки ПО.

**Философия:**
- Terminal-first UX для реальной работы
- Practical built-ins из коробки
- Advanced behavior configurable, not hidden
- Native performance через Rust

## Архитектура

### Time-Traveling Stream Rules (TTSR)

Проектные regex/AST-правила «спят» до срабатывания. При совпадении с
потоком вывода модели (включая思维 chain и tool-call параметры):

1. Поток обрывается mid-token
2. Правило инжектится системным напоминанием
3. Генерация возобновляется с той же точки

Инжекции переживают compaction. Это «real-time policy enforcement» —
буквальная иллюстрация принципа «детерминизм важнее интеллекта».

### Subagent IRC

Встроенный `irc`-инструмент: параллельные воркеры в worktree-изоляции
договариваются о рукопожатиях, шлют DM, ждут ответов. Typed yields
(schema-validated объекты) вместо прозы. Используется только для
быстрых ответов между peer-агентами, не для long-form content.

## Уникальные возможности

### 1. Debugger Support

omp умеет подключаться к реальным debuggers:

#### lldb (C/C++)

```
User: This C binary segfaults, debug it

omp:
1. Runs binary with lldb attached
2. Catches segfault signal
3. Reads stack trace
4. Inspects bad pointer
5. Reads frame context
6. Reports: "Segfault at line 42: dereferencing NULL pointer
   returned by uninitialized malloc"
```

#### dlv (Go)

```
User: Go service hangs, investigate

omp:
1. Attaches dlv to process
2. Lists goroutines
3. Finds stuck goroutine
4. Walks call stack
5. Reports: "Goroutine blocked on channel send
   in worker.go:15, no receiver"
```

#### debugpy (Python)

```
User: Python process is wedged, debug it

omp:
1. Attaches debugpy
2. Pauses process
3. Inspects variables
4. Evaluates expressions
5. Reports: "Deadlock: Thread A holds lock1,
   waits for lock2; Thread B holds lock2,
   waits for lock1"
```

**Конкуренты не имеют этого:** OmO Native ❌, Pi ❌, Mastra ❌.

### 2. Persistent Code Execution

omp запускает **постоянные** Python и Bun workers:

```
Main Agent
    │
    ├─ Python Worker (persistent)
    │   └─ Can call back: tool.read, tool.search, tool.task
    │
    └─ Bun Worker (persistent)
        └─ Can call back: tool.read, tool.search, tool.task
```

**Преимущества:** нет overhead на запуск каждый раз, stateful computation,
быстрее для iterative задач, можно держать большие данные в памяти.

### 3. LSP Wired Into Every Write

```text
User: Rename function "calculateTotal" to "computeTotal"

omp:
1. Calls workspace/willRenameFiles
2. Updates all references
3. Updates re-exports
4. Updates barrel files
5. Updates aliased imports
6. THEN moves the file
```

**LSP operations (14):** rename, goto definition, find references,
diagnostics, formatting, code actions, symbol search, workspace symbol,
document highlights, code lens, folding ranges, selection ranges,
signature help, hover.

### 4. First-Class Subagents с Worktree Isolation

#### Встроенные специалисты

| Специалист | Назначение |
|---|---|
| **scout** | Fast, read-only exploration |
| **designer** | UI/UX implementation, accessibility |
| **reviewer** | Evidence-backed correctness review |
| **security-reviewer** | Vulnerability discovery |
| **librarian** | Source-verified research |
| **task** | General multi-step work |
| **sonic** | Strictly mechanical edits, data collection |

#### Worktree Isolation

**Backends:** APFS (macOS), btrfs (Linux), zfs (Linux), reflink
(copy-on-write), overlayfs, projfs (Windows), rcopy (fallback).

**Конфигурация:**
```yaml
task:
  isolation:
    mode: auto  # или конкретный backend
    apply: true  # применять изменения после успеха
    merge: patch  # или branch
```

**Преимущества:** нет конфликтов между workers, безопасное параллельное
редактирование, можно откатить изменения, атомарное применение.

### 5. Plan Mode с Review

```text
User: /plan Replace the in-memory job queue with Postgres.
      Preserve the public API, include a rollback path,
      and call out every migration step.

omp (Plan mode):
1. Switches to plan model
2. Investigates codebase (read-only)
3. Checks assumptions
4. Builds Markdown plan
5. Opens Plan Review surface

User: [reviews plan in full-screen TUI]

Options:
- Approve and execute (fresh session)
- Approve and compact context
- Approve and keep context
- Refine plan (with annotations)
- Save and quit
```

### 6. Atomic Edits с Preview

```text
1. Agent calls ast_edit
2. Returns (proposed) card with:
   - Replacement count
   - Diff preview
   - Change staged

3. Agent writes reason to xd://resolve

4. TUI shows Accept card:
   ┌─────────────────────────────────┐
   │ Proposed: 3 replacements        │
   │ Reason: Fix null checks         │
   │                                 │
   │ [Accept] [Reject]               │
   └─────────────────────────────────┘

5. Disk move happens — atomic, all or nothing
```

### 7. workflowz — детерминированные multi-subagent workflows

Ключевое слово «workflowz» в промпте активирует детерминированный
контракт через eval kernel:

```
User: "workflowz an adversarial review of auth changes"

→ LLM строит DAG через eval kernel
→ agent(), parallel(), pipeline(), completion()
→ Контракт направляет, но модель выбирает детали
```

## Сильные стороны

### 1. Уникальные возможности

Никто другой не имеет: debugger support (lldb, dlv, debugpy),
persistent Python/Bun workers, полная LSP интеграция на уровне writes.

### 2. Производительность

80k строк Rust. Быстрый запуск, низкий overhead, эффективные операции,
меньше resource usage.

### 3. Batteries Included

Всё из коробки. Не нужно строить инструменты, не нужно интегрировать,
быстрый старт, меньше настройки.

### 4. First-Class Subagents

7 специалистов с worktree isolation. Безопасное параллельное выполнение,
нет конфликтов, можно откатить, атомарное применение.

### 5. Plan Mode

Полноценный режим планирования. Лучше для сложных задач, можно ревьюить
план, документация решений, меньше ошибок.

### 6. ACP из коробки

Нативная поддержка. Легкая интеграция с IDE, стандартный протокол,
не нужно строить.

### 7. workflowz

Детерминированные multi-subagent workflows через eval kernel.

## Слабые стороны

### 1. Меньше готовых workflow patterns

Нет ultrawork, /ulw-plan как в OmO. Нужно строить свои, меньше
автоматизации, больше ручной работы.
- **PR-политика:** с vouch-экспериментом вклад сообщества ограничен
  (PR временно открыты как trial; vouch-система может вернуться).

### 2. Нет автоматической оптимизации стоимости

Нет category-based routing. Нужно вручную выбирать модели, сложнее
оптимизировать, нет автоматических fallbacks (есть ручные).

### 3. Opinionated

Батареи включены, но сложно кастомизировать. Меньше гибкости,
нужно адаптироваться, сложнее интегрировать нестандартные решения.

### 4. Меньше сообщество

Форк, меньше пользователей чем у оригинала. Меньше примеров,
меньше third-party, медленнее развитие.

### 5. Сложность

80k строк Rust + TypeScript — большая кодовая база. Сложнее понимать
внутренности, труднее отлаживать, больше potential bugs.

## Пример использования: Debugging Session

```text
User: My Go API server is hanging in production. Debug it.

omp:
1. Attaches dlv to running process
2. Lists all goroutines
3. Finds 3 goroutines blocked
4. Walks each call stack
5. Identifies deadlock pattern:
   - Goroutine 1: waiting on mutex A
   - Goroutine 2: holding mutex A, waiting on mutex B
   - Goroutine 3: holding mutex B, waiting on mutex A
6. Reports root cause
7. Suggests fix: reorder mutex acquisition

User: Apply the fix

omp:
1. Creates plan
2. Shows proposed changes
3. Applies after confirmation
4. Runs tests
5. All pass
```

## Когда выбирать Oh My Pi

### Выбирайте, если:

- ✅ Нужны debuggers (lldb, dlv, debugpy)
- ✅ Нужны persistent workers (Python, Bun)
- ✅ Нужна полная LSP интеграция
- ✅ Важна производительность
- ✅ Нужны first-class subagents с isolation
- ✅ Нужен plan mode
- ✅ Нужна ACP интеграция
- ✅ Хотите батареи из коробки
- ✅ Нужна Windows native (no WSL)

### Не выбирайте, если:

- ❌ Нужны готовые workflow patterns как в OmO
- ❌ Нужна автоматическая оптимизация стоимости
- ❌ Не нужны уникальные возможности
- ❌ Хотите максимальную гибкость
- ❌ Не готовы к большой кодовой базе

## Альтернативы

- **Pi (Earendil)** — более модульный, легче
- **OmO Native** — больше готовых паттернов, автоматизация
- **Mastra** — полный контроль, observability

## Выводы

Oh My Pi — это **самое мощное решение** для разработки ПО с уникальными
возможностями, которых нет у конкурентов.

**Главное преимущество:** Уникальные возможности (debuggers, persistent
workers, LSP).
**Главный недостаток:** Меньше готовых паттернов и автоматизации.
**Лучше всего подходит для:** Задач, требующих глубокой отладки,
производительности и профессиональных инструментов.
**Не рекомендуется для:** Простых задач или когда важна автоматизация.
