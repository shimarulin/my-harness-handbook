# Принципы проектирования

**Статус:** черновик | **Дата:** 2026-09

## Принцип 1: Детерминизм важнее интеллекта

> «Меньше полагаться на LLM, больше детерминизма. Но при этом сохранять
> гибкость, чтобы можно было быстро перестраиваться.»

### Проблема

LLM-driven оркестрация (когда модель сама решает, какой агент вызвать
дальше) непредсказуема:

- Один и тот же запрос может пойти разными маршрутами
- Слабая модель может «заблудиться» в делегировании
- Невозможно отладить: почему этот шаг, а не другой?

### Решение: Spectrum of Control

```
Full LLM          Hybrid                 Full Code
  │                  │                       │
  ▼                  ▼                       ▼
OmO Team Mode    omp workflowz          Mastra workflows
(Pi pi-subagents)  (contract-guided)    (Zod schemas)
                  │                       │
                  ▼                       ▼
              "Модель следует       "Код определяет
               контракту"            каждый шаг"
```

**Наша позиция:** по умолчанию — ближе к «Full Code» (Mastra workflows,
omp workflowz). LLM-driven — для exploratory задач (research, unfamiliar
codebase), где предсказуемость менее важна.

### Паттерны усиления детерминизма

| Паттерн | Что делает | Где реализовано |
|---|---|---|
| **Code Mode** | LLM пишет TypeScript программу, статически проверяется, выполняется в sandbox | pi-fabric, omp eval |
| **Typed Contracts** | Zod schemas между шагами, compile-time проверка | Mastra |
| **Workflow Keyword** | «workflowz» в промпте активирует детерминированный контракт | omp |
| **IntentGate** | Keyword detection (ultrawork/ulw, team, hyperplan) перед tool use | senpi, OmO |

## Принцип 2: Усиление слабых моделей через harness

> «Усиливаем слабые модели, снижаем стоимость решения с помощью harness
> каждой отдельно взятой рабочей задачи.»

### Идея

Вместо «купи самую дорогую модель для всего» — **подбери harness под
слабую модель так, чтобы она работала как сильная**:

| Техника | Эффект | Пример |
|---|---|---|
| **Hashline edits** | −61% output tokens (Grok 4 Fast), меньше retry на bad diffs | omp |
| **Tool-call absorption** | Десятки вызовов collapse в один шаг | OmO |
| **Per-model prompts** | Claude → step-by-step, GPT → другой формат | senpi prompt-preset |
| **Parallel-tool routing** | Независимые вызовы выполняются параллельно | senpi, omp |
| **Compaction** | Adaptive thresholds, emergency compaction | senpi, omp |

### Kibitzer / Advisor паттерн

Дешёвая модель наблюдает за дорогой:

```
Main agent (Claude Opus)      Advisor (Grok 4 Fast)
    │                              │
    │ plan schema change           │ watch every turn
    │ write migration              │ read memory
    │                              │ judge
    │ skip test ← ─────────────────┤ nudge: "Last time
    ▼                              │  this broke production"
  [course-correct]                 │
                                   │
```

Реализовано в: **omp** (advisor role, built-in), **OmO** (Kibitzer), **pi-fabric** (advisor стал встроенным).

## Принцип 3: Per-step model routing

> «Если для решения задачи достаточно более дешевой модели,
> не нужно использовать дорогую.»

### Уровни routing

| Уровень | Гранулярность | Пример реализации |
|---|---|---|
| **Per-role** | Роль агента → модель | omp: 10 ролей (default, smol, slow, plan, ...) |
| **Per-step** | Шаг workflow → модель | Mastra: `model: "groq/llama-4-scout"` |
| **Per-category** | Категория задачи → модель | OmO: deep, quick, visual-engineering |
| **Fallback chain** | При 429/quota → следующая модель | omp: `retry.fallbackChains` |

### Fallback Chains (omp)

```yaml
retry.fallbackChains:
  default:
    - anthropic/claude-opus-5
    - openai/gpt-6-sol
    - kimi/k3
  smol:
    - xai/grok-4-fast
    - deepseek/v4-flash
```

## Принцип 4: Терминал-first, но не терминал-only

```
TUI (основной) ──── Web (дополнительный) ──── IDE/ACP (интеграция)
     │                      │                        │
     ▼                      ▼                        ▼
  Быстрая             Наблюдение из               Работа из
  итерация            браузера                    редактора
```

- **TUI**: для daily work, debugging, интерактива
- **Web UI**: для observability (traces, costs), удалённого наблюдения
- **ACP**: для бесшовной интеграции с IDE (Zed, JetBrains)

## Принцип 5: Переживать сбои

| Уровень | Механизм | Инструмент |
|---|---|---|
| **Процесс** | Session survives disconnect | Herdr, pi-web |
| **Workflow** | Snapshots, suspend/resume | Mastra |
| **Модель** | Fallback chains при 429 | omp, OmO |
| **Машина** | Multi-machine federation | Herdr |

## Принцип 6: Разделение ответственности

Каждый компонент решает свою задачу и не пытается заменить остальные:

- **Harness** — оркестрация и агенты
- **Observability** — сбор traces, costs, evals
- **Persistence** — сохранение состояния и координация
- **Sandbox** — изоляция выполнения

Интеграция компонентов даёт лучший результат, чем выбор одного монолита.

## Чего мы НЕ делаем

- **Не строим собственный LLM-фреймворк с нуля** — используем существующие
- **Не оптимизируем для enterprise** — solo developer, local-first
- **Не жертвуем UX ради детерминизма** — если LLM-driven работает лучше
  для exploratory задач, используем её там
- **Не интегрируем всё сразу** — каждая интеграция добавляет сложность
