# Руководство по выбору

**Статус:** черновик | **Дата:** 2026-09 | **Сверить с первоисточниками**

Этот документ помогает выбрать подходящее решение на основе ваших
конкретных требований и ограничений.

## Быстрый выбор

Если у вас нет времени читать весь документ, используйте эту таблицу:

| Если вам нужно... | Выбирайте |
|---|---|
| Быстрый старт без настройки | **omp** (стабильный) / **OmO Native** (beta) |
| Максимальная гибкость | **Mastra / LangGraph** |
| Отладка сложных багов | **omp** (debuggers — уникально) |
| Модульность и лёгкость | **Pi (Earendil)** |
| Координация нескольких агентов | **Любой + Herdr** |
| Веб-интерфейс для observability | **Mastra Studio** |
| Автоматическая оптимизация стоимости | **OmO Native** |
| Production-ready без рисков | **Mastra / LangGraph** |
| Native performance + Windows | **omp** |
| Permissive-лицензия (MIT/Apache) | Pi / omp / Mastra core / LangGraph / Herdr |
| Memory без compaction из коробки | **Mastra Code** |

## Decision Tree

Вопросы упорядочены от «жёстких» дифференциаторов (уникальные
возможности, доступные только одному решению) к компромиссным:

```
Начало
  │
  ├─ Нужны debuggers (lldb/dlv/debugpy) или persistent workers?
  │    └─ ДА → omp (единственное решение)
  │
  ├─ Нужен полный детерминированный контроль над каждым шагом
  │  + snapshots + time-travel?
  │    └─ ДА → Mastra (+ omp/Pi как executor для code-инструментов)
  │         → проверить сначала Mastra Code (готовый агент)
  │
  ├─ Нужна автоматическая оптимизация стоимости (category routing,
  │  готовые discipline-агенты, Team Mode)?
  │    └─ ДА → OmO Native (учтите: beta, SUL-1.0)
  │
  ├─ Нужна memory без compaction (observational memory) и единый
  │  вендор фреймворка?
  │    └─ ДА → Mastra Code
  │
  ├─ Строите собственный стек с нуля, нужна модульная основа?
  │    └─ ДА → Pi (earendil-works) + расширения по необходимости
  │
  ├─ Нужна координация нескольких агентов/машин?
  │    └─ ДА → Любой из выше + Herdr
  │
  └─ Не уверен / нужен сбалансированный выбор?
       └─ → omp (наиболее сбалансированный:
            батареи + стабильность + MIT + ACP)
```

## Детальный процесс выбора

### Шаг 1: Определите тип задач

**Какие задачи будет решать система?** (отметьте все подходящие)

- [ ] Простой поиск по коду
- [ ] Исследование и анализ
- [ ] Реализация новых фич
- [ ] Исправление багов
- [ ] Refactoring
- [ ] Code review
- [ ] Тестирование
- [ ] Документация

**Насколько сложны задачи?**

- [ ] Простые (одна-две операции)
- [ ] Средние (несколько шагов)
- [ ] Сложные (многошаговые, с планированием)

## Готовые сценарии

### Сценарий 1: Соло-разработчик, быстрая разработка

**Требования:** быстрый старт, батареи, стабильность, MIT.

**Рекомендация:**
```bash
# omp (основной инструмент этого исследования)
curl -fsSL https://omp.sh/install | sh
omp setup
# + Herdr при необходимости persistence
```

**Почему:** батареи из коробки, debuggers, ACP, стабильный, MIT.

**Сравнение с Mastra Code:** если приоритет — observational memory
без compaction и единый вендор фреймворка, рассмотрите **Mastra Code**
(`npm i -g mastracode`). Для daily driver с максимальной широтой
инструментов (debuggers, persistent workers, LSP wired into writes)
omp остаётся предпочтительнее.

### Сценарий 2: Максимум автоматизации, минимум ручной настройки

**Требования:** автоматический выбор моделей, готовые паттерны,
готовы к beta.

**Рекомендация:**
```bash
# OmO Native + Herdr + DAG viewer
bun add -g omo-ai@beta
npx omo-herdr-dag@latest install
herdr start omo
```

**Почему:** ultrawork, category routing, Team Mode, DAG viewer.
Учтите: beta-канал, лицензия SUL-1.0.

### Сценарий 3: Корпоративный проект, большая команда

**Требования:** полный контроль, observability, production-ready.

**Рекомендация:**
```bash
# Mastra + omp (executor) + Herdr
npx create-mastra my-harness
# omp как executor для code-задач
curl -fsSL https://omp.sh/install | sh
herdr start omp
```

**Почему:** Mastra Studio, snapshots, Zod-контракты; omp — инструменты;
Herdr — координация.

### Сценарий 4: Отладка сложных багов

**Требования:** debuggers, persistent workers, LSP.

**Рекомендация:**
```bash
curl -fsSL https://omp.sh/install | sh
omp
# > My Go service hangs, debug it
```

**Почему:** единственное решение с lldb/dlv/debugpy; dlv attach —
omp ходит по goroutines и находит deadlocks.

### Сценарий 5: Собственный стек с нуля

**Требования:** максимальная модульность, полный контроль,
близость к upstream.

**Рекомендация:**
```bash
npm install -g @earendil-works/pi-coding-agent
pi install npm:pi-subagents    # агенты
pi install git:github.com/code-yeongyu/pi-lsp-client
pi install git:github.com/code-yeongyu/pi-ast-grep
```

**Почему:** чистая основа, extension-first, RPC/SDK для встраивания.

### Сценарий 6: Переход с существующего решения

1. Проанализируйте текущее решение
2. Определите, что не работает
3. Выберите решение, решающее эти проблемы
4. Мигрируйте постепенно (Herdr позволяет держать оба рядом)

```bash
# Оба агента рядом, сравнение в реальной работе
herdr start claude-code
herdr start omp
```

## Anti-patterns (чего НЕ делать)

### Про выбор решения

**❌ Использовать OmO для всего.** LLM-driven orchestration непредсказуема
для repeatable задач → для pipelines используйте Mastra, не Team Mode.

**❌ Использовать Mastra для exploratory work.** Написание workflow-кода
для ad-hoc research — overhead → omp workflowz или OmO ultrawork.

> ⚠️ Смягчение: Mastra Code (фев 2026) имеет plan mode и subagents,
> что делает его пригодным для exploratory сценариев. Анти-паттерн
> относится к core-фреймворку без Mastra Code.

**❌ Писать собственный framework с нуля.** Потратите месяцы на
существующее → возьмите omp/Mastra/OmO и расширяйте.

**❌ Выбирать без тестирования.** Прогоните решение на реальных задачах
хотя бы неделю перед миграцией.

### Про эксплуатацию

**❌ Игнорировать cost optimization.** Одна дорогая модель для всего =
$200+/день → model roles (omp) + per-step routing (Mastra) + advisor.

**❌ Игнорировать требования к стабильности.** Beta-инструменты в
production-цепочках = сюрпризы → omp/Mastra для критичного,
beta — для экспериментов.

**❌ Не проверять лицензии.** OmO — SUL-1.0 (source-available):
для коммерческого использования проверьте условия; остальные
(Pi, omp, Mastra core, LangGraph, Herdr) — permissive.

**❌ Не планировать миграцию.** Экосистема меняется быстро →
модульный стек (omp + Mastra + Herdr) позволяет заменять компоненты
по отдельности.

## Заключение

Выбор решения — это баланс между:
- Функциональностью и простотой
- Гибкостью и готовностью
- Стоимостью и возможностями
- Стабильностью и инновациями

Нет идеального решения для всех. Итоговая рекомендация этого
исследования — **omp + Mastra + Herdr** — обоснована в
[16.our-solution.md](16.our-solution.md). Используйте это руководство
как процесс, а не как догму.
