# Паттерны интеграции

**Статус:** черновик | **Дата:** 2026-09

Этот документ описывает практические паттерны интеграции различных
компонентов в единую систему harness.

> ⚠️ Все примеры кода — концептуальные. API решений меняются быстро;
> перед использованием сверяйтесь с документацией (см.
> [17.references.md](17.references.md)).

## Зачем нужна интеграция

Одно решение редко покрывает все требования:

- **Mastra** даёт оркестрацию, но не имеет готовых агентов
- **Pi** даёт инструменты для кода, но не имеет веб-интерфейса
- **OmO** даёт автоматизацию, но не имеет debuggers
- **omp** даёт уникальные возможности, но меньше готовых паттернов
- **Herdr** даёт координацию, но не является оркестратором

Интеграция позволяет комбинировать сильные стороны разных решений.

## Паттерн 1: Оркестратор + Исполнитель

### Концепция

Один компонент управляет логикой workflow, другой выполняет конкретные
задачи.

```
┌─────────────────────┐
│   Orchestrator      │
│ (Mastra/LangGraph)  │
│                     │
│ - Workflows         │
│ - State management  │
│ - Routing           │
└──────────┬──────────┘
           │ API calls
           ▼
┌─────────────────────┐
│    Executor         │
│ (Pi/omp/OmO)        │
│                     │
│ - Code tools        │
│ - Agents            │
│ - Execution         │
└─────────────────────┘
```

### Пример: Mastra + Pi

**Когда использовать:** нужен полный контроль над логикой, но не
хотите строить инструменты для кода с нуля.

**Архитектура (концептуально):**

```typescript
import { createWorkflow, createStep, createTool } from "@mastra/core";
import { z } from "zod";
import { ReadTool, GrepTool } from "@earendil-works/pi-agent-core/tools";

// Pi tools как Mastra-инструменты
const piRead = createTool({
  id: "pi-read",
  inputSchema: z.object({ path: z.string() }),
  outputSchema: z.object({ content: z.string() }),
  execute: async ({ inputData }) => {
    return new ReadTool().execute({ path: inputData.path });
  }
});

const piGrep = createTool({
  id: "pi-grep",
  inputSchema: z.object({ pattern: z.string() }),
  outputSchema: z.object({ matches: z.array(z.any()) }),
  execute: async ({ inputData }) => {
    return new GrepTool().execute(inputData);
  }
});

// Шаги с типизированными контрактами
const searchStep = createStep({
  id: "search",
  inputSchema: z.object({ query: z.string() }),
  outputSchema: z.object({ files: z.array(z.string()) }),
  execute: async ({ inputData }) => {
    // использует piGrep / piRead
    return { files: await search(inputData.query) };
  }
});

const judgeStep = createStep({
  id: "judge",
  inputSchema: z.object({ files: z.array(z.string()) }),
  outputSchema: z.object({ sufficient: z.boolean() }),
  execute: async ({ inputData }) => ({
    sufficient: inputData.files.length > 0
  })
});

// Workflow
const investigationWorkflow = createWorkflow({
  inputSchema: z.object({ query: z.string() }),
  outputSchema: z.object({ sufficient: z.boolean() })
})
  .then(searchStep)
  .then(judgeStep)
  .commit();
```

**Преимущества:** полный контроль над логикой, готовые инструменты
для кода, Mastra для observability, Pi для execution.

**Недостатки:** два слоя, сложнее отлаживать, нужно поддерживать
интеграцию.

### Пример: Mastra + OmO (subprocess)

**Когда использовать:** нужна оркестрация Mastra, но хотите
использовать готовые паттерны OmO для сложных подзадач.

```typescript
import { spawn } from "child_process";

const invokeOmOStep = createStep({
  id: "invoke-omo",
  inputSchema: z.object({ task: z.string() }),
  outputSchema: z.object({ result: z.string() }),
  execute: async ({ inputData }) => {
    // One-shot режим через subprocess
    const proc = spawn("omo", ["-p", inputData.task]);
    const output = await collectStdout(proc);
    return { result: output };
  }
});

const hybridWorkflow = createWorkflow({
  inputSchema: z.object({ task: z.string() }),
  outputSchema: z.object({ result: z.string() })
})
  .then(invokeOmOStep)
  .commit();
```

**Преимущества:** готовые паттерны OmO (ultrawork) для сложных
подзадач, контроль Mastra над пайплайном.

**Недостатки:** process isolation, сложнее передавать состояние,
больше overhead.

## Паттерн 2: Координатор + Множество агентов

### Концепция

Один компонент координирует работу нескольких агентов.

```
┌─────────────────────┐
│    Coordinator      │
│ (Herdr)             │
│                     │
│ - Session management│
│ - Status tracking   │
│ - Multi-machine     │
└──────┬──────────────┘
       │
  ┌────┼────┬────┬────┐
  │    │    │    │    │
  ▼    ▼    ▼    ▼    ▼
 Pi   OmO  Claude Code  omp
```

### Пример: Herdr + несколько агентов

**Когда использовать:** работаете с несколькими агентами
одновременно и нужна координация.

**Настройка:**
```bash
# Запустить несколько агентов в Herdr
herdr start pi              # для исследования
herdr start omo             # для реализации
herdr start claude-code     # для ревью
herdr start omp             # для отладки

# Мониторить статус
herdr status
```

**Автоматизация (документированный API):**
```bash
#!/bin/bash
# Ожидание завершения конкретного агента в pane
# (по документации Herdr: herdr agent wait <pane> --until done)
# ⚠️ Сверить точную семантику по herdr.dev/docs — рекомендуется
# начинать с CLI-обёрток
herdr agent wait w1:p1 --until done
echo "Агент в w1:p1 завершил работу"

# Чтение результата
herdr pane read w1:p1 --source recent --lines 50
```

**Преимущества:** единый интерфейс для всех агентов, мониторинг
статуса, не нужно менять агентов, легко добавлять новых.

**Недостатки:** не управляет логикой workflow, нужно координировать
вручную, больше компонентов.

## Паттерн 3: Специализированные слои

### Концепция

Каждый компонент решает свою специфическую задачу.

```
┌─────────────────────────────────────────┐
│ Layer 1: Orchestration                  │
│ (Mastra/LangGraph)                      │
│ - Workflow logic                        │
│ - State management                      │
└────────────────┬────────────────────────┘
                 │
┌────────────────┴────────────────────────┐
│ Layer 2: Code Tools                     │
│ (Pi SDK / omp tools)                    │
│ - read, grep, edit, bash                │
│ - LSP, AST                              │
└────────────────┬────────────────────────┘
                 │
┌────────────────┴────────────────────────┐
│ Layer 3: Execution                      │
│ (Sandbox)                               │
│ - Docker/microsandbox                   │
│ - Isolation                             │
└────────────────┬────────────────────────┘
                 │
┌────────────────┴────────────────────────┐
│ Layer 4: Observability                  │
│ (Langfuse/OpenTelemetry)                │
│ - Traces                                │
│ - Metrics                               │
└─────────────────────────────────────────┘
```

### Пример: Полный стек (концептуально)

**Когда использовать:** строите решение с полным разделением
ответственности.

```typescript
// Layer 2: Pi/omp tools для работы с кодом
const localizeStep = createStep({
  inputSchema: z.object({ bugReport: z.string() }),
  outputSchema: z.object({ files: z.array(z.string()) }),
  execute: async ({ inputData }) => {
    const matches = await piGrep.execute({
      inputData: { pattern: extractError(inputData.bugReport) }
    });
    return { files: matches.matches.map(m => m.file) };
  }
});

// Layer 3: Sandbox для выполнения
const testStep = createStep({
  inputSchema: z.object({ patch: z.string() }),
  outputSchema: z.object({ fixed: z.boolean() }),
  execute: async ({ inputData }) => {
    const result = await sandbox.run({
      command: "npm test",
      workDir: "/workspace"
    });
    return { fixed: result.exitCode === 0 };
  }
});

// Layer 2b: фикс (пример)
const fixStep = createStep({
  inputSchema: z.object({ files: z.array(z.string()) }),
  outputSchema: z.object({ patch: z.string() }),
  execute: async ({ inputData }) => ({ patch: "// применяется через omp/Pi" })
});

// Workflow — после определения всех шагов
const bugfixWorkflow = createWorkflow({
  inputSchema: z.object({ bugReport: z.string() }),
  outputSchema: z.object({ fixed: z.boolean() })
})
  .then(localizeStep)
  .then(fixStep)
  .then(testStep)
  .commit();

// Layer 4: Observability (OTLP export)
// настраивается на уровне Mastra/инструментов
```

**Преимущества:** чёткое разделение ответственности, каждый слой
можно заменять, легко масштабировать, хорошая поддерживаемость.

**Недостатки:** сложная начальная настройка, больше кода,
нужно управлять интеграцией.

## Паттерн 4: Гибридный подход по типу задач

### Концепция

Разные типы задач обрабатываются разными решениями.

```
┌─────────────────────┐
│    Task Router      │
│ (Classifier)        │
└──────────┬──────────┘
           │
    ┌──────┼──────┬──────┐
    │      │      │      │
    ▼      ▼      ▼      ▼
 Simple  Complex  Debug  Multi-agent
    │      │      │      │
    ▼      ▼      ▼      ▼
   Pi    OmO     omp    Herdr
```

### Пример: Роутер задач (концептуально)

**Когда использовать:** есть разные типы задач и хотите использовать
лучшее решение для каждого.

```typescript
// Концептуальный пример: классификация по ключевым словам.
// В реальной системе используйте LLM-классификатор
// (дешёвая модель) или явные команды.
async function routeTask(task: string) {
  const category = await classifyTask(task);

  switch (category) {
    case "simple_search":
      return piSearch(task);        // Pi + pi-subagents scout
    case "feature_implementation":
      return omoUltrawork(task);    // omo ultrawork
    case "bug_debugging":
      return ompDebug(task);        // omp (debuggers)
    case "multi_agent":
      return herdrCoordinate(task); // Herdr orchestration
    default:
      return ompDefault(task);      // omp как default
  }
}
```

> В практике проще: не строить роутер, а использовать model roles
> omp (per-role routing) или categories OmO (per-category routing) —
> см. [10.model-routing.md](10.model-routing.md).

**Преимущества:** лучшее решение для каждой задачи, гибкость.

**Недостатки:** сложнее поддерживать, нужен классификатор,
больше точек отказа.

## Паттерн 5: Интеграция через протоколы

### Концепция

Компоненты общаются через стандартные протоколы.

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│    IDE       │────▶│ ACP Server   │────▶│ Agent        │
│ (Zed, etc.)  │     │ (pi-acp /    │     │ (Pi/omp)     │
│              │     │  omp acp)    │     │              │
└──────────────┘     └──────────────┘     └──────────────┘

┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  Frontend    │────▶│ REST/SSE     │────▶│ Workflow     │
│  (React)     │     │ API          │     │ (Mastra)     │
└──────────────┘     └──────────────┘     └──────────────┘

┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  Other Agents│────▶│ MCP          │────▶│ Tools        │
│              │     │ Protocol     │     │ (Various)    │
└──────────────┘     └──────────────┘     └──────────────┘
```

### Пример: ACP для IDE

```bash
# omp: ACP встроен
omp acp
# В IDE (Zed): agent = omp, protocol = ACP

# Pi: ACP через сторонний адаптер (Pi-пакет)
pi install npm:@geohar/pi-acp
# Адаптер поднимает pi --mode rpc и мостит к ACP
```

**Возможности:** отправка задач из IDE, получение результатов,
streaming ответов, confirmation для опасных операций.

### Пример: MCP для инструментов

```json
{
  "mcpServers": {
    "websearch": { "url": "https://mcp.context7.com/mcp" },
    "grep_app": { "url": "https://mcp.grep.app" }
  }
}
```

**Преимущества:** стандартный протокол, работает с любыми
инструментами, легко добавлять новые, экосистема.

## Паттерн 6: Наблюдаемость как сервис

### Концепция

Все компоненты отправляют данные в единую систему наблюдаемости.

```
┌──────────┐  ┌──────────┐  ┌──────────┐
│  Mastra  │  │  Pi/omp  │  │   OmO    │
│          │  │          │  │          │
│ traces   │  │ traces   │  │ traces   │
└────┬─────┘  └────┬─────┘  └────┬─────┘
     │             │             │
     └─────────────┼─────────────┘
                   │
                   ▼
          ┌─────────────────┐
          │  Observability  │
          │     Service     │
          │                 │
          │ - Langfuse      │
          │ - OTLP          │
          │ - Custom        │
          └─────────────────┘
```

### Пример: Единая наблюдаемость (концептуально)

```typescript
const observability = new ObservabilityClient({
  exporter: "otlp",
  endpoint: "http://localhost:4317"
});

// Pi/omp: pi-telemetry (vendor-neutral contracts)
// Mastra: встроенная observability + exporters
// OmO: hooks для телеметрии
```

**Преимущества:** единая точка для всех данных, легко анализировать,
можно строить дашборды, упрощает отладку.

**Недостатки:** нужна инфраструктура, больше данных, нужно управлять
доступом.

## Паттерн 7: OmO + omo-herdr-dag + Herdr (reference-интеграция)

Единственный проверенный end-to-end DAG-viewer стек:

```bash
npx omo-herdr-dag@latest install
herdr start omo
# /dag-pane — открыть viewer в side pane
```

**Требования:** Node 24+, OmO ≥5.0.0-0.beta.42, Senpi 2026.9.4-3,
Herdr protocol 20. Панель ~35% ширины; автооткрытие при первом
workflow DAG; работает и со standalone-сборкой `omob`.

> Чистый Herdr end-to-end на момент README «не верифицирован» —
> помечаем как integration-tested, но young.

## Практические рекомендации

### Начните с малого

**Не пытайтесь интегрировать всё сразу:**

1. Выберите одно основное решение
2. Добавьте один компонент для решения конкретной проблемы
3. Протестируйте на реальных задачах
4. Добавьте следующий компонент при необходимости

### Избегайте излишней сложности

**Каждая интеграция добавляет:**
- Точки отказа
- Сложность отладки
- Время на поддержку
- Потенциальные баги

**Правило:** добавляйте интеграцию только если она решает
конкретную проблему, которую не решить иначе.

### Документируйте интеграции

**Для каждой интеграции документируйте:**
- Какие компоненты интегрируются
- Как они общаются
- Какие данные передаются
- Как обрабатываются ошибки
- Как тестировать

### Тестируйте интеграции

**Тестируйте:** нормальные сценарии, ошибки и сбои, таймауты,
повторные попытки, крайние случаи.

### Мониторьте интеграции

**Отслеживайте:** latency между компонентами, частоту ошибок,
использование ресурсов, стоимость.

## Пример: Полная интеграция

Сценарий: проект с несколькими типами задач и требованиями
к observability.

```bash
# Архитектура:
# - omp для daily work и отладки
# - Mastra для repeatable pipelines и Studio
# - Herdr для координации и persistence

# Шаг 1: Запуск компонентов
herdr start omp                     # основной агент
herdr start "npm run mastra-dev"    # Mastra server (Studio: 4111)

# Шаг 2: Настройка роутинга
# Daily work → omp (TUI/ACP)
# Repeatable → Mastra workflows (REST API)
# Отладка → omp (debuggers)

# Шаг 3: Observability
# Mastra Studio: http://localhost:4111
# omp stats: локальная статистика

# Шаг 4: IDE
# omp acp — нативная интеграция
```

**Результат:** лучшее решение для каждого типа задач, полная
наблюдаемость через Studio, persistence через Herdr, интеграция
с IDE через ACP.

## Заключение

Интеграция позволяет комбинировать сильные стороны разных решений,
но добавляет сложность. Используйте паттерны осознанно и только
когда это необходимо.

**Главное правило:** интеграция должна решать конкретную проблему,
а не добавлять сложность ради сложности.
