# Архитектурные паттерны и модели оркестрации

**Статус:** черновик | **Дата:** 2026-09

Этот документ описывает ключевые архитектурные паттерны для построения
multi-agent harness и спектр подходов к оркестрации.

## Часть 1: Спектр оркестрации

```
┌─────────────────────────────────────────────────────────────┐
│              SPECTRUM OF ORCHESTRATION CONTROL               │
├────────────┬────────────────┬───────────────┬───────────────┤
│  Full LLM  │    Hybrid      │  Code-guided  │   Full Code   │
│            │                │               │               │
│  Модель    │  Модель +      │  Контракт     │  Явный код    │
│  решает    │  подсказки     │  направляет   │  определяет   │
│  всё       │                │               │  каждый шаг   │
├────────────┼────────────────┼───────────────┼───────────────┤
│  OmO       │  Pi +          │  omp          │  Mastra       │
│  Team Mode │  pi-subagents  │  workflowz    │  workflows    │
│            │                │               │               │
│  OmO       │  senpi         │  pi-fabric    │  LangGraph    │
│  ultrawork │  IntentGate    │  code mode    │               │
└────────────┴────────────────┴───────────────┴───────────────┘
```

### 1. LLM-Driven (полная свобода модели)

**Пример:** OmO Team Mode.

```
Пользователь: "mass ulw migrate database schema"

Модель (Sisyphus):
  → анализирует задачу
  → делит на waves
  → Wave 1: planning (Claude Fable 5.1)
  → Wave 2: scope-check (Opus) + source-sweep (GPT 6 Astra) [parallel]
  → Wave 3: implementation (Kimi K3)
  → Wave 4: review (GLM 5.2)
```

**Плюсы:** адаптация к незнакомым задачам, быстрый старт.
**Минусы:** непредсказуемость, невоспроизводимость, сложная отладка.
**Где:** exploratory research, unfamiliar codebase, прототипирование.

### 2. Contract-Guided (гибрид)

**Пример:** omp workflowz.

```
Пользователь: "workflowz an adversarial review of auth changes"

Ключевое слово "workflowz" активирует контракт:
  → LLM строит DAG через eval kernel
  → agent(), parallel(), pipeline(), completion()
  → Контракт направляет, но модель выбирает детали
```

**Плюсы:** предсказуемая структура (DAG), гибкость в деталях.
**Минусы:** менее выразителен, чем явный код, нет compile-time проверки.
**Где:** code review, migration, ad-hoc multi-agent research.

### 3. Code-Mode (LLM пишет программу)

**Пример:** pi-fabric.

```typescript
// LLM генерирует эту программу, статически проверяется, выполняется в QuickJS
const [manifest, sources] = await Promise.all([
  pi.read({ path: "package.json" }),
  pi.find({ pattern: "**/*.ts", path: "src" }),
]);

return {
  package: JSON.parse(manifest).name,
  sourceCount: sources.split("\n").filter(Boolean).length,
};
```

**Плюсы:** полная выразительность TypeScript, статическая проверка.
**Минусы:** LLM должен уметь писать код, сложность отладки.
**Где:** complex data transformations, fan-out с логикой.

### 4. Full Code (явный workflow definition)

**Пример:** Mastra workflows.

```typescript
const workflow = createWorkflow({
  inputSchema: z.object({ query: z.string() }),
  outputSchema: z.object({ issues: z.array(z.any()) })
})
  .then(classifyStep)      // модель: groq/llama-4-scout (дешёвая)
  .then(scoutStep)         // инструменты: grep, ast-grep
  .parallel([
    analyzeStep,            // модель: anthropic/claude-opus-4-5 (дорогая)
    verifyStep             // без LLM: запуск тестов
  ])
  .then(verdictStep)       // агрегация
  .commit();
```

**Плюсы:** максимальная предсказуемость, Zod schemas, snapshots, observability.
**Минусы:** требует написания кода, медленнее итерация, избыточно для ad-hoc.
**Где:** repeatable pipelines, production workflows.

## Часть 2: Архитектурные паттерны

### Паттерн 1: Producer-Verifier

```
┌─────────────────┐
│ Producer Agent  │
│ (Search/Analyze)│
└────────┬────────┘
         │ Evidence Package
         ▼
┌─────────────────┐
│ Verifier Agent  │
│ (Judge)         │
└────────┬────────┘
         │
    ┌────┴────┐
    │         │
Sufficient  Insufficient
    │         │
    ▼         ▼
  Done    Retry with
          refined query
```

**Когда:** поиск по коду с проверкой полноты, генерация с верификацией,
исследование с валидацией гипотез.

**Контракты:**

Producer обязан:
- Возвращать структурированные evidence (не только текст)
- Указывать, что не найдено
- Сохранять использованные запросы

Verifier обязан:
- Проверять по критериям задачи, а не только по тексту
- Формировать конкретные follow-up queries
- Оценивать уверенность

**Реализации:** Pi+pi-subagents (scout → oracle → evidence-auditor),
OmO Native (explore → plan-consultant → plan-reviewer),
Oh My Pi (scout → reviewer → security-reviewer).

### Паттерн 2: Planner-Executor-Verifier

```
┌──────────┐
│ Planner  │
└────┬─────┘
     │ Plan
     ▼
┌──────────┐
│ Executor │
└────┬─────┘
     │ Implementation
     ▼
┌──────────┐
│ Verifier │
└────┬─────┘
     │
┌────┴────┐
│         │
Pass    Fail
│         │
▼         ▼
Done   Back to
       Planner/Executor
```

**Когда:** реализация features, bug fixes, refactoring, миграции.

**Контракты:**

Planner обязан: формировать атомарные шаги, указывать риски, определять
критерии успеха.
Executor обязан: следовать плану, сообщать об отклонениях, генерировать
минимальные изменения.
Verifier обязан: проверять по критериям из плана, давать конкретную
обратную связь, решать, достаточно ли качества.

**Реализации:** Mastra Workflows, OmO Native (/ulw-plan → /ulw-execute),
Oh My Pi (/plan → approve → execute).

### Паттерн 3: Blackboard Architecture

```
┌─────────────────────────────────────┐
│         Blackboard (Store)          │
│  ┌─────────────────────────────┐    │
│  │ Search Reports              │    │
│  │ Plans                       │    │
│  │ Patches                     │    │
│  │ Test Results                │    │
│  │ Reviews                     │    │
│  └─────────────────────────────┘    │
└──────────┬──────────────────────────┘
           │
    ┌──────┼──────┬──────┬──────┐
    │      │      │      │      │
    ▼      ▼      ▼      ▼      ▼
 Search  Plan   Code  Test  Review
 Agent   Agent  Agent Agent Agent
```

**Когда:** сложные задачи с множеством артефактов, параллельная работа,
история изменений, воспроизводимость.

**Преимущества:** меньше потери информации, легко аудировать, агенты
не зависят друг от друга.
**Недостатки:** версионирование, конфликты, сложнее отлаживать.

**Реализации:** Mastra (State + Snapshots), OmO Native (Boulder state +
task system), Oh My Pi (Session artifacts).

### Паттерн 4: Category-Based Routing

```
┌──────────────┐
│   Task       │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  Classifier  │
└──────┬───────┘
       │
    ┌──┴──┬──┬──┬──┐
    │     │  │  │  │
    ▼     ▼  ▼  ▼  ▼
  Quick Deep Visual Security Writing
    │     │  │  │  │
    ▼     ▼  ▼  ▼  ▼
  Cheap  Expensive Specialized
  Model  Model    Models
```

**Категории (пример OmO Native):**

| Категория | Для чего | Модель |
|---|---|---|
| `quick` | Простые правки, опечатки | GPT-5.6 Luna Fast |
| `deep` | Сложная логика, архитектура | GPT-6 Astra |
| `ultrabrain` | Трудные задачи | GPT-6 Astra max |
| `visual-engineering` | UI/UX | Claude Fable 5.1 |
| `architect` | Консультации по дизайну | Claude Fable 5.1 max |

**Актуальный список (README OmO):** visual-engineering, ultrabrain,
deep + deep-high/deep-low, quick, artistry, writing,
unspecified-low/high.

> Модельные маппинги меняются между релизами — срез на сентябрь 2026.

**Когда:** разные задачи требуют разных моделей, нужна автоматическая
оптимизация стоимости.

**Реализации:** OmO Native (автоматический routing), Oh My Pi (model roles).

### Паттерн 5: Hierarchical Delegation

```
┌─────────────────┐
│ Main Agent      │
│ (Orchestrator)  │
└────────┬────────┘
         │
    ┌────┼────┬────┬────┐
    │    │    │    │    │
    ▼    ▼    ▼    ▼    ▼
 Scout  Reviewer Worker Librarian Oracle
```

**Когда:** нужна специализация, задачи можно параллелить, главный агент
должен оставаться «чистым».

**Реализации:** Pi+pi-subagents (родительская сессия → child sessions),
OmO Native (task tool), Oh My Pi (task tool с worktree isolation).

### Паттерн 6: Plan-First с Review

```
┌─────────────────┐
│   Plan Mode     │
│ (Read-only)     │
└────────┬────────┘
         │ Plan
         ▼
┌─────────────────┐
│  Plan Review    │
│ (Human approval)│
└────────┬────────┘
         │
    ┌────┴────┐
    │         │
Approve    Refine
    │         │
    ▼         ▼
Execute    Back to
           Plan Mode
```

**Когда:** сложные задачи с ordering constraints, миграции,
архитектурные изменения, нужна документация решений.

**Реализации:** OmO Native (/ulw-plan), Oh My Pi (/plan).

## Комбинирование паттернов

```
Main Agent (Hierarchical)
  │
  ├─ Plan-First (для сложных задач)
  │    └─ Planner → Plan Review → Executor → Verifier
  │
  ├─ Category-Based Routing (для выбора моделей)
  │    └─ Quick → Cheap model
  │    └─ Deep → Expensive model
  │
  └─ Producer-Verifier (для поиска)
       └─ Search → Sufficiency Judge
       
Blackboard (для всех артефактов)
  └─ Все агенты пишут/читают
```

## Принципы выбора паттернов

1. **Начинайте с простого** — Producer-Verifier для поиска,
   Planner-Executor для реализации.
2. **Добавляйте сложность по необходимости** — Category-based routing
   только когда есть много разных типов задач.
3. **Избегайте over-engineering** — не все задачи требуют hierarchical
   delegation.
4. **Комбинируйте осознанно** — каждый паттерн добавляет complexity.
5. **Документируйте решения** — почему выбран этот паттерн, какие
   альтернативы рассматривались.

## Рекомендация

**По умолчанию**: Full Code (Mastra) для repeatable задач.
**Для exploratory**: LLM-Driven (omp, OmO) — когда предсказуемость менее важна.
**Переход**: начать с LLM-Driven для исследования, мигрировать критичные
цепочки в Full Code.
