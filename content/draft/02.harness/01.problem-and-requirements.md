# Проблема и требования

**Статус:** черновик | **Дата:** 2026-09 | **Обновить перед использованием**

## Проблема

Разработка ПО с помощью LLM-агентов страдает от двух полярных проблем:

1. **Недо-автоматизация**: простой chat-интерфейс к модели. Каждый шаг —
   ручной. Контекст теряется между сессиями. Нет инструментов для работы
   с кодом (поиск, чтение, редактирование).

2. **Пере-автоматизация**: LLM сам решает, какой агент вызвать, в каком
   порядке, с какой моделью. Результат непредсказуем, стоимость варьируется,
   ошибки не воспроизводятся.

Нужен harness, который занимает середину: **достаточно детерминизма для
воспроизводимости, достаточно гибкости для адаптации**.

## Ключевые проблемы

Помимо базовой дилеммы, multi-agent подход добавляет собственные проблемы.

### Координация агентов

Одиночный агент, решающий все задачи, имеет ограничения:

- Контекстное окно быстро заполняется
- Невозможно оптимизировать модель под конкретную задачу
- Сложно отлаживать и оценивать качество отдельных этапов
- Высокая стоимость (дорогая модель используется для всего)

**Пример:** агент ищет файлы, анализирует их, планирует изменения,
реализует патч, запускает тесты — всё в одном контексте. К моменту
запуска тестов контекст переполнен, модель «забывает» важные детали.

### Управление состоянием

Multi-agent системы требуют:

- Передачи контекста между агентами без потерь
- Сохранения промежуточных результатов (evidence, артефакты)
- Возможности возобновления после сбоев
- Отката к предыдущим состояниям
- Параллельного выполнения независимых задач

### Наблюдаемость и оценка

Без observability невозможно:

- Понять, где система работает плохо
- Оптимизировать стоимость
- Сравнить разные подходы
- Выявить регрессии
- Доказать эффективность системы

### Гибкость vs. готовность

Дилемма:

- **Готовые решения** (OmO, omp) — быстрый старт, но ограниченная гибкость
- **Универсальные фреймворки** (Mastra, LangGraph) — максимальная гибкость,
  но нужно строить всё с нуля
- **Гибридные подходы** — сложность интеграции

## Целевой пользователь

Одиночный разработчик (solo), использующий harness на своей машине:

- Работает в терминале (TUI-first)
- Иногда нужен web-интерфейс (с телефона, планшета)
- Использует IDE (Zed, VS Code, JetBrains) и хочет интеграцию
- Имеет доступ к моделям от разных провайдеров (Anthropic, OpenAI, Google, локальные)
- Заботится о стоимости токенов

## Требования

### Функциональные

| # | Требование | Приоритет |
|---|---|---|
| F1 | Мультиагентные цепочки: специализированные агенты для разных типов задач | High |
| F2 | Детерминизм: одинаковый input → предсказуемый маршрут выполнения | High |
| F3 | Per-step model routing: дешёвая модель для простых шагов, дорогая для сложных | High |
| F4 | TUI-интерфейс (terminal-first) | High |
| F5 | Web-интерфейс для наблюдения и управления | Medium |
| F6 | IDE-интеграция через ACP | Medium |
| F7 | Переживание сбоев: suspend/resume, snapshots | Medium |
| F8 | Memory между сессиями | Medium |
| F9 | Observability: traces, cost tracking | Medium |
| F10 | Model context/memory management (observational memory, compaction) | Medium |

### Детализация функциональных требований

1. **Оркестрация агентов** (F1, F2)
   - Поддержка цепочек (chains) и графов (graphs)
   - Условные переходы и циклы
   - Параллельное выполнение
   - Human-in-the-loop

2. **Управление моделями** (F3)
   - Поддержка 40+ провайдеров
   - Автоматический выбор модели по задаче
   - Fallback chains при недоступности
   - Cost tracking per task

3. **Инструменты для работы с кодом**
   - Поиск (ripgrep, tree-sitter, embeddings)
   - Редактирование (diff-based, hash-anchored)
   - LSP интеграция (rename, references, diagnostics)
   - Запуск команд (sandbox, bash)
   - Debuggers (lldb, dlv, debugpy) — опционально

4. **Управление сессиями** (F7, F8)
   - Сохранение и восстановление
   - Branching и forking
   - Экспорт и шеринг
   - История изменений

5. **Наблюдаемость** (F9)
   - Tracing каждого шага
   - Cost breakdown
   - Метрики качества
   - Eval harness

### Нефункциональные

| # | Требование |
|---|---|
| N1 | Локальное выполнение (данные не покидают машину, кроме LLM API calls) |
| N2 | Язык реализации не критичен (TypeScript, Rust — любой) |
| N3 | Модели из разных источников (API + локальные) |
| N4 | Быстрый старт: от установки до первого workflow — минуты, не часы |
| N5 | Надёжность: graceful degradation, retries с exponential backoff, idempotency |
| N6 | Безопасность: изоляция (sandbox), контроль доступа к секретам, аудит |
| N7 | Опциональный рост: параллельные агенты и вторая машина (federation) без требования командной инфраструктуры |
| N8 | Производительность: минимальные задержки между агентами, эффективное использование контекста, кэширование результатов |

## Пример использования

Типичный сценарий, под который проектируется harness:

```
Пользователь: "Найди все места в коде, где токены обновляются,
               и проверь, есть ли обработка ошибок"

Система:
  1. [classify] Определяет тип задачи (code search + analysis)
  2. [scout] Дешёвая модель + grep/ast-grep ищет по коду
  3. [analyze] Дорогая модель анализирует найденные места
  4. [verdict] Формирует заключение с указанием проблем

Результат: детерминированный отчёт, воспроизводимый при повторном запуске
```

## Критерии успеха

### Критерий 1: Качество результата

- Точность локализации проблем (precision@k, recall@k)
- Качество сгенерированного кода (проходит тесты, соответствует стилю)
- Минимальность изменений (не вносит лишних правок)

### Критерий 2: Эффективность

- Время выполнения задачи
- Стоимость (токены, API calls)
- Количество итераций до успеха

### Критерий 3: Usability

- Время на настройку (time to first task)
- Простота отладки
- Качество документации

### Критерий 4: Extensibility

- Легкость добавления новых агентов
- Легкость добавления новых инструментов
- Легкость кастомизации workflow

## Ограничения

- **Solo developer**: не оптимизируем для команд/enterprise (рост до второй
  машины и параллельных агентов — опционально, см. N7)
- **Local-first**: не проектируем для облачного развертывания
- **2026 ecosystem**: решения привязаны к текущему состоянию инструментов
- **Бюджет** — стоимость API calls должна быть предсказуемой
- **Время** — разработка должна быть итеративной, с быстрыми результатами
- **Компетенции** — решение должно быть доступно без глубокой экспертизы в AI/ML
- **Интеграция** — должно работать с существующими инструментами (git, IDE, CI/CD)

## Что НЕ является проблемой

- **Sandboxing/изоляция** — отдельная тема, см. [01.sandbox](../01.sandbox/README.md)
- **Обучение моделей** — используем готовые, не fine-tune
- **Multi-tenancy** — один пользователь, одна машина
