## 1. Антипаттерны контекста

### 1.1. Копирование всей истории в каждого субагента

**Что не так:** убивает саму идею изоляции и взрывает бюджет токенов.

**Правильно:** в контекст субагента передаётся только задача + минимально необходимый ввод.

### 1.2. Использование одного гигантского разговора как system of record

**Что не так:** project state хранится внутри session context, а не в durable external state. Session context переполняется, context rot ускоряется.

**Правильно:** session context — временный; project state — в reviewable files (markdown, YAML, JSON).

### 1.3. Передача raw worker transcripts между воркерами

**Что не так:** воркеры наследуют нерелевантные логи и устаревшие допущения. Context pollution.

**Правильно:** передавать только типизированные артефакты (findings.json, decision.yaml).

### 1.4. Persisting каждого thought вместо только verified state

**Что не так:** в project state попадают raw chain-of-thought, шумные логи, неверифицированные догадки.

**Правильно:** промоутить только approved decisions, stable interfaces, verified findings.

### 1.5. Заставление воркеров реконструировать project state из памяти

**Что не так:** воркер должен угадывать, что произошло, вместо чтения файлов.

**Правильно:** durable external state в файлах; воркер читает файлы, а не вспоминает.

## 2. Антипаттерны оркестрации

### 2.1. Критик-цикл без счётчика итераций

**Что не так:** на враждебных или out-of-domain запросах цикл крутится до исчерпания токен-бюджета.

**Правильно:** `max_iterations` (обычно 2–3) + явная fallback-ветка.

### 2.2. Отсутствие схем на границах хедоффов

**Что не так:** если сводка от search-агента приходит как строка без структуры, критик не сможет надёжно её оценить, а ошибка одного агента отравит всю цепочку.

**Правильно:** валидировать выходы через pydantic/zod-схемы на каждом ребре.

### 2.3. Полностью LLM-маршрутизация там, где можно детерминизм

**Что не так:** если workflow можно нарисовать как блок-схему — пишите его как workflow (детерминированный), а не как свободного supervisor-агента.

**Правильно:** детерминированный граф для фиксированных цепочек; LLM только внутри узлов.

### 2.4. Опора на 1M контекст как архитектуру

**Что не так:** Chroma протестировала 18 frontier-моделей в июле 2025 — **все 18 деградировали** с ростом длины входа . Anthropic удалил 80% system prompt Claude Code в июле 2026 без потери качества .

**Правильно:** субагенты с изолированными окнами + retrieval (граф/вектор) + 1M как fallback.

### 2.5. Слишком много параллельных агентов

**Что не так:** coordination overhead, сложность отладки, риск конфликтов.

**Правильно:** параллелить только контекстно-изолированные задачи; для правок одного кода — последовательные handoffs.

## 3. Антипаттерны стоимости

### 3.1. Использование frontier-модели для всех вызовов

**Что не так:** 60–80% inference budget тратится на subtasks, которые smaller models обрабатывают equally well.

**Правильно:** model routing по типу задачи; cheap-first, escalate-on-failure.

### 3.2. Игнорирование prompt caching

**Что не так:** каждый вызов платит полную цену input-токенов.

**Правильно:** стабильный префикс, cache_control markers. Cache reads cost 0.1× базовой цены.

### 3.3. Отсутствие телеметрии

**Что не так:** все оптимизации — гадания.

**Правильно:** cost per phase, cache hit rate, context growth, quality per cost — с первого дня.

### 3.4. Критик на той же модели, что и генератор

**Что не так:** оценка — это классификация, а не генерация; для критика обычно хватает дешёвой модели.

**Правильно:** критик — самая дешёвая модель, которая справляется.

## 4. Антипаттерны памяти

### 4.1. Хранение project state внутри session context

**Что не так:** session context переполняется; context rot.

**Правильно:** разделять session context и project state.

### 4.2. Отсутствие fresh-context workers

**Что не так:** воркеры наследуют весь orchestrator transcript.

**Правильно:** fresh-context workers с bounded task brief.

### 4.3. Игнорирование ADR

**Что не так:** решения не записываются; каждый раз объяснять с нуля.

**Правильно:** ADR в markdown + MCP-инструменты.

## 5. Антипаттерны выбора

### 5.1. OpenCode как основа для SDLC-оркестратора

**Проблемы:**
- Context engineering слабее Cursor/Pi.
- Prompt caching хрупкий.
- Opinionated system prompts.

**Вердикт:** приятный CLI, но не основа для кастомного SDLC-оркестратора.

### 5.2. Claude Managed Agents / Agent SDK как единственная основа

**Проблема:** вендор-лок на модель и инфраструктуру.

### 5.3. Переписывание runtime с нуля

**Проблема:** Pi / OpenHands / Codex уже решают то, что вы бы писали месяцами.

---

## 6. Чеклист для избежания антипаттернов

- [ ] Субагенты получают только задачу + минимальный ввод.
- [ ] Project state — в durable external state, не в session context.
- [ ] Типизированные артефакты на каждой границе.
- [ ] `max_iterations` для каждого цикла.
- [ ] Детерминированные gates перед LLM-judge.
- [ ] Model routing по типу задачи.
- [ ] Prompt caching с стабильным префиксом.
- [ ] Телеметрия с первого дня.
- [ ] Fresh-context workers для независимых задач.
- [ ] ADR для каждого решения.
