## 1. Экономика планирования

Ошибка плана стоит не «один шаг», а каскад: каждая итерация реализации, выросшая из плохого плана, оплачивается полностью ([04](./04.economics-and-cost.md)). При этом само планирование — малая доля токенов задачи. Отсюда правило:

**Планирование — самая дешёвая страховка.** Сильная модель на планировании (<10% бюджета задачи) окупается снижением числа итераций на реализации (~25% бюджета в целевой экономике, [04.7](./04.economics-and-cost.md)).

| Фаза | Цена ошибки | Модель |
|---|---|---|
| Поиск | Низкая (переспросить дёшево) | Cheap |
| Планирование | Каскадная | Strong |
| Реализация | Локальная (gate поймает) | Mid |
| Интеграционное ревью | Каскадная | Strong |

## 2. Режимы планирования

### 2.1. ReAct (interleaved)

Рассуждение и действие чередуются, план не фиксируется.

**Когда:** exploration, неизвестная местность, короткие горизонты.
**Предел:** на длинных горизонтах — thrash (блуждание, повтор пройденного), контекст растёт, цель размывается (context rot, [03.1.2](./03.context-engineering.md)).

### 2.2. Plan-then-execute

План фиксируется до реализации.

**Когда:** тип задачи известен, декомпозиция предсказуема.
**Предел:** план устаревает при расхождении с реальностью; нужен механизм перепланирования.

### 2.3. Гибрид с точками перепланирования (рекомендация)

```
research → plan (артефакт) → validate → [реализация задачи → gates] × N
                                  ↑                        │
                                  └── replan на границе ───┘
                                      (не внутри задачи)
```

Перепланирование разрешено **только на границах задач** — внутри задачи агент дорабатывает в рамках плана или останавливается с отчётом. Это сохраняет предсказуемость и делает перепланирование дешёвым: план — артефакт, а не переписка.

### 2.4. ReWOO-стиль для детерминированных цепочек

План с плейсхолдерами строится один раз, инструменты исполняются по плану без возвращения промежуточных результатов в рассуждение. Экономия вызовов; подходит фиксированным пайплайнам ([02.1](./02.orchestration-patterns.md)), плохо сочетается с задачами, где каждый шаг зависит от неожиданного результата.

### 2.5. Сравнение

| Режим | Предсказуемость | Стоимость | Адаптивность | Когда |
|---|---|---|---|---|
| ReAct | Низкая | Высокая (много вызовов) | Высокая | Exploration |
| Plan-then-execute | Высокая | Низкая | Низкая | Известный тип задачи |
| Гибрид | Высокая | Средняя | Ограниченная точками | Большинство задач SDLC |
| ReWOO | Высокая | Самая низкая | Нет | Фиксированные цепочки |

## 3. План как артефакт

```yaml
id: plan-auth-rotation-v2
task: "Refresh token rotation"
spec: docs/specs/auth-rotation.md
tasks:
  - id: t1
    goal: "Инвалидация старого refresh token при ротации"
    files_owned: [src/auth/token_service.py]
    do_not_touch: [src/auth/session_store.py]
    depends_on: []
    acceptance:
      - "pytest tests/auth/test_refresh.py -q"
    model: mid
  - id: t2
    goal: "401 на истёкшем refresh token"
    files_owned: [src/auth/session_store.py]
    depends_on: [t1]
    acceptance:
      - "pytest tests/auth/test_session.py -q"
    model: mid
integration_review:
  model: strong
  criteria: "Соответствие spec, отсутствие расползания scope"
```

Свойства:

- **Версия плана** фиксируется; перепланирование = новая версия, а не правки в переписке.
- **`files_owned` / `do_not_touch`** — основа параллельной реализации без конфликтов ([05.6.1](./05.memory-and-knowledge.md)).
- **`acceptance`** — детерминированные команды; без них задача не считается завершённой ([02.5.3](./02.orchestration-patterns.md)).
- Todo-лист агента (TodoWrite-паттерн) — рабочая память **внутри** сессии; план-артефакт — состояние **между** фазами и сессиями. Различие принципиально: session context vs project state ([05.2](./05.memory-and-knowledge.md)).

**Spec-driven разработки** (requirements → design → tasks; инструменты типа Spec Kit, Kiro): оправданы для многосессионных работ, где спека — durable артефакт, устраняющий двусмысленности. Для мелких задач спека — накладные расходы. *Статус: практика сообщества, сверить.*

## 4. Валидация плана (gate до кода)

**Детерминированные проверки (бесплатно):**
- все пути из `files_owned` существуют;
- упомянутые интерфейсы/символы существуют (symbol check, [13](./13.code-search-and-retrieval.md));
- acceptance-команды воспроизводимы (запускаются в чистом checkout);
- граф зависимостей ацикличен; листья можно параллелить.

**LLM-проверки (субъективное):**
- противоречия между компонентами: «t1 меняет интерфейс X, t3 использует X» (Consistency Checker, [08.2.3](./08.research-and-benchmarks.md));
- полнота против задачи/спеки;
- расползание scope: задачи вне исходного запроса.

**Модель:** mid с рубрикатором для пунктных проверок; strong — только архитектурный обзор плана целиком ([02.5.2](./02.orchestration-patterns.md)).

## 5. Гранулярность декомпозиции

**Правило context-sized task:** задача должна помещаться в одно окно воркера вместе с необходимым кодом и своим фрагментом плана.

Признаки слишком крупной задачи:
- `files_owned` больше ~5–7 файлов;
- acceptance нельзя свести к 1–3 командам;
- задача смешивает «понять» и «поменять» — разбить: исследование отдельно, правка отдельно;
- внутри задачи есть собственная декомпозиция на уровни — вынести подзадачи в план.

Параллелятся только листья графа зависимостей; интерфейсы замораживаются до старта параллельной реализации; критический путь закрывается интеграционным ревью (strong).

## 6. Политика перепланирования

| Параметр | Значение |
|---|---|
| Триггеры | Падение теста вне `files_owned`; дрейф интерфейса; находка, противоречащая плану; двукратный провал gate с одной причиной |
| Бюджет | Max 2 перепланирования на план |
| Процедура | Новая версия артефакта + diff причин; перезапуск только затронутых задач |
| При исчерпании | Эскалация: strong-модель на план или человек |

## 7. Исследования

| Работа | Суть | Практический вывод для кодинг-агентов |
|---|---|---|
| ReAct (Yao et al., 2022) | Чередование рассуждения и действия | Хорош для exploration; слаб на длинных горизонтах |
| Plan-and-Solve (Wang et al., 2023) | Сначала план, потом исполнение | Дешевле для известных типов задач |
| Least-to-Most (Zhou et al., 2022) | Декомпозиция от простого к сложному | Нарастающая сложность; подзадачи решаются последовательно |
| Tree of Thoughts (Yao et al., 2023) | Поиск по дереву рассуждений | Дорог; только на фазе design, не в рантайме |
| Self-Consistency (Wang et al., 2022) | N сэмплов + голосование | Для решений/классификации (выбор подхода), не для генерации кода |
| ReWOO (Xu et al., 2023) | План с плейсхолдерами | Экономия вызовов в фиксированных цепочках |

*Все шесть — академические работы; перенос на кодинг-агентов — по практике сообщества, сверить при использовании.*

---

## 8. Антипаттерны

- Планирование внутри импл-чата (смешивание фаз) → thrash.
- План без acceptance-критериев → «завершение» по словам модели.
- Монолитный план без task-графа → нет параллелизма, нет точек перепланирования.
- Спекулятивные задачи (ничем не запрошены) → расползание scope.
- План не версионируется → невозможно отследить, на чём сломалось.
