## 1. Базовая экономика

### 1.1. Token Economics

Anthropic опубликовал цифры по своим research-агентам:

| Тип системы | Расход токенов относительно чата |
|---|---|
| Чат | 1× |
| Обычный агент | ~4× |
| Мультиагентная система | ~15× |

**~80% дисперсии качества** объясняется количеством потраченных токенов, а не «умом» модели.

Это значит: экономить можно и нужно, и главный рычаг — не замена модели, а **что и в какой контекст попадает**.

### 1.2. Где тратятся токены

| Источник | Доля | Как сократить |
|---|---|---|
| System prompt + tool definitions | 5–15% | Prompt caching, фазовая загрузка MCP |
| История диалога | 20–40% | Изоляция субагентов, суммаризация |
| Tool responses | 30–50% | Tool response → файлы, reading tail |
| Reasoning (thinking) | 10–20% | Модельный роутинг, каскадирование |

## 2. Стратегии снижения стоимости

### 2.1. Изоляция контекста субагентов

**Механизм:** каждый субагент стартует с чистым окном и получает только задачу + типизированный вход. Возвращает наружу только итог, а не журнал работы.

**Экономия:** предотвращает кумулятивную пересылку tool-выводов через все последующие шаги.

**Реализация:** subagent-as-tool, external artifact store, paths + summaries instead of raw content.

### 2.2. Model Routing

**Механизм:** правило «задача → модель», с конфигом.

**Цифры (сентябрь 2026, статусы верификации):**
- **ACRouter / Agent-as-a-Router** (arXiv:2606.22902, ✅ верифицирован): лучший cost-aware cumulative regret на потоке задач против статических роутеров и online bandits; диагноз «information deficit» — +15.3% relative gain уже от статистики моделей; статические обученные роутеры (RouteLLM-варианты) на OOD-задачах **не генерализуются**.
- **xRouter** (arXiv:2510.08439, ✅ Salesforce AI Research): RL-роутинг с cost-aware reward («no success, no reward; on success, cheaper is better»); «существенное сокращение затрат при сопоставимом completion rate».
- **Cascadeflow**: «до 85%».

**Практическое правило:** дешёвая модель на первых итерациях, дорогая — на финальной или когда cheap-модель дважды провалила gate.

### 2.3. Prompt Caching

**Механизм:** кэширование статического префикса (tools → system → messages). Cache reads cost **~10%** базовой цены — **90% скидка** , , . Cache writes — one-time premium 1.25× . Снижает latency до 85% .

**Условия:**
- Стабильный префикс (не меняется между вызовами).
- Минимальный порог (2,048–4,096 токенов в зависимости от модели).
- TTL: 5 минут (default) или 1 час (2× базовая цена).

**Экономия:** для агентов с длинным system prompt и стабильными tool definitions — **60-90% reduction** input token costs .

### 2.4. Tool Response → Files

**Механизм:** длинные ответы инструментов пишутся в файл, а не в контекст.

**Экономия:** выгода = `размер_ответа × число_последующих_шагов` (кумулятивная пересылка).

**Накладные:** лишние `read_file`-итерации.

**Порог:** адаптивная эвристика по телеметрии (старт ~2000 символов).

### 2.5. Кэширование артефактов

**Механизм:** если несколько workflow используют одни и те же субшаги (например, «поиск похожих решений» запускается и на этапе планирования, и перед реализацией плана), артефакты этого шага сохраняются в blackboard и переиспользуются.

**Экономия:** дешевле, чем прогонять поиск заново.

### 2.6. Фазовая загрузка MCP

**Механизм:** список MCP-серверов на фазу, стабильный список tools внутри фазы.

**Экономия:** сохраняет prompt cache (стабильный префикс).

**Почему не per-call:** мета-инструмент per-call несовместим с function calling (модель не может вызвать инструмент без schema в поле `tools`).

## 3. Телеметрия: что и как измерять

**P0 — с первого дня.**

| Метрика | Формула | Зачем |
|---|---|---|
| **Cost per phase** | Сумма токенов × цена | Понять, какие фазы дорогие |
| **Cache hit rate** | `cacheRead / (input + cacheRead)` | Эффективность prompt caching |
| **Context growth** | Размер контекста по шагам | Обнаружить context rot |
| **Tool response sizes** | Распределение | Настроить порог для tool response → files |
| **File-based overhead** | Число `read_file` | Оценить накладные |
| **Quality per cost** | Качество / стоимость | Сравнить альтернативы |

**Без телеметрии все оптимизации — гадания.**

## 4. Каскадирование моделей

### 4.1. Cheap-First, Escalate-on-Failure

```
[Cheap Model] → результат
     ↓
[Quality Gate] → passed → [Done]
     ↓ failed
[Cheap Model] → повторная попытка
     ↓ failed again
[Strong Model] → результат
```

**Правило:** дешёвая модель на первых итерациях, дорогая — когда cheap-модель дважды провалила gate.

**Условие:** быстрый и дешёвый критерий провала (детерминированные gates).

### 4.2. Voting с дешёвыми моделями

**Механизм:** N дешёвых моделей голосуют, сильная модель только разрешает ничьи.

**Экономия:** N × cheap < 1 × strong при сопоставимом качестве.

## 5. Сравнение подходов по стоимости

| Подход | Стоимость | Качество | Когда выбирать |
|---|---|---|---|
| Один агент, frontier-модель | Высокая | Высокое | Простые задачи, прототип |
| Мультиагентный, frontier-модель | Очень высокая | Максимальное | Критические задачи |
| Мультиагентный, model routing | Средняя | Высокое | Production |
| Мультиагентный, cheap-first | Низкая | Достаточное | Большинство задач |
| Workflow с gates | Низкая | Предсказуемое | Фиксированные цепочки |

## 6. Практические рекомендации

1. **Изолируйте субагентов.** Чистое окно, только задача.
2. **Используйте prompt caching.** Стабильный префикс, cache_control markers.
3. **Роутьте модели по типу задачи.** Дешёвая на поиск/суммаризацию, сильная на планирование/критику.
4. **Каскадируйте.** Cheap-first, escalate-on-failure.
5. **Tool response → files.** Порог по телеметрии.
6. **Кэшируйте артефакты.** Переиспользуйте результаты поиска.
7. **Измеряйте с первого дня.** Cost per phase, cache hit rate, context growth.
8. **Не оптимизируйте вслепую.** Без телеметрии — гадания.

## 7. Целевая экономика harness

```
┌─────────────────────────────────────────────────────┐
│  Фаза 1: Поиск (cheap)           — 15% бюджета      │
│  Фаза 2: Design (strong)         — 20% бюджета      │
│  Фаза 3: Декомпозиция (strong)   — 10% бюджета      │
│  Фаза 4: Планы (mid, parallel)   — 15% бюджета      │
│  Фаза 5: Валидация (strong)      — 10% бюджета      │
│  Фаза 6: Реализация (mid+cheap)  — 25% бюджета      │
│  Фаза 7: Интеграция (strong)     — 5% бюджета       │
└─────────────────────────────────────────────────────┘
```

**Ключевой принцип:** сильные модели только на критических участках (планирование, валидация, интеграция), дешёвые — на всём остальном.
