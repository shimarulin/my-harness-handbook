## 1. Базовые паттерны

### 1.1. Prompt Chaining (цепочка промптов)

**Суть:** последовательные LLM-вызовы, где выход одного — вход следующего. Между шагами можно ставить программные «гейты» (проверки).

**Когда использовать:** задача естественно декомпозируется на фиксированные шаги.

**Пример для разработки ПО:**
```
[Search Agent] → [Summary Agent] → [Critic Agent]
```

**Преимущества:** простота, предсказуемость, низкая стоимость (один вызов на шаг).

**Недостатки:** ошибка на раннем шаге каскадом тянет вниз всё остальное.

### 1.2. Routing (маршрутизация)

**Суть:** классификатор направляет вход в одну из нескольких специализированных ветвей.

**Когда использовать:** разные типы задач требуют разных цепочек.

**Пример:**
```
Incoming Task → [Classifier] → bugfix_chain | feature_chain | investigation_chain
```

**Преимущества:** специализация, экономия (каждая ветвь оптимизирована под свой тип задач).

**Недостатки:** нужен надёжный классификатор; ошибка маршрутизации отправляет задачу не туда.

### 1.3. Parallelization (параллелизация)

**Суть:** независимые задачи запускаются одновременно. Вариант — один вход прогоняется через несколько оценщиков (voting).

**Когда использовать:** подзадачи независимы, время критично.

**Пример:**
```
[Search Agent A] ─┐
[Search Agent B] ─┼→ [Aggregator] → [Summary]
[Search Agent C] ─┘
```

**Преимущества:** скорость, redundancy (voting).

**Недостатки:** coordination overhead, сложность агрегации.

**Важно:** параллельные субагенты безопасны только для **контекстно-изолированных** задач. Параллельные правки одного кода — нет; там лучше последовательные handoffs.

### 1.4. Orchestrator-Workers (оркестратор-воркеры)

**Суть:** центральный LLM динамически декомпозирует задачу, делегирует воркерам и синтезирует результат.

**Когда использовать:** задача декомпозируется динамически, число подзадач заранее неизвестно.

**Пример:**
```
[Orchestrator] → декомпозирует → [Worker 1], [Worker 2], [Worker 3]
                ← собирает ←
```

**Преимущества:** гибкость, адаптация под задачу.

**Недостатки:** выше стоимость (дополнительный LLM-вызов оркестратора), сложнее отладка.

### 1.5. Evaluator-Optimizer (оценщик-оптимизатор)

**Суть:** один LLM генерирует, другой оценивает, цикл до сходимости. Это ровно паттерн «поиск → сводка → критика → уточнённые запросы».

**Структура:**
```
[Generator] → draft → [Critic] → approve: да → [Final]
                ↑                     │
                │              нет: refined_queries
                └─────────────────────┘
                  (loop, max 3 итерации)
```

**Ключевые моменты реализации:**
- **Критик получает только `summary` + `original_query`** — не сырые документы, не историю поиска.
- **Обратный цикл передаёт только `refined_queries`** — search-агент стартует с чистого контекста с новыми запросами.
- **Max-iterations = 2–3** — жёсткий предохранитель, дальше fallback на «лучшее, что есть».
- **Схемы (pydantic/zod) на каждом ребре** — ошибка ловится на границе, а не тянется дальше.

**Важно:** критик-цикл без счётчика итераций — главная причина исчерпания токен-бюджета. Нужен `max_iterations` и явная fallback-ветка.

## 2. Паттерны мультиагентной координации (Azure)

Microsoft Agent Framework выделяет пять паттернов:

### 2.1. Sequential Orchestration

Агенты в фиксированном порядке, каждый получает полный выход предыдущего.

**Пример:** draft → review → polish.

**Когда использовать:** задача естественно раскладывается на последовательные фазы.

### 2.2. Concurrent Orchestration

Параллельная работа независимых агентов с последующей агрегацией.

**Когда использовать:** подзадачи независимы, нужна скорость.

### 2.3. Group Chat Orchestration

Агенты общаются в общем чате, менеджер-агент решает, кто говорит следующим.

**Когда использовать:** collaborative problem-solving, где важен диалог.

**Недостатки:** сложнее контролировать детерминированность, риск бесконечных диалогов.

### 2.4. Handoff Orchestration

Агенты передают управление друг другу.

**Пример:** OpenAI Agents SDK — явная передача контроля между агентами.

**Преимущества:** простота, предсказуемость.

**Недостатки:** разработчик должен определить все точки handoff.

### 2.5. Magentic Orchestration

Оркестратор итеративно координирует агентов, динамически выбирая следующего исполнителя.

**Преимущества:** адаптация под задачу.

**Недостатки:** сложность, выше стоимость.

## 3. Supervisor-паттерн

**Суть:** один оркестратор делегирует задачи специализированным агентам и валидирует результаты. В LangGraph это реализуется через supervisor-узел с tool-based handoff.

**Когда использовать:** нужно централизованное управление специализированными агентами.

**Преимущества:** централизованный контроль, специализация агентов.

**Недостатки:** supervisor становится bottleneck, выше стоимость.

---

## 4. Blackboard-паттерн

**Суть:** все агенты работают над общим объектом состояния (blackboard), но в контекст каждого агента передаются только нужные поля.

**Пример:** критик получает `summary` и `original_query`, но не историю поиска.

**Преимущества:**
- Меньше потери информации.
- Аудит.
- Агенты накапливают знания, а не только передают текст друг другу.

**Недостатки:**
- Нужно управлять версионированием и конфликтами.

**Практика:** для сложного harness это обычно лучше, чем чистая линейная передача сообщений.

## 5. Conditional Edges и Quality Gates

### 5.1. Conditional Edges

**Суть:** переход между узлами зависит от результата проверки.

**Пример:**
```python
def should_continue(state) -> str:
    if state["approved"] or state["iteration"] >= 3:
        return "final_answer"
    return "search"  # передаём только refined_queries, не всю историю
```

**Ключевой момент:** conditional edge не должен передавать всю историю — только необходимые артефакты.

### 5.2. Quality Gates

**Суть:** цикл завершён ≠ задача выполнена. Нужны явные проверки.

**Двухуровневая система:**

**Уровень 1: детерминированные gates** (быстро и дёшево):
- компиляция;
- линтер;
- статический анализ;
- типы;
- юнит-тесты;
- интеграционные тесты.

Это бесплатно по токенам и не пропускает грубые ошибки.

**Уровень 2: LLM-as-judge** (субъективные критерии):
- архитектурное ревью;
- стиль;
- поддерживаемость.

LLM-судья с **явным рубрикатором** (не «хороший ли код», а чеклист из 10 пунктов с числовой оценкой по каждому). Дешёвая модель с хорошим рубрикатором надёжнее, чем сильная без него.

**Правило:** если детерминированная проверка может поймать дефект — она должна стоять перед LLM-judge, а не после.

### 5.3. Stop Hooks

**Суть:** агент не завершает работу по собственной воле — он завершает её, когда **внешний код** подтвердил прохождение всех gate. Если gate провален, оркестратор запускает следующую итерацию с фидбек-списком дефектов.

## 6. Max Iterations и Stopping Conditions

**Правила:**
- Max iterations для критик-цикла: **2–3**.
- Max iterations для кодинг-цикла (implement → review): **3–5**.
- Fallback при исчерпании: «лучшее, что есть» + явный отчёт о нерешённых проблемах.

**Без счётчика итераций:**
- Цикл крутится до исчерпания токен-бюджета.
- На враждебных или out-of-domain запросах — бесконечно.

## 7. Пример полной цепочки для разработки ПО

```yaml
name: feature_implementation
version: 1
entrypoint: search_analyst
nodes:
  - id: search_analyst
    agent: RepoSearchAnalyst
    output: SearchReport

  - id: sufficiency_judge
    agent: SufficiencyJudge
    input: SearchReport
    output: SufficiencyDecision

  - id: planner
    agent: Planner
    input: SearchReport
    output: ImplementationPlan

  - id: coder
    agent: Coder
    input: ImplementationPlan
    output: PatchArtifact

  - id: test_runner
    agent: TestRunner
    input: PatchArtifact
    output: TestResult

  - id: reviewer
    agent: Reviewer
    input: PatchArtifact, TestResult
    output: ReviewReport

edges:
  - from: search_analyst
    to: sufficiency_judge

  - from: sufficiency_judge
    condition: sufficient
    to: planner

  - from: sufficiency_judge
    condition: insufficient
    to: search_analyst
    max_iterations: 3
    carry:
      - missing_requirements
      - followup_queries

  - from: planner
    to: coder

  - from: coder
    to: test_runner

  - from: test_runner
    condition: passed
    to: reviewer

  - from: test_runner
    condition: failed
    to: coder
    max_iterations: 3
    carry:
      - test_failures

  - from: reviewer
    condition: approved
    to: finalize

  - from: reviewer
    condition: needs_changes
    to: coder
    max_iterations: 3
    carry:
      - review_issues
```

## 8. Комбинирование паттернов

Реальные workflow — это комбинации. Пример для разработки ПО:

```
Фаза 1: Поиск готовых решений
  → N параллельных дешёвых search-агентов (parallelization)
  → суммаризатор (prompt chaining)
  → blackboard: solutions.json

Фаза 2: Design собственного решения
  → сильная модель: анализ подходов, выбор (orchestrator)

Фаза 3: Декомпозиция на части и связи
  → сильная модель: выделяет компоненты, их интерфейсы

Фаза 4: Планы на каждую часть
  → средняя модель на каждый компонент (parallelization)

Фаза 5: Валидация планов
  → сильная модель-критик: противоречия, пропуски (evaluator-optimizer)

Фаза 6: Реализация каждого плана
  → для каждого плана: детализатор → кодер → gates → reviewer (prompt chaining)

Фаза 7: Интеграционное ревью
  → сильная модель: соответствие глобальному дизайну
```
