## 1. Формализация эффективности

Метки:

- **Q** — качество (доля задач, прошедших gates; оценка на golden-наборе, [08](./08.research-and-benchmarks.md));
- **C** — стоимость (Σ токены × цена с учётом cache; плюс стоимость инфраструктуры);
- **T** — время (критический путь по параллельным ветвям, не сумма).

Эффективное решение — одно из:

1. тот же **Q** при меньших **C** и/или **T**;
2. незначительный рост **T** при существенном снижении **C**;
3. тот же **Q** силами более дешёвой модели;
4. существенный рост **Q** без значимого роста **C** (дешёвые модели на объёме, сильные — на критических участках).

**Опасная зона:** рост **C** или **T** «ради качества», который не измерен на golden-наборе. Каждое усложнение проходит проверку по §5.

## 2. Реестр механик

Сила доказательств: **A** — вендорские исследования из верифицированной базы; **B** — академические работы; **C** — практика сообщества; **D** — гипотеза, мало данных.

| Механика | Эффект | Порядок величины | Сила | Риски/условия | Раздел |
|---|---|---|---|---|---|
| Изоляция субагентов (subagent-as-tool) | C↓, Q↑ | устраняет кумулятивную пересылку tool-выводов | A | потеря контекста при плохом брифе | [03.2.1](./03.context-engineering.md) |
| Blackboard с типизированными артефактами | Q↑, C↓ | меньше потерь при обмене | A/C | версионирование и конфликты | [02.4](./02.orchestration-patterns.md) |
| Tool response → files | C↓ | 30–50% расхода — tool responses | A | лишние read-итерации | [03.3.1](./03.context-engineering.md) |
| Prompt caching | C↓ | ~90% скидка на чтение префикса | A | инвалидируется любым изменением префикса | [03.3.5](./03.context-engineering.md) |
| Фазовая загрузка MCP | C↓, Q↑ | стабильный префикс → кэш; меньше выбора | A/C | несовместима с per-call мета-инструментом | [03.3.2](./03.context-engineering.md) |
| Очистка старых tool-результатов | C↓ | зависит от длины сессии | C | cache miss при очистке; планировать на границах | [11.4.1](./11.tool-engineering.md) |
| Programmatic tool calling | C↓ | растёт с числом вызовов | C | sandbox, отладка | [11.4.2](./11.tool-engineering.md) |
| Model routing по типу задачи | C↓ | +15.3% relative gain уже от статистики моделей (ACRouter); 40–70% — реалистичный диапазон экономии (author-run оценки) | A/B | нужен дешёвый верификатор результата; статические роутеры деградируют на OOD | [03.4](./03.context-engineering.md), [04.2.2](./04.economics-and-cost.md) |
| Cheap-first, escalate-on-failure | C↓ | экономия на большинстве шагов | A/C | требует дешёвого детерминированного критерия провала | [04.4.1](./04.economics-and-cost.md) |
| Voting дешёвыми моделями | Q↑ | N×cheap < 1×strong | C | только для классификации/коротких ответов | [04.4.2](./04.economics-and-cost.md) |
| Критик-цикл с рубрикатором и max-iterations | Q↑ | ловит дефекты до gates | A/B | без счётчика — исчерпание бюджета | [02.1.5](./02.orchestration-patterns.md) |
| Валидация плана до кода | Q↑, C↓ | устраняет каскад ошибок плана | B/C | накладные на мелких задачах | [12.4](./12.planning-and-decomposition.md) |
| LSP/символ-инструменты | C↓, Q↑ | детерминированные ответы | C | серверы на каждый язык | [13.2](./13.code-search-and-retrieval.md) |
| Repo map как префикс | C↓, Q↑ | константный бюджет на ориентацию | C | обзорность ≠ поиск | [13.2](./13.code-search-and-retrieval.md) |
| Векторный индекс + rerank | T↓, C↓ на запрос | оправдан на больших репо | C | поддержка индекса, ложные срабатывания | [13.2](./13.code-search-and-retrieval.md) |
| Fresh-context workers | Q↑ | убирает наследование мусора | A | нужен качественный бриф | [05.6.1](./05.memory-and-knowledge.md) |
| ADR + база знаний (markdown + MCP) | Q↑ между сессиями | 0 инфраструктуры | C | дисциплина ведения | [05.4](./05.memory-and-knowledge.md) |
| Автооптимизация workflow (AFlow, ADAS) | C↓/Q↑ | ~5.7% средний прирост (AFlow) | B | нужен eval-контур | [08.5](./08.research-and-benchmarks.md) |

## 3. Синергии и конфликты комбинаций

**Синергии (применять вместе):**

| Комбинация | Почему работает |
|---|---|
| Изоляция субагентов + artifact store + summaries | Канонический паттерн мультиагентного поиска Anthropic: контекст не раздувается, знания не теряются |
| Model routing + детерминированные gates | Cheap-first возможен только при дешёвом и надёжном критерии провала |
| Фазовая загрузка MCP + prompt caching | Стабильный список инструментов в фазе = стабильный префикс |
| План-артефакт + fresh-context workers | Воркер получает bounded brief + slice плана, а не историю |
| Repo map + agentic search | Карта сокращает число поисковых итераций |

**Конфликты (применять с осторожностью):**

| Комбинация | Конфликт | Смягчение |
|---|---|---|
| Компакция/очистка × prompt caching | Изменение префикса → cache miss | Компакция только на границах фаз ([14.3](./14.reliability-and-recovery.md)) |
| Много параллельных воркеров × caching | Кэш не шарится между агентами → каждый платит префилл | Ограничить fan-out; считать экономику параллелизма отдельно ([03.5.1](./03.context-engineering.md)) |
| Tool→files × слабые read-инструменты | Экономия съедается итерациями чтения | Адаптивный порог по телеметрии ([04.2.4](./04.economics-and-cost.md)) |
| Критик × та же модель, что генератор | Согласованность ошибок (self-agreement bias) | Критик — другая/дешёвая модель + рубрикатор ([09.3.4](./09.anti-patterns.md)) |
| Voting × открытая генерация | Голосование осмысленно для классификации, не для кода | Voting только на выборах решений ([12.7](./12.planning-and-decomposition.md)) |
| Мультиагентный fan-out × согласованность решений | Действия несут неявные решения; без общего контекста они конфликтуют (Cognition) | Единая точка решений (design/plan), замороженные интерфейсы ([12.5](./12.planning-and-decomposition.md)) |
| 1M контекст × длинные циклы | Lost in the middle, context rot, экономика KV | Только как fallback ([03.5.1](./03.context-engineering.md)) |

## 4. Правила выбора модели

| Правило | Обоснование |
|---|---|
| Ошибка каскадирует → strong | План, design, выбор подхода, интеграционное ревью: доля токенов мала, цена ошибки велика |
| Ошибка локальна и ловится gate → mid/cheap | Реализация по готовому плану, механические правки |
| Классификация/оценка с рубрикатором → дешёвая | Judge — классификация, не генерация ([02.5.2](./02.orchestration-patterns.md)) |
| Двукратный провал дешёвой → эскалация | Cheap-first с ограниченным числом попыток |
| Подозрительно дешёвый результат → перепроверить | Дешёвая модель может «проходить» слабые gates; усиливать gates, а не запрещать дешёвые модели |

## 5. Процедура внедрения (measure-first)

1. **Baseline:** один агент + сильная модель + детерминированные gates + телеметрия ([04.3](./04.economics-and-cost.md)).
2. **Измерить** C/T/Q по фазам; найти доминирующую статью расходов.
3. **Одна механика** за раз, направленная на доминирующую статью (§2).
4. **Перемерить** на том же golden-наборе; принять, если выполняется критерий §1.
5. **Структурные изменения** (мультиагент, оркестрация) — только когда single-agent упёрся в потолок по данным, а не по интуиции.

Правило одной переменной: два изменения за раз не дают атрибуции.

---

## 6. Когда НЕ усложнять

- Одиночный агент с хорошими инструментами и gates часто дешевле и надёжнее мультиагента. Мультиагент оправдан при: естественной изоляции контекста, независимости подзадач, потребности в параллелизме, специализированных наборах инструментов.
- Cognition, «Don't Build Multi-Agents»: общий контекст и согласованность решений — главные причины провала мультиагентных систем ([10.4](./10.references.md)).
- Каждая новая механика — новая поверхность отказов; сложность должна покупаться измеренным эффектом (§5).

## 7. Стартовые конфигурации по типу задачи

| Тип задачи | Фазы | Модели | Механики |
|---|---|---|---|
| Investigation / вопрос по репо | Поиск → сводка → проверка достаточности | cheap + mid-judge | Изоляция поискового субагента; tool→files; repo map |
| Bugfix | Поиск → план → правка → тесты → ревью | mid + strong на плане/ревью | LSP-символы; детерминированный фидбек тестов; max-iterations 3 |
| Небольшая фича | План → реализация → gates → ревью | strong план; mid код | Валидация плана; blackboard; caching |
| Крупная фича | Спека → план → декомпозиция → параллельная реализация → интеграция | strong план/интеграция; mid листья; cheap поиск | Артефакты; fresh-context workers; ветки; ограниченный fan-out |
| Рефакторинг | Анализ влияний → план по шагам → шаги с gates | strong анализ; mid шаги | Символ-граф; kill criteria на шаг; WIP-коммиты |
| Ревью без правок | Диффы → чек-листы | mid с рубрикатором; strong для архитектуры | Детерминированные линтеры до judge |

---

- Каждая новая механика — новая поверхность отказов; сложность должна покупаться измеренным эффектом (§5).
