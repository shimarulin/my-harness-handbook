## 1. Проблема: почему контекст — узкое место

### 1.1. Lost in the Middle

Исследование Liu et al. (Stanford, 2023, ~6400 цитирований) показало U-образную кривую точности: LLM-модели отлично помнят начало и конец контекста, но информация в середине «теряется». Производительность деградирует существенно, когда релевантная информация оказывается в середине длинного контекста.

### 1.2. Context Rot

Исследование Chroma (июль 2025) показало: даже когда модель формально «помещает» весь контекст, качество рассуждения падает с ростом длины входа — особенно когда нужно найти релевантное в шуме . Протестировано **18 frontier-моделей** (GPT-4.1, Claude 4, Gemini 2.5, Qwen3) — **все 18 деградировали** с ростом длины входа . При заполнении окна больше 50% модели начинают путаться.

Anthropic в июле 2026 удалил **80% system prompt** Claude Code для новейших моделей «с нулевой измеримой потерей на наших кодинг-эвалюациях»  — что подтверждает, что компактный, хорошо структурированный контекст важнее объёма.

**Симптомы context rot**:
- агент перечитывает одни и те же файлы и забывает предыдущие решения;
- воркеры наследуют нерелевантные логи или устаревшие допущения;
- границы задач размываются, правки расширяются за пределы scope;
- модель начинает использовать устаревшие инструкции из начала разговора.

### 1.3. Экономика контекста

Агент расходует **~4× токенов** по сравнению с чатом; мультиагентная система — **~15×**. При этом **~80% дисперсии качества** объясняется количеством потраченных токенов, а не «умом» модели. Это значит: экономить можно и нужно, и главный рычаг — не замена модели, а **что и в какой контекст попадает**.

## 2. Три стратегии изоляции контекста

### 2.1. Subagent-as-tool (изолированные контекстные окна)

Каждый субагент вызывается как инструмент с чистым контекстом: он получает только промпт-описание задачи, выполняет её автономно и возвращает наружу **только финальный результат/сводку**.

**Когда использовать:**
- задача забьёт родительский контекст чтением файлов, поиском или логами;
- задаче нужны специальные разрешения инструментов, которых не должно быть у основного агента;
- задача независима, и промежуточная работа не должна появляться в основном контексте.

**Когда НЕ использовать:** задача достаточно мала, чтобы сделать её inline.

**Ключевое правило:** субагент стартует с пустым окном. В контекст субагента передаётся только задача + минимально необходимый ввод. Это предотвращает раздувание контекста главного агента и убивает эффект «испорченного телефона».

### 2.2. Shared state с фильтрацией (blackboard)

Все агенты работают над общим объектом состояния, но в контекст каждого агента передаются только нужные поля.

**Пример:** критик получает `summary` и `original_query`, но не историю поиска.

**Преимущества:**
- Агенты обмениваются фактами через структуру, а не через переписку.
- Меньше потери информации.
- Аудит.

**Недостатки:**
- Нужно управлять версионированием и конфликтами.

### 2.3. Внешнее хранилище + ссылки

Сырые результаты (документы, длинные выводы инструментов) складываются в БД/файл/векторное хранилище, а в контекст идут хэши, ID и краткие summary.

**Это единственный способ пройти длинные исследовательские задачи**, где один только поиск может занять 100+ тысяч токенов.

Anthropic в своём multi-agent research system рекомендует **вывод артефактов в файловую систему** напрямую, минуя оркестратора: субагент пишет результат в файл, а в контекст родителя идёт только путь + 1-строчный summary.

## 3. Механики Context Engineering

### 3.1. Tool Response → Files

**Суть:** длинные ответы инструментов пишутся в файл, а не в контекст. Агент читает tail при необходимости.

**Порог:** адаптивная эвристика по телеметрии (старт ~2000 символов), не константа.

**Экономика:** выгода = `размер_ответа × число_последующих_шагов` (кумулятивная пересылка), накладные = лишние `read_file`-итерации.

**Реализация:** через `afterToolCall` hook.

### 3.2. Фазовая загрузка MCP

**Суть:** список MCP-серверов на фазу, стабильный список tools внутри фазы → **сохраняет prompt cache**.

**Почему не per-call мета-инструмент:** мета-инструмент per-call несовместим с function calling (модель не может вызвать инструмент без schema в поле `tools`).

**Альтернатива:** tool_search двухшаговый — только если фазовой загрузки не хватит.

### 3.3. Суммаризация на артефактах

**Суть:** суммаризировать **tool-шум**, решения/контракты — дословно в артефактах. Ссылки на **артефакты blackboard** (стабильные пути), НЕ на номера сообщений (regex-парсинг хрупок).

**Реализация:** через `beforeLLMCall` (в pi-agent-core — через `shouldStopAfterTurn` + `ctx.getContextUsage()`).

### 3.4. Progressive Disclosure (Skills)

**Суть:** инструкции, скрипты и ресурсы упаковываются в переиспользуемые папки, которые LLM загружает **по требованию** для task-specific enhancement.

**Best practices** (Anthropic Claude Skills, октябрь 2025):
- Инструкции — до 500 строк .
- Progressive disclosure через CLAUDE.md и подфайлы.
- Anthropic formalized context engineering в сентябре 2025 .
- Валидация по token limits (500–1000 токенов на чанк).
- Загрузка только когда нужна.

**Преимущество:** сохраняет статический префикс → **сохраняет prompt cache**.

### 3.5. Prompt Caching

**Суть:** кэширование статического префикса (tools → system → messages). Cache reads cost **~10%** базовой цены input-токена — скидка **90%** , , . Cache writes cost **1.25×** базовой цены (one-time premium) . Снижает latency до 85% .

**Canonical placement для агентов:**
```json
{
  "tools": [
    { "name": "tool_1", ... },
    { "name": "tool_2", ..., "cache_control": { "type": "ephemeral" } }
  ],
  "system": [
    { "type": "text", "text": "Static system prompt", "cache_control": { "type": "ephemeral" } }
  ],
  "messages": [...]
}
```

**TTL:** 5 минут (default) или 1 час (2× базовая цена).

**Что инвалидирует кэш:**
- Изменение tool definitions → весь кэш.
- Изменение system prompt → system + messages.
- Любое различие в статическом префиксе → полный cache miss.

**Минимальные пороги:** Claude Sonnet 4.6 — 2,048 токенов; Claude Opus 4.6 — 4,096 токенов; Claude Haiku 3.5 — 2,048 токенов.

**Обновление (июль 2026):** у Claude Opus 5 минимальный порог кэша снижен до **512 токенов**, окно 1M токенов — дефолт и максимум; beta-режим mid-conversation tool changes позволяет менять набор инструментов между ходами без инвалидации кэша. В том же месяце Anthropic опубликовала «новые правила context engineering для Claude 5»: **~80% system prompt Claude Code удалено** для Opus 5 / Fable 5 без измеримой потери на кодинг-эвалюациях (конфликтующие инструкции хуже их отсутствия) — сильное подтверждение тезиса «компактный непротиворечивый префикс важнее объёма».

**Критически важно:** timestamps, user IDs и другие динамические данные должны появляться **после** последнего `cache_control` marker, а не до.

### 3.6. Каскадирование моделей (cheap-first, escalate-on-failure)

**Суть:** не решайте заранее, какая модель нужна — попробуйте дешёвую, и только если результат не прошёл quality gate, эскалируйте на дорогую.

**Работает только при наличии быстрого и дешёвого критерия провала** (детерминированные gates).

**Практическое правило:** дешёвая модель на первых итерациях, дорогая — на финальной или когда cheap-модель дважды провалила gate.

## 4. Модельный роутинг по типу задачи

| Тип задачи | Модель | Почему |
|---|---|---|
| Планирование проекта, декомпозиция | **Strong** (Opus/GPT-5-class) | Цена ошибки каскадом тянет вниз весь цикл |
| Поиск по теме, суммаризация | **Cheap** (Haiku/GPT-5-mini) | Чистая классификация/извлечение |
| Чтение документации библиотек | **Cheap** | Механическая работа |
| Генерация кода по готовому плану | **Mid** (Sonnet-tier) | План уже формализован, творчества мало |
| Ревью архитектуры, поиск противоречий | **Strong** | Требует «понимания» контекста проекта |
| LLM-as-judge для качества кода/сводки | **Mid** | Классификация, не генерация |
| Проектирование связей между частями | **Strong** | Критическая точка противоречий |

**Цифры (сентябрь 2026):** обученные роутеры дают значимую экономию, но почти все оценки — author-run. Верифицированный ориентир — **ACRouter** (arXiv:2606.22902): уже простое добавление статистики производительности моделей по типам задач даёт **+15.3% relative gain** к качеству роутинга; ключевой механизм — execution-grounded feedback (sandbox-верификация выходов), а не сам классификатор. Реалистичный диапазон экономии при корректных gates — 40–70%, но требует собственного замера ([04.3](./04.economics-and-cost.md)).

## 5. Что не работает

### 5.1. Один агент с 1M контекстом + KV-кэш

**Вердикт: НЕТ для длинных циклов.**

**Причины:**
1. **Lost in the Middle** — U-образная кривая.
2. **Context Rot** — деградация с ростом входа.
3. **Экономика KV-кэша:** нужен стабильный префикс; у агентов input:output ≈ 100:1; кэш протухает за минуты, **не шарится между агентами/моделями/машинами** → параллельные субагенты платят полный префилл каждый.

**Правильная комбинация:** субагенты с изолированными окнами + retrieval (граф/вектор) + 1M как fallback.

### 5.2. Копирование всей истории в каждого субагента

Убивает саму идею изоляции и взрывает бюджет токенов.

### 5.3. Отсутствие схем на границах

Если сводка от search-агента приходит как строка без структуры, критик не сможет надёжно её оценить, а ошибка одного агента отравит всю цепочку.

## 6. Практические рекомендации

1. **Всегда изолируйте субагентов.** Чистое окно, только задача.
2. **Типизированные артефакты на границах.** Pydantic/zod схемы.
3. **Сырые данные → во внешнее хранилище.** В контекст — только пути и summary.
4. **Prompt caching — обязателен.** Стабильный префикс, cache_control markers.
5. **Фазовая загрузка MCP.** Стабильный список tools внутри фазы.
6. **Каскадирование моделей.** Cheap-first, escalate-on-failure.
7. **Мониторьте context usage.** `ctx.getContextUsage()`, порог суммаризации ~80%.
8. **Не полагайтесь на 1M контекст.** Это fallback, не архитектура.
