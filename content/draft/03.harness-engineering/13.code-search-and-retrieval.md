## 1. Почему поиск доминирует в стоимости

Поиск — самая частая активность кодинг-агента, а ошибки поиска — самые дорогие:

- лишнее чтение файлов → токены × все последующие шаги ([03.3.1](./03.context-engineering.md));
- чтение **не тех** файлов → неверные допущения → каскад в план и код;
- неполный поиск → «решение» уже существующей проблемы заново.

Tool responses — 30–50% расхода ([04.1.2](./04.economics-and-cost.md)), и большая их часть — результаты поиска. Форма ответов — [11.3](./11.tool-engineering.md); стратегия поиска — здесь.

## 2. Альтернативы

| Подход | Свежесть | Поддержка | Стоимость/запрос | Точность | Когда выбирать |
|---|---|---|---|---|---|
| **Agentic search** (grep/glob/read в цикле) | Всегда свежий | Нулевая (нет индекса) | Средняя (несколько вызовов) | Высокая при умной модели; зависит от навыка модели | Дефолт; любые репо; частые правки |
| **Векторный индекс** (embeddings) | Требует инкрементальной переиндексации | Пайплайн индексации + хранилище | Низкая на запрос | Средняя; ложные срабатывания на идентификаторах | Большие монорепо; кросс-репо; поиск «по смыслу» |
| **Гибрид BM25+dense + reranker** | Как у индекса | Выше | Низкая + rerank | Выше recall и precision | Когда вектора мало, а grep не находит по смыслу |
| **Символ-граф / LSP** (definition, references, callers) | Свежий (по исходникам) | Серверы на каждый язык | Очень низкая | Детерминированная, точная | «Где определено/используется», планирование рефакторингов |
| **Repo map** (Aider: tree-sitter + PageRank + бюджет) | Свежая | Низкая | Константная (вписан в бюджет) | Обзорная, не поиск | Ориентация в архитектуре как постоянный префикс |
| **Код-граф MCP** ([05.5.1](./05.memory-and-knowledge.md)) | По расписанию индексации | Графовая БД | Низкая | Структурная | Анализ зависимостей и влияний изменений |

**Ключевой спор: agentic vs indexed.** Claude Code исторически обходится без эмбеддингов для кода — agentic grep + чтение. Аргументы: свежесть без пайплайна, отсутствие ложных срабатываний индекса, качество сильной модели компенсирует больше вызовов. *Статус: практика, сверить с первоисточниками.* Обратная сторона: больше вызовов и latency; при слабой модели — блуждание. Индекс оправдан, когда репо велико, модель дешевле/слабее, запросы семантические.

**Правило композиции:** индекс — **генератор кандидатов**; верификация кандидатов — всегда агентным чтением. Не подставлять фрагменты из индекса в контекст без чтения окружения.

## 3. Композиции по размеру

| Масштаб | Композиция |
|---|---|
| Малый/средний репо (до ~100K LOC) | Agentic grep/glob + LSP-символы + repo map как постоянный префикс |
| Большой монорепо | + инкрементальный векторный индекс по символам + reranker; кандидаты → агентная верификация |
| Мульти-репо | Изолированные поисковые субагенты на репо ([02.1.3](./02.orchestration-patterns.md), [03.2.1](./03.context-engineering.md)) + агрегатор; обмен — типизированные findings ([02.4](./02.orchestration-patterns.md)) |

## 4. Подача результатов в контекст

- `path:line` всегда — инструментам правок нужны номера строк.
- Сниппеты 3–5 строк, не целые файлы; целевое чтение — через read с диапазоном.
- Dedupe совпадений из одного файла; top-k ≤ 10 на запрос.
- Для каждого совпадения — причина выбора (совпадение имени/семантики): помогает модели решить, читать ли.
- Сырые выдачи большого объёма — в файл ([03.3.1](./03.context-engineering.md)), в контекст — tail.

## 5. Экономика и метрики

| Метрика | Зачем |
|---|---|
| Recall@k / Precision@k на golden-запросах ([08.8](./08.research-and-benchmarks.md)) | Сравнение стратегий поиска |
| Среднее число `read_file` на задачу | Overhead стратегии; настройка порогов ([04.3](./04.economics-and-cost.md)) |
| Доля задач, где нужный файл не найден | Верхняя граница качества поиска |
| Токены поиска на решённую задачу | Итоговая эффективность, а не точность на запрос |

**Без A/B на golden-наборе выбор «grep vs индекс» — гадание:** эффект зависит от репозитория, языка и модели.

## 6. Антипаттерны

- Чанкинг кода по фиксированному числу токенов — ломает семантику; резать по символам/блокам (tree-sitter).
- Semantic-only поиск — точные идентификаторы не находятся; комбинировать с grep.
- Подача top-k raw в контекст без чтения окружения.
- Переиндексация на каждый запрос; индекс без инкрементальности.
- Доверие score без rerank: сходство ≠ релевантность задаче.
- Поиск как единственный источник правды: результаты поиска — гипотезы, подтверждение — чтением и тестами.
