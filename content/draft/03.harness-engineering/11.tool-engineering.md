## 1. Почему инструменты — самый дешёвый рычаг

Инструменты влияют на стоимость, время и качество одновременно, не требуя смены модели:

| Эффект | Механизм |
|---|---|
| Меньше итераций | Каждый неудачный вызов инструмента — полный LLM-вызов впустую. Инструмент, чьё сообщение об ошибке «подсказывает» исправление, экономит целый цикл |
| Меньше токенов на шаг | Форма ответа определяет, сколько мусора попадёт в контекст. Tool responses — 30–50% расхода ([04.1.2](./04.economics-and-cost.md)) |
| Выше точность выбора | Доля ошибочных выборов растёт с числом и неоднозначностью инструментов |

**Порядок действий:** прежде чем менять модель или добавлять агентов, проверьте, не является ли узкое место интерфейсом инструментов. Это самый дешёвый класс изменений: не трогает оркестрацию, оценивается A/B на golden-наборе.

## 2. Каталог: количество, гранулярность, имена

### 2.1. Внимание модели — ограниченный ресурс

- С ростом числа инструментов растёт доля неверных выборов и «декоративных» вызовов.
- Практический ориентир: ~20–30 хорошо именованных инструментов в активном наборе. Дальше — фазовая загрузка или двухшаговый tool search ([03.3.2](./03.context-engineering.md)).
- MCP-серверы — главный источник раздутия: один «полный» сервер приносит 30–50 инструментов. Подключать выборочно; использовать namespaces (префикс сервера в имени) для устранения коллизий.

### 2.2. Консолидация против микрораздробления

**Антипаттерн:** отдельный инструмент на каждое микро-действие (`read_thread`, `list_messages`, `get_message`, `search_messages`...).
**Правильно:** один инструмент с параметром режима — меньше выборов, короче префикс, стабильнее кэш.

Обратная крайность — «мега-инструмент»: размытая семантика, непредсказуемая форма ответа. Цель — **средняя гранулярность**: инструмент = одно осмысленное действие с предсказуемым ответом.

### 2.3. Описания — это контракт для модели

| Элемент | Правило |
|---|---|
| Имя | `verb_noun` (`read_file`, `search_symbols`), без аббревиатур |
| Description | Что делает + когда использовать + когда НЕ использовать; 1–3 предложения. Это промпт, а не документация API |
| Параметры | `enum` вместо свободной строки везде, где возможно; плоская схема (глубокая вложенность → невалидные вызовы); обязательный минимум; значения по умолчанию |
| Лимиты и форматы | В описании соответствующего параметра, а не только в системном промпте |

## 3. Форма ответа: инструмент работает на следующее решение

Модель читает ответ, чтобы выбрать следующее действие. Всё, что не помогает выбору, — шум, оплачиваемый на каждом последующем шаге.

| Инструмент | Плохой ответ | Хороший ответ |
|---|---|---|
| Поиск | Полное содержимое найденных файлов | `path:line` + фрагмент 3–5 строк + счётчик совпадений |
| Чтение файла | Весь файл | Строки N–M с номерами + «всего X строк — используйте offset» |
| Тесты | Полный stdout | Сводка + первые N уникальных ошибок + путь к полному логу |
| Ошибка | `Error: failed` | Причина + подсказка к исправлению + допустимые значения |

### 3.1. Errors are prompts

Сообщение об ошибке — единственный контекст, по которому модель исправится сама:

```text
Файл не найден: src/autth/token.py
Похожие пути: src/auth/token.py, src/auth/token_service.py
Используйте glob "src/auth/*.py", чтобы посмотреть каталог.
```

### 3.2. Странификация и обрезка

- `offset/limit`, `head/tail`, `max_bytes` — параметры вызова, а не константы.
- При обрезке всегда указывать, сколько осталось и как получить остальное.
- Tail по умолчанию для логов (ошибки обычно в конце), head — для листингов.

## 4. Продвинутые механики

### 4.1. Очистка старых tool-результатов (context editing)

Старые результаты заменяются плейсхолдером («результат получен, полный вывод: путь/файл») — структура истории сохраняется, вес падает. Триггер по usage (`shouldStopAfterTurn`, [03](./03.context-engineering.md)).

**Осторожно:** очистка меняет префикс сообщений → cache miss. Планировать очистку на границах фаз ([14.3](./14.reliability-and-recovery.md)).

### 4.2. Programmatic tool calling (инструменты как код)

Вместо «вызов → результат в контекст → следующий вызов» модель пишет код, который вызывает инструменты, и видит только итог:

- промежуточные данные вообще не входят в контекст;
- выигрыш растёт с числом вызовов (агрегации, фильтрации, переборы);
- требования: среда исполнения кода + sandbox ([01.sandbox](../01.sandbox/README.md));
- цена: сложнее отладка; часть рассуждений уходит в код; нужен контроль ошибок в сгенерированном коде.

**Когда:** многошаговые комбинации инструментов. **Когда нет:** одиночные действия, где проще прямой вызов.

### 4.3. Параллельные вызовы

- Безопасно: независимые read-only операции → выигрыш по latency.
- Опасно: записи и операции с зависимостями по порядку.

### 4.4. MCP-аннотации

`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint` — машиночитаемые подсказки, на которых строятся permission gates ([06.2.5](./06.harness-architecture.md)) без ручных списков.

## 5. Оценка изменений инструментов

Изменение инструмента = изменение среды промптов. Оценивать до/после на одном golden-наборе ([08.9](./08.research-and-benchmarks.md)):

1. Success rate.
2. Среднее число итераций на задачу.
3. Токены на задачу (по фазам).
4. Точность выбора инструмента (по трейсам).

---

## 6. Что не работает

| Антипаттерн | Почему |
|---|---|
| Микро-инструменты | Много вызовов на простое действие → лишние LLM-итерации |
| Мега-инструменты | Размытая семантика, непредсказуемые ответы |
| Дублирующие/пересекающиеся инструменты | Выбор становится случайным; рост префикса |
| Человеческие API как инструменты | Модели не нужна REST-эргономика — ей нужны действия |
| Полные дампы в ответах | Токены × все последующие шаги ([03.3.1](./03.context-engineering.md)) |
| Вычисления руками модели | Детерминированное считает обычный код — дешевле и надёжнее |

### Академический фундамент: ACI (Agent-Computer Interface)

Тезис «инструменты — самый дешёвый рычаг» (§1) имеет прямое академическое обоснование в работе SWE-agent (NeurIPS 2024). Ключевой вклад — **Agent-Computer Interface (ACI)**: интерфейс между агентом и компьютером, спроектированный так же тщательно, как Human-Computer Interface (HCI). Авторы показали, что **качество ACI — измеримый фактор success rate** на SWE-bench: простая смена формата команд, стратегии поиска и формы ошибок меняет долю решённых задач.

**Источник:** [Yang et al., «SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering» (arXiv:2405.15793, NeurIPS 2024)](https://arxiv.org/abs/2405.15793).

**Связь с документом:** §2 (консолидация vs микрораздробление), §3 (форма ответа под следующее решение), §3.1 (errors are prompts) — всё это частные случаи проектирования ACI. SWE-agent даёт эмпирическое подтверждение: изменение интерфейса без смены модели меняет результат.
