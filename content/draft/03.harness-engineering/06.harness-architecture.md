## 1. Четыре необходимых условия

Согласно формальному определению, harness — это система, которая обеспечивает четыре необходимых условия:

1. **Agent loop** — цикл, который чередует рассуждение, действие и наблюдение во время выполнения.
2. **Tool interface** — модель может воспринимать и изменять среду.
3. **Context management** — управление тем, что попадает в окно модели.
4. **Control mechanisms** — верификация, guardrails, детерминированные обработчики.

**Без любого из этих четырёх условий система не является harness.**

## 2. Семь подсистем harness

### 2.1. Agent Loop

**Назначение:** циклическое выполнение reason → act → observe.

**Компоненты:**
- LLM call с tool definitions;
- парсинг tool calls;
- execution tools;
- observation (результаты обратно в контекст);
- termination condition (stop_reason, max iterations).

**Ключевой момент:** termination через `stop_reason`, а не через presence/absence tool calls.

```rust
match response.choices[0].finish_reason {
    FinishReason::ToolCalls => { /* execute tools, continue */ }
    FinishReason::Stop => break,
    FinishReason::Length => {
        compact_old_tool_results(&mut messages);
        // do NOT break — continue the loop
    }
    _ => break,
}
```

### 2.2. LLM Integration

**Назначение:** унифицированный доступ к LLM-провайдерам.

**Компоненты:**
- multi-provider abstraction;
- tool calling formats;
- streaming;
- prompt caching;
- retry logic.

**Не дублировать:** если используете pi-ai или LiteLLM, не пишите свой слой.

### 2.3. Tools

**Назначение:** каталог того, что агент может делать.

**Базовые инструменты:**
- `read_file`;
- `write_file`;
- `edit_file`;
- `bash`;
- `grep`;
- `glob`.

**Расширенные:**
- `semantic_search`;
- `symbol_search`;
- `run_tests`;
- `run_linter`;
- `apply_patch`;
- `create_branch`;
- `open_pr`.

**Протоколы:** MCP, OpenAPI, custom RPC.

### 2.4. Memory & Context

**Назначение:** управление тем, что попадает в контекст.

**Компоненты:**
- context manager (compaction, selection);
- memory (survives across steps and sessions);
- artifact store (external);
- summarization;
- tool response → files.

### 2.5. Safety & Permissions

**Назначение:** ограничения безопасности.

**Компоненты:**
- permission gates (Allow once / Always allow / Reject);
- allowlist команд;
- запрет опасных операций (`rm -rf`, force push);
- audit log;
- secrets management;
- network isolation.

### 2.6. Orchestration

**Назначение:** координация нескольких агентов / цепочек.

**Компоненты:**
- workflow engine (nodes + edges);
- conditional edges;
- quality gates;
- max iterations;
- parallel branches;
- checkpointing.

### 2.7. Extensibility

**Назначение:** возможность добавления новых возможностей.

**Компоненты:**
- extensions API (TypeScript modules);
- skills;
- hooks (beforeToolCall, afterToolCall, shouldStopAfterTurn);
- MCP servers;
- custom tools.

## 3. Минимальный vs Максимальный harness

### 3.1. Минимальный harness

```
┌─────────────────────────────────────┐
│  Agent Loop (reason → act → observe) │
│  ├─ LLM integration                  │
│  ├─ 4 basic tools (read, write, edit, bash) │
│  └─ Basic context management         │
└─────────────────────────────────────┘
```

**Пример:** mini-swe-agent — ~100 строк, всё через shell.

**Когда достаточно:** простые задачи, прототип.

### 3.2. Production harness

```
┌─────────────────────────────────────────────────────┐
│  Workflow Engine (phases, conditional edges, gates) │
├─────────────────────────────────────────────────────┤
│  Agent Loop                                          │
│  ├─ Hooks Layer:                                     │
│  │   beforeToolCall: inject artifacts, per-model instructions │
│  │   afterToolCall: tool response → file, token logging │
│  │   shouldStopAfterTurn: context usage check        │
│  └─ LLM Integration (multi-provider, caching)        │
├─────────────────────────────────────────────────────┤
│  Telemetry Layer (cost per phase, cache hit rate)    │
├─────────────────────────────────────────────────────┤
│  Knowledge Layer:                                    │
│  ├─ SurrealDB / Mem0 / Graphiti                      │
│  ├─ CodeGraphContext MCP                             │
│  └─ ADR (markdown + MCP)                             │
├─────────────────────────────────────────────────────┤
│  Safety Layer: sandbox, permission gates, audit      │
└─────────────────────────────────────────────────────┘
```

### 4.1. OpenHands: архитектура «всё есть событие»

OpenHands (f.k.a. OpenDevin) — референс event-driven harness, где **всё есть событие**: любое действие агента, наблюдение, сообщение или изменение состояния публикуется в общий `EventStream` и обрабатывается через колбэки (`on_event(event: Event) -> None`).

**Ключевые архитектурные решения:**

- **EventStream как центральный хаб.** Любой компонент может публиковать события или подписываться на них. `EventStream` служит «позвоночником» всей коммуникации в системе.
- **Event = Action или Observation.** Агент исполняется через event-driven loop, который обрабатывает состояние разговора шаг за шагом, а не возвращает результаты напрямую.
- **Event-sourced state model с deterministic replay.** V1 SDK определяет event-sourced модель состояния, которая позволяет воспроизводить выполнение детерминированно, а также immutable configuration для агентов и typed tool system с MCP-интеграцией.
- **Append-only лог как память агента.** События формируют append-only log, который служит одновременно памятью агента и точкой интеграции для вспомогательных сервисов.

**Практический вывод:** архитектура «всё есть событие» — один из двух доминирующих подходов к production harness (наряду с graph-based orchestration). Даёт аудируемость, deterministic replay и естественную интеграцию с sandbox-исполнением. См. также [07.3.5](./07.selection-guide.md) (OpenHands как готовый SWE-стек).

**Источник:** [Wang et al., «OpenHands: An Open Platform for AI Software Developers as Generalist Agents» (arXiv:2407.16741, ICLR 2025)](https://arxiv.org/abs/2407.16741) — оригинальная статья; [OpenHands Software Agent SDK (arXiv:2511.03690, MLSys 2026)](https://arxiv.org/abs/2511.03690) — V1 SDK с event-sourced state и typed tool system.

## 5. Hooks API

### 5.1. pi-agent-core

**Подтверждённые hooks:**
- `beforeToolCall` — после `tool_execution_start` и validated argument parsing, может блокировать (`return { block: true, reason: "..." }`).
- `afterToolCall` — после выполнения, до `tool_execution_end`, может модифицировать результат.
- `shouldStopAfterTurn` — после `turn_end`, до следующего LLM-вызова.

**`beforeLLMCall` НЕ существует** как hook. Нужно реализовывать через:
- `shouldStopAfterTurn` + `ctx.getContextUsage()`, ИЛИ
- `session_before_compact` в extensions layer.

### 5.2. Pi extensions

**События:**
- `session_before_compact` — до compaction, можно cancel или customize.
- `ctx.getContextUsage()` — текущий usage контекста.
- `ctx.compact()` — trigger compaction.
- `tool_call` — can block (эквивалент `beforeToolCall`).
- `tool_result` — can modify result (эквивалент `afterToolCall`).

## 6. Архитектура v3.0 (рекомендуемая)

Ключевой принцип: **Context Engineering — это hooks вокруг каждого LLM-вызова, а не отдельный слой** между блоками.

```
Workflow Engine (фазы + фазовая загрузка MCP, conditional edges, gates)
        │
pi-agent-core Runtime
  ├─ Hooks Layer:
  │   beforeToolCall: инжекция артефактов, per-model инструкции
  │   afterToolCall:  tool response → файл (если > threshold), логирование токенов
  │   shouldStopAfterTurn:  проверка размера контекста, триггер суммаризации (>80%),
  │                   инжекция ссылок на артефакты
  └─ pi-ai (unified LLM API)
        │
Telemetry Layer (P0): input/output/cache_read/cache_creation на каждый вызов,
агрегация по фазам, детализация по tool calls
        │
Knowledge Layer: SurrealDB (ADR + artifacts + metrics) | Tree-sitter + CodeGraphContext MCP | Mem0/Graphiti
```

## 8. Практические рекомендации

1. **Начните с минимального harness.** 4 базовых tool + loop.
2. **Добавляйте подсистемы по мере необходимости.** Не строьте всё сразу.
3. **Context Engineering — через hooks.** Не отдельный слой.
4. **Телеметрия с первого дня.** Без неё — гадания.
5. **Используйте готовый runtime.** Pi / OpenHands / Codex.
6. **Свой слой — только оркестрация и context engineering.**
7. **Safety — не опция.** Sandbox, permission gates, audit.
