## 1. Что такое harness

**Harness** — это операционный слой вокруг LLM, который управляет control loop, маршрутизирует tool-запросы, инъектирует контекст и обеспечивает исполнение. Модель — это «двигатель», harness — всё остальное, что делает двигатель управляемым транспортным средством.

Согласно формальному определению, harness — это система, которая обеспечивает четыре необходимых условия:

1. **Agent loop** — цикл, который чередует рассуждение, действие и наблюдение во время выполнения.
2. **Tool interface** — модель может воспринимать и изменять среду.
3. **Context management** — управление тем, что попадает в окно модели.
4. **Control mechanisms** — верификация, guardrails, детерминированные обработчики.

Без любого из этих четырёх условий система не является harness: без loop это генератор, без tool interface модель заперта в своём окне, без context management нет жизнеспособного цикла, без control mechanisms невозможно определить, действительно ли задача выполнена.

**Что не является обязательным для harness:** мультиагентность (один агент в цикле с инструментами — уже harness), обучение или fine-tuning, конкретная модель, пользовательский интерфейс.

## 2. Границы: что входит в harness

Современный harness включает:

| Компонент | Назначение |
|---|---|
| **Tool registry** | Каталог того, что агент может делать: читать файлы, запускать команды, браузить |
| **Context manager** | Сжатие истории, выбор релевантного |
| **Memory** | То, что выживает между шагами и сессиями |
| **Agent loop** | Reason → Act → Observe |
| **Verifier** | Проверяет, действительно ли задача выполнена, а не принимает слова модели |
| **Retry logic** | Повторные попытки с возможной сменой модели |
| **Observability** | Аудируемая запись того, что произошло |
| **Guardrails** | Ограничения безопасности |
| **Deterministic handlers** | Обычный код для частей, слишком чувствительных для модели |

## 3. Классификации паттернов

Существует пять основных классификаций, которые дополняют друг друга.

### 3.1. Anthropic: Building Effective Agents (декабрь 2024)

Первичный строительный блок — **augmented LLM** (LLM + retrieval + tools + memory). Два уровня:

**Workflows** (путь задан кодом):
- **Prompt chaining** — последовательные LLM-вызовы, выход одного — вход следующего; между шагами можно ставить программные «гейты».
- **Routing** — классификатор направляет вход в одну из нескольких ветвей.
- **Parallelization** — независимые задачи запускаются одновременно (или один вход прогоняется через несколько оценщиков — voting).
- **Orchestrator-workers** — центральный LLM динамически декомпозирует задачу, делегирует воркерам и синтезирует результат.
- **Evaluator-optimizer** — один LLM генерирует, другой оценивает, цикл до сходимости.

**Agent** (LLM сам направляет процесс): используется, когда предсказать число шагов невозможно; критично грамотно проектировать инструменты, обязательно задавать stopping conditions.

### 3.2. Microsoft Azure: AI agent orchestration patterns

Классификация (обновлена 12 февраля 2026 ) начинается с трёх уровней сложности (прямой вызов модели → один агент с инструментами → мультиагентная оркестрация) и описывает пять паттернов координации:

- **Sequential orchestration** — агенты в фиксированном порядке, каждый получает полный выход предыдущего.
- **Concurrent orchestration** — параллельная работа независимых агентов с последующей агрегацией.
- **Group chat orchestration** — агенты общаются в общем чате, менеджер-агент решает, кто говорит следующим.
- **Handoff orchestration** — агенты передают управление друг другу.
- **Magentic orchestration** — фирменный паттерн Microsoft: оркестратор итеративно координирует агентов, динамически выбирая следующего исполнителя.

### 3.3. Google Cloud: Choose a design pattern

Документ Google объединяет одноагентные и мультиагентные подходы. InfoQ выделяет восемь ключевых паттернов. Базовые — **Reflection, Tool Use, Planning, Multi-Agent** (наследие Andrew Ng) плюс расширенные мультиагентные схемы.

### 3.4. Andrew Ng: четыре базовых паттерна

Самая педагогически влиятельная классификация:

- **Reflection** — агент критикует свой или чужой выход и итеративно улучшает.
- **Tool Use** — LLM вызывает внешние инструменты (веб-поиск, код, API).
- **Planning** — агент декомпозирует задачу в подзадачи и планирует последовательность.
- **Multi-Agent Collaboration** — несколько специализированных агентов работают вместе, разделяя роли.

### 3.5. Академическая таксономия (arXiv)

Статья «LLM-Enabled Multi-Agent Systems: Empirical Evaluation» формализует emerging-паттерны из литературы. Для практических целей полезна как справочник терминов, но для инженерии меньше применима, чем практики Anthropic/Azure.

## 4. Workflow vs Agent: ключевое различие

| Критерий | Workflow | Agent |
|---|---|---|
| **Путь** | Задан кодом | Определяется LLM |
| **Предсказуемость** | Высокая | Переменная |
| **Стоимость** | Ниже (меньше вызовов) | Выше (больше итераций) |
| **Когда использовать** | Задачу можно нарисовать как блок-схему | Задача open-ended, число шагов неизвестно |
| **Контроль** | Полный | Частичный (нужны stopping conditions) |

**Правило Mastra:** если можешь нарисовать блок-схему — пиши workflow (детерминированный), а не свободного supervisor-агента, который каждый раз изобретает путь заново. Стоимость отладки несравнима.

## 5. Архитектурные паттерны фреймворков

Анализ 44 фреймворков выявил пять доминирующих архитектурных паттернов:

| Паттерн | Представители | Когда выбирать |
|---|---|---|
| **Graph-based Orchestration** | LangGraph, Mastra, Google ADK, Flowise | Production-агенты с audit trail, compliance, сложными многошаговыми workflow |
| **Multi-Agent Orchestration** | CrewAI, OpenAI Agents SDK, AutoGen, AG2 | Задачи, требующие разнообразной экспертизы, естественная декомпозиция на подзадачи |
| **Event-driven** | OpenHands, AG2 (частично) | Распределённые развёртывания, параллельное исполнение |
| **Role-based** | CrewAI, MetaGPT | Быстрый прототип, имитация человеческой команды |
| **Workflow-graph** | Mastra, Inngest | TypeScript-стек, event-driven воркфлоу |

**Graph-based Orchestration** стал доминирующим подходом для production-систем, потому что обеспечивает явный контроль над потоком исполнения: детерминированное исполнение, визуальная отладка, checkpointing, условные переходы.

**LangGraph** стал доминирующим фреймворком для production multi-agent систем в 2026 году .

**Multi-Agent Orchestration** даёт специализацию, параллелизацию и модульность, но создаёт coordination overhead, сложность отладки и критический вопрос shared vs isolated context.

## 6. Сравнение подходов к оркестрации

| Фреймворк | Модель оркестрации | Изоляция контекста | Стек |
|---|---|---|---|
| **LangGraph** | Граф состояний: nodes + conditional edges + checkpointing | Субагенты stateless по умолчанию | Python/JS |
| **Mastra** | `createWorkflow` с `.then/.branch/.parallel/.dountil` | Субагенты как tools, типизированные схемы | TypeScript |
| **CrewAI** | Role-based crews, hierarchical process | Контекст шарится внутри crew, изоляция слабее | Python |
| **AutoGen** | Group chat + reflection pattern | Сессии разделяются между участниками | Python |
| **OpenAI Agents SDK** | Handoffs + agents-as-tools | Sub-agents получают только промпт | Python/TS |
| **Microsoft Agent Framework** | Sequential, Concurrent, Group Chat, Handoff, Magentic | Встроенный thread management | Python/.NET |
| **OpenHands** | Event-driven, CodeAct | Изолированный sandbox-runtime | Python |

## 7. Ключевой вывод для выбора

Для задач разработки ПО с фиксированными цепочками под тип задач и evaluator-loop:

1. **Оркестрация — детерминированным кодом.** Граф (LangGraph, Mastra) или свой тонкий слой.
2. **Обмен — через типизированные артефакты**, не через общий контекст.
3. **Роли — специализированные агенты** с чёткими входными/выходными контрактами.
4. **Quality gates — обязательны** на каждой границе.
5. **Модель под роль** — дешёвая на поиск/суммаризацию, сильная на планирование/критику.
