На основе анализа `specs.md`, GitHub Spec Kit, `spec-kitty.ai`, OpenSpec и `obra/superpowers` можно сформулировать требования к гипотетическому «идеальному» инструменту. Он не должен быть монолитом — скорее это **модульная экосистема**, где каждый слой можно включать по необходимости. Вот ключевые требования.

### 1. Архитектура и философия
- **Модульность**: разделение на слои — спецификации, планирование, исполнение, оркестрация, аудит. Пользователь подключает только нужные компоненты.
- **Git-native и local-first**: все артефакты и конфиги хранятся в репозитории, а не в глобальных скрытых папках. Работа офлайн по умолчанию.
- **Открытость и прозрачность**: открытый исходный код, понятная конфигурация, отсутствие скрытой телеметрии.
- **Отсутствие привязки к вендору**: инструмент не должен диктовать конкретного AI-агента, IDE или облако.

### 2. Слой спецификаций
- **Поддержка greenfield и brownfield**: полные спецификации для новых систем и дельта-спецификации для существующих.
- **Единый источник истины, но с уровнями детализации**: от лёгких заметок до формальных SHALL/MUST-требований.
- **Надёжная валидация**: команды проверки должны быть согласованными, без багов вроде «no requirement entries parsed».
- **Человекочитаемость**: Markdown + схемы, но без скатывания в псевдокод. Спецификация должна быть понятна и бизнес-аналитику, и агенту.
- **Постепенное уточнение**: не требовать исчерпывающих данных на старте — контекст должен наращиваться итеративно.

### 3. Слой исполнения
- **Навыки (skills) для инженерных дисциплин**: TDD, систематическая отладка, верификация, ревью — как в `Superpowers`.
- **Настраиваемая строгость**: профили от «vibe coding» до «милитаризованного» процесса. Жёсткие gates не должны быть обязательными для всех задач.
- **Гибкость при изменении требований**: возможность быстро вернуться на шаг назад, переутвердить дизайн и продолжить без полной регенерации.
- **Корректная работа субагентов**: наследование контекста и правил родительского агента, чтобы они не игнорировали TDD и другие ограничения.

### 4. Оркестрация и параллелизм
- **Изоляция через git worktrees**, но без конфликтов в общих файлах состояния (`state.yaml`).
- **Живой Kanban-дэшборд** с отслеживанием прогресса, как в `spec-kitty`.
- **Автоматическое или полуавтоматическое разрешение конфликтов** между параллельными агентами.
- **Поддержка монорепозиториев**: вложенные проекты, независимые конфигурации, отсутствие «разрастания инструкций».

### 5. Безопасность и приватность
- **Opt-in для телеметрии и синхронизации**: согласие должно быть явным, храниться в репозитории и быть видимым для ревью.
- **Локальная работа по умолчанию**: никаких скрытых отправок данных.
- **Аудит и прозрачность**: логирование действий, понятная политика конфиденциальности, возможность отключить любую сетевую активность.

### 6. Эффективность и производительность
- **Экономия токенов**: селективная загрузка контекста, кэширование, суммаризация, отказ от «раздувания» инструкций.
- **Быстрый CLI и минимальные зависимости**: установка без тяжёлых рантаймов, быстрый запуск.
- **Оффлайн-режим**: возможность работать без постоянного подключения к API.

### 7. Интеграция и экосистема
- **Агент-агностик**: поддержка Claude Code, Cursor, GitHub Copilot, Gemini CLI и других без «stopgap»-решений.
- **IDE-агностик**: работа в любом редакторе, не только в специализированной IDE.
- **Расширяемость**: кастомные навыки, шаблоны, плагины, хуки.
- **Хорошая документация**: примеры, миграционные руководства, понятные имена команд без конфликтов вроде `openspec` vs `opsx`.

### 8. UX и управление изменениями
- **Стабильный цикл review → merge**: без регенерации всего пакета при отклонении.
- **Автоматическая архивация** выполненных изменений.
- **Понятные метрики и трассируемость**: видно, что сделано, кем и на основании каких требований.
- **Минимальная когнитивная нагрузка**: отсутствие избыточной многословности в генерируемых файлах.

### 9. Управление и развитие
- **Прозрачный roadmap и безопасность**: регулярные аудиты, реакция на issue, обратная совместимость.
- **Версионирование и миграции**: предсказуемые обновления без ломающих изменений.
- **Сообщество**: активная поддержка, примеры реальных внедрений, возможность влиять на развитие.

### 💎 Главный принцип
Идеальный инструмент — это **не замена** всех перечисленных, а **композиция**:
- `OpenSpec` — для лёгкого управления изменениями.
- `Superpowers` — для дисциплины исполнения.
- `spec-kitty` — для оркестрации параллельной работы.
- `Spec Kit` / `specs.md` — для строгих спецификаций в сложных проектах.

Но всё это должно быть объединено **единой оболочкой** с общими конфигами, API и Git-нативным хранением. Ключевые требования: **конфигурируемость, прозрачность, безопасность по умолчанию, экономия токенов и отсутствие жёсткой привязки к одному агенту или процессу**.
