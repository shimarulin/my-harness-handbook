# Ferro Labs AI Gateway: настройка для Pi Coding Agent

## Что это

Ferro Labs AI Gateway — open-source LLM-шлюз на Go, single binary. Позиционируется как быстрый и лёгкий routing tier. Поддерживает 30 providers, 2,500+ models, live model discovery.

**Ключевые возможности:**
- `DiscoveryProvider` — live model discovery via provider API (`DiscoverModels`).
- `ConfiguredModelProvider` — authority for local/custom models.
- 4 стратегии маршрутизации: Single, Fallback (w/ exponential backoff), Weighted Load Balancing, Conditional (model-based).
- Per-target retry, failover, model aliases.
- Single binary, predictable latency, minimal resource usage.

## Установка

### One-line install (Linux / macOS / Windows)

```bash
# Linux / macOS
curl -fsSL https://get.ferrolabs.ai/install.sh | sh

# Windows (PowerShell)
irm https://get.ferrolabs.ai/install.ps1 | iex
```

Инсталлятор скачивает статический бинарник без runtime-зависимостей, проверяет SHA-256 и кладёт его в `/usr/local/bin` (Linux/macOS) или `%LOCALAPPDATA%\Programs\ferrogw` (Windows). Версия фиксируется через `FERROGW_VERSION` (например, `FERROGW_VERSION=v1.5.8`).

### Homebrew

```bash
brew install ferro-labs/tap/ferrogw
```

### Скачивание архива вручную

Все релизы публикуют архивы для Linux/macOS/Windows на x86-64 и arm64. Их можно скачать со страницы релизов GitHub.

### Docker

```bash
docker run -d -p 8080:8080 \
  -e OPENAI_API_KEY=sk-... \
  ferro-labs/ai-gateway:latest
```

### Из исходников

```bash
git clone https://github.com/ferro-labs/ai-gateway.git
cd ai-gateway
make run
```

## Конфигурация провайдера

Провайдеры объявляются через `<PROVIDER>_BASE_URL` и `<PROVIDER>_API_KEY`:

```bash
export CUSTOM_BASE_URL=https://internal-llm.company.com/v1
export CUSTOM_API_KEY=sk-internal-...
```

`<PROVIDER>_BASE_URL` is the API root, used verbatim — version segment included. Model discovery appends only its operation path to that root.

## Подключение произвольного OpenAI-совместимого провайдера

Ferro Labs **не предоставляет** отдельного типа `custom_openai`. Вместо этого нужно **переиспользовать существующий OpenAI-совместимый провайдер**, переопределив его `BASE_URL` на адрес вашего кастомного сервиса. Механизм работает так:

1. Выберите любого провайдера из списка OpenAI-совместимых (например, `openai`, `groq`, `deepseek`).
2. Установите его API-ключ и `BASE_URL` так, чтобы они указывали на ваш кастомный эндпойнт:

```bash
export OPENAI_API_KEY=sk-your-custom-key
export OPENAI_BASE_URL=http://localhost:4000/v1
```

3. В `config.yaml` добавьте `targets[]` с `virtual_key: openai`. После этого все запросы, которые маршрутизируются на «провайдера openai», будут уходить на ваш кастомный сервис.

**Важное ограничение:** этот способ **заменяет** официального провайдера `openai`. Если вам нужно одновременно использовать и официальный OpenAI, и кастомный сервис, выберите для кастомного другого провайдера из списка (например, `deepseek`), переопределив его `BASE_URL` и `API_KEY`. Тогда `virtual_key: deepseek` будет указывать на ваш сервис, а `virtual_key: openai` останется для официального API.

**Правило BASE_URL:** начиная с v1.4.0 `_BASE_URL` — это API-корень, используемый дословно, включая сегмент версии. Пишите `https://proxy.example.com/v1`, а не `https://proxy.example.com`. Если BASE_URL не содержит пути, он разрешается в дефолтный сегмент провайдера (`/v1` для OpenAI-wire).

**Пример с кастомным сервисом на `deepseek`:**

```yaml
targets:
  - virtual_key: openai      # официальный OpenAI
  - virtual_key: deepseek    # ваш кастомный сервис через переопределение
```

```bash
export OPENAI_API_KEY=sk-official-openai-key
export DEEPSEEK_API_KEY=sk-custom-key
export DEEPSEEK_BASE_URL=http://localhost:4000/v1
```

Теперь модель, которую вы объявите в кастомном сервисе, будет маршрутизироваться через `deepseek`, а официальные модели OpenAI — через `openai`.

## Model discovery для кастомного провайдера

Ferro Labs выполняет live discovery через `DiscoveryProvider`, который запрашивает список моделей у провайдера. Для OpenAI-совместимых провайдеров discovery работает, если провайдер отдаёт `/v1/models` в стандартном формате OpenAI. Однако Ferro Labs **не гарантирует**, что `/v1/models` вашего кастомного сервиса будет содержать поля `contextWindow`, `maxTokens` и `cost` — это зависит от реализации сервиса.

Если ваш кастомный сервис не отдаёт эти метаданные, можно:
1. Использовать `kosha-discovery` или `RouteHub` для обогащения.
2. Объявить модели вручную через `targets[].models` в `config.yaml` — это additive к каталогу и live discovery.

## Fallback-стратегии

Fallback настраивается на уровне `targets[]`:

```yaml
strategy:
  mode: fallback
targets:
  - virtual_key: openai
  - virtual_key: deepseek
  - virtual_key: gemini
```

При ошибке (5xx, 429, timeout) запрос автоматически перенаправляется на следующий target в цепочке. Retry-политика настраивается per-target:

```yaml
targets:
  - virtual_key: openai
    retry:
      attempts: 3
      on_status_codes: [429, 502, 503]
      initial_backoff_ms: 100
```

Также доступны режимы `load-balance`, `conditional`, `ab-test`.

## Ограничение

Не подтверждено, что `/v1/models` возвращает cost/contextWindow/maxTokens. Для проброса в Pi может потребоваться обогащение через `kosha-discovery` или `RouteHub`.
