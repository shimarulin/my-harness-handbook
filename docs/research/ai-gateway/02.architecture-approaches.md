# Архитектурные подходы к генерации `models.json` для Pi

## Три подхода

### Подход 1: CLI-скрипт

Внешний скрипт запрашивает `/v1/models`, обогащает данные и записывает в `~/.pi/agent/models.json`.

**Инструменты:**
- `@seqyuan/pimodel` — интерактивный CLI, обогащает context window и max output через detail-эндпойнты; defaults по ID модели.
- `xsync-cli` — синхронизация OpenAI-совместимого эндпойнта в каталог Codex.
- `litellm-controller` (`litellmctl`) — управление метаданными LiteLLM Proxy, приоритетное слияние скриптов.

**Плюсы:** полный контроль, работает с любым шлюзом, несколько источников обогащения.
**Минусы:** ручной запуск, нет авто-обновления, нет fallback.

### Подход 2: Расширение Pi

Расширение при старте Pi запрашивает `/v1/models`, обогащает метаданные и регистрирует через `pi.registerProvider()`.

**Ключевое расширение:** `pi-openai-api-models-sync`
- Синхронизирует модели из `/models` и обогащает из Sub2API metadata repository.
- Метаданные: context windows, output limits, input modalities, token pricing, long-context tiers, reasoning levels.
- Fallback: если discovery не удался — статическая конфигурация не трогается.
- Конфиг: `pi-openai-api-models-sync.json` (providerId, pricingUrl, include/exclude).

**Другие расширения:**
- `pi-autofill-model-metadata` — обогащение из models.dev через явные маппинги.
- `@fe-essential/pi-custom-provider-manager` — slash-команды + models.dev.
- `pi-model-discovery` (MasuRii) — авто-импорт из models.json + фоновое обновление.
- `@brglng/pi-model-discovery` — только `/models`, без обогащения.
- `better-custom-provider` — интерактивный мастер с несколькими источниками.

**Плюсы:** автоматизация, готовые решения, fallback.
**Минусы:** ограничены возможностями расширения.

### Подход 3: Прокси-эндпойнт обогащения (sidecar)

Лёгкий прокси, который отдаёт обогащённый `/v1/models`.

**Компоненты:**
- Шлюз → `/v1/models` (только ID).
- Обогащение: `kosha-discovery`, `litellm-controller`, `models.dev`, LiteLLM cost map.
- Слияние → обогащённый JSON.

**Плюсы:** максимальная гибкость, централизованное управление, кэширование.
**Минусы:** нужно писать прокси.

## Хуки в шлюзах

**LiteLLM:** `/model/new` API с `model_info`; custom callbacks (не влияют на `/v1/models`); `litellm-controller` для метаданных.

**Portkey:** hooks architecture (`beforeRequestHook`, `afterRequestHook`) — для запросов, не для `/v1/models`.
