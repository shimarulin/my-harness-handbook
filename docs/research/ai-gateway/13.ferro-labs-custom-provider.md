# Ferro Labs: подключение произвольного OpenAI-совместимого провайдера

## Проблема

Ferro Labs AI Gateway поддерживает 30 провайдеров, но **не имеет отдельного типа `custom_openai`**. В документации перечислены только конкретные провайдеры с их env vars. Если у вас есть собственный OpenAI-совместимый сервис (например, LiteLLM Proxy, корпоративный шлюз), нужно понять, как его подключить.

## Решение: переопределение `BASE_URL`

Механизм Ferro Labs таков: каждый OpenAI-совместимый провайдер регистрируется через переменные окружения `<PROVIDER>_API_KEY` и опционально `<PROVIDER>_BASE_URL`. Если вы установите `<PROVIDER>_BASE_URL` на адрес вашего кастомного сервиса, все запросы к этому «провайдеру» будут уходить туда.

### Шаги

1. **Выберите провайдера-«носителя»** из списка OpenAI-совместимых. Он должен иметь `_BASE_URL` override в таблице провайдеров. Например:
   - `openai` → `OPENAI_BASE_URL`
   - `deepseek` → `DEEPSEEK_BASE_URL`
   - `groq` → `GROQ_BASE_URL`
   - `mistral` → `MISTRAL_BASE_URL`

2. **Установите переменные окружения** для этого провайдера, указав ваш кастомный эндпойнт:
   ```bash
   export DEEPSEEK_API_KEY=sk-custom-key
   export DEEPSEEK_BASE_URL=http://localhost:4000/v1
   ```

3. **Добавьте target** в `config.yaml`:
   ```yaml
   targets:
     - virtual_key: deepseek
   ```

4. **Проверьте**, что провайдер зарегистрирован и target активен:
   ```bash
   curl http://localhost:8080/readyz
   ```
   В ответе `targets` должен появиться `deepseek`.

### Ограничение: замена провайдера

Этот способ **заменяет** официального провайдера `deepseek` (или любого другого, которого вы выбрали «носителем»). Если вам нужно одновременно использовать и официальный DeepSeek, и ваш кастомный сервис, придётся задействовать **двух** провайдеров-«носителей». Например:

- `virtual_key: openai` → официальный OpenAI.
- `virtual_key: deepseek` → ваш кастомный сервис.

### Правило `BASE_URL`

С v1.4.0 `_BASE_URL` — это API-корень, используемый **дословно**, включая сегмент версии. Пишите:
- `https://proxy.example.com/v1` — правильно.
- `https://proxy.example.com` — неправильно (для OpenAI-wire провайдеров Ferro Labs добавит `/v1` сам, но лучше указывать явно).
- `https://api.groq.com/openai/v1` — правильно для Groq.

**Исключение:** если BASE_URL не содержит пути вообще, он разрешается в дефолтный сегмент провайдера (`/v1` для OpenAI-wire). Так `http://host:9901` и `http://host:9901/v1` эквивалентны.

## Model discovery

Ferro Labs выполняет live discovery через `DiscoveryProvider`, который запрашивает список моделей у провайдера по стандартному пути. Для OpenAI-совместимых провайдеров это работает, если ваш сервис отдаёт `/v1/models` в формате OpenAI.

**Ограничение:** Ferro Labs **не гарантирует** получение `contextWindow`, `maxTokens` и `cost` из `/v1/models` — это зависит от вашего сервиса. Если этих полей нет, используйте:
- `kosha-discovery` — HTTP API для обогащения метаданных.
- `RouteHub` — Python-библиотека с live model catalog.
- Ручное объявление моделей через `targets[].models` в `config.yaml`.

## Пример: LiteLLM Proxy как кастомный провайдер

```bash
# LiteLLM запущен на localhost:4000
export DEEPSEEK_API_KEY=sk-litellm-master-key
export DEEPSEEK_BASE_URL=http://localhost:4000/v1
```

```yaml
# config.yaml
targets:
  - virtual_key: deepseek
  - virtual_key: openai
```

Теперь запросы к моделям, которые LiteLLM отдаёт под именами, принадлежащими «deepseek», будут маршрутизироваться через LiteLLM.
