# Agent Instructions

This repository contains the source code for an advanced book on AI-Agent Architecture.

## Context
- **Audience:** Senior developers and architects who already know what a harness and tools are.
- **Tone:** Technical, pragmatic, deeply architectural. Avoid basic "hello world" LLM examples.
- **Language:** Primary content is in Russian, code examples and variable names are in English.

## Rules
1. When generating code examples, prioritize production-ready patterns (retry logic, structured output, error handling).
2. Do not generate generic LangChain wrappers unless specifically demonstrating their limitations.
3. Follow the Specification-Driven Development (SDD) workflow defined in `docs/00-specification/`.
4. When proposing a new architectural component, always suggest creating an ADR in `decisions/`.

## Key Concepts
- We use **EARS** syntax for requirements.
- We use **BDD** scenarios to define agent behaviors.
- We use **ADR** (Architecture Decision Records) to track why a specific tool (e.g., Kiro vs SpecWeave) was chosen.

# 00. Спецификация и проектирование агентных систем

В мире вероятностных систем (LLM) классический подход "написать код -> протестировать" перестает работать. Если вы не можете специфицировать ожидаемое поведение агента *до* написания промптов и harness-обвязки, вы получите "галлюцинирующий скрипт".

Эта глава посвящена **Specification-Driven Development (SDD)** для AI — дисциплине, которая превращает хаотичный промпт-инжиниринг в предсказуемую инженерию.

## Ключевые концепции и инструменты

### 1. Требования и сценарии
- **[EARS](./ears-requirements.md) (Easy Approach to Requirements Syntax):** Как формулировать требования к агентам, чтобы LLM не могла их трактовать двояко. (Например: *"While the user is uploading a file, the agent shall not trigger the summarization tool"*).
- **[BDD](./bdd-for-agents.md) (Behavior-Driven Development):** Использование Given/When/Then для тестирования недетерминированного поведения агентов и описания edge-cases.

### 2. Инструменты SDD (Specification-Driven Development)
Современные IDE и фреймворки внедряют спецификацию прямо в процесс разработки:
- **[Kiro](./tools/kiro.md):** AWS IDE, где цикл разработки начинается с `.md` спецификаций (Requirements -> Design -> Tasks), и AI-агенты пишут код строго по утвержденному дизайну (Steering).
- **[Spec Kit](./tools/spec-kit.md) & [OpenSpec](./tools/openspec.md):** Открытые стандарты и CLI-утилиты для создания машиночитаемых спецификаций, которые AI-агенты используют как "источник истины" при генерации кода.
- **[BMAD](./tools/bmad.md):** Фреймворк (Business Model Agile Development), который использует мультиагентные системы для генерации полных бизнес-требований и архитектурных схем из сырой идеи.
- **[SpecWeave](./tools/specweave.md):** Инструмент для связывания разрозненных спецификаций в единую ткань проекта, позволяющий агентам проверять, не нарушает ли новый код уже описанные контракты.

### 3. Фиксация решений
- **[ADR](../decisions/README.md) (Architecture Decision Records):** В агентных системах цена ошибки высока (выбор между ReAct и Plan-and-Solve, выбор векторной БД). ADR — это единственный способ объяснить будущим разработчикам (и самим себе через год), *почему* было выбрано именно это решение.

# ADR 0001: Adoption of Specification-Driven Development (SDD) via Kiro

**Date:** 2026-10-01
**Status:** Accepted
**Deciders:** Architecture Team, Lead AI Engineer

## Context
When writing a book about complex AI-agent systems, the risk of "code drift" is extremely high. Examples written in early chapters may contradict the advanced patterns described in later chapters. Standard coding workflows (write code -> debug) fail to maintain consistency across a large documentation/codebase project.

We evaluated several approaches to maintain architectural integrity:
- Traditional TDD (Test-Driven Development) - insufficient for LLM-based non-deterministic logic.
- Ad-hoc prompting - leads to architectural fragmentation.
- **SDD (Specification-Driven Development)** - writing requirements and design docs first, then generating code.

## Decision
We will adopt a strict SDD workflow for this repository, heavily utilizing **Kiro** (or equivalent SDD tools like Spec Kit) as our primary IDE.

Every new major concept (e.g., "Multi-Agent Routing") must follow this cycle:
1. **Specs:** Define requirements using EARS syntax.
2. **Design:** Create design documents and sequence diagrams.
3. **Tasks:** Break down into implementation tasks.
4. **Implementation:** AI-assistants (steered by `AGENTS.md` and specs) generate the code/examples.

## Consequences
- **Positive:** High consistency across book chapters. Examples are guaranteed to match the theoretical models described in the text.
- **Negative:** Higher upfront cost per chapter. Writing specs takes 2x longer than just writing code.
- **Trade-offs rejected:** We rejected the "fast-and-loose" approach (just writing code snippets directly), as it previously resulted in refactoring nightmares during the drafting of "Chapter 5: Memory Systems".
