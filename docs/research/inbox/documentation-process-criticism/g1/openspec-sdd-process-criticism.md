# Расширенное исследование: критика OpenSpec / SDD и универсальные принципы процессов с AI-агентами

Дата: 2026-09-29 (v2 — интеграция материалов из обоих поисковых сессий)
Источники: расширенный поиск по опыту использования и критике OpenSpec; феноменологическая критика SDD (Андрей Шапиро); постмортем планирования (Ayman Nadeem); практические отчёты команд.

---

## Контекст

Цель — не выбор или отказ от конкретного инструмента (OpenSpec, Spec Kit, Kiro), а извлечение универсальных принципов построения процессов разработки, где:

- код генерируют AI-агенты,
- задачи прорабатывает человек,
- спеки и документация живут в одном потоке с кодом.

OpenSpec рассматривается как кейс-исследование, из которого видны общие проблемы SDD, а не как целевое решение.

# Часть 1. OpenSpec: устройство, workflow, реальный опыт

## 1.1. Что такое OpenSpec

Легковесный фреймворк Spec-Driven Development (SDD) от Fission-AI: npm-пакет `@fission-ai/openspec` (Node 20.19+), MIT-лицензия, ~70K звёзд GitHub, ~77K загрузок [3][13]. Работает с 30+ AI-ассистентами через slash-команды и `AGENTS.md`. Не вызывает LLM сам — генерирует и менеджит spec-файлы, генерацию делает ваш агент. «No API Keys», «No MCP» — нулевая дополнительная стоимость инференса, никакого lock-in [3].

Контекст идеи: SDD — не изобретение 2025 года, а BDD/formal requirements/ICD, переосмысленные через LLM. Что изменилось: LLM превратили natural-language спеки в исполнимые артефакты — Markdown + Claude/GPT даёт работающий код без DSL и генератора [10]. AWS Kiro сделал похожее с жёсткой привязкой к своему IDE и Claude Sonnet через Bedrock за $20/мес; OpenSpec — открытая альтернатива без vendor lock [10].

## 1.2. Структура и workflow

Директория в репо:

```
openspec/
├── project.md              ← контекст проекта
├── specs/                  ← текущее поведение системы (source of truth)
│   └── [domain]/spec.md    ← домены: auth/, payments/, search/
└── changes/                ← предложенные изменения, по одной папке
    ├── [change-name]/
    │   ├── proposal.md     ← что меняем и зачем
    │   ├── specs/          ← дельты: ADDED / MODIFIED / REMOVED
    │   ├── design.md       ← опциональный технический подход
    │   └── tasks.md        ← чеклист имплементации
    └── archive/            ← завершённые, с префиксом даты
```

Цикл работы через slash-команды (в чате ассистента, не в терминале):

```
/opsx:explore   →  /opsx:propose  →  /opsx:apply  →  /opsx:archive
(опционально)      (создать change)   (исполнить      (архивировать +
                                       tasks.md)       merge дельт в specs/)
```

Расширенный профиль добавляет `/opsx:verify` и `/opsx:sync`. Каждый инструмент пишет команды по-своему: `/opsx:propose` в Claude Code, `/opsx-propose` в Cursor/Copilot, `@opsx-propose` в Amazon Q, `$openspec-propose` в Codex [4].

Ключевой механизм — дельта-маркеры. Каждый change не переписывает спеку целиком, а описывает только изменение в трёх секциях: ADDED (новое поведение, аппендится в main spec при архивации), MODIFIED (заменяет соответствующий requirement), REMOVED (удаляет). Две следствия: два параллельных change могут править один `spec.md` без конфликтов, если затрагивают разные requirements; ревьюер читает дельту, чтобы понять что и почему изменилось, вместо reverse-engineering из raw diff [3].

Brownfield-first: не нужно спекать весь проект до старта — документируется только срез, который меняет конкретный change, а `openspec/specs/` заполняется естественно за месяцы работы [3][4].

## 1.3. Что работает

| Сценарий | Результат | Источник |
|---|---|---|
| Legacy-проект, инкрементальные изменения | Дельты дисциплинируют агента, предотвращают галлюцинацию новых требований на существующее поведение. «Cleanest delta model I have seen in this category» | [3] |
| Brownfield-внедрение | `openspec init` + первый маленький реальный change. Не bulk-конверсия 40-страничного PRD (даёт спеку, которой никто не доверяет через полгода) | [4] |
| Множественные параллельные изменения | Скоупированные дельты не конфликтуют на разных requirements | [3] |
| Документация как побочный продукт | Архивированные дельты дают system-level spec, растущий с кодовой базой | [3] |
| Легковесность | Типичный change ~250 строк против ~800 у более тяжёлых тулкитов; низкий review overhead; самый лёгкий в освоении SDD-фреймворк | [3] |
| Переносимость | Файлы в репо, 20+ агентов, ноль lock-in | [3] |

## 1.4. Что ломается

| Проблема | Уточнение | Источник |
|---|---|---|
| Спек-дрейф | Спеки не обновляются сами во время имплементации; синхронизация — конвенция, не принуждение | [3] |
| Advisory verification | `openspec validate` проверяет только структуру; `/opsx:verify` не блокирует archive; `archive --no-validate` пропускает проверку целиком. Нет mandatory gate, нет behavioral enforcement: можно зашипить change без единого сценария | [3] |
| Дрейф на длинной дистанции | «When you do the sync process, it just keeps drifting and drifting until you have duplication and contradictions across specs… I've stopped doing it entirely and just archive directly after implementation» — «maintaining the main specs is not worth it». Прямая потеря living-spec benefits, которые составляют смысл дельта-модели | [3][18] |
| Видимость для multi-disciplinary команды | Спеки в репо связали планирование с инженерным инструментом; BA, delivery manager, QA и клиент не работают в этом workspace. Потеря visibility по scope/cost/variance на epic level | [5] |
| Traceability и reporting | Спеки в репо не сообщают, как scope сдвинулся против estimate, что стоило, что драйвит variance | [5] |
| Мульти-репо / polyrepo | Одна фича затрагивает фронт и бэк в разных репо — непонятно, где живёт спека, как агент узнаёт релевантные репо, как поддерживать консистентность. Issue #725: «Where should the spec be maintained when it can't be mapped to a specific repo?» | [8] |
| Legacy codebase при поиске кода | «AI needs to find the relevant code to change it. It's pretty easy to miss something in large codebase (especially when there is lots of legacy stuff)» | [3] |
| Сложность при масштабировании | «Using it got way too complicated» — миграция к AIDLC | [6] |
| Квалификация расхождений | «Модель проверяет модель» — круг размыкается только проверками исполнением; всё непокрытое держится на доверии к модели | [2] |

## 1.5. Дискуссия про Stores и разрыв MVP ↔ реальный проект

Stores (beta) — официальная попытка решить мульти-репо: `openspec/` выносится в собственный репо, несколько кодовых репо им делятся. `openspec store setup` → пуш в git-хост → каждый тиммейт `openspec store register`. Типичные случаи: фронт и бэк в отдельных репо (один план на фичу), один продукт и несколько клиентских репо (Android/iOS/web, одна спека поведения) [16].

Реакция из треда Хабра: nihil-pro (Константин Роман) указывает, что «дизайн и таскс» OpenSpec трещат по швам именно на реальных проектах — «если бэк в одном репозитории, фронт в другом, девопс тоже, а где-то ещё и сопровождение должно подключаться?… если у нас MVP ToDo-листа — это прекрасно работает, а на любом более-менее реальном проекте именно дизайн и таскс никак в концепцию не укладываются». На предложение Stores: «Костыль призывный решить описанную выше проблему. Не решает» [7].

Дискуссия не закрыта: Issue #725 помечен design-review, внутри репозитория есть exploration-документ `workspace-architecture.md` (680+ строк), оценивающий четыре модели (Flat, Nested, Distributed, Hybrid); рекомендованная — Model D (Hybrid). Связанный кластер issues: hierarchical specs #662, nested specs #594, collaboration #435, configurable paths #581/#697. Предложенный порядок реализации: hierarchical → paths → multi-repo workspace [8].

## 1.6. Кейс: почему Talk Think Do ушли

UK-компания, custom software dev на Azure. Цикл: Q4 2025 внедрение → апрель 2026 «OpenSpec maturity — один из четырёх драйверов 84% AI-authored code» → июнь 2026 полный отказ. Самый быстрый цикл «внедрили → оценили → ушли» за историю их ревью [5].

> «The repository is the wrong workspace for the work that happens before code, even when everyone can technically use it. Specs in the repository coupled the planning process to a tool optimised for engineering, and that does not work for a multi-disciplinary team.» [5]

Причина не tooling и не доступ: у всех GitHub Enterprise и Claude Code, BA активно пользуются Claude и Cursor. Проблема структурная — requirements work не только инженерная активность; discovery, refinement, scope-разговоры и stakeholder alignment происходят до репо и включают BA, delivery managers, QA leads и клиента [5].

Модель доставки у них — semi-agile: оценки на уровне user story, бюджеты на epic/feature, работа к бюджетам без контрактного фриза scope в первый месяц. Трейдофф: модель работает только при bulletproof traceability и reporting. Спеки в репо работали против этой модели, скрывая, как scope и cost двигались против estimate [5].

Замена: не другой спек-фреймворк, а планирование в Claude Team, governance в Azure DevOps work items, собственный delivery plugin + MCP server. «Дисциплина планирования и change-подход [OpenSpec] — genuinely good, и мы её сохранили. Изменилось место, где живут артефакты» [5]. Traceability-слой: тесты линкуются к acceptance criteria и work item ID; coverage — свойство work item; агенты обновляют work item по ходу, фиксируя модель, токены, AI cost на каждой user story; сторилевел-актуалы роллятся в epic/feature для сравнения с estimate [5].

# Часть 2. Plan Mode is Dead: контекст Ayman Nadeem

Статья, вокруг которой частично крутится дискуссия в комментариях Хабра. Автор — не наблюдатель: Ayman Nadeem построила и запустила целое десктоп-кодинг-приложение Nuanced с planning как core feature, наблюдала его провал и написала постмортем. Пост вышел на HN, 538 points, 469 комментариев [11][12].

## 2.1. Две задачи plan mode

Plan modes тихо делали две разные работы, и только одна ещё существует [11]:

1. **Задать инструкции достаточно точно для исполнения агентом.** В 2024 — начале 2025 модели требовали этого: приходилось прописывать архитектуру, файлы, edge cases, иначе агент заполнял пробелы догадками. План был контрактом. — Эта задача быстро устаревает: модели научились исследовать репозиторий и делать разумные допущения.
2. **Помочь человеку понять, что он строит.** Акт ревью плана заставлял продумать решения до того, как они станут 500 строками сгенерированного кода. — Важнее, чем когда-либо, но план-мод — не та абстракция для неё.

## 2.2. Четыре причины провала planning-first workflow

1. **Планирование сконфлиировано с планом.** Мышление до кода ценно; длинный структурированный документ, сохраняющий мышление, оказался никому не нужен. Процесс был точкой; артефакт — нет.
2. **Модели стали очень хорошими.** Model capability конкурировала с interface design. Продукт, чья ценность была upstream модели, обнаружил, что модель съедает его ценность снизу.
3. **Никто не хочет читать AI-сгенерированный текст.** Спеки Nuanced были длинными, точными и нечитаемыми. «Spec Tour» для проводки по важным частям — вердикт автора: «если нужна короткая выжимка, чтобы документ был юзабельным, зачем был документ?»
4. **Разрыв непрерывного процесса.** Waterfall-подход: chat → disambiguate → spec → review → approve → implement → review code. Реальное мышление работает иначе: понял часть проблемы → попробовал → результат чему-то научил → передумал. Продукт заставлял заканчивать мышление преждевременно [11].

## 2.3. Что заменяет plan-approve-execute

Цикл: **understand → act → inspect (включая тесты) → clarify (только где результат поднял реальное решение) → adjust → act again**. Планирования внутри цикла много; исчезает документ под названием «план», стоящий между мышлением и действием как обязательный gate [11].

Открытая проблема, которую никто не решил: если plan mode мёртв, что держит вас ориентированным? Понимание, что агент изменил и почему — всё ещё открытая проблема, резко усложняющаяся при масштабировании от 5 параллельных агентов к сотням. Предложение Nadeem: агенты должны находить минимум мест, где внимание человека даёт максимум эффекта. Это product-shaped hole, которую никто не заполнил [11].

## 2.4. Когда план всё же стоит писать

Чеклист из постмортема [11]:

- **Blast radius — production.** Миграции БД, auth, деньги. Цена неверного направления всё ещё достаточна, чтобы checkpoint окупился.
- **Результат нельзя проверить.** Если ни вы, ни агент не можете протестировать исход, approve — единственный quality gate.
- **Requirements contested.** Несколько стейкхолдеров с разногласиями — человеческая проблема; документ — продуктивный формат несогласия.
- **Работа днями, не минутами.** Long-running work переживает chat context; что-то durable должно переносить решения между сессиями.

Для остального — цикл.

## 2.5. Связь с практикой из треда

Gromilo сформулировал тот же shift независимо: «Т.к. заметил, что всё что агент может превратить в план, он может просто сделать по исходным данным. Хочешь план, а хочешь сразу исходный код. Отношение к плану сменилось с "инструкции, которые агент должен сделать" на "вот как агент понял задачу". Можно свериться» [7]. План стал не контрактом, а зеркалом понимания агента.

# Часть 3. Феноменология SDD (Андрей Шапиро)

Два источника: «Феномены код-агентной разработки и слабости SDD» [1] и «К контрмерам от потери устойчивости ИИ-обвязки, работающей на базе спецификаций» [2]. Автор разрабатывает обвязку второго уровня (L2-harness) для ИИ-код-агентов — полуавтомат, «выращивающий» код информационной системы по многоуровневой спецификации.

Контекст наблюдений из работы с обвязкой [2]:
- Агент раз за разом писал commit-сообщения транслитом вопреки инструкции; ориентиром были соседние коммиты в истории. Помогла чистка примеров, новая инструкция — нет.
- Норма тихо исчезала из текста спеки при очередной правке. Заметить мог только тот, кто держал её в голове.
- Агент расширял поручение до «сделать хорошо» и переписывал то, о чём не просили.

## 3.1. Аксиома Русакова

> «Обратная связь от процесса выращивания системы на основе спецификации асимметрична и касается только тех мест, где машине не повезло.» [2]

Следствия [1][2]:

1. Оператор видит ошибку и исправляет спеку. Удачу не замечает — и ничего не правит.
2. Спека улучшается только там, где машина промахнулась.
3. Измеренное качество спеки завышено.
4. Перегенерация не идемпотентна по поведению.
5. Каждый молча принятый результат повышает доверие к спеке, не повышая её определяющей силы. Разрыв между доверием и силой растёт незаметно.

## 3.2. Зазор творчества

> «Спецификация всегда недоопределена, и машина молчаливо заполняет её пробелы своим выбором.» [1]

Неопределённое место спека не останавливает машину — она выбирает сама и оператору об этом не сообщает. Совокупность таких скрытых выборов, осевших в коде и поведении системы — зазор творчества. Отличить обдуманно заданное в спеке от случайно удавшегося нечем: и то, и другое выглядит замыслом при поверхностном взгляде. Чем меньше у оператора конкретных ожиданий к конечной форме, тем большая часть работы уходит в зазор [1][2].

## 3.3. Четыре феномена

| Феномен | Определение | Лечится спекой? |
|---|---|---|
| **Умолчание** | Спека не определяет место, без которого не пройти; машина заполняет сама молча | Да — место можно определить явно |
| **Дрейф** | Спека место определяет, но машина отклоняется от исполнения. «Определённость требования не влечёт определённости его исполнения». Примеры: сегодня код без комментариев, завтра с ними; сегодня операнды в одну строку, завтра в две; отступ то в 2, то в 4 пробела | Нет |
| **Эрозия** | Машина теряет часть содержания, правя уже принятое. «Содержание, чья причина не записана рядом с ним или не дана в отсылке по связи, для машины неотличимо от лишнего». Правку заказывает человек, исполняет машина — заказанное неотличимо от потерянного попутно. Каждая правка стартует с уже обеднённого состояния | Нет |
| **Наплыв** | Машина переносит структуру и стиль из всего, что видит — кода, текстов, схем, примеров — без прямого требования о переносе. Пример, приложенный как подсказка, становится образцом целиком, включая случайные черты; скопированная форма становится образцом для нового копирования — загрязнение растёт снежным комом | Частично — через организованные ориентиры |

По результату феномены неразличимы. Различить можно, только вернувшись к спеке («было ли место определено?») и к прежнему состоянию («было ли там содержание раньше?») [1][2].

## 3.4. Почему это не компилятор

> «Выбор компилятора не меняет поведения программы, выбор агента в умолчании меняет. Компилятор тоже выбирает: раскладывает переменные по регистрам, переставляет инструкции. Семантика языка полностью задаёт поведение программы, и все выборы компилятора остаются внутри неё. У спецификации на естественном языке такой семантики нет. Два разных ответа машины на одно умолчание дают на одних и тех же данных разное поведение.» [1]

Детерминированный агент делает выбор повторяемым, но не принятым: он поменяется вместе с моделью, версией или соседним контекстом. В one-shot-режиме любая правка спеки разыгрывает все умолчания заново — поменяли одно требование, могло поменяться и то, чего правка не касалась [1].

## 3.5. Единственный внешний судья

> «Машинописные тесты по той же спецификации на эту роль не годятся — они будут содержать ошибки того же рода. Приёмка удостоверяет один прогон, оставляя прочие неизвестными. Приёмка удостоверяет лишь то, что наблюдалось. Приёмка необходима, но недостаточна.» [2]

## 3.6. Экономика внимания

> «Машина обрабатывает сведения многократно быстрее человека. Человек в этой связке — самое медленное звено. Подобные средства тем бесполезнее, чем больший объём артефактов в единицу времени создаётся: их объём растёт, предельная ёмкость внимания человека остаётся прежней.» [2]

Сплошное сличение силами человека замедляет пару человек-машина до скорости человека. Вопрос: как удержать поведение системы так, чтобы внимание человека не росло вместе с объёмом производимых артефактов [2].

# Часть 4. Универсальные принципы для построения процессов

## 4.1. Требование должно жить в самой дешёвой форме, которая способна его удерживать

| Тип требования | Самая дешёвая форма | Пример |
|---|---|---|
| Структурный инвариант домена | Тип (illegal states unrepresentable) | `Money` не может быть отрицательным на уровне типа |
| Граница систем | Схема + контрактный тест | OpenAPI + Pact |
| Обобщённое намерение | Property-based тест | «Сумма долей равна единице» |
| Конкретное поведение | Пример (unit test) | `calculateDiscount(500, gold) == 12%` |
| Причины решений, конфликты, триггеры пересмотра | ADR | Почему выбрали 12%, а не 15%; при каком условии решение перестанет быть верным |

Словами остаётся только то, что формализуется дороже, чем нарушается. Практический комментарий из треда: «Нужен какой-то лок, где мы говорим агенту и самим себе: вот это истинно, это нарушать нельзя, тут нужно подумать при изменении. А всё остальное можно править без проблем. Главное поймать агента, когда он начнёт костылить, чтобы обойти инварианты» [7].

## 4.2. Машинная проверка — фундамент, не надстройка

> «Судьба SDD решится не качеством спек и не workflow, а появлением дешёвого машинного enforcement/доказательства: заранее созданных тестов, типов, контрактов… Спека словами не отменяется, она сжимается до минимума.» [7]

Идея «спека = исполняемые тесты» индустрия уже проверяла: BDD и Specification by Example Гойко Аджича (2011). Взлетело частично. Ценность оказалась в разговоре при построении сценариев; артефакт (Gherkin + step definitions) стал вторым слоем поддержки, гниющим быстрее кода [7].

Проблема 1: машинно проверяемое только то, что формализуется дёшево — либо полнота (дорого), либо неполные требования [7].

Проблема 2: машина сверяет код с контрактом; контракт с намерением сверяет по-прежнему голова. Старое различие Бёма (1981): verification («правильно ли построен продукт») vs validation («тот ли продукт построен») [7].

Проблема 3: «Если enforcement/доказательство создал LLM, то это фигня, надо писать самому. Сложность из разработки перетекает в проектирование, доказательство корректности» [7].

Практика OpenSpec подтверждает: advisory verification без блокирующего gate приводит к дрейфу как дефолтному исходу. «If nothing blocks on spec/code divergence, divergence is the default outcome over time» [18].

## 4.3. Инварианты должны быть явно зафиксированы и проверяемы

Формулировка Shapiro: «Инвариант фиксирует устойчивое свойство там, где сами результаты законно меняются. Например: сумма долей равна единице, значение не растёт с возрастом когорты, у записи не больше одного значения на ключ» [2].

Кейс EPAM (brownfield, Spec Kit): конституция содержала явное правило — «NO try-catch blocks in route handlers — use global middleware». Агент его проигнорировал и добавлял try-catch. Причина: pattern-matching против миллионов кодовых баз, где try-catch в хендлерах — норма, перевесил единственную строку запрета. Фикс: усилить правило контекстом, объясняющим *почему* (middleware-based error handling даёт централизованный логгинг и консистентные error responses), а не только *что*. Глубокий урок: «Конституция — не конфиг-файл. Написать "don't do X" недостаточно. Нужно "don't do X because Y, and instead do Z". Конституция, которая работает, пишется так, будто вы онбордините умного, но буквального junior-разработчика, который никогда не видел вашу кодовую базу. Потому что это ровно то, чем агент является» [10].

## 4.4. Модель двух версий кода

Для консистентного развития системы [2]:

- **Опорная версия** — неизменная точка сравнения.
- **Рабочая версия** — машина правит происходящую от неё.
- После разбора перехода новая рабочая версия занимает место опорной.
- Приёмка относится к результату и изменениям, предъявленным человеку; фриз сохраняет выборочную часть кода как точку продолжения, включая непросмотренное.
- «По отсутствию замечания невозможно отличить просмотренное от непросмотренного. Поэтому молчание не считается согласием». Вместе с фризом фиксируется область явной приёмки; остальное — непросмотренное содержание с неизвестным статусом, не признанная норма.

Код по отношению к спеке — временный кэш [2]. Следует пересчитывать вслед за изменившейся спекой; неизменённая часть спеки сама по себе не даёт основания переписывать соответствующую часть кода. Опасность: код — не только кэш спеки, но и состояние системы, в котором разрешены конкретные развилки, не описанные в спеке. Переписав их без явного противоречия спеке, машина может изменить уже устраивавшее поведение [2].

## 4.5. Сжатые представления как индексы к кодовому снимку

Типы представлений — каждое отвечает на отдельный вопрос, не заменяет код и не копирует его [2]:

| Представление | Что фиксирует | Что обнаруживает |
|---|---|---|
| Проверка результата на закреплённом входе | Наблюдаемое поведение: на таких-то данных система дала такой-то ответ | Изменение смысла вычисления (не реагирует на переписывание реализации с тем же результатом) |
| Инвариант | Устойчивое свойство при законно меняющихся результатах | Нарушение свойства |
| Контракт границы | Имена, параметры вызовов, схему данных, формат ответа, код завершения | Поломку внешних потребителей |
| Карта понятий | Состав домена: сущности, различия, состояния | Раздвоение сущности, слипание понятий, исчезновение допустимого состояния |
| Граф связей | Кто кого вызывает | Утрату, при которой код и тест на месте, но вызывать их перестают |
| Основание решения | Почему сделано именно так и при каком условии решение перестанет быть верным | Смысл, невосстановимый из текста кода |

> «Полнота здесь не нужна. Новое представление имеет смысл заводить, если оно устойчиво при обычной работе и обнаруживает потерю, значимую для человека.» [2]

Имена внутренних функций, форматирование и прочие детали реализации отдельно не записываются: они уже в кодовом снимке, дублирование не добавляет смысла [2].

## 4.6. Контроль перехода — необходимый gate

> «Обязательная проверка перехода происходит после того, как машина объявила рабочую версию готовой, и до решения человека о приёмке и новом фризе. В долгой работе те же проверки можно запускать после промежуточных правок, но перед фризом их нельзя пропустить.» [2]

Этапы [2]:

1. До правки машина получает организованное окружение: применимую часть спеки, связанные инварианты и основания, канонические примеры с областью действия, контрольные списки, маркеры внимания.
2. Машина строит механическую разницу с опорной версией; смысловые проверки — только для изменённых мест и связанных записей.
3. Изменения разделяются минимум на: прямо заказанные, необходимые последствия заказа, произошедшие вне заказа, не поддавшиеся квалификации.
4. Отдельно ведётся ведомость допущений — места, где спека молчала и машина выбирала сама. Принятое поднимается в спеку: «удача оставляет след так же, как ошибка».
5. Человеку предъявляются только существенные или неразрешённые расхождения: «вы просили изменить А; вместе с ним изменилось Б, которое удерживало основание В; Б — необходимое следствие или отдельное решение?»
6. По каждому расхождению человек выбирает статус: отклонить и восстановить / принять без разрешения на перенос / поднять в спеку / признать каноническим образцом в названной области / отложить.
7. После решения: рабочая версия становится опорной, фриз закрепляет выбранные части, сохраняются версия спеки и карта статусов перехода.

Ограничения, отмеченные самим Шапиро [2]: квалификацию делает модель — круг «модель проверяет модель» размыкают только проверки исполнением; ведомость допущений неполна (попадает только выбор, который машина за собой заметила); механическая разница — опора, только если её кто-то читает, а сплошное чтение человеку не по силам.

## 4.7. Организованные ориентиры против наплыва

> «Канонический пример показывает, какую структуру или стиль следует переносить, а его область действия называет, где такой перенос допустим. Стандарт называет сохраняемую норму. Контрольный список задаёт места, которые машина должна последовательно обойти. Маркер внимания выделяет несущее в текущей работе. Без таких ориентиров случайный соседний код и признанный образец выглядят для машины одинаково убедительно.» [2]

Ограничение: ориентиры направляют наплыв, но не гарантируют исполнения — машина может не удержать их или предпочесть другой доступный образец. Они дополняют проверку результата, а не заменяют её [2].

## 4.8. Типичные ошибки, дорогостоящие для команды

Из сравнительного анализа фреймворков [10]:

- **SDD как waterfall.** 50-страничная спека, замороженная до имплементации — не SDD, это BDUF в Markdown. Спеки должны меняться во время имплементации; итеративный цикл — суть подхода.
- **Трёхстраничная спека без edge cases.** Красиво покрывает happy path; ничего про malformed input, downstream 500, истечение сессии. Агент имплементирует ровно то, что специфицировано. Шипите демо; ломается в первый день продакшена.
- **Зелёные тесты, неправильное поведение.** Все acceptance criteria проходят, тесты зелёные, решение не решает проблему пользователя. Acceptance criteria — прокси интента, не интент. Добавлять «Why this matters» и «Non-goals» в каждую спеку.
- **Framework shopping.** Можно сжечь спринт, сравнивая четыре фреймворка. Четыре недели реального использования на реальных тикетах научат быстрее. Выбрать из TL;DR, начать, пересмотреть через месяц.

# Часть 5. Сравнение SDD-фреймворков

Структурный анализ из сравнительной статьи [10] с disclosure автора: он не гонял все три в production; анализ построен на docs, кейсах и отчётах сообщества. Опыт ветеранов ценится выше.

## 5.1. Spec Kit (GitHub)

CLI `specify`, 90K+ звёзд, 30+ интегрированных агентов. Slash-команды: `/speckit.constitution` → `/speckit.specify` → `/speckit.plan` → `/speckit.tasks` → `/speckit.implement`. `constitution.md` — документ, на который ссылается каждая последующая спека: стратегия тестирования, security posture, стек, конвенции обработки ошибок. Greenfield-оптимизирован: branch-per-spec модель трактует спеки как change-артефакты, не долгоживущие capability-контракты. На зрелой кодовой базе каждая фича начинается с reverse-engineering; артефакты не компаундятся в system-level документацию [10].

Требует Python 3.11+ и uv [10].

## 5.2. BMAD-METHOD

Multi-agent фреймворк, 43K+ звёзд, 12+ AI-персон (Analyst → PM (PRD) → Architect → Scrum Master (stories) → Developer → QA), смоделированных как Markdown «Agent-as-Code». Каждый хендофф — versioned артефакт; audit trail из коробки; каждая decision трейсится от requirement до PR [10].

Сила для SOC 2 аудита, консалтинговых поставок, multi-team платформ. Ловушка для двух-членной команды: process multiplier, не process creator. Если у команды нет структурированных процессов, BMAD не создаст их — воспроизведёт хаос на семи агентах. Конкретные издержки: больше токенов на цикл; handoff failures — реальная поверхность дебага; когда Architect-агент делает допущение, не задокументированное PM-агентом, Scrum Master распространяет его в stories, Developer уверенно имплементирует — обнаруживается в QA или продакшене. Pipeline хорош настолько, насколько хорош слабейший хендофф [10].

Требует Node.js v20+ [10].

## 5.3. OpenSpec (Fission-AI)

Легковесный, brownfield-first, npm-пакет, 25+ ассистентов, `AGENTS.md` как «README для роботов». Дельта-маркеры ADDED/MODIFIED/REMOVED — механизм для существующих кодовых баз, предотвращающий галлюцинацию новых требований на существующее поведение. При шипинге дельты мержатся в main specs — system-level документация компаундится [10].

Ограничения: спеки не обновляются сами во время имплементации (дрейф ресинкается вручную); нет multi-agent оркестрации (один агент ведёт весь флоу); для простых задач (багфикс, копи-правка) overhead полного proposal-design-tasks цикла — «хирургия вилочным погрузчиком» [10].

## 5.4. Kiro (AWS)

VS Code fork с SDD, встроенным в IDE: генерирует requirements в EARS-нотации, технический дизайн, таски — всё внутри редактора, без CLI. Claude Sonnet через Amazon Bedrock, $20/мес. Трейдофф — vendor lock: их IDE, их model pipeline, их экосистема [10].

## 5.5. Augment Intent

Standalone desktop app (Mac, public beta на начало 2026) вокруг «living specs» — спецификаций, обновляющих себя по мере работы агентов, решающих проблему дрейфа, которую CLI-фреймворки оставляют ручной. Coordinator/specialist/verifier архитектура: несколько агентов параллельно на изолированных git worktrees, делят одну эволюционирующую спеку. Credit-based ($20–200/мес), BYOA (Claude Code, Codex, OpenCode). «Living-spec — самый интересный архитектурный bet в этом пространстве: если сработает надёжно, делает ручную реконсиляцию ненужной. Пока beta, независимая production-валидация ограничена» [10].

## 5.6. Roll your own

Если контекст проекта уже документирован (стек, стандарты, воркфлоу), четыре custom slash-команды и `AGENTS.md` дают ~80% функциональности [10]:

```
.claude/commands/
plan-feature.md       → produce spec + design from intent
break-into-tasks.md   → decompose spec into tasks
implement.md          → execute one task within your conventions
review-spec.md        → critique the spec for gaps
AGENTS.md             → project rules
```

Остальные 20% — presets Spec Kit, дельта-маркеры OpenSpec, agent handoffs BMAD — причина, почему люди используют фреймворки. Начинать custom, если фреймворки борются с вашим воркфлоу; иначе — взять фреймворк и расширить [10].

## 5.7. Рекомендации по выбору

| Ситуация | Рекомендация | Обоснование |
|---|---|---|
| Existing codebase, adding features | OpenSpec | Минимизация adoption friction, brownfield-first |
| New project from scratch | Spec Kit | Greenfield-оптимизация, конституция как ядро |
| Compliance, audit trails, regulated | BMAD | Process multiplier с audit trail из коробки |
| Не уверены | OpenSpec | Работает на greenfield и brownfield, не lock'ит |
| Мульти-репо | Stores (beta) + кастомные skills, или roll your own | Issue #725 открыт; Stores частичен |
| Простые задачи / багфиксы | Пропустить SDD | Overhead полного цикла не окупается |
| Living specs (автообновление) | Augment Intent (beta) | Самый интересный bet против дрейфа; независимая валидация ограничена |

Практический старт с OpenSpec [10]:

```
npm install -g @fission-ai/openspec
openspec init
```

Мульти-репо: `openspec store setup` → пуш в git-хост → у каждого тиммейта `openspec store register ~/openspec/<name>` [16].

# Часть 6. Опыт команд: подтверждение принципов

## 6.1. Talk Think Do

Полный цикл «внедрили → 84% AI-authored → ушли». См. раздел 1.6. Ключевой перенос: место хранения артефактов определяет, может ли остальная часть команды видеть работу и действовать на ней [5].

## 6.2. Gromilo (.net-разработчик, 4 голоса)

Дропнул OpenSpec через неделю: «Openspec хорош тем, что даёт простой, понятный процесс, но я его друпнул через неделю. Для моих задач оказался как-будто слишком плоским, как-будто для чего-то маленького, что ты можешь полностью загрузить в голову. Очень быстро получил миллион папочек со спеками, которые хз как организовывать и вообще контролировать. Я даже дельты офигел читать, не то что результат мержа» [7].

Перешёл на иерархическую структуру: общие требования → общий процесс → скоупы → внутри скоупа его требования, истории, дизайны → только там решения по модели, коду и имплементации. «При этом всё живое, списки открытых вопросов, правки спеки, решений по ходу реализации… Не могу я сначала всё придумать, а потом получить программу целиком» [7].

Позднее в треде: «Если бы мне нужно было допиливать легаси проект, обязательно был взял openspec, чтобы вносить и фиксировать изменения. Но для моих текущих задач даже "схем" недостаточно, т.к. вообще не помогают разработке в условиях неопределённости» [7]. Ссылку на openspec-schemas получил от Evgeniy Kudinov как пример вариаций SDD [7][15].

## 6.3. Dhwtj (Enterprise Architect)

«Памяти усопшего Rational Rose утверждаю: SDD и OpenSpec в частности не работают. Как не работал и сам Rational Rose. Модель и код всегда расходятся. Модель устаревает. Процесс тяжеловесен. Требования оторваны от кода. Требования нельзя полностью сформировать заранее, требования не проверяемы на корректность и совместимость машинно как компилятором» [7].

Про будущее: «Судьба SDD решится… появлением дешёвого машинного enforcement/доказательства… Тесты типы и контракты становятся спекой» [7]. Источник принципа «дешёвой формы» — см. 4.1.

## 6.4. Evgeniy Kudinov

«Зная, что ллм-агенты недетерминированные, нет 100% уверенности, что реализация соответствует тому, что описано в spec. Даже наличие тестов, которые прошли, не дают такой гарантии, и пока приходится глазами смотреть за реализацию» [7]. Про OpenSpec: «Подозреваю вы решили весь проект обработать openspec и это не рекомендуется. Но можно постепенно, по мере изменения фич и требований делать changes. Ну и настроить можно инструмент под ваши потребности, в сети уже много разных вариаций SDD для openspec» [7].

## 6.5. Hacker News практики

Отчёт из сообщества, цитируемый CodeMySpec: «When you do the sync process, it just keeps drifting and drifting until you have duplication and contradictions across specs… I've stopped doing it entirely and just archive directly after implementation… maintaining the main specs is not worth it» [3][18]. Та же нить: «AI needs to find the relevant code to change it. It's pretty easy to miss something in large codebase (especially when there is lots of legacy stuff)» [3].

# Итоговая матрица для проектирования процесса

| Принцип | Что требует | Что отвергает |
|---|---|---|
| Дешёвая форма требования | Типы, контракты, property-based тесты, примеры, ADR — по типу требования | Единую текстовую спеку для всего |
| Машинная проверка | Блокирующий gate на противоречии спека/код | Advisory verification, «доверие к модели» |
| Инварианты | Явный список, проверяемый исполнением; правило с «почему», а не только «что» | Неявные ожидания в голове оператора; конфиг-файл без rationale |
| Контроль перехода | Механическую разницу + смысловую квалификацию + решение человека по каждому расхождению | Автоматическое принятие или сплошное ручное чтение |
| Сжатые представления | Индексы к коду, каждый отвечает на отдельный вопрос | Полную вторую спеку или дублирование кода |
| Две версии кода | Опорную и рабочую с явной приёмкой и фризом; молчание ≠ согласие | Слияние «принятое» и «непросмотренное» |
| Ведомость допущений | Фиксацию удачи так же, как ошибки — подъём в спеку | Только отрицательную обратную связь |
| Экономика внимания | Автоматизацию сличения; предъявление только существенных расхождений | Объём артефактов, растущий вместе с вниманием человека |
| Место артефактов | Workspace, доступный всем ролям процесса (BA, delivery, QA, клиент) | Репозиторий как единственное место для upstream-работ |
| Планирование ≠ план | Цикл understand → act → inspect → clarify → adjust | Waterfall «спека → approve → код»; план как обязательный gate для простых задач |

# Открытые вопросы

1. **Круг «модель проверяет модель»**: квалификацию расхождений делает модель. Размыкают только проверки исполнением. Всё, что ими не покрыто, держится на доверии к модели [2].
2. **Ведомость допущений неполна**: попадает только выбор, который машина за собой заметила [2].
3. **Больше контекста — больше материала для вредного наплыва**: как отбирать окружение, чтобы случайное соседство в него не попадало, не решено [2].
4. **Эмпирики нет**: какие сжатые представления окупаются при обычной работе, не проверено [2].
5. **Полнота vs дешевизна формализации**: машинно проверяемое только то, что формализуется дёшево — либо дорогая полнота, либо неполные требования [7].
6. **Verification vs validation**: машина сверяет код с контрактом; контракт с намерением сверяет голова. Автоматизации второй сверки нет [7].
7. **Экономика под вопросом**: подготовка и поддержка спек — дополнительная работа; при высокой неопределённости затраты могут не окупиться [7].
8. **Ориентация в параллельных агентах**: понимание, что агент изменил и почему, — открытая проблема, обостряющаяся от 5 агентов к сотням. «Product-shaped hole в рынке, которую никто не заполнил» [11].
9. **Мульти-репо**: кластер issues (#662, #594, #435, #581, #697, #725) указывает на иерархию → paths → workspace как порядок, но решения нет [8].

# Приложение: практические советы

1. **Не ретро-спекать весь проект за раз.** Для legacy — инкрементальные changes по мере реальных задач; существующие PRD/SRS в Notion/Confluence использовать как исходник для `/opsx:explore`, не bulk-конвертировать (механическая конвертация 40-страничного PRD даёт спеку, которой никто не доверяет через полгода) [4].
2. **Конституция — как онбординг умного junior-разработчика.** «Не делай X, потому что Y, вместо этого делай Z». Модели следуют «почему» лучше, чем «не» [10].
3. **План — зеркало понимания, не инструкция.** «Всё что агент может превратить в план, он может просто сделать по исходным данных… Отношение к плану сменилось с "инструкции, которые агент должен сделать" на "вот как агент понял задачу". Можно свериться» [7].
4. **Коммитить весь `openspec/` в git.** Активные changes и архив — durable, versioned record того, что система делает и почему менялась, не scratch pad для удаления после merge [4].
5. **Меньше контекста — больше контроля над наплывом.** Агент, писавший commit-сообщения транслитом, ориентировался на соседние коммиты; чистка примеров помогла, новая инструкция — нет [2].
6. **Провести подготовительную работу вместо борьбы с умолчаниями.** «Мне проще провести нормальную подготовительную работу и получать более-менее предсказуемый результат, чем бороться с умолчаниями… Ощущение, что я делаю то же самое, только не в процессе написания кода, а в процессе подготовки документации для агента» [7].
