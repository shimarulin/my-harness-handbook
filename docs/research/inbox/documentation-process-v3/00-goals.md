## 1. Назначение документа

Определить цели, требования и принципы проектирования процессов разработки ПО,
которые:

- покрывают полный жизненный цикл: **идея → требования → дизайн → реализация →
  верификация → поставка → сопровождение**;
- фиксируют все значимые артефакты в **git-репозитории** (проекта или отдельном
  документационном);
- используют преимущественно **OpenSource-инструменты** и **открытые форматы**;
- следуют принципу **«сначала документ — потом код»** (docs-first);
- рассчитаны на совместную работу **людей и AI-агентов**;
- масштабируются от небольших проектов до крупных.

## 2. Проблема

Современная практика даёт разрозненные инструменты и практикы:

- **Тяжеловесные enterprise-процессы** (TOGAF, ISO 42010) — пригодны для
  крупных организаций, но избыточны для малых команд.
- **Лёгкие практики** (ADR, BDD) — хорошо работают локально, но не собраны в
  сквозной пайплайн «идея → продакшн».
- **AI-ассистированная разработка** (SDD-инструменты) — быстро развивается,
  но часто привязана к конкретным экосистемам и закрытым форматам.
- **Документация отрывается от кода** и устаревает, если не хранится рядом
  и не проверяется автоматически.

Необходима связная модель процессов, которая:

1. объединяет проверенные практики в единый пайплайн;
2. не привязывает к вендору (открытые форматы, заменяемые инструменты);
3. одинаково читаема человеком и машиной (AI-агентом);
4. деградирует изящно: для маленькой задачи — минимальный overhead,
   для крупной инициативы — полный цикл с ревью и следами решений.

## 3. Цели

### G1. Сквозной прослеживаемый пайплайн артефактов

Каждое изменение проходит через цепочку артефактов, где каждый следующий
ссылается на предыдущий:

```
Idea → PRD/Job Story → RFC/Design Doc → Spec (EARS/Gherkin) → ADR → Code → Tests → Release Notes
```

Требования:

- каждый артефакт — файл в git (Markdown/YAML/PlantUML/Mermaid);
- сквозная трассировка через явные ссылки (`prd-001`, `rfc-007`, `adr-014`);
- ни один значимый артефакт не существует только «в голове» или в чате.

### G2. Docs-first: документ опережает код

- Спецификация задачи создаётся и ревьюится **до** имплементации.
- PR без связанного артефакта (задача/спека/ADR) не принимается, кроме
  тривиальных правок (typo, hotfix) — их статус фиксируется явно.
- AI-агентам запрещено генерировать код вне контекста approved-артефактов
  (правило закрепляется в правилах агентов — см. G5).

### G3. Открытые форматы и OpenSource-инструменты

**Обязательно** (форматы):

| Формат | Назначение |
|---|---|
| Markdown | Все текстовые артефакты |
| YAML | Машинно-читаемые метаданные, YADR, конфигурации |
| PlantUML / Mermaid / D2 | Диаграммы как код |
| Gherkin | Исполняемые сценарии |
| JSON Schema / OpenAPI / AsyncAPI | Контракты API и данных |
| AsciiDoc | Опционально для крупных документационных корпусов |

**Желательно** (инструменты): OpenSource с активным сообществом и возможностью
замены без конвертации форматов (формат первичен, инструмент вторичен).

**Запрещено** vendor-lock:

- бинарные/закрытые форматы как единственный носитель артефакта;
- сервисы, не позволяющие экспорт в открытый формат;
- трекинг задач, не имеющий API и экспорта (артефакт задачи дублируется
  в репозитории, внешний трекер — только зеркало).

### G4. Human + AI collaboration

- Все артефакты пишутся в формате, одинаково удобном для чтения человеком
  и парсинга AI-агентом (структурированный Markdown, EARS, Gherkin, YAML).
- Роли разделены: **человек владеет решениями** (what & why, ADR/RFC
  approval), **AI-агент исполняет и готовит черновики** (формулирование
  спеков по инструкциям, генерация кода по спекам, сверка кода со спекой).
- Правила для агентов хранятся в репозитории (`.ai/rules`, `AGENTS.md`,
  `CLAUDE.md`) и версионируются вместе с процессами.
- Артефакты — «долговременный контекст» (durable context) для агентов:
  агенты читают спеки/ADR вместо переобъяснения в каждом промпте.

### G5. Масштабируемость процессов

Процессы имеют **уровни (scale levels)**, выбираемые per-инициатива:

| Уровень | Размер изменения | Обязательные артефакты |
|---|---|---|
| L0 | Typo/hotfix | Коммит + пометка `trivial` |
| L1 | Малое изменение | Задача (Job Story) + tasks.md |
| L2 | Фича | PRD-lite + spec + design notes |
| L3 | Крупная фича/модуль | PRD + RFC/Design Doc + Spec + ADR |
| L4 | Платформа/продукт | PRD + RFC + arc42 + ADR + BDD + Q&A |

Проект может **расти**: артефакты L1–L2 не выбрасываются, а «продвигаются»
(Job Story разворачивается в PRD; design notes оформляются в RFC).
Процесс меняется под масштаб, а не наоборот.

### G6. Воспроизводимость и живая документация

- Документация собирается/проверяется в CI (docs-as-code): lint, сборка сайта,
  рендер диаграмм, проверка ссылок.
- Исполняемые спецификации (Gherkin/EARS→tests) запускаются в CI и являются
  living documentation.
- Для исследовательских задач — принципы Research Compendium (данные+код+текст
  вместе, окружение зафиксировано).

## 4. Не-цели (Non-goals)

- **Не** строим полный enterprise-фреймворк уровня TOGAF для всех проектов —
  тяжёлые стандарты остаются опциональным L4.
- **Не** привязываемся к одному AI-харнесу (Claude Code, Copilot и т.п.) —
  процессы должны работать в любом, включая отсутствие AI.
- **Не** заменяем внешние системы (Jira, Confluence) полностью — репозиторий
  является source of truth, внешние системы могут зеркалировать.
- **Не** enforced waterfall: артефакты допускают итеративное уточнение,
  главное — след решения сохраняется.

## 5. Ограничения и принципы проектирования

| # | Принцип | Следствие |
|---|---|---|
| P1 | Git — единственный source of truth | Все артефакты — файлы в репо |
| P2 | Формат важнее инструмента | Markdown/YAML первичны, генераторы заменяемы |
| P3 | Один артефакт — одно решение (ADR) | Никаких «мегадокументов решений» |
| P4 | Структура предсказуема | Единая раскладка директорий во всех проектах |
| P5 | Автоматизируй проверку доков | CI линтит и собирает документацию |
| P6 | Минимальный overhead по умолчанию | Уровень процесса выбирается per-инициатива |
| P7 | Пишем для будущего читателя | ADR — «разговор с будущим разработчиком» |
| P8 | Человек утверждает, агент исполняет | Approval-гейты у людей |
| P9 | Обратная совместимость масштаба | L2-артефакт разворачивается в L3 без переписывания |
| P10 | Инструмент можно выкинуть | Никакой критической зависимости от одного OSS-проекта |

## 6. Критерии успеха

1. **Traceability-тест**: для любого коммита non-trivial изменения можно
   по цепочке артефактов дойти до исходной идеи/PRD.
2. **Onboarding-тест**: новый участник (или AI-агент) может по репозиторию
   понять состояние проекта без устных объяснений.
3. **Vendor-exit-тест**: замена любого инструмента (генератора сайта,
   test-раннера) не требует конвертации артефактов.
4. **Scale-тест**: задача уровня L1 выполняется с overhead ≤ 15 минут
   на документацию; задача L4 — с полным набором артефактов.
5. **AI-тест**: агент, получивший только файлы репозитория (без истории
   чатов), корректно имплементирует задачу L1–L2 по спеке.
