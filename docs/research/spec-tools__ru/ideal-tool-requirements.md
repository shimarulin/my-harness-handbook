# Требования к идеальному инструменту spec-driven разработки

## Назначение

Этот документ определяет требования к гипотетическому инструменту, который сочетает сильные стороны исследованных инструментов spec-driven разработки (SDD) и избегает их задокументированных слабостей. Каждое требование прослеживается к конкретным доказательствам из [исследовательского документа по spec-tools](./spec-tools-research.md).

**Проанализированные инструменты:** specs.md, OpenSpec, obra/superpowers, Spec Kitty, GitHub Spec Kit, BMAD, Kiro, Tessl, GSD.

**Соглашения документа:**
- Каждое функциональное требование (FR) в этом документе несёт критерии приемки. Без исключений.
- «Нетривиальное» определено в P3. Приоритет между уровнями церемонии и профилями строгости определён в FR-1.4.
- Бюджеты токенов в FR-1.1 — это **базовые линии церемонии**, применяемые при профилях строгости vibe и balanced; принудительное исполнение, обусловленное строгостью, имеет собственный ограниченный допуск (FR-1.4).
- Начиная с v2.0 этот документ является замороженной базовой версией; последующие изменения вносятся через датированные предложения об изменениях (см. примечание о стабилизации), а не через полные ревизии текста.

## Принципы проектирования

Идеальный инструмент должен удовлетворять этим незыблемым принципам:

### P1. Адаптивная церемония

Вес процесса должен масштабироваться со сложностью задачи, а не со значениями по умолчанию инструмента.

- **Доказательства:** FIRE-поток specs.md адаптирует контрольные точки (0 для простых, 1 для стандартных, 2 для критических); OpenSpec получает 5/5 за тривиальные модификации, а Spec Kitty — 2/5; Superpowers задокументирован как «overkill by design» для небольших задач; 21-агентный workflow BMAD назван «malpractice» для производственных аварий.
- **Требование:** инструмент должен поддерживать как минимум три уровня церемонии, выбираемых per-task, а не per-project.

### P2. Долговечные, но лёгкие артефакты

Артефакты должны сохраняться как проверяемые, версионированные записи, не становясь бюрократической нагрузкой.

- **Доказательства:** delta-формат OpenSpec (ADDED/MODIFIED/REMOVED) победил в независимом сравнении по качеству спецификаций; живая wiki Spec Kitty создаёт долговечную память проекта, но генерирует «46 markdown-файлов за 20 минут» (Dilger); критический анализ SDD отмечает «двойное бремя обзора (спецификации + код)».
- **Требование:** каждый артефакт должен оправдывать своё существование, служа конкретному нижестоящему потребителю (рецензент, будущая сессия, аудит или агент).

### P3. Принудительное исполнение, а не просто существование

Инструмент должен проверять, что код соответствует спецификации, а не только что файлы спецификаций существуют.

- **Доказательства:** документация OpenSpec признаёт: «он проверяет только то, что артефакты существуют, а не то, что код им соответствует»; критический анализ инструментов SDD обнаруживает, что «агенты часто игнорируют детальные спецификации»; разрыв между спецификацией и реализацией — наиболее часто цитируемый режим отказа.
- **Требование:** автоматическая проверка соответствия спецификации должна запускаться при каждом нетривиальном изменении. В этом документе **нетривиальное** означает изменение, выполненное на уровне церемонии Standard или Critical (FR-1.1); изменения уровня Trivial освобождены от обязательного принудительного исполнения, **если профиль строгости не распространяет его на них (FR-1.4)**.

### P4. Эффективность токенов

Инструмент должен минимизировать потребление токенов, не жертвуя дисциплиной.

- **Доказательства:** Superpowers v6.0.0 достиг «до 50% быстрее и до 60% дешевле» за счёт объединения рецензентов и предварительной генерации входов; OpenSpec устанавливает лимит контекста 50KB; пользователи Superpowers сообщают, что «сожгли весь мой max plan» на простых задачах; FIRE-поток specs.md использует адаптивные контрольные точки для снижения накладных расходов.
- **Требование:** инструмент должен измерять и сообщать стоимость токенов по фазам и предоставлять механизмы для её снижения без удаления ценности процесса.

### P5. Командная наблюдаемость без привязки к инструменту

Команды должны видеть активность агентов across projects, не отказываясь от существующих инструментов.

- **Доказательства:** Teamspace в Spec Kitty обеспечивает кросс-командную наблюдаемость; интеграция с трекерами сохраняет Linear/Jira авторитетными; IDE-привязка Kiro оценивается как «high» риск; OpenSpec и specs.md не имеют привязки.
- **Требование:** инструмент должен интегрироваться с существующими трекерами, чат-платформами и репозиториями кода, не требуя миграции.

### P6. Модульная композиция вместо монолита

Идеальная система — это композируемая экосистема слоёв — спецификация, планирование, исполнение, оркестрация, аудит — а не единый монолитный инструмент. Пользователи включают только нужные компоненты.

- **Доказательства:** схема `superpowers-bridge` демонстрирует композицию OpenSpec + Superpowers на практике; рекомендация spec-coding.dev — «один инструмент планирования (OpenSpec для гибких brownfield-изменений, Spec Kit для более строгого жизненного цикла) плюс Superpowers для исполнения»; обзор требований r1 утверждает, что идеальный инструмент — «не замена» исследованным инструментам, «а композиция» — OpenSpec для лёгкого управления изменениями, Superpowers для дисциплины исполнения, Spec Kitty для параллельной оркестрации, Spec Kit/specs.md для строгих спецификаций — под единой оболочкой с общими конфигурациями, общим API и git-native хранилищем.
- **Требование:** каждый слой должен быть независимо внедряемым, индивидуально отключаемым и совместимым с другими через документированные мосты или схемы. Ядро должно быть open-source, с прозрачной конфигурацией и без скрытой телеметрии.

Этот принцип разрешает бывший открытый вопрос 1 («единый инструмент vs комбинация?») в пользу композиции.

## Функциональные требования

### 1. Адаптивное управление процессом

#### FR-1.1: Выбор уровня церемонии

Инструмент должен поддерживать выбор уровня церемонии per task, а не per project.

| Уровень | Контрольные точки | Сценарии использования | Базовая линия церемонии (профили vibe и balanced) |
|---|---|---|---|
| **Trivial** | 0 | Исправления багов с чётким repro, изменения конфигурации, исправления опечаток, обновления документации | <5k токенов накладных расходов |
| **Standard** | 1-2 | Добавление функций, рефакторинг, API-эндпоинты | <20k токенов накладных расходов |
| **Critical** | Полная | Изменения безопасности, изменения модели данных, кросс-сервисная работа | <50k токенов накладных расходов |

Базовые линии церемонии покрывают накладные расходы артефактов и процесса и независимы от интенсивности принудительного исполнения: они применяются при профилях строгости **vibe** и **balanced** одинаково (vibe отличается только тем, что принудительное исполнение дисциплины рендеринга является рекомендательным, согласно FR-1.4). Профиль **strict** добавляет ограниченный допуск принудительного исполнения, определённый в FR-1.4, так что стоимость церемонии и стоимость строгости остаются независимо атрибутируемыми.

**Критерии приемки:**
- Пользователь может указать уровень церемонии одним флагом или конфигурацией
- Инструмент автоматически определяет сложность и предлагает уровень (пользователь может переопределить)
- Trivial-режим по умолчанию пропускает генерацию спецификации для задач ниже настраиваемого порога; **исключение:** когда профиль строгости (FR-1.4) требует дисциплин, зависящих от спецификации, на уровне Trivial, вместо неё генерируется минимальный встроенный артефакт критериев приемки в пределах базовой линии Trivial плюс допуск строгого принудительного исполнения
- Critical-режим требует обзора спецификации до начала реализации

**Прослеживается к:** адаптивные контрольные точки FIRE-потока specs.md; «skip it for a typo fix» OpenSpec; «bypass it explicitly for trivia» Superpowers.

#### FR-1.2: Итеративное уточнение без перезапуска

Инструмент должен позволять корректировку курса внутри функции без отбрасывания завершённой работы.

- **Доказательства:** BMAD получает 5/5 за «Mid-feature course correction», а Spec Kit — 2/5; OpenSpec позволяет редактировать любой артефакт в любое время без фазовых шлюзов; критический анализ SDD отмечает, что «агенты чрезмерно применяют или неверно интерпретируют инструкции», требуя коррекции.
- **Требование:** изменение спецификации в середине реализации должно запускать распространение дельты на затронутые задачи, а не полный перезапуск.

**Критерии приемки:**
- Изменение спецификации в середине реализации распространяется только на задачи, чьи критерии приемки оно затрагивает; незатронутые задачи и их результаты остаются неизменными
- Затронутые задачи помечаются для повторной верификации, а не регенерируются с нуля
- Распространение логируется с перечислением каждой затронутой задачи и изменённого пункта спецификации

#### FR-1.3: Исследовательский режим

Инструмент должен поддерживать исследовательскую/spike-работу без принудительной преждевременной спецификации.

- **Доказательства:** критика Superpowers отмечает: «вы исследуете, а не строите... spikes, прототипы и сессии "что вообще делает этот код" борются со структурой plan-first»; Ideation Flow specs.md (Spark → Flame → Forge) существует именно для этого.
- **Требование:** исследовательский режим должен создавать концепт-брифы, а не спецификации реализации, и не должен учитываться в spec debt проекта.

**Критерии приемки:**
- Исследовательские сессии создают только концепт-брифы; никакие спецификации реализации, планы или списки задач не генерируются
- Концепт-брифы исключены из канонической валидации spec-tree и из метрик spec debt
- Переход от исследования к реализации идёт через фазу спецификации; брифы могут быть затравкой, но не заменяют спецификации

#### FR-1.4: Профили строгости

Интенсивность принудительного исполнения отдельных дисциплин должна настраиваться независимо от веса процесса через именованные профили строгости с per-setting переопределениями.

- **Доказательства:** обзор r1 требует профилей «от vibe coding до militarized process», отмечая, что жёсткие шлюзы не должны быть обязательными для всех задач. Уровни церемонии (FR-1.1) управляют весом процесса; они сами по себе не разрешают, например, тяжёлый процесс с ослабленным TDD или лёгкий со строгим обнаружением дрейфа. Единый фиксированный набор дисциплин Superpowers — контрпример: «bypass it explicitly for trivia» — задокументированный выход.
- **Требование:** инструмент должен предоставлять именованные пресеты строгости — как минимум **vibe** (все дисциплины рекомендательны), **balanced** (значения по умолчанию уровня церемонии; базовые линии FR-1.1 применяются как указано) и **strict** (TDD и обнаружение дрейфа принудительны даже на Trivial через минимальные встроенные критерии приемки FR-1.1; состязательный обзор на всех изменениях, выполняемый как лёгкий шлюз во время merge на Trivial) — и каждый переключатель дисциплины (принуждение TDD, глубина обзора, обнаружение дрейфа, ограничения многословности) должен быть индивидуально настраиваемым с переопределением любого пресета.

  **Правило приоритета:** профили строгости переопределяют значения по умолчанию принудительного исполнения уровня церемонии (включая FR-2.2 и FR-3.2). Уровень церемонии управляет объёмом артефактов и весом процесса; эффективный профиль строгости управляет интенсивностью принудительного исполнения. Профиль никогда не меняет объём артефактов уровня церемонии сверх минимального встроенного артефакта, необходимого для того, чтобы у принудительного исполнения был референт. Заметьте, что **процессные шлюзы** уровня церемонии (например, обязательный обзор спецификации на Critical, FR-1.1) — это контрольные точки процесса, а не принудительное исполнение дисциплины, и они **не** отменяются никаким профилем: vibe делает *принудительное исполнение дисциплины* (TDD, обнаружение дрейфа, состязательный обзор) только рекомендательным.

  **Безопасность Critical-церемонии:** выбор профиля vibe для изменения, классифицированного как Critical, разрешён (полная настраиваемость намеренна), но закрыт явным предупреждением: инструмент называет дисциплины, которые станут рекомендательными против Critical-классификации изменения, и предупреждение должно быть подтверждено один раз на проект; подтверждение записывается в конфигурации (FR-6.2) и отображается при инспекции эффективной конфигурации и в отчётах миссии.

  **Допуск строгого принудительного исполнения:** строгое принудительное исполнение на уровне Trivial работает в рамках явного допуска **≤5k токенов сверх базовой линии церемонии Trivial**, отдельно детализируемого в отчётах о стоимости (FR-5.4). Это сохраняет strict+Trivial выполнимым (проверка дрейфа, merge-time шлюз и генерация критериев делят допуск), а стоимость церемонии и строгости остаётся отдельно атрибутируемой; профили vibe и balanced не затронуты.

**Критерии приемки:**
- Переключение профилей меняет только поведение принудительного исполнения; состояние проекта и артефакты не теряются и не регенерируются
- Каждый переключатель дисциплины индивидуально настраивается на уровне проекта и задачи
- Эффективная конфигурация (профиль плюс переопределения) инспектируется одной командой и хранится согласно FR-6.2
- Выбор vibe для Critical-классифицированного изменения вызывает предупреждение; продолжение требует записанного подтверждения, видимого при инспекции эффективной конфигурации
- При профиле strict на уровне Trivial: существует минимальный встроенный артефакт критериев приемки, обнаружение дрейфа работает против него, и выполняется merge-time шлюз обзора — при этом накладные расходы базовой линии церемонии остаются в бюджете FR-1.1, а накладные расходы принудительного исполнения — в допуске ≤5k, оба детализируются в отчёте о стоимости (FR-5.4)

### 2. Управление спецификациями

#### FR-2.1: Delta-спецификации

Спецификации должны использовать delta-формат (ADDED, MODIFIED, REMOVED), а не полные перезаписи.

- **Доказательства:** delta-формат OpenSpec специально создан для модификаций и победил в независимом сравнении по качеству спецификаций (4/5) против 2/5 у Spec Kit; критический анализ отмечает: «Spec-Kit требует обходного пути `/speckit.clarify`, не оптимизирован для небольших изменений».
- **Требование:** каждое изменение спецификации должно выражать только то, что меняется, с автоматическим слиянием в каноническое spec-tree при архивации.

**Критерии приемки:**
- Изменение одного поля создаёт дельту, ссылающуюся только на это поле и его требование
- Архивация сливает дельту в каноническое дерево без перезаписи незатронутых требований
- Каноническая спецификация восстановима только из истории архива

#### FR-2.2: Обнаружение дрейфа спецификации

Инструмент должен обнаруживать и предупреждать, когда реализация расходится со спецификацией.

- **Доказательства:** критический анализ определяет «spec drift over time» как нерешённый вопрос; `/opsx:verify` в OpenSpec существует именно для этого, но требует явного вызова; разрыв между спецификацией и реализацией — «наиболее часто цитируемый режим отказа».
- **Требование:** автоматическое обнаружение дрейфа должно запускаться на каждом PR для нетривиальных изменений (согласно P3). Профиль строгости может распространить принудительное исполнение на изменения уровня Trivial согласно правилу приоритета FR-1.4; значение по умолчанию уровня церемонии само по себе никогда не отключает явно принудительно исполняемую дисциплину.

**Критерии приемки:**
- Обнаружение дрейфа запускается на каждом PR для изменений Standard и Critical без ручного вызова
- При строгом профиле оно также запускается для изменений Trivial против их минимальных встроенных критериев приемки
- Расхождения сообщаются как пары «пункт спецификации ↔ местоположение кода» — ссылка на пункт спецификации плюс местоположение кода в виде файла с диапазоном строк или ссылкой на символ — в машиночитаемом отчёте и блокируют merge

#### FR-2.3: Память отклонённых предложений

Инструмент должен помнить отклонённые предложения, чтобы предотвращать повторное предложение отклонённых идей.

- **Доказательства:** документация OpenSpec признаёт, что `/opsx:archive` не имеет «выделенного статуса для отклонённого изменения, поэтому ничто не сообщает будущему предложению, что идея уже была исследована и отклонена».
- **Требование:** отклонённые изменения должны архивироваться с обоснованием и быть доступными для поиска будущими предложениями.

**Критерии приемки:**
- Отклонённое изменение архивируется с машиночитаемой записью решения, включающей причину
- Новое предложение, затрагивающее ту же область, выявляет предыдущее отклонение и его обоснование
- Отклонения доступны для поиска одной командой по требованию, дате и причине

#### FR-2.4: Контроль многословности спецификации

Инструмент должен применять ограничения длины спецификации, соответствующие области изменения.

- **Доказательства:** самая частая жалоба на OpenSpec: «ИИ генерирует гораздо больше спецификации, чем мне нужно... агент может превратить тридцатиминутную функцию в 800-строчную спецификацию»; лимит контекста 50KB заставляет соблюдать некоторую дисциплину, но «у delta-спецификаций самих по себе нет жёсткого лимита».
- **Требование:** настраиваемые лимиты размера спецификации по уровням церемонии; автоматическое помечание при превышении порогов; агент должен обосновать, почему спецификация превышает лимит.

**Критерии приемки:**
- Лимиты размера настраиваются по уровням церемонии и применяются во время генерации
- Спецификация сверх лимита помечается и не может быть финализирована без явной записи обоснования
- Лимиты по умолчанию удерживают спецификацию уровня Standard в бюджете токенов FR-1.1

#### FR-2.5: Разрешение конфликтов параллельных изменений

Инструмент должен обрабатывать несколько изменений в полёте, затрагивающих одно требование или общее состояние, с правилами разрешения, определёнными по классам конфликтов.

- **Доказательства:** задокументированный крайний случай OpenSpec: «Два изменения затронули одно требование, и одно молча отбросило сценарий другого... архивация применяет MODIFIED-дельту как замену целого блока по имени требования». Обзор r1 дополнительно отмечает конфликты в файлах общего состояния (например, `state.yaml`), когда параллельные агенты работают в отдельных worktree; первоначальная стратегия worktree-per-work-package в Spec Kitty была достаточно нестабильной, чтобы её заменили в v3.1.0.
- **Требование:** одновременные модификации должны обнаруживаться до merge/archive и разрешаться согласно классу конфликта:
  - **Class A — независимые** (разные требования, разные файлы): автослияние; никогда не блокирует
  - **Class B — одно требование** (два изменения в полёте модифицируют одно требование): требуется человеческий арбитраж до архивации; обе версии представляются со своими сценариями. Арбитр — **ответственный владелец** затронутой области, определяемый через механизм решений FR-4.1; вердикт записывается как запись решения согласно FR-4.4, а **невыбранная версия архивируется с обоснованием отклонения** (согласно FR-2.3), чтобы ни одна версия не была потеряна. **Цепочка fallback:** если ответственный владелец для затронутой области не настроен, арбитраж переходит к сопровождающим репозитория через **настраиваемое объявление владения** (хранится согласно FR-6.2): CODEOWNERS там, где платформа хостинга это поддерживает, или настроенный эквивалентный файл владения на платформах без него; если ни одно объявление владения не разрешается, архивация остаётся заблокированной с явной ошибкой, называющей отсутствующую конфигурацию и способ её задать — никогда не тихий сброс и не бесконечная необъяснимая блокировка
  - **Class C — файлы общего состояния** (например, состояние координации worktree, такое как `state.yaml`): автоматически предпринимается трёхстороннее слияние; неразрешённые конфликты эскалируются на человеческий обзор
- **Критерии приемки:**
  - Изменения Class A сливаются без взаимодействия
  - Изменения Class B всегда блокируют архивацию до арбитража; ни одна версия не отбрасывается молча; вердикт арбитража — связанный версионированный артефакт, а проигравшая версия сохраняется с обоснованием и извлекается согласно FR-2.3
  - Когда владелец не настроен, включается настроенный fallback владения (CODEOWNERS по умолчанию, эквивалентный файл владения на других платформах); когда ни одно объявление не разрешается, блокировка сопровождается ошибкой конфигурации
  - Попытки слияния Class C логируются; сбои представляют читаемый конфликт для разрешения

#### FR-2.6: Генерация greenfield-спецификаций

Инструмент должен поддерживать полную генерацию спецификаций для новых систем, а не только delta-изменения к существующим.

- **Доказательства:** Spec Kit получает 5/5 за greenfield-работу («Constitution-driven governance... purpose-built for greenfield»), а OpenSpec — 3/5 («lightweight, better suited for modifications than greenfield»); specs.md нацелен и на greenfield, и на brownfield в своих потоках; обзор r1 требует явной поддержки обоих.
- **Требование:** greenfield-режим должен создавать полные спецификации требований, дизайна и задач из проектного брифа, переиспользуя те же форматы артефактов, что и brownfield delta-спецификации, чтобы проекты могли переходить между режимами без миграции.

**Критерии приемки:**
- Greenfield-режим создаёт спецификации требований, дизайна и задач из проектного брифа за одну сессию
- Greenfield-артефакты используют те же форматы, что и brownfield delta-спецификации; миграция формата не нужна, когда проект становится brownfield
- Переход репозитория из greenfield в brownfield не требует преобразования артефактов

#### FR-2.7: Спектр формальности спецификаций

Спецификации должны поддерживать спектр формальности от лёгких заметок до формального языка требований в рамках единого источника истины.

- **Доказательства:** delta-спецификации OpenSpec используют формальный SHALL-язык сценариев («The app SHALL let users switch between light and dark themes»); критический анализ SDD отмечает сохраняющуюся путаницу о том, «где заканчиваются функциональные спецификации и начинается техническая реализация», и непоследовательную интерпретацию в инструментах; обзор r1 требует «уровней детализации: от лёгких заметок до формальных SHALL/MUST требований».
- **Требование:** шаблоны спецификаций должны поддерживать как минимум три уровня формальности — note-style, структурированный сценарий, формальный SHALL/MUST с тестируемыми критериями приемки — выбираемые per requirement и повышаемые на месте без перезаписи.

**Критерии приемки:**
- Любое требование может быть выражено на любом уровне формальности
- Требование повышается на месте (note → scenario → SHALL/MUST) без перезаписи соседних требований
- Требования формального уровня несут тестируемые критерии приемки; требования уровня заметок допустимы без них

#### FR-2.8: Надёжная валидация спецификаций

Команды валидации спецификаций должны быть детерминированными и устойчивыми; сбои валидатора никогда не должны молча пропускать или порождать ложные ошибки.

- **Доказательства:** обзор требований r1 сообщает об ошибках валидации класса «no requirement entries parsed» в существующих инструментах; OpenSpec поставляет `openspec validate` как核心 команду, делая валидатор единой точкой отказа для CI-интеграции.
- **Требование:** валидация должна давать однозначные результаты pass/fail с указанием местоположения ошибок на offending lines; сбои валидации должны блокировать archive/merge. Валидатор должен поставляться с регрессионным набором, покрывающим **каждый задокументированный класс сбоев** (включая сбои парсинга класса «no requirement entries parsed»), минимум один тест на класс; классы сбоев, обнаруженные в реальной эксплуатации, должны добавляться в набор до следующего релиза.

**Критерии приемки:**
- CI запускает регрессионный набор валидатора при каждом релизе
- Ни один задокументированный класс сбоев не остаётся без регрессионного теста
- Ошибки валидатора указывают файл и строку; спецификация, которая не парсится, никогда не может валидироваться как true

#### FR-2.9: Монорепозитории и иерархические стандарты

Инструмент должен поддерживать монорепозитории с вложенными проектами, независимой конфигурацией каждого модуля и без раздувания инструкций.

- **Доказательства:** FIRE-поток specs.md обеспечивает «hierarchical standards with module-specific overrides. One project, multiple tech stacks»; лимит контекста 50KB в OpenSpec — частичная мера, но не дизайн для монорепозитория; обзор r1 явно требует вложенных проектов с независимыми конфигурациями и без «instruction growth».
- **Требование:** конфигурация подпроекта должна наследовать и переопределять стандарты уровня репозитория; контекст, инжектируемый агентам, должен ограничиваться затронутым модулем и его предками; несвязанные соседние модули не должны раздувать контекст работы над данным модулем.

**Критерии приемки:**
- Контекст модуля содержит его собственные стандарты плюс унаследованные стандарты репозитория и не содержит стандартов соседних модулей
- Добавление соседнего модуля не меняет полезную нагрузку контекста работы над существующим модулем
- Переопределения на уровне модуля выражаются без редактирования значений по умолчанию уровня репозитория

#### FR-2.10: Прогрессивная детализация

Спецификациям должно быть разрешено начинаться неполными и детализироваться итеративно; неизвестные должны явно помечаться, никогда не угадываться.

- **Доказательства:** шаблоны Spec Kit «flag unknowns as NEEDS CLARIFICATION rather than guessing» — самая сильная существующая реализация этого паттерна; обзор r1 требует, чтобы инструмент «не требовал исчерпывающих данных в начале — контекст должен строиться итеративно». Контраст с потоками elicitation, которые требуют полноты до начала любой работы.
- **Требование:** спецификация, содержащая явно помеченные неизвестные, должна быть валидной, а её известные части — реализуемыми. Неизвестные должны использовать стандартный, доступный для поиска маркер; агенты никогда не должны разрешать их молча. Задачи реализации, зависящие от неразрешённых неизвестных, должны блокироваться до разрешения. **Механизм разрешения:** помеченное неизвестное может быть разрешено только через поток разрешения инструмента, который требует атрибуции пользователя и записывает запись решения (кто разрешил, когда и источник ответа, согласно FR-4.4).

**Критерии приемки:**
- Спецификация с помеченными неизвестными проходит валидацию и реализуема для известных требований
- Разрешение неизвестного через поток разрешения обновляет спецификацию на месте через дельту и записывает атрибутированную запись решения
- Задачи, заблокированные на неизвестных, сообщают блокирующий маркер
- Дельта, удаляющая маркер неизвестного без соответствующей атрибутированной записи решения, не проходит валидацию (тихое разрешение обнаружимо и отклоняется)

#### FR-2.11: Без псевдокода в бизнес-ориентированных спецификациях

Бизнес-ориентированные слои спецификации не должны содержать псевдокод или нотацию, похожую на реализацию.

- **Доказательства:** обзор r1 требует «Markdown + schemas, but without sliding into pseudocode»; критика Dilger документирует неспособность бизнес-заинтересованных сторон взаимодействовать с выводом инструмента. На практике агенты часто превращают спецификации требований в псевдокод, что подрывает plain-language review FR-7.3.
- **Требование:** бизнес-ориентированные слои спецификации (требования, сценарии, критерии приемки) не должны содержать псевдокод, кодоподобную нотацию или язык реализации. Детали реализации принадлежат исключительно слоям плана и задач.

**Критерии приемки:**
- Линтинг спецификаций помечает псевдокодоподобные конструкции в бизнес-ориентированных слоях
- Plain-language резюме генерируются без кодовой нотации
- Бизнес-ориентированные и технические артефакты структурно разделены (отдельные файлы или разделы)

### 3. Исполнение и обеспечение качества

#### FR-3.1: Контекстный запуск навыков

Навыки дисциплины должны запускаться автоматически на основе контекста, а не требовать явного вызова.

- **Доказательства:** модель автотриггеров Superpowers хвалят: «Агент не *решает* брейнштормить; навык brainstorming срабатывает, потому что пользователь упомянул расплывчатую идею»; контраст с Spec Kit: «человек набирает `/speckit.plan`. Явно, детерминированно».
- **Требование:** как минимум 80% навыков дисциплины должны автотриггериться; пользователи должны иметь возможность принудительно запустить любой навык явно. Частота автотриггеров измеряется на референсном корпусе репрезентативных задач как доля применимых вызовов навыков, происходящих без явной пользовательской команды.

**Критерии приемки:**
- На референсном корпусе ≥80% применимых вызовов навыков происходят без явной пользовательской команды
- Каждый навык дисциплины может быть принудительно запущен явной командой
- Решения о триггерах логируются, чтобы частота была аудируемой

#### FR-3.2: Обязательный TDD (настраиваемый)

Test-Driven Development должен принудительно применяться по умолчанию для стандартного и критического уровней церемонии, с возможностью отказа для тривиального.

- **Доказательства:** «Iron Law» TDD в Superpowers — его определяющая характеристика: «No production code without a failing test first»; контролируемое сравнение показало лучшее качество вывода на нетривиальных задачах при принуждении TDD.
- **Требование:** принуждение TDD должно быть включено по умолчанию, настраиваться per-project и per-task (в том числе через профили строгости, FR-1.4), с автоматическим удалением кода реализации, написанного до тестов.

**Критерии приемки:**
- При принудительном профиле и уровне церемонии код реализации, написанный до падающего теста, удаляется или блокируется от слияния
- Отказы на уровне задачи записываются в журнал миссии с указанием отказавшегося пользователя
- При профиле vibe принуждение рекомендательное: нарушения предупреждают, но не блокируют

#### FR-3.3: Изоляция субагентов с наследованием правил

Каждая задача реализации должна выполняться в изолированном контексте, но субагенты должны наследовать правила управления и определённый минимальный пакет контекста от родительской сессии.

- **Доказательства:** subagent-driven development в Superpowers назван «блестящим решением проблемы context collapse. Каждый субагент знает только о своей конкретной задаче, что мешает ему запутаться в предыдущих шагах или несвязанном коде». Однако собственный bootstrap `using-superpowers` в Superpowers предписывает: «Если вы были отправлены как субагент для выполнения конкретной задачи, игнорируйте этот навык» — субагенты явно освобождены от bootstrap дисциплины, создавая именно тот разрыв, который выявляет обзор r1 (субагенты игнорируют TDD и другие ограничения).
- **Требование:** задачи должны выполняться в изолированных субагентах; результаты субагентов должны проверяться до слияния в основной контекст. **Изоляция применяется к накопленному контексту сессии, но не к управлению.** Каждый субагент должен наследовать как минимум:
  1. Конституцию/доктрину проекта
  2. Настройки принуждения дисциплины (TDD и эффективный профиль строгости, FR-1.4)
  3. Границы области и определение задачи
  4. Конфигурацию interrupt-триггеров (FR-3.6), чтобы отклонения внутри субагента останавливали его так же, как родительскую сессию
  5. Стандарты кодирования и безопасности
  6. Релевантные дельты спецификации для задачи

  Каждый субагент должен получать **минимальный пакет контекста**: определение задачи, затронутые дельты спецификации и интерфейсные контракты модулей, которых касается задача. Накопленная история сессии и контекст несвязанных задач должны исключаться. Наследование управления может поставляться в компактной **digest-форме** (полные тексты конституции и стандартов остаются доступными по запросу), чтобы удерживать инжектируемый контекст в границах.
- **Критерии приемки:**
  - Промпты субагентов проверяемо содержат конституцию (или её digest) и эффективные настройки принуждения
  - Субагент, пытающийся пропустить TDD при принудительном профиле, блокируется
  - Общий инжектируемый контекст субагента — наследование управления плюс минимальный пакет контекста — ограничен: он не должен превышать **большее из 2 000 токенов или 15% эффективного бюджета токенов задачи** (применимая базовая линия церемонии FR-1.1 плюс любой активный допуск строгости FR-1.4), считаясь внутри этого бюджета, а не в дополнение к нему; его стоимость токенов сообщается согласно FR-5.4
  - Никакой всегда загружаемый bootstrap не инжектируется в контекст субагента: правила управления прикрепляются per-task к пакету контекста, а накладные расходы наследования per-task измеряются и сообщаются согласно FR-5.4 (вопрос минимизации этих накладных расходов остаётся открытым вопросом 6)

#### FR-3.4: Состязательный обзор (не подтверждающий)

Обзор плана и спецификации должен пытаться сломать план, а не просто подтверждать полноту.

- **Доказательства:** GitHub issue #1803 по Superpowers: «Встроенный self-review writing-plans подтверждающий — он проверяет покрытие, типы и placeholder’ы. Он не пытается сломать план... Claude в "completion state" создаёт планы, которые выглядят правильными, но содержат тихие сбои».
- **Требование:** фаза обзора должна явно инструктировать рецензента трассировать промежуточные состояния, мысленно выполнять команды и проверять допущения против реальной кодовой базы.

**Критерии приемки:**
- Промпты обзора инструктируют рецензента пытаться сломать план, а не просто подтверждать покрытие
- Непроверенные shell-команды и допущения об окружении выявляются как находки
- Находки категоризируются по типу исправления (поверхностное исправление, архитектурная проблема, неверная проблема)

#### FR-3.5: Руководство по очистке контекста

Инструмент должен указывать, когда контекст можно безопасно очистить между фазами.

- **Доказательства:** Superpowers issue #655: «Он не даёт руководства о том, когда контекст можно безопасно очистить (/clear) между фазами. От начала до конца он оставался в одном контексте... 80k токенов балласта, которые ухудшат точность будущей генерации?»
- **Требование:** после завершения каждой фазы инструмент должен указывать, можно ли очистить контекст и какое минимальное состояние должно быть сохранено.

**Критерии приемки:**
- При завершении каждой фазы инструмент сообщает, можно ли очистить контекст, без запроса
- Сохраняемое минимальное состояние (пути файлов, указатель миссии, активные дельты) перечисляется в руководстве
- Возобновление из очищенного контекста не теряет состояние миссии

#### FR-3.6: Прерывания с участием человека

Агент должен останавливаться и спрашивать, когда реализация отклоняется от плана или сталкивается с неожиданными ограничениями.

- **Доказательства:** Superpowers issue #655: «Claude Code, похоже, обычно несётся сам, никогда не останавливаясь, чтобы спросить меня, если что-то идёт не по плану... Claude продолжал пытаться YOLO-ить, играясь с критическими аргументами».
- **Требование:** настраиваемые триггеры прерываний для: отклонения от плана, ошибок внешних инструментов, инвалидации допущений и расширения области.

**Критерии приемки:**
- Каждое условие триггера (отклонение от плана, ошибка внешнего инструмента, инвалидация допущения, расширение области) останавливает агента с вопросом, а не автономным обходом
- Возобновление требует ответа пользователя; обмен логируется
- Триггеры индивидуально включаются/отключаются per project и per task

#### FR-3.7: Навык систематической отладки

Навык systematic-debugging должен автотриггериться на ошибках и требовать анализа первопричины до попыток исправления.

- **Доказательства:** Superpowers поставляет `systematic-debugging` и `verification-before-completion` среди своих核心 навыков; обзор r1 перечисляет систематическую отладку среди обязательных инженерных дисциплин наряду с TDD, верификацией и обзором.
- **Требование:** навык отладки должен срабатывать автоматически, когда агент сталкивается с ошибкой или падающим тестом, и должен требовать последовательность: воспроизвести → изолировать → выдвинуть гипотезу → проверить гипотезу → исправить → верифицировать. Исправления, предпринятые без воспроизведения, должны отклоняться.

**Критерии приемки:**
- Навык срабатывает при обнаружении ошибки без вызова пользователем
- Предложения исправлений без шага воспроизведения отклоняются workflow
- Вызовы создают артефакт debug-log, связанный с задачей (FR-4.6)

### 4. Командная коллаборация и управление

#### FR-4.1: Моменты решений с маршрутизацией заинтересованных сторон

Важные решения должны выноситься соответствующим заинтересованным сторонам до продолжения агентом.

- **Доказательства:** Decision Moments в Spec Kitty «расширяют эти моменты, перемещая вопрос в ветку Slack или Teams, чтобы люди, которым нужно участвовать, могли высказаться до продолжения агентом».
- **Требование:** решения, влияющие на политику развёртывания, язык предметной области, архитектуру, влияние на клиентов или стратегию миграции, должны маршрутизироваться к accountable/consulted/informed сторонам.

**Критерии приемки:**
- Решения в перечисленных категориях маршрутизируются назначенным заинтересованным сторонам (через чат-ветку или эквивалент) до продолжения агентом
- Цели маршрутизации настраиваются по категории решения
- Неразрешённое решение блокирует агента; блокировка и её разрешение логируются

#### FR-4.2: Кросс-командная наблюдаемость (условный дашборд)

Там, где дашборд включён, он должен показывать активность миссий агентов; те же данные должны быть доступны через CLI и API независимо от использования дашборда.

- **Доказательства:** Teamspace в Spec Kitty: «показывает, какие миссии Spec Kitty выполняются в каких сборках каких проектов, в каком они состоянии и как эта работа связана с каноническим трекером и репозиторием команды».
- **Требование:** где включён, дашборд должен показывать активные миссии, их состояние, владельца, блокеры и связь с тикетами трекера. Все данные наблюдаемости должны быть в равной степени доступны через CLI-команды и query API независимо от дашборда (согласно FR-6.4). Различаются два компонента: **локальный дашборд** (один репозиторий, офлайн-способный, читает состояние репозитория) и опциональный **командный дашборд** (кросс-репозиторная агрегация, сетевой; его недоступность не должна влиять на локальную работу, согласно NFR-2).
- **Критерии приемки:**
  - CLI-команда перечисляет все миссии с состоянием, владельцем и блокерами
  - Локальный дашборд работает без сетевого подключения
  - Отключение дашборда не удаляет никаких возможностей: все данные остаются достижимыми через CLI/API
  - Отдельные состояния workflow — включая arbitration-pending и escalation-pending (FR-2.5, FR-8.4) — индивидуально видимы и фильтруемы

#### FR-4.3: Сохранение авторитета трекера

Внешние трекеры (Linear, Jira, GitHub Issues) должны оставаться источником истины для статуса работы.

- **Доказательства:** дизайн Spec Kitty: «разработчик может вытащить тикет из Linear или Jira в Spec Kitty CLI и превратить его в полную миссию... Пока работа реализуется, Spec Kitty поддерживает тикет обновлённым, чтобы обычный трекер команды оставался полезным».
- **Требование:** двусторонняя синхронизация как минимум с Linear, Jira и GitHub Issues; статус трекера должен обновляться автоматически по мере прогресса работы агента. Синхронизация трекера **opt-in для каждой интеграции**: согласие записывается как версионированный файл репозитория (NFR-3), действия синхронизации логируются, согласие можно отозвать в любой момент — отзыв останавливает синхронизацию без потери данных. Глобальный сетевой kill switch (NFR-3) переопределяет все per-integration согласия, пока активен; конфигурации согласия сохраняются и снова вступают в силу, когда kill switch снят.

**Критерии приемки:**
- Статус тикета трекера отражает состояние миссии без ручных правок, в обоих направлениях (ticket → mission, mission → ticket)
- Согласие каждой интеграции — отдельный, версионированный, проверяемый файл; его отзыв останавливает синхронизацию этой интеграции без потери состояния репозитория
- Активация kill switch останавливает всю opted-in синхронизацию, сохраняя файлы согласия для повторного включения
- Каждое действие синхронизации логируется с отметкой времени и направлением

#### FR-4.4: Живая память проекта

Инструмент должен поддерживать доступную для поиска, долговечную запись решений, спецификаций и доказательств.

- **Доказательства:** wiki `kitty-specs` в Spec Kitty: «specs, plans, evidence, review trails, and Decision Moment ADRs... не просто церемония. Они — живая wiki о том, как изменяется программное обеспечение»; сравнение с поддержкой Karpathy «LLM-maintained Markdown knowledge bases».
- **Требование:** все решения, спецификации, планы и результаты обзора должны храниться как версионированные, доступные для поиска, связанные артефакты в репозитории.

**Критерии приемки:**
- Каждое решение, спецификация, план и результат обзора существует как версионированный связанный артефакт в репозитории
- Артефакты доступны для поиска по содержимому и навигации по графу ссылок
- Ни одно решение или результат обзора не существует только в истории чата или эфемерном состоянии

#### FR-4.5: Онбординг и восстановление контекста

Новые члены команды и свежие сессии должны иметь возможность восстановить контекст проекта из артефактов.

- **Доказательства:** критический анализ SDD отмечает «long-term maintenance: unclear maintenance story, risk of spec drift, may abandon specs after initial development»; механизм архивации OpenSpec создаёт долговечное описание текущего состояния.
- **Требование:** одна команда должна генерировать исчерпывающее резюме контекста проекта из сохранённых артефактов, достаточное для новой сессии или члена команды, чтобы понять текущее состояние.

**Критерии приемки:**
- Одна команда создаёт резюме контекста, охватывающее активные миссии, текущие спецификации, открытые решения и недавние изменения
- Резюме генерируется полностью из сохранённых артефактов — история сессии не требуется
- Свежая сессия, возобновлённая только из резюме, может продолжить миссию в полёте

#### FR-4.6: Отчётность о прослеживаемости

Инструмент должен обеспечивать запрашиваемую прослеживаемость: что было построено, кем (каким агентом или человеком) и на основе каких требований и решений.

- **Доказательства:** Spec Kitty позиционирует себя как обеспечивающий «auditable delivery record from first decision to merge»; критический анализ SDD перечисляет «who maintains specifications during bug fixes?» среди нерешённых вопросов; обзор r1 требует видимых метрик «who/what/why».
- **Требование:** каждое слитое изменение должно связываться с исходным требованием(ями), записями решений, которые его сформировали, реализующим агентом/сессией и вердиктами обзора. Одна команда должна создавать отчёт о прослеживаемости для любого артефакта или требования.

**Критерии приемки:**
- Каждое слитое изменение связывается с исходным требованием(ями), записями решений, реализующей сессией и вердиктами обзора
- Одна команда создаёт отчёт о прослеживаемости в обоих направлениях (requirement → changes → code; code → change → requirement)
- Битые ссылки валят CI

### 5. Эффективность токенов и контекста

#### FR-5.1: Фазовые бюджеты токенов

Каждая фаза должна иметь настраиваемые бюджеты токенов с оповещениями при превышении.

- **Доказательства:** история оптимизации Superpowers: v5.0.6 удалил циклы обзора субагентов после «~25 минут накладных расходов без измеримого выигрыша в качестве»; v6.0.0 достиг «до 50% быстрее и до 60% дешевле»; однако «никакая оптимизация не делает design interview бесплатным».
- **Требование:** использование токенов должно отслеживаться по фазам; оповещения должны срабатывать при превышении бюджета; инструмент должен предлагать, какую фазу упростить.

**Критерии приемки:**
- Бюджеты по фазам настраиваются, фактическое использование записывается по фазам
- Превышение бюджета поднимает оповещение с указанием превышенной фазы
- Оповещение включает предложение, какую фазу упростить или пропустить

#### FR-5.2: Прогрессивное раскрытие

На каждой фазе должен загружаться только релевантный контекст, а не полное состояние проекта.

- **Доказательства:** прогрессивное раскрытие Superpowers: «~100 токенов на навык для всегда загружаемых метаданных, тела навыков менее 5k токенов загружаются только по триггеру»; задокументированный подход Anthropic.
- **Требование:** инъекция контекста должна ограничиваться текущей задачей; нерелевантное состояние проекта не должно занимать окно контекста.

**Критерии приемки:**
- Полезная нагрузка контекста для задачи содержит только релевантные задачи дельты спецификации, планы и стандарты
- Неактивные навыки стоят только своих всегда загружаемых метаданных (ограниченных, per-skill)
- Инжектированный контекст для несвязанных модулей или миссий измеримо равен нулю

#### FR-5.3: Изоляция worktree с очисткой

Параллельная работа должна использовать изолированные worktree с автоматической очисткой при слиянии.

- **Доказательства:** Spec Kitty стала пионером «built-in git worktree support among SDD tools... Automatic worktree creation per feature, Parallel feature isolation without branch switching, Automated cleanup on merge»; Superpowers «Using Git Worktrees: Isolated branches with verified test baselines».
- **Требование:** управление worktree должно быть автоматическим, с настраиваемой стратегией (per-feature или per-swim-lane) и очисткой по завершении.

**Критерии приемки:**
- Параллельные задачи получают изолированные worktree и ветки без ручных git-команд
- Слияние (или отклонение) автоматически запускает очистку worktree и ветки
- Стратегия настраивается per project; после завершения миссии не остаётся осиротевших worktree

#### FR-5.4: Отчётность о стоимости

Инструмент должен сообщать стоимость токенов и времени per mission, phase и task.

- **Доказательства:** анализ «hidden costs of spec-driven development» выделяет шесть типов затрат, которые команды забывают отслеживать; контролируемое сравнение MCP.Directory обнаружило «runs 9% cheaper with 14% fewer tokens» на нетривиальных задачах.
- **Требование:** пост-миссионные отчёты должны включать: общее количество токенов, токены по фазам, прошедшее время и сравнение с базовой линией проекта.

**Критерии приемки:**
- Каждая завершённая миссия создаёт отчёт с общим количеством токенов, токенами по фазам и прошедшим временем
- Отчёт включает сравнение с текущей базовой линией проекта
- Накладные расходы пакета контекста субагента (FR-3.3) детализируются в отчёте
- Где активен профиль строгости, накладные расходы принудительного исполнения, обусловленные строгостью (например, допуск Trivial из FR-1.4), детализируются отдельно от накладных расходов базовой линии церемонии

#### FR-5.5: Кэширование и суммаризация контекста

Инструмент должен снижать потребление токенов через кэширование и суммаризацию ранее установленного контекста.

- **Доказательства:** Superpowers v6.0.0 достиг «до 50% быстрее и до 60% дешевле» частично за счёт предварительной генерации входов обзора; прогрессивное раскрытие делает неактивные навыки дешёвыми; обзор r1 явно требует «selective context loading, caching, summarization».
- **Требование:** выходы фаз должны кэшироваться и переиспользоваться между сессиями, где не изменились; долгоживущий контекст должен суммаризироваться в компактную форму для нижестоящих фаз; инвалидация кэша должна быть автоматической при изменении спецификации или плана.

**Критерии приемки:**
- Повторный запуск неизменённой фазы потребляет <10% токенов исходной генерации
- Кэш автоматически инвалидируется при изменении входов спецификации или плана
- Суммаризированный контекст явно помечен и отличим от первичных артефактов

### 6. Интеграция и переносимость

#### FR-6.1: Поддержка множества агентов

Инструмент должен работать как минимум с 10 AI-ассистентами кодирования без привязки.

- **Доказательства:** OpenSpec поддерживает «30+ assistants including Claude Code, Cursor, GitHub Copilot, Gemini CLI, Codex, Kiro, and OpenCode»; Superpowers имеет first-class плагины для нескольких harness (Antigravity, Codex, Cursor, Devin CLI, Gemini CLI, GitHub Copilot CLI, OpenCode, Qwen Code и другие); привязка Kiro оценивается как «high» риск.
- **Требование:** поддержка Claude Code, Cursor, GitHub Copilot, Gemini CLI, Codex, OpenCode, Windsurf, Antigravity, Devin CLI и Qwen Code — как минимум 10 именованных ассистентов — плюс расширяемая архитектура плагинов для других.

**Критерии приемки:**
- Каждый именованный ассистент поддерживается через документированную интеграцию
- Добавление нового ассистента не требует изменений ядра, только плагин
- Ни одна возможность не является эксклюзивной для одного ассистента

#### FR-6.2: Репозиторно-нативное хранение и конфигурация

Все артефакты и вся конфигурация должны жить в репозитории как версионируемые файлы.

- **Доказательства:** Spec Kitty: «specs, plans, work packages, acceptance criteria, decision records, review state, and merge status become repo-native artifacts, not ephemeral chat»; OpenSpec: «commit the whole `openspec/` folder to git»; обзор r1 требует, чтобы конфигурация была версионированной и проверяемой, без скрытого глобального состояния.
- **Требование:** никакая внешняя база данных или сервис не требуются для核心 функциональности; всё состояние восстановимо из git. **Вся конфигурация** — значения по умолчанию церемонии, профили строгости, настройки интеграций, согласие на телеметрию, объявления владения (FR-2.5) — также должна храниться как версионируемые файлы в репозитории; никакое скрытое глобальное состояние вне репозитория не может влиять на поведение проекта.
- **Критерии приемки:**
  - Клонирование репозитория воспроизводит полное поведение инструмента
  - Изменения конфигурации проходят code review как любое другое изменение
  - Никакое состояние инструмента вне репозитория и git-кэшей не влияет на семантику

#### FR-6.3: Поддержка мостов/комбинаций

Инструмент должен поддерживать комбинацию с complementary инструментами через документированные схемы или мосты.

- **Доказательства:** схема `superpowers-bridge` для OpenSpec перенаправляет вывод Superpowers в папки изменений OpenSpec; spec-coding.dev рекомендует «один инструмент планирования (OpenSpec для гибких brownfield-изменений, Spec Kit для более строгого жизненного цикла) плюс Superpowers для исполнения».
- **Требование:** механизмы экспорта/импорта артефактов спецификаций; документированные паттерны комбинации как минимум с Superpowers и OpenSpec.

**Критерии приемки:**
- Артефакты спецификаций экспортируются и повторно импортируются без потерь (round-trip сохраняет семантику)
- Существует документированная, протестированная комбинация как минимум с OpenSpec и с Superpowers
- Комбинация избегает дублирующихся артефактов: один designated home на тип артефакта

#### FR-6.4: CLI-first с опциональным дашбордом

Ключевая функциональность должна полностью работать из CLI; дашборды — опциональные улучшения.

- **Доказательства:** OpenSpec — «a free, open-source CLI... does not write code by itself or replace Claude Code, Codex, Cursor, or GitHub Copilot»; дашборд Spec Kitty — «visual kanban boards tracking work progress», но CLI-first.
- **Требование:** все операции должны быть скриптуемыми; дашборд должен быть опциональным слоем, а не зависимостью.

**Критерии приемки:**
- Каждая операция выражается CLI-командой (в том числе в CI)
- Удаление или отсутствие установки дашборда не теряет возможностей
- Состояние дашборда выводится из состояния репозитория, а не хранится только в дашборде

#### FR-6.5: Работа независимо от IDE

Инструмент должен работать из любого редактора или без редактора вообще; никакая функциональность не может требовать специализированной IDE.

- **Доказательства:** матрица сравнения specs.md оценивает IDE-привязку Kiro как «High — Kiro IDE + Claude Sonnet only», а все CLI-инструменты — «None (any IDE)»; обзор r1 явно требует IDE-agnostic operation.
- **Требование:** все функции должны быть доступны через CLI и стандартные форматы файлов; расширения IDE, где предлагаются, должны быть дополнительными удобствами и никогда единственным путём к возможности.
- **Критерии приемки:**
  - Каждая функция доступна через CLI и файлы
  - Расширения IDE добавляют только удобство; удаление расширения не теряет возможностей
  - Документированная матрица feature × access-path не показывает IDE-only ячеек

#### FR-6.6: Дисциплина документации и именования команд

Документация должна включать примеры и руководства по миграции; имена команд должны быть однозначными и без конфликтов, с единой унифицированной политикой устаревания.

- **Доказательства:** самая частая критика namespace OpenSpec: «Why `/opsx:*`? This is awkward, hard to remember because 'opsx' is not 'openspec', so I have to take a minute to think about what I'm writing»; spec-coding.dev предупреждает, что отслеживаемые инструменты «ship new releases every few weeks, so treat the command names as current rather than permanent».
- **Требование:** пространства имён команд должны быть согласованы с именем инструмента; каждая команда должна иметь документацию `--help`. **Унифицированная политика устаревания (соблюдение — обязательство проекта, PG-1):** уведомления об устаревании должны появляться как минимум за одну минорную версию до удаления, а устаревшие команды/алиасы должны оставаться функциональными как минимум через одну мажорную версию. Каждое ломающее изменение должно поставляться с руководством по миграции.

  Разделение верификации: критерии приемки ниже проверяют **поведение продукта на релиз** (старое имя остаётся функциональным в релизе после переименования). Продольное соблюдение на протяжении истории релизов проекта — обязательство проекта, проверяемое в PG-1.
- **Критерии приемки:**
  - Переименованные команды сохраняют старые имена функциональными через одну мажорную версию, выдавая предупреждения об устаревании
  - Каждая команда документирует использование и примеры через `--help`
  - Примечания к релизу для ломающих изменений ссылаются на руководство по миграции

#### FR-6.7: Независимость от облака и SaaS

Сам инструмент не должен требовать конкретного облака, SaaS или хостинга; собственные операции инструмента должны быть независимы от сети. Сетевые потребности AI-ассистента — забота ассистента, а не привязка инструмента.

- **Доказательства:** привязка Kiro оценивается как «high — Kiro IDE + Claude Sonnet only»; обзор r1 расширяет независимость от вендора за пределы AI-агента и IDE на облако: «инструмент не должен диктовать конкретного AI-агента, IDE или облако». Обзор v1.2 отмечает, что первоначальная формулировка («full workflow with zero network dependency») была недостижима, поскольку реализация обычно выполняется облачными ассистентами.
- **Требование:** все нативные операции инструмента (написание спецификаций, валидация, архивация, бухгалтерия оркестрации, локальный дашборд, обнаружение дрейфа) должны завершаться без исходящей сети от самого инструмента. Инструмент должен работать с любым ассистентом, локальным или облачным; никакая функция не может требовать конкретного облачного провайдера или хостингового сервиса. Любые хостинговые функции (командный дашборд, кросс-репозиторная синхронизация) должны быть опциональными add-on с локальными альтернативами или graceful degradation.
- **Критерии приемки:**
  - **Настройка офлайн-теста:** тестовый стенд блокирует egress процесса инструмента, разрешая egress ассистента. На Linux (эталонная CI-среда) это выделенный network namespace или политика блокировки egress, применённая к процессу инструмента; на других платформах допустимы эквивалентные механизмы (например, правила pf на macOS, правила Windows Firewall) — инвариант: «egress инструмента заблокирован, egress ассистента разрешён». Все нативные операции инструмента должны завершаться под этим стендом
  - Инструмент работает одинаково с локальным и облачным ассистентом
  - Ни одна функция не требует конкретного облачного аккаунта; хостинговые функции чисто деградируют с уведомлением

#### FR-6.8: Безопасный общественный маркетплейс

Общественный маркетплейс схем/навыков должен обеспечивать подпись, верификацию, раскрытие разрешений и песочницу исполнения.

- **Доказательства:** каталог общественных схем OpenSpec (где указан `superpowers-bridge`) демонстрирует паттерн маркетплейса; обзор v1.1 отмечает, что общественные навыки/схемы — исполняемый контент (код и промпты) и требуют подписи, верификации, песочницы и политики обзора.
- **Требование:** элементы маркетплейса должны быть криптографически подписаны и проверяться при установке (неподписанные элементы по умолчанию отказываются устанавливаться); установки должны раскрывать запрашиваемые разрешения; навыки должны исполняться в песочнице с least privilege — без сетевого или файлового доступа за пределами объявленных областей — а нарушения области должны блокироваться и логироваться; политика обзора контролирует листинги.
- **Критерии приемки:**
  - Неподписанные элементы маркетплейса не могут быть установлены при настройках по умолчанию
  - Раскрытие разрешений при установке предшествует любому предоставлению
  - Нарушения области песочницы блокируются и логируются
  - Листинги несут статус обзора; нерассмотренные элементы помечаются как таковые

### 7. Опыт разработчика

#### FR-7.1: Elicitation от проблемы

Интервью для спецификации должно понимать проблему до предложения технических решений.

- **Доказательства:** критика Martin Dilger в адрес Spec Kitty: «Третий вопрос уже был о tech stack. Это меня смутило. Не должны ли мы потратить больше времени на понимание проблемы сначала? Затем он почти сразу выдал "domain model"... до того, как у него появилось реальное понимание проблемы».
- **Требование:** elicitation должен следовать структурированной последовательности: понимание проблемы → моделирование предметной области → выявление ограничений → технический подход. Вопросы о tech stack не должны появляться до подтверждения понимания проблемы.

**Критерии приемки:**
- Последовательность elicitation соблюдается: вопросы о техническом подходе блокируются до записи понимания проблемы
- Транскрипт сессии показывает фазу каждого вопроса
- Попытка перескочить вперёд (например, к tech stack) до подтверждения отклоняется или помечается

#### FR-7.2: Структурированный поток вопросов

Вопросы должны следовать логическим границам предметной области, а не перескакивать произвольно между функциями.

- **Доказательства:** Dilger: «Требования охватывали несколько разных функциональностей, и вопросы возвращались в произвольном порядке, перескакивая между функциями без структуры... Бизнес-заинтересованное лицо не имело бы понятия, должно ли оно отвечать по функциям или думать о системе в целом».
- **Требование:** вопросы должны группироваться по функции или доменному концепту; инструмент должен указывать, какая функция/домен обсуждается.

**Критерии приемки:**
- Каждый вопрос помечен функцией или доменом, к которому относится
- Поток завершает вопросы одной функции до открытия другой, если пользователь явно не переключится
- Произвольное перемежение функций в одном потоке вопросов не происходит

#### FR-7.3: Понятный бизнес-заинтересованным сторонам вывод

Нетехнические заинтересованные стороны должны иметь возможность участвовать в обзоре спецификации.

- **Доказательства:** критика Dilger, что «a business stakeholder on the other end of that conversation would have no idea», как участвовать; позиционирование SDD для enterprise требует кросс-функционального участия.
- **Требование:** вывод спецификации должен включать plain-language резюме, понятное нетехническим рецензентам; технические детали должны быть чётко отделены от бизнес-требований.

**Критерии приемки:**
- Каждая спецификация генерирует plain-language резюме рядом с техническими артефактами
- Бизнес-ориентированный контент не содержит нотации реализации (принудительно через FR-2.11)
- Нетехнический рецензент может одобрить или отклонить требования только по резюме

#### FR-7.4: Контроль объёма артефактов

Инструмент не должен генерировать чрезмерное количество markdown-файлов для простых функций.

- **Доказательства:** Dilger: «Мы получили 46 markdown-файлов за 20 минут... Через двадцать минут у вас пятьдесят markdown-файлов. Кто всё это читает? Кто это поддерживает?»
- **Требование:** максимальное количество артефактов на уровень церемонии; автоматическая консолидация, где возможно; явное предупреждение при превышении порога количества артефактов.

**Критерии приемки:**
- Лимиты количества артефактов определены по уровням церемонии и применяются
- Превышение порога вызывает предупреждение и предложение консолидации
- Изменение уровня Trivial создаёт максимум минимальный набор артефактов: одну запись изменения плюс встроенные критерии приемки, где требуется эффективным профилем строгости (FR-1.1, FR-1.4)

#### FR-7.5: Восстановление после неудачного эксперимента

Когда spec-driven подход не даёт лучших результатов, инструмент должен поддерживать graceful fallback.

- **Доказательства:** эксперимент dev.to с OpenSpec: «Новый фронтенд выглядел почти идентично оригиналу. Не совсем тот премиальный редизайн UI, на который я надеялся... Я полностью удалил OpenSpec и создал файл Instructions.md».
- **Требование:** «упрощённый режим» должен извлекать核心 инструкции из неудачных попыток спецификации в минимальный формат для прямого исполнения агентом.

**Критерии приемки:**
- Одна команда извлекает核心 инструкции из существующих артефактов спецификации в минимальный файл инструкций
- Извлечённый файл непосредственно исполним агентом без workflow инструмента
- Извлечение сохраняет исходные артефакты для последующей ретроспективы (ничего не уничтожается)

### 8. Поддержка и эволюция

#### FR-8.1: Синхронизация спецификации при изменениях кода

Когда код меняется вне workflow спецификации (hotfix, ручное редактирование), спецификации должны помечаться для обновления.

- **Доказательства:** критический анализ: «Что происходит, когда спецификации и код расходятся?... Spec-First Tools: unclear maintenance story, risk of spec drift, may abandon specs after initial development».
- **Требование:** git-хуки или CI-проверки должны обнаруживать изменения кода без соответствующих обновлений спецификации и помечать для синхронизации.

**Критерии приемки:**
- Изменение кода, затрагивающее область со спецификацией, без дельты спецификации помечается хуком или CI
- Пометка сохраняется, пока спецификация не синхронизирована или явно не отменена (с записанной причиной)
- Пути hotfix могут откладывать, но не молча пропускать синхронизацию

#### FR-8.2: Ретроактивная генерация спецификаций

Для существующих кодовых баз без спецификаций инструмент должен поддерживать генерацию спецификаций из кода.

- **Доказательства:** brownfield-руководство OpenSpec: «pick something small and real that you were already going to build this week, run `/opsx:explore` on the area you are about to touch so the agent maps how things actually work first».
- **Требование:** команда для анализа существующего кода и генерации delta-спецификаций для затронутой области, а не всего репозитория.

**Критерии приемки:**
- Команда генерирует delta-спецификации только для указанной области/файлов
- Время генерации и размер вывода масштабируются с затронутой областью, а не со всем репозиторием
- Сгенерированные спецификации валидны согласно FR-2.8 без ручного ремонта

#### FR-8.3: Миграция уровня церемонии

Проекты должны иметь возможность менять уровень церемонии без потери истории.

- **Доказательства:** философия specs.md «start where you are»: «Use Simple for quick specs, FIRE for rapid execution, or AI-DLC for full methodology. No upgrade path required—each flow is designed for different needs».
- **Требование:** переключение с trivial на standard на critical должно сохранять все существующие артефакты и добавлять только то, что требует новый уровень.

**Критерии приемки:**
- Смена уровня церемонии сохраняет каждый существующий артефакт дословно
- Создаются только дополнительные артефакты, требуемые новым уровнем
- Никакой регенерации или перезаписи предыдущей работы не происходит

#### FR-8.4: Сужение цикла обзора при отклонении

Когда рабочий пакет отклонён и переработан, последующие циклы обзора должны сужаться до дельты, а не повторять полный контракт приемки — с предохранительным клапаном для вновь обнаруженных критических дефектов, арбитражем при отсутствии сходимости и наблюдаемым состоянием эскалации, когда арбитраж задерживается.

- **Доказательства:** Spec Kitty issue #3925 (из собственного dogfooding проекта): «each review pass took 12–22 minutes of wall-clock, most of it re-verifying settled items. By the third pass the marginal signal is close to zero... successive review cycles must narrow, not repeat». Тот же issue документирует счётчик циклов исходного implement-review skill с эскалацией к арбитру после максимум трёх обзоров («max 3 → arbiter»).
- **Требование:** обзор цикла 1 покрывает полный контракт; цикл 2 покрывает пункты обратной связи плюс diff с предыдущего обзора; цикл 3 покрывает только пункты обратной связи. Ранее проверенные пункты должны считаться settled, если дельта их не затрагивает. **Предохранительный клапан:** если любой цикл обнаруживает новый критический дефект вне текущей суженной области, обзор сбрасывается на полное покрытие контракта затронутой области на один цикл, затем снова сужается; эскалация логируется. **Отсутствие сходимости:** если пункты обратной связи остаются неразрешёнными после цикла 3, миссия эскалируется к арбитражу ответственным владельцем (маршрутизация согласно FR-2.5 Class B, включая его цепочку fallback), а не продолжает циклы обзора. **SLA арбитража:** арбитраж имеет настраиваемый SLA ответа (по умолчанию: 72 часа). Если арбитр не отвечает в пределах SLA, миссия переходит в состояние **escalation-pending**: работа остаётся заблокированной (никакого небезопасного авторазрешения), состояние явно помечается и отображается в наблюдаемости (FR-4.2, дашборд и CLI), а маршрут арбитража — включая его цепочку fallback — повторно уведомляется с настраиваемой каденцией до разрешения.
- **Критерии приемки:**
  - Промпты обзора цикла 2+ содержат только дельту, предыдущую обратную связь и неразрешённые пункты
  - Settled-пункты перечисляются как treated-as-settled без повторной верификации
  - Эскалации предохранительного клапана появляются в журнале миссии с вызвавшим дефектом
  - Неразрешённая обратная связь после цикла 3 запускает арбитраж, а не четвёртый полный цикл обзора
  - Арбитраж без ответа после SLA отображается как escalation-pending в дашборде и CLI с повторным уведомлением маршрута арбитража

#### FR-8.5: Автоматическая архивация завершённых изменений

Завершённые и слитые изменения должны архивироваться автоматически, с слиянием delta-спецификаций в каноническое spec-tree без ручных шагов.

- **Доказательства:** OpenSpec требует явного шага `/opsx:archive`, создавая риск, что завершённые изменения остаются неархивированными; команда merge в Spec Kitty включает очистку; обзор r1 требует автоматической архивации завершённых изменений.
- **Требование:** при слиянии (или настраиваемом пост-merge триггере) папка изменения должна архивироваться, delta-спецификации сливаться, а тикет трекера обновляться — без дополнительного ручного вызова. Отклонённые изменения должны архивироваться с обоснованием согласно FR-2.3.
- **Критерии приемки:**
  - Merge запускает архивацию, слияние спецификации и обновление трекера без дальнейших команд
  - Отклонённые изменения архивируются с записью решения согласно FR-2.3
  - Архивация идемпотентна; повторный вызов не вызывает дублирования

#### FR-8.6: Инструменты миграции и предварительные проверки обновления

Изменения формата артефактов должны поставляться с автоматическими миграциями, а обновления должны быть проверяемы до применения.

- **Доказательства:** документация `superpowers-bridge` предупреждает о version drift: «compatibility baselines of OpenSpec 1.4.1 and Superpowers v5.1.0, while current releases are 1.13.2 and 6.4.1» — комбинированные workflow ломаются молча, когда компоненты расходятся; обзор r1 требует «predictable updates without breaking changes». (Обязательство проекта по семантическому версионированию — PG-2.)
- **Требование:** инструмент должен предоставлять скрипты миграции для изменений формата артефактов и предварительную проверку совместимости, сообщающую требуемые миграции до их применения. **Классы миграции:**
  - **Миграции с потерей данных** (изменения формата, которые отбрасывают или преобразуют контент): должны быть обратимыми, обратимость проверяется down-migration тестом до релиза
  - **Add-only миграции** (введение новых полей/разделов): должны быть идемпотентными и недеструктивными по построению
  - **Миграции с намеренной потерей** (удаление контента, семантика которого не может быть восстановлена из любого оставшегося источника истины — например, удаление раздела схемы без архивного представления): необратимы по дизайну; должны поставляться с окном устаревания — удаление происходит как минимум через одну мажорную версию после уведомления об устаревании, согласно FR-6.6/PG-1 — и предупреждением при обновлении, называющим точно, что будет потеряно и как сделать резервную копию; предварительная проверка обновления должна помечать каждую миграцию с намеренной потерей до применения
- **Критерии приемки:**
  - Предварительная проверка обновления сообщает требуемые миграции до применения чего-либо
  - Миграции с потерей данных проходят down-migration тест до релиза; add-only миграции проверяются на идемпотентность
  - Миграции с намеренной потерей помечаются предварительной проверкой обновления и несут предупреждение при обновлении, называющее потерю и путь резервной копии
  - Ни одно изменение формата артефактов не требует ручного редактирования файлов

### 9. Обязательства по управлению проектом (непродуктовые требования)

Следующие обязательства касаются того, как управляется проект, производящий инструмент. Они **не являются функциональными требованиями самого инструмента** и помечены отдельно (PG-*), чтобы не смешивать продукт и уровень проекта. Продуктовые пункты, ранее находившиеся в этом разделе, теперь находятся в FR-6.8 (безопасный маркетплейс) и FR-8.6 (инструменты миграции).

#### PG-1: Прозрачная дорожная карта, триаж issue и соблюдение устаревания

- **Доказательства:** обзор r1 требует прозрачной дорожной карты, регулярных аудитов, отзывчивости на issue и обратной совместимости; скорость ландшафта SDD («treat the command names as current rather than permanent») делает гарантии совместимости дифференциатором для adoption.
- **Обязательство:** публиковать публичную версионированную дорожную карту; документировать политику триажа issue с целями по времени ответа; соблюдать унифицированную политику устаревания, определённую в FR-6.6 (уведомление как минимум за одну минорную версию, алиасы функциональны через одну мажорную версию).
- **Как проверяется:** дорожная карта и политика триажа публично доступны; история релизов демонстрируемо следует политике устаревания. (Критерии приемки FR-6.6 проверяют поведение на релиз; это обязательство проверяет продольное соблюдение на протяжении истории релизов.)

#### PG-2: Семантическое версионирование

- **Доказательства:** обзор r1 требует «predictable updates without breaking changes»; инструменты миграции FR-8.6 зависят от контракта версионирования, чтобы знать, когда применяются миграции.
- **Обязательство:** следовать семантическому версионированию; ломающие изменения происходят только в мажорных версиях и всегда поставляются с миграциями (FR-8.6) и руководством по миграции (FR-6.6).
- **Как проверяется:** история релизов соответствует semver; ни одно ломающее изменение не появляется в минорном или патч-релизе.

#### PG-3: Вклад сообщества и доказательства реального мира

- **Доказательства:** adoption Spec Kitty (~1.7k звёзд) при редком независимом обзоре иллюстрирует цену слабых доказательств сообщества; обзор v1 требует влияния сообщества на разработку и примеров реальных внедрений.
- **Обязательство:** поддерживать публичные руководства по вкладу; курировать список документированных производственных внедрений; предоставлять каналы для влияния сообщества на дорожную карту.
- **Как проверяется:** руководства по вкладу существуют и соблюдаются; список внедрений содержит проверяемые случаи; изменения дорожной карты ссылаются на вклад сообщества.

## Нефункциональные требования

### NFR-1: Производительность
- Генерация спецификации для стандартного уровня церемонии должна завершаться <2 минут
- Обнаружение дрейфа на PR должно завершаться <30 секунд
- Локальный дашборд: вид по умолчанию (с пагинацией) должен рендериться <2 секунд, а навигация по страницам <1 секунды для любого количества активных миссий; стоимость листинга ограничена размером страницы, а не количеством миссий

### NFR-2: Надёжность
- Никакой потери данных при прерывании сессии; всё состояние восстановимо из git
- Graceful degradation, когда AI-ассистент недоступен (ручное редактирование спецификаций)
- Офлайн-режим:核心 операции (написание спецификаций, валидация, архивация и **локальный** дашборд) должны работать без сетевого подключения. **Командный** дашборд (кросс-репозиторная агрегация, FR-4.2) сетевой и опциональный; его недоступность не должна влиять на локальную работу. Сетевые функции (синхронизация трекера, телеметрия) должны мягко отказывать и ставиться в очередь

### NFR-3: Безопасность и приватность
- Никаких секретов в файлах спецификаций (автоматическое сканирование)
- Local-first: никакие данные не покидают репозиторий без явного opt-in
- Аудиторский след для всех действий агента
- Opt-in согласие для телеметрии и синхронизации должно быть **per integration** (см. FR-4.3), храниться как проверяемый файл в репозитории, быть видимым в code review и отзываемым
- Опубликованная политика приватности должна документировать каждый сетевой вызов, который может делать инструмент
- Конфигурационный переключатель должен отключать всю сетевую активность («network kill switch») без ухудшения локальной функциональности. **Приоритет:** kill switch переопределяет все per-integration opt-in (FR-4.3), останавливая opted-in синхронизацию; конфигурации согласия сохраняются без изменений и снова вступают в силу, когда kill switch снят

### NFR-4: Расширяемость
- Архитектура плагинов для пользовательских навыков, схем и интеграций
- Документированный API для программного взаимодействия
- Общественный маркетплейс схем (согласно требованиям безопасности FR-6.8)

### NFR-5: Лёгкая установка и запуск
- Установка не должна требовать тяжёлых runtime за пределами одного стандартного менеджера пакетов
- Холодный старт CLI должен быть <1 секунды для `--version` и <3 секунд для `init`
- Никакой daemon или фоновая служба не требуются для核心 работы

**Доказательства:** spec-compare перечисляет «Python dependency (pip install) vs. Node-based alternatives» как ограничение Spec Kitty; обзор r1 требует «installation without heavy runtimes, fast startup».

## Критерии успеха

Реализация этих требований была бы успешной, если:

1. **Победа в независимом сравнении:** она набирает ≥4/5 по всем сценариям использования в сравнении, подобном [методологии ranthebuilder.cloud](https://ranthebuilder.cloud/blog/i-tested-three-spec-driven-ai-tools-here-s-my-honest-take), без сценария ниже 3/5.

2. **Эффективность токенов:** контролируемое сравнение показывает ≥10% сокращение токенов против Superpowers на нетривиальных задачах, при этом тривиальные задачи стоят не больше, чем stock agent без инструмента **при профиле строгости balanced или vibe**. (Профиль strict на Trivial намеренно покупает принудительное исполнение в пределах своего ограниченного допуска, FR-1.4, и освобождён от границы паритета со stock agent. **Базовая линия «stock agent»:** тот же ассистент, выполняющий ту же задачу только из issue или промпта, без артефактов spec-workflow — контрольное условие, используемое в контролируемых сравнениях, таких как оценка Superpowers от MCP.Directory.)

3. **Продольная валидация:** исследование длительностью 4+ месяца с несколькими инженерами (как [имитационное исследование OpenSpec](https://medium.com/@vinodh.thiagarajan/simulating-a-software-team-to-study-spec-driven-development-using-openspec-5d2195fb2a37)) показывает разрыв между спецификацией и реализацией <10% и отсутствие дрейфа спецификации на активно развиваемых областях.

4. **Трение внедрения:** онбординг новой команды до продуктивного использования <1 дня (как заявление specs.md «Establish an SDD Workflow in One Day», но валидированное).

5. **Валидация сообществом:** ≥1k звёзд GitHub за 6 месяцев с содержательными независимыми обзорами (не только документация вендора) и проверяемым списком внедрений согласно PG-3.

6. **Модульное внедрение:** отдельные слои могут внедряться независимо и комбинироваться с существующими инструментами (OpenSpec, Superpowers) через мосты без дублирующихся артефактов — подтверждено как минимум двумя документированными производственными комбинациями.

## Открытые вопросы

Эти требования оставляют несколько нерешённых вопросов, требующих проектных решений:

1. ~~**Единый инструмент vs комбинация?**~~ **Разрешено в v1.1:** P6 принимает модульную композицию как основную архитектуру. Оставшийся пограничный вопрос покрыт Q2.

2. **Владение слоем управления?** Управление Spec Kitty (Charter, Decision Moments) тесно связано с его workflow. Может ли управление быть отдельным слоем, применимым к любому SDD-инструменту?

3. **Надёжность автотриггеров?** Автотриггеры Superpowers работают благодаря его bootstrap-принуждению («IF A SKILL APPLIES TO YOUR TASK, YOU DO NOT HAVE A CHOICE»). Можно ли этого достичь без стоимости bootstrap по токенам? **Область:** этот вопрос касается *механизма принуждения для запуска навыков в основной сессии*; измерение частоты триггеров определено в FR-3.1. (См. Q6 для параллельного вопроса на стороне субагента.)

4. **Жизнеспособность spec-as-source?** Подход Tessl «spec-as-source» (спецификации ЕСТЬ источник, код автогенерируется) не доказан с недетерминированными LLM. Должен ли идеальный инструмент поддерживать это как опциональный режим?

5. **Кросс-репозиторное планирование?** Функция OpenSpec «Stores» (beta) адресует планирование, охватывающее несколько репозиториев. Насколько она необходима для первоначального релиза идеального инструмента?

6. **Наследование правил без стоимости bootstrap?** FR-3.3 требует, чтобы субагенты наследовали правила управления, но механизм принуждения Superpowers (всегда загружаемый bootstrap) — именно то, что его документация говорит субагентам пропускать. Можно ли инжектировать правила в промпты субагентов без повторяющейся стоимости токенов полного bootstrap? **Область:** этот вопрос касается *механизма инъекции для пакета контекста субагента*, включая то, насколько далеко можно сжать наследование в digest-форме FR-3.3. Q3 и Q6 — параллельные применения одной и той же фундаментальной проблемы — дешёвое принуждение без всегда загружаемого bootstrap — к двум контекстам с разными ограничениями (запуск навыков в основной сессии vs наследование правил субагентом); они разделены, потому что решения могут различаться.

## Связь с существующими инструментами

| Существующий инструмент | Что идеальный инструмент наследует | Что улучшает |
|---|---|---|
| **OpenSpec** | Delta-спецификации, brownfield-first, механизм архивации, поддержка множества инструментов | Добавляет обнаружение дрейфа, классы конфликтов с настраиваемым на платформе fallback арбитража, память отклонённых предложений, верификацию спецификации и реализации, прогрессивную детализацию |
| **Superpowers** | Автотриггерные навыки, изоляция субагентов, принуждение TDD, направление состязательного обзора, систематическая отладка | Добавляет уровни церемонии, профили строгости с ограниченным допуском принуждения, бюджеты токенов, руководство по очистке контекста, обход тривиальных задач, наследование правил для субагентов |
| **Spec Kitty** | Слой управления, наблюдаемость Teamspace, интеграция с трекерами, Decision Moments | Добавляет elicitation от проблемы, контроль объёма артефактов, сужение цикла обзора с наблюдаемым арбитражем; избегает взрыва markdown |
| **specs.md** | Подключаемые потоки, адаптивная церемония, фаза Ideation, поддержка монорепозиториев | Добавляет независимую валидацию, продольные доказательства, adoption сообщества |
| **GitHub Spec Kit** | Фреймворк Constitution, прослеживаемость spec-to-code, паттерн неизвестных NEEDS CLARIFICATION | Добавляет гибкую итерацию, delta-формат, оптимизацию brownfield |
| **BMAD** | Качество elicitation, workflow корректировки курса | Снижает церемонию для не-enterprise использования, устраняет накладные расходы 21 агента для стандартных задач |

**Карта композиции (согласно обзору r1 и P6):** идеальная система композирует, а не заменяет — OpenSpec как лёгкий слой управления изменениями, Superpowers как слой дисциплины исполнения, Spec Kitty как слой параллельной оркестрации и управления, Spec Kit/specs.md как слой строгой спецификации для сложных проектов — объединённые общей конфигурацией, общим API и git-native хранилищем.

## Примечание о стабилизации (v2.0)
