# Протокол управления

## Назначение

Этот документ отвечает на открытые вопросы Q2 и Q6 [базовой версии требований v2.0](../ideal-tool-requirements.md):

- **Q2 (владение слоем управления):** управление — **отдельный, отключаемый слой**, реализующий **core-adjacent протокол**. Протокол — схема событий, формат записи решений, идентичность сессии, контракт идентификаторов — часть核心 API; *реализация* управления (маршрутизация, эскалация, применение политик) — подключаемый слой согласно P6 («индивидуально отключаемый»). Протокол не может быть чистым плагином, потому что нормативные критерии приемки ссылаются на его конструкты: FR-2.5 требует вердикты арбитража «recorded as a decision record per FR-4.4», а FR-4.6 требует ссылок на записи решений и реализующую сессию. Контракт, определяющий эти конструкты, должен поэтому поставляться с ядром, а runtime-поведения остаются заменяемыми.
- **Q6 (наследование правил без стоимости bootstrap):** представление правил использует **наследование в digest-форме, разрешение во время сборки и ключи кэша по content-digest**, удерживая инъекцию субагента в пределах FR-3.3 без всегда загружаемого bootstrap.

Согласно NQ-C, это **один версионированный контракт с двумя гранями** — схема событий и представление правил — с синхронным мажорным версионированием: мажорное изменение любой грани вынуждает мажорную версию протокола.

Эта ревизия (1.1.0) применяет пост-обзорные решения: модель авторитета (NQ-L: artifacts-as-primary, log as audit), структура и компакция журнала (NQ-P: per-mission logs, cross-mission stream, compaction on archive), контракт идентичности сессии (NQ-Q), минимальный контракт идентификаторов `spec://` и разделение gate-vs-trigger.
Ревизия 1.1.1 применяет заметки пост-приёмочного обзора: гранулярность адресуемости `spec://`, отложение распределения mission-id к `data-formats.md` и исправленную формулировку signed-manifest (ни один профиль v1 не требует подписей).
Ревизия 1.1.2 уточняет две формулировки из обзора композиции: семантику разрешения mission-record `spec://` (запись существует с начала миссии как живой индекс) и формулировку CP для signed-manifest (новое нормативное требование, расширяющее FR-1.4 / затрагивающее NFR-3, а не модификация любого из них).
Ревизия 1.2.0 закрывает вопрос словаря событий и добавляет сигнал обнаружения, оба из второго обзора композиции: таксономия объявлена **закрытой** (core-defined; адаптеры отображают только на существующие типы; расширение через версионирование протокола), тип события `projection.gap` записывает классификацию неразрешимых переходов во время запроса, и принцип потребителя (отсутствие события не является доказательством отсутствия) сформулирован для всех нижестоящих потребителей.
Ревизия 1.2.1 уточняет принцип потребителя по классу эмиттера (projected vs core-emitted), записывает жизненный цикл `projection.gap` (append-only observation, query-time resolution) и указывает его статус как core-emitted diagnostic относительно отклонённого adapter namespace.
Ревизия 1.3.0 добавляет первое запланированное расширение таксономии с момента объявления словаря закрытым: тип события `skill.invoked` (испускается с записью вызова, несущей классификацию `invocation_origin`), закрывая пробел, при котором решения о триггерах требовалось логировать (FR-3.1), но ни один тип таксономии их не нёс.

## Соблюдаемые проектные ограничения

Все механизмы соблюдают [проектные ограничения, выведенные из NFR](./README.md#nfr-derived-design-constraints): никакого daemon (доставка событий ограничена вызовом), офлайн-способность (никакого сетевого транспорта в核心 протоколе) и дешёвый запуск (digest, а не жадный парсинг).

## Модель авторитета (NQ-L)

**Артефакты первичны; журнал событий — append-only аудиторский след.**

- **Источник истины:** spec-tree, записи решений и состояние миссии/изменения — все repo-native артефакты (FR-6.2).
- Журнал событий записывает **наблюдаемую инструментом активность**. Он никогда не определяет состояние артефактов, и потребители никогда не должны выводить состояние артефактов из него.
- Ручные и внешние правки (разрешённые FR-1.2) меняют артефакты напрямую и не испускают событий; расхождение обнаруживается **сравнением артефактов** — обнаружение дрейфа (FR-2.2) и флаги синхронизации спецификаций (FR-8.1) — а не воспроизведением журнала.
- Следствие для дизайна: `data-formats.md` определяет форматы артефактов как авторитетные схемы; записи событий *ссылаются* на артефакты, а не наоборот. Двунаправленная синхронизация отклонена: она создаёт класс конфликтов (log ↔ artifact), который базовая версия не покрывает.

## Грань 1: Схема событий

### Принцип: строить на существующих базовых точках событий

Протокол не изобретает параллельную систему событий. Его источники событий — точки, которые базовая версия уже нормативно определяет:

| Точка события | Базовая привязка | Испускается когда |
|---|---|---|
| Граница фазы | FR-3.5 (руководство по очистке контекста отмечает завершение фазы) | фаза завершается |
| Прерывание | FR-3.6 (отклонение от плана, ошибка внешнего инструмента, инвалидация допущения, расширение области) | срабатывает триггер прерывания |
| Конфликт обнаружен | FR-2.5 (обнаружение Class A/B/C до merge/archive) | обнаруживается одновременная модификация |
| Момент решения | FR-4.1 (решения в маршрутизируемых категориях) | возникает решение в перечисленной категории |
| Вердикт обзора | FR-3.4 / FR-8.4 (состязательный обзор; вердикты циклов; арбитраж) | обзор или арбитраж завершается |
| Архивация | FR-8.5 (автоархивация при merge) | изменение архивируется |
| Неизвестное разрешено | FR-2.10 (поток разрешения) | помеченное неизвестное разрешается через поток |

Эти привязки — нормативные FR, поэтому каждый соответствующий инструмент уже производит лежащие в основе условия; протокол стандартизирует их *поверхность наблюдения*.

### Структура и компакция журнала (NQ-P)

Per-mission журналы плюс кросс-миссионный поток:

```
events/
  missions/<mission-id>/log.jsonl     # append-only within a mission
  global/log.jsonl                    # cross-mission events (protocol upgrades, ownership changes, kill-switch toggles)
```

**Компакция при `change.archived` (FR-8.5):** журнал миссии складывается в запись миссии, хранимую с архивированным изменением. **Сохраняется:** вердикты, ссылки на решения, записи эскалации, ссылки на сессии. **Отбрасывается:** детали обзора по циклам — зеркалируя собственный вывод FR-8.4, что «by the third pass the marginal signal is close to zero». Отклонённые изменения компактизируются так же при архивации отклонения, с сохранением обоснования отклонения как записи решения (FR-2.3).

Это соблюдает P2 по духу: после архивации per-event файлы не служат ни одному нижестоящему потребителю, которому не служила бы запись миссии; компакция сохраняет то, что служит.

### Формат записи события

События хранятся как repo-native артефакты (FR-6.2):

```yaml
type: conflict.detected | decision.required | review.verdict | ...
session: spec://<repo>/sessions/<session-id>   # emitting session (see Session identity)
ts: <ISO-8601>
mission: spec://<repo>/missions/<mission-id>
refs:                       # traceability links (FR-4.6)
  requirement: spec://<repo>/requirements/<id>
  change: spec://<repo>/changes/<id>
  decision: spec://<repo>/decisions/<id>
payload:                    # type-specific structured data
  ...
```

**Семантика доставки (ограничение no-daemon):** события *записываются*, а не *проталкиваются*. Потребители (слой управления, дашборды, CI-проверки) читают журнал в своих точках вызова — CLI-команды, хуки, шаги CI, обновление дашборда. Это удовлетворяет NFR-5/NFR-2: никакого постоянного слушателя, никакого сетевого транспорта. Уведомления в реальном времени (маршрутизация Slack/Teams согласно FR-4.1) — опциональный оверлей, читающий тот же журнал и могущий использовать сеть, чисто отключаемый kill switch согласно NFR-3.

### Таксономия событий (начальная)

| Тип | Испускается при | Потребляется |
|---|---|---|
| `phase.completed` | граница фазы | восстановление контекста (FR-4.5), отчётность о стоимости (FR-5.4) |
| `interrupt.raised` | триггер FR-3.6 | слой управления (маршрутизация), журнал миссии |
| `conflict.detected` | обнаружение FR-2.5 | слой управления (маршрутизация арбитража) |
| `decision.required` | категория FR-4.1 | слой управления (маршрутизация заинтересованных сторон) |
| `decision.recorded` | запись FR-4.4 | прослеживаемость, память (FR-4.4/4.6) |
| `review.verdict` | FR-3.4/FR-8.4 | сужение цикла обзора, состояние эскалации |
| `arbitration.pending` | истечение SLA FR-8.4 | наблюдаемость (FR-4.2 escalation-pending) |
| `arbitration.resolved` | вердикт арбитража | разблокировка архива |
| `change.archived` | FR-8.5 | слияние spec-tree, синхронизация трекера (opt-in) |
| `unknown.resolved` | поток FR-2.10 | обновление спецификации, валидация |
| `projection.gap` | core-проход обнаружения (шлюзы, проверки tripwire, CI — см. composition.md, шаблон адаптера #4): переход артефакта, релевантный фазе, не соответствовал объявленной сигнатуре | обслуживание адаптера, верификация полноты сигнатур (KU #7), наблюдаемость |
| `skill.invoked` | любой вызов навыка дисциплины на всех путях триггеров (preemptive hooks/trigger-list, remedial gate dispatch — оба канала согласно execution-layers, и явный) | метрики FR-3.1 / NQ-H, классификация интерференции (triggering) |

**Словарь закрыт и core-defined.** Адаптеры (согласно [`composition.md`](./composition.md)) отображают внешние переходы только на *существующие* core-типы и не могут объявлять новые типы событий. Расширение происходит через версионирование протокола: новые core-типы поставляются в релизе протокола, а правило ignore-unknown-types делает такие релизы обратно совместимыми для существующих потребителей. Зарезервированный adapter namespace (`adapter.<vendor>.<type>`) рассматривался и был отклонён: события без core-потребителя — церемония согласно P2, а adapter-writable журнал сделал бы гарантии аудита NQ-L зависимыми от дисциплины адаптера. Потребители подписываются на определённый набор и должны игнорировать неизвестные типы (прямая совместимость с будущими версиями протокола).

**Статус `projection.gap`.** Он избегает обоих оснований отклонения: он **core-emitted** — диагностика о здоровье самого слоя проекции, производимая core-проходом обнаружения — а не adapter-declared наблюдение внешней активности, и он потребляется core-owned поверхностями (фильтр пробелов наблюдаемости, FR-4.2; рабочие процессы обслуживания адаптера и верификации KU #7). Критерий церемонии P2 нацелен на adapter-declared события внешней активности без core-потребителя; здесь он не применяется.

**Принцип потребителя (два класса эмиттеров).** **Projected events** — выводимые адаптерами из внешней активности — *наблюдения*, а не истина: их отсутствие — отсутствие доказательства, никогда не доказательство отсутствия. Потребители, нуждающиеся в авторитетном состоянии, падают на артефакты (NQ-L). **Core-emitted events** несут доказательную силу: эмиссия привязана к завершению core-действий, которые якорятся таксономией (фиксируется атомарно с артефактами действия), поэтому для этих действий отсутствие события *является* доказательством отсутствия — сигнал tripwire (нет `change.archived` после завершённой миссии означает, что архивация не запускалась). Артефакты остаются финальным авторитетом для состояния согласно NQ-L; событие — сигнал, а не истина. Оговорка области: core-тишина значима только для anchored действий — неanchored активность (ручные правки согласно FR-1.2) по дизайну ничего не испускает. Потребители должны классифицировать по эмиттеру: никогда не считать тишину projected-event невхождением; считать тишину core-event tripwire о core-действиях. Это управляет шлюзами, tripwire и обнаружением интерференции в [`triggering.md`](./triggering.md).

**Жизненный цикл `projection.gap`.** Событие gap — неизменяемое историческое наблюдение; разрешение не является событием журнала. Полезная нагрузка события несёт ссылку на переход (идентификаторы артефакта и diff), поэтому разрешение выводится во время запроса повторным сопоставлением этого перехода с *текущим* набором сигнатур адаптера; аудируемость обеспечивается версионированным объявлением адаптера (FR-6.2, история git), и каждый вновь покрытый переход становится кейсом корпуса соответствия (composition KU #3/#7). Тип `projection.gap.resolved` не добавляется — разрешение выводимо, и ни один потребитель не нуждается в нём как в отдельном событии (P2). Журнал остаётся append-only согласно NQ-L.

### Подписка, гейтинг и разделение gate/trigger

Слой управления подписывается декларативно (repo-native конфигурация, отображающая типы событий на обработчики).

**Gates vs triggers.** *Trigger* решает, вызывается ли навык (уровень контекста агента, во время или до исполнения). *Gate* решает, проходит ли шаг workflow — merge, archive, продвижение фазы (уровень инструмента). Оба потребляют один поток событий; они действуют на разных стадиях и не должны смешиваться:

- Шлюзы core и нормативны (FR-2.2, FR-3.2, FR-8.4, FR-8.6); triggering — подключаемая комбинация Q3 (→ [`triggering.md`](./triggering.md)).
- Шлюзы проверяют **evidence** — артефакты, которые называет критерий приемки — никогда вызовы навыков как таковые. Merge никогда не проходит потому, что «навык TDD запускался»; он проходит потому, что существует test-first evidence (FR-3.2).
- Шлюз может *вызвать* remedial-вызов навыка как следствие заблокированного шага. Такие gate-forced вызовы считаются в частоте FR-3.1 (они происходят без явной пользовательской команды) и аудируются отдельно как remedial согласно NQ-H.

Это разделение на уровне протокола, чтобы `triggering.md` проектировал механизмы без переопределения шлюзов, а шлюзы не могли стать избыточными из-за дизайна триггеров.

## Грань 2: Представление правил

### Что такое набор правил

Наследование управления (FR-3.3) доставляет шесть пунктов в контекст субагента. Их представление:

| Пункт | Представление |
|---|---|
| Конституция/доктрина | **Digest**: только релевантные для принуждения пункты (tool-compilable checklist), а не полный философский текст |
| Настройки принуждения дисциплины | Структурированные данные (профиль, переключатели) — ~десятки токенов |
| Границы области + определение задачи | Ограничено задачей, уже ограничено |
| Конфигурация interrupt-триггеров | Структурированные данные |
| Стандарты кодирования/безопасности | **Ссылка + content digest** (разрешается при сборке) |
| Релевантные дельты спецификации | Ограничено задачей |

### Механизм: разрешение во время сборки с кэшем по content-digest

1. **Хранение.** Правила живут как repo-native файлы (FR-6.2): конституция, стандарты, конфигурация принуждения.
2. **Компиляция.** Конституция *компилируется* один раз на версию контента в digest принуждения — подмножество пунктов, которые проверяют шлюзы. Компиляция локальна, детерминирована, офлайн.
3. **Сборка.** Когда строится пакет контекста субагента (FR-3.3), ссылки разрешаются: стандарты раскрываются из хранилища в пакет, дедуплицируются across tasks.
4. **Кэширование (FR-5.5).** Ключи кэша — **content digests входов** — правила и конфигурация, дельты спецификаций, артефакты планов — что покрывает требование инвалидации FR-5.5 по всем его входным классам; конфигурация — один класс среди них. Любое изменение входа меняет digest, вызывая промах кэша и регенерацию; идентичные фрагменты across tasks попадают в одну запись кэша.
5. **Граница.** Общий инжектируемый контекст (digest + разрешённые ссылки + элементы, ограниченные задачей) остаётся в пределах FR-3.3: max(2,000 токенов, 15% эффективного бюджета), считается внутри бюджета. Фактическая стоимость детализируется в отчётах о стоимости (FR-5.4).

### Почему не hash+diff (отклонённая альтернатива)

Content hash непригоден для модели, а diff против базовой линии, которую субагент никогда не получал, нечитаем. Digest-форма (скомпилированный, релевантный для принуждения текст) — правильное представление; content digest используется *только* как ключ кэша, никогда не инжектируется.

## Контракт идентичности сессии (NQ-Q)

FR-4.6 требует прослеживаемости к «the implementing agent/session» — разрешимость ссылок, а не криптографическое доказательство авторства.

### session_id

- Непрозрачный, уникальный, неизменяемый, никогда не переиспользуемый (UUIDv7 или ULID).
- **Не выводится** из (harness, branch, timestamp): ветки переименовываются и force-push (дополнительно дестабилизировано изоляцией worktree FR-5.3), временные метки коллизируются, а вывод не даёт ни связи parent/child (FR-3.3), ни защиты от backdated записей. Эти поля — *метаданные* манифеста, а не идентичность.

### Манифест сессии

Версионированный repo-native артефакт (FR-6.2) на сессию, по стабильному шардированному пути, ключ — session_id (точное дерево в `data-formats.md`):

```json
{
  "session_id": "…",
```

Все артефакты миссии/изменения/решения/обзора ссылаются на сессии через `session_id`; CI-валидатор разрешает каждую ссылку на существующий манифест с согласованными полями (уточнение «broken links fail CI» FR-4.6, не новый критерий).

### Сегментация, происхождение и человеческая атрибуция

- **Сессия — один непрерывный контекст агента.** Очистка контекста (FR-3.5) завершает сессию; возобновление начинает новую, связанную через `continues_session_id`, с `mission_id`, стабильным across mission. Гранулярность окна контекста — правильная единица атрибуции — именно она фактически выполняла работу.
- **Субагенты** несут `parent_session_id`, образуя цепочку наследования FR-3.3.
- **Люди:** интерактивные человеческие сессии инструмента получают манифесты `kind: human`. Внешние правки (FR-1.2) атрибутируются через git committer identity; история git авторитетна для человеческих правок, согласно модели авторитета.

### Сохранение и взаимодействие с компакцией

Манифесты сессий — постоянные записи идентичности — никогда не перемещаются и не удаляются, иначе ссылки FR-4.6 ломаются. При компакции записи миссии встраивают *резюме* манифестов (session_id, kind, harness, agent/operator, ключевые refs, digests); файлы остаются как цели ссылок. Манифесты исключены из лимитов количества артефактов церемонии FR-7.4: они — аудиторская инфраструктура, служащая потребителю прослеживаемости FR-4.6 (P2-обосновано), а их рост ограничен тем, что это небольшие структурированные записи.

Приватность: никаких секретов, минимальные PII (NFR-3); манифесты сканируются как любой артефакт.

### Опциональное улучшение: подписанные манифесты

Криптографическая подпись (подписи манифестов, подписанные коммиты с session trailers, аттестационные артефакты) добавила бы tamper-evidence и non-repudiation для аудиторских следов NFR-3. Это **не часть контракта v1**: она приносит управление ключами, отзыв, офлайн-ограничения (NFR-2, FR-6.7) и вес установки (NFR-5). Ни один профиль v1 не требует подписей. `execution-layers.md` может специфицировать механизм верификации — где проверялась бы подпись, если бы возможность когда-либо была включена — но любое требование подписанных манифестов — **новое нормативное требование**: где оно привязано к семантике профиля, оно расширяет FR-1.4, а где влияет на целостность аудита, оно затрагивает NFR-3; в любом случае это накопленный CP, со вторым рецензентом, когда затронут NFR-3, согласно процессу предложений об изменениях.

## Контракт идентификаторов: `spec://` (минимальный)

```
spec://<repo>/<class>/<id>
  classes: requirements | changes | decisions | missions | sessions
```

- `<repo>` — настроенный идентификатор репозитория — future-proofing Q5 (адресуемость по идентификатору репозитория); single-repo v1 разрешает локальный default.
- Разрешение локальное и офлайн (NFR-2), против дерева артефактов репозитория.
- **Гранулярность адресуемости:** отдельные записи журнала событий не `spec://`-адресуемы. `spec://…/missions/<id>` разрешается в запись миссии — созданную в начале миссии как живой индекс миссии, свёрнутую с деталями событий при компакции — которая, таким образом, является единственной `spec://`-адресуемой единицей для активности миссии. Физические цели разрешения определены в `data-formats.md`.
- Классы ссылок (broken vs unresolvable, NQ-E) и семантика кросс-репозиторного разрешения расширены в `data-formats.md`, который владеет деревом артефактов.
- Схема следует классам миграции FR-8.6, как только артефакты появятся в реальной эксплуатации.

Определение минимального контракта здесь — а не в `data-formats.md` — устраняет циклическую зависимость, отмеченную в обзоре: этот документ использует `spec://` в своих форматах записей, поэтому семантика идентификаторов протокольного уровня; `data-formats.md` расширяет, а не определяет их.

## Версионирование протокола

Один semver для обеих граней; мажорные версии синхронизированы (NQ-C). Производимые протоколом артефакты (записи событий, манифесты, digests) подчиняются классам миграции FR-8.6 после релиза; предрелизные ревизии макета не требуют миграции. Текущая: **1.3.0** — добавлены модель авторитета, структура/компакция журнала, идентичность сессии, контракт идентификаторов и разделение gate/trigger (1.1.0); уточнения формулировок (1.1.1–1.1.2); закрытый словарь событий, тип обнаружения `projection.gap` и принцип потребителя (1.2.0); уточнение класса эмиттера и жизненный цикл `projection.gap` (1.2.1); расширение таксономии `skill.invoked` (1.3.0) — первое добавление через механизм версионирования, обратно совместимое через ignore-unknown-types. Все предрелизные; обязательств миграции пока нет.

## Runtime слоя управления (подключаемый)

Слой над протоколом:

- **Router** — отображает события `decision.required` / `conflict.detected` / `arbitration.pending` на ответственных владельцев согласно FR-2.5/FR-4.1, включая цепочку fallback объявления владения (CODEOWNERS по умолчанию, эквивалентный файл владения в других средах) и семантику подтверждения per-repo NQ-F.
- **Policy engine** — применяет эффективный профиль строгости (FR-1.4) к обработке событий; рендерит рекомендательное vs принудительное поведение.
- **Observability adapter** — проецирует состояние журнала событий в локальный дашборд / CLI (FR-4.2), включая фильтр escalation-pending.

Все три отключаемы (P6); журнал событий протокола и core tool-gates остаются. Отключение слоя ухудшает маршрутизацию/наблюдаемость, но никогда нормативные шлюзы — *наблюдение* управления слоисто; *шлюзы* core.
