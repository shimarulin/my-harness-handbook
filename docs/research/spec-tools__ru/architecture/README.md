# Архитектурная документация

## Назначение

Этот каталог содержит архитектуру идеального инструмента, специфицированного в [ideal-tool-requirements.md](../ideal-tool-requirements.md) (замороженная базовая версия v2.0), и механизм предложений об изменениях, определённый в [change-proposal-process.md](../change-proposal-process.md).

Фаза требований закрыта. Эта фаза реализует эти требования без их изменения; там, где проектное решение выбирает среди одинаково допустимых прочтений текста базовой версии, оно записывается согласно механизму (b) процесса предложений об изменениях (архитектурный документ, без CP). Любое изменение, требующее нормативной силы, — это накопленный CP, а не правка здесь.

## Общий контракт: что живёт здесь vs в документах слоёв

Чтобы избежать перекрёстной чехарды между тесно связанными документами, **общий контракт** — единый версионированный протокол управления с двумя гранями (схема событий, представление правил) — *определяется один раз* в [`governance-protocol.md`](./governance-protocol.md) и *упоминается* всеми другими документами. Документы слоёв его не пересказывают.

Две поверхности повсюду остаются раздельными:

- **Внутренний контракт** (governance-protocol.md): события и правила *внутри* инструмента — как принуждение дисциплины, моменты решений и прослеживаемость наблюдают и ограничивают исполнение.
- **Внешний контракт** (composition.md): как инструмент соединяется с существующими инструментами (OpenSpec, Superpowers, Spec Kit/specs.md) — владение артефактами, разделение командных поверхностей, посредничество схем.

## Проектные ограничения, выведенные из NFR

Следующие базовые NFR — жёсткие ограничения на выбор механизмов. Каждый документ слоя должен для каждого вводимого механизма указывать, как он удовлетворяет или соблюдает эти ограничения. Они перечислены здесь один раз и упоминаются далее.

1. **NFR-5 — никакого daemon, никакой фоновой службы.** Ни один механизм не может требовать постоянного слушателя. Доставка событий должна работать через транзитные, ограниченные вызовом потоки (вызовы CLI, хуки, шаги CI). Маршрутизация управления в Slack/Teams (FR-4.1) — опциональный оверлей, а не транспорт самого протокола.
2. **NFR-2 — офлайн-режим.** Протокол управления, триггеры, валидация и архивация должны работать без сети. Любая маршрутизация событий или запуск навыков, использующие сетевой транспорт, — опциональный оверлей, который чисто деградирует (согласно разделению локального/командного дашборда в FR-4.2 и приоритету kill-switch в NFR-3).
3. **NFR-1 — границы производительности.** Обнаружение дрейфа <30 с на PR ограничивает его область: это не может быть полное сканирование репозитория; оно должно ограничиваться парами пунктов спецификации изменения (FR-2.2). Генерация спецификации <2 минут (Standard) и границы рендеринга дашборда (NFR-1) ограничивают бухгалтерию оркестрации, чтобы избегать последовательных LLM round-trip там, где артефакты можно вывести локально.
4. **NFR-3 — приоритет kill-switch.** Ни один核心 механизм не может зависеть от сетевого компонента, отключение которого ломает核心 поведение (формализует NQ-A). Базовая комбинация триггеров (хуки + минимальный список триггеров + tool-gate) должна быть независима от сети; middleware, где разрешён, — отключённый по умолчанию плагин, подчинённый kill switch, проанализированный на приватность, с раскрытием обработки данных.
5. **NFR-5 — холодный старт.** Холодный старт CLI <1 с (`--version`) / <3 с (`init`) ограничивает загрузку правил во время запуска: наследование управления должно использовать digest и ссылки, разрешаемые во время сборки, а не жадно парсить полные тексты.

## Антипаттерны, перенесённые из исследования

Документы композиции и исполнения наследуют эти задокументированные паттерны отказов как именованные ограничения; они повторяются здесь, чтобы ни один документ слоя не reintroduced их:

- **Дублированный вывод дизайна** — два артефакта, описывающих одно решение (наблюдается, когда брейншторминг Superpowers и предложения OpenSpec сосуществуют без designated home)
- **Два списка задач** — грубый чек-лист и микрошаговый TDD-план отслеживают одну работу в разных местах и расходятся
- **Неоднозначность ручной оркестрации** — нет designated владельца, решающего, какой навык какого инструмента запускать следующим

Соответствующее положительное ограничение — критерий приемки FR-6.3: **один designated home на тип артефакта** в любой комбинации.
