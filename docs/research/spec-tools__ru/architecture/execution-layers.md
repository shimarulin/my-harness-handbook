# Слои исполнения

## Назначение

Этот документ реализует требования, обращённые к исполнению, [базовой версии v2.0](../ideal-tool-requirements.md) — FR-3.x, FR-5.x, FR-8.x — и разрешает открытые входы, зарегистрированные предыдущими документами: **механизм диспетчеризации gate-to-skill** (triggering KU #6), условие **атомарной эмиссии событий** (governance-protocol v1.2.1), **механизм верификации подписанного манифеста** (отложен там) и **референсный корпус** (отложен из triggering.md).

Он компонует уже установленные контракты: идентичность сессии и представление правил (governance-protocol), разделение trigger/compliance (triggering), семантику событий с принципом потребителя по классу эмиттера (governance-protocol v1.2.1).

## Соблюдаемые проектные ограничения

- **NFR-5 (без daemon):** шлюзы, таймеры арбитража и эскалация ограничены вызовом — оцениваются в точках входа CLI/хука/CI и арифметикой дедлайнов, никогда фоновыми процессами.
- **NFR-2 / FR-6.7 (офлайн):** каждый механизм здесь локален; повторное уведомление SLA может использовать сетевые оверлеи, отключаемые kill switch согласно NFR-3.
- **NFR-1 (производительность):** обнаружение дрейфа ограничено парами пунктов спецификации изменения (FR-2.2), никогда сканированием репозитория; промпты циклов обзора сужаются согласно FR-8.4.
- **Принцип потребителя:** core-эмиссия событий атомарна с действиями, определёнными в этом документе (ниже), поэтому тишина — tripwire о них.

## Слой 1: Сборка контекста субагента (FR-3.3, FR-3.5)

### Pipeline сборки

Для каждой задачи сборка пакета выполняется **в коде инструмента, никогда в контексте агента**:

1. **Собрать** определение задачи, затронутые дельты спецификации, интерфейсные контракты модулей (минимальный пакет контекста FR-3.3).
2. **Разрешить управление** — представление правил согласно governance-protocol Facet 2: digest принуждения, структурированные настройки, конфигурация прерываний, стандарты по ссылке с content digest.
3. **Наследовать идентичность сессии** — родительская сессия создаёт дочерний манифест (цепочка `parent_session_id`, наследование FR-3.3).
4. **Собрать** ограниченный пакет: общий инжектируемый контекст в пределах FR-3.3 — большее из 2 000 токенов или 15% эффективного бюджета — считается внутри, а не в дополнение к этому бюджету.
5. **Сообщить** детализированную стоимость инъекции (FR-5.4).

**Верификация наследования (FR-3.3 AC):** манифест записывает `governance_digest`; первое действие субагента — проверяемая инструментом проверка, что его рабочая конфигурация соответствует объявленному профилю родителя — механизм проверяемого присутствия для «subagent prompts verifiably contain the constitution and effective enforcement settings». Несоответствие блокирует субагента до любой работы (это шлюз, а не инструкция промпта — evidence, а не compliance-проза).

### Руководство по очистке контекста (FR-3.5)

При завершении каждой фазы инструмент испускает руководство, называющее минимальное состояние для сохранения (указатель миссии, активные дельты, id манифеста сессии) и безопасно ли очищать. Событие `phase.completed` испускается **атомарно с коммитом артефакта фазы** — удовлетворяя условию governance-protocol v1.2.1, что тишина core-event должна быть tripwire: закоммиченный артефакт фазы без своего события — аномалия, которую отмечает проход обнаружения.

## Слой 2: Конечный автомат цикла обзора (FR-8.4)

### Состояния

```
implement → review(cycle-1: full contract)
   ├─ accept → next stage
   ├─ reject → rework → review(cycle-2: feedback + delta since prior)
   │             ├─ accept → next stage
   │             ├─ reject → rework → review(cycle-3: feedback items only)
   │             │             ├─ accept → next stage
   │             │             └─ reject/unchanged → arbitration
   │             └─ safety valve (new critical defect) → review(full contract, one cycle) → re-narrow
   └─ ...
```

- **Сужение ограничено промптом:** промпты обзора цикла 2+ содержат только дельту, предыдущую обратную связь, неразрешённые пункты; settled-пункты перечисляются как treated-as-settled (FR-8.4 AC).
- **Предохранительный клапан:** новый критический дефект вне суженной области сбрасывает покрытие на один цикл (логируется).
- **Отсутствие сходимости → арбитраж:** маршрутизация согласно FR-2.5 Class B, включая цепочку fallback (ответственный владелец → объявление владения → блокирующая ошибка конфигурации).
- **SLA арбитража (по умолчанию 72 ч):** истечение SLA — **арифметика дедлайна в точках вызова** — каждая точка входа CLI/CI вычисляет pending deadlines из временных меток `arbitration.pending`; истечение переключает состояние миссии в escalation-pending, отображается в наблюдаемости FR-4.2 с повторным уведомлением по настраиваемой каденции. Никакого процесса-таймера не существует (NFR-5). Повторное уведомление может использовать сетевой оверлей, отключаемый kill switch (NFR-3).
- **Атомарная эмиссия:** `review.verdict` коммитится с артефактом вердикта; `arbitration.pending` с записью вычисления дедлайна. Тишина о завершённом обзоре — tripwire, а не отсутствие доказательства.

## Слой 3: Runtime шлюзов и remedial-диспетчеризация (triggering KU #6)

### Шлюзы как проверки evidence

Каждый шлюз — код инструмента, проверяющий именованное evidence — никогда вызовы навыков (разделение gate/trigger). Нормативные шлюзы: **FR-2.2** drift, **FR-3.2** TDD, **FR-3.3** верификация наследования (Layer 1), **FR-4.1** блокировка неразрешённого решения, **FR-8.4** правила циклов, **FR-8.6** предварительная проверка обновления — список неисчерпывающий; любая tool-side проверка именованного evidence, решающая, проходит ли шаг, является шлюзом. Вердикт шлюза — **core-emitted событие, коммитируемое атомарно с его записью решения**.

**Механизм атомарной эмиссии.** «Коммитится атомарно» означает: **один git commit несёт и изменение артефакта, и добавленную запись события.** Git — транзакция — никакого write-ahead log, никакой отдельной транзакционной машинерии. Per-mission журналы single-writer по построению (изоляция worktree FR-5.3 даёт каждой миссии собственный worktree); редкие параллельные записи глобального журнала (обновления протокола, переключения kill-switch) разрешаются как обычные git merge. Физическая схема записи определена в [data-formats.md](./data-formats.md) под требованием атомарности, записанным здесь.

### Механизм диспетчеризации (KU #6 разрешён)

Двухканальная диспетчеризация, с разделением, выбранным так, чтобы канал существовал в каждом контексте, где работают шлюзы:

1. **Интерактивный канал (контексты с агентом).** Шлюз инжектирует remedial-запрос в контекст следующего хода сессии — **tool-side mid-session инъекция**, отличная от always-loaded списка триггеров (который является ambient-метаданными, читаемыми агентом): компактный блок, называющий заблокированное evidence и производящий навык. Доставка гарантирована, потому что шлюз контролирует tool-side точку инъекции; затем агент вызывает навык через нативную грамматику harness. Это универсальный канал для интерактивных harness (FR-6.1) и не требует поверхности хуков.
2. **Headless-канал (CI/контексты без агента).** Нет контекста агента для инъекции. Шлюз **валит шаг с remedial exit code** и структурированной failure payload, называющей evidence и навык. Remedial-вызов затем выполняется тем runner, который вызывает инструмент (CI job, pre-commit hook) — наша командная поверхность предоставляет `run <skill>` headlessly. «May dispatch» из triggering.md v1.0.0 разрешается в: *интерактивные контексты получают гарантированную in-session диспетчеризацию; headless-контексты получают гарантированный failure-plus-command, и backstop-гарантия в том, что шаг не проходит — что всегда было核心 утверждением.*

**Headless-классификация (FR-3.1 / NQ-H).** Вызовы классифицируются по **происхождению решения** — кто решил, что навык применим. В обоих каналах это шлюз: интерактивно через инъекцию, headlessly через failure payload, называющий evidence и навык. Вызов runner, выполненный *непосредственно в ответ на payload* (запуск названного навыка), — тупой исполнитель решения шлюза: считается **remedial auto-triggered**. Вызов, настроенный независимо от payload, — **explicit** — конфигурация — ближайший аналог пользовательской команды в терминах FR-3.1. Это сохраняет метрику хорошо определённой в CI-средах, где шлюзы делают большую часть работы.

**Граница цикла (per FR-8.4 cycle):** одна диспетчеризация на блокировку шлюза на цикл обзора; постоянный сбой эскалируется (прерывание FR-3.6 или отклонение FR-8.4), никогда не повторяется.

**Известное неизвестное #1 (этот документ):** достаточны ли два канала — в частности, предоставляет ли каждый интерактивный harness в наборе FR-6.1 tool-controllable точку инъекции, пригодную для канала 1. Профили интеграции FR-6.1 (data-formats) должны записать это per harness.

## Слой 4: Отчётность о стоимости и учёт церемонии (FR-5.4, FR-1.1/1.4)

Отчёты о стоимости детализируют per mission и phase:

- Накладные расходы базовой линии церемонии vs **допуск строгого принуждения** (FR-1.4) — отдельная атрибуция, согласно решению v1.4.
- **Стоимость инъекции пакета субагента** (FR-3.3), per package.
- **Split preemptive/remedial** вызовов навыков (NQ-H, только наблюдаемость; установка цели — CP).
- **Bridged vs native flows** (composition KU #5).
- Сравнение с текущим средним проекта.

Отчёты выводятся из журнала событий + манифестов (артефакты первичны, NQ-L) в точках вызова — без accounting daemon.

## Слой 5: Референсный корпус (FR-3.1 / NQ-H измерение)

Корпус — судья ground truth для первичной метрики (triggering v1.0.1):

- **Состав:** набор репрезентативных задач по уровню церемонии (trivial/standard/critical), каждая с **ground-truth метками, какие навыки применимы**.
- **Политика разметки (контроль независимости).** Авторство меток мейнтейнерами корпуса разрешено (независимый разметчик не знает наших навыков), но каждая метка проходит **состязательный обзор не-автором соответствующего навыка** (ротация), **слепой к runtime-результатам** — обзор меток происходит до или независимо от измерительных прогонов, чтобы рецензент никогда не видел, что «должно было» сработать. Community-contributed кейсы несут метки контрибьюторов через ту же политику, что постепенно расширяет независимость за пределы команды мейнтейнеров. Метки и их обзоры — версионированные артефакты (FR-6.2).
- **Измерение:** запустить корпус per harness; оценить auto-trigger rate как *correctly-triggered applicable invocations without explicit user command, judged by corpus labels*; сообщить split preemptive/remedial рядом (цель в v1 отсутствует).
- **Размер:** достаточно задач на класс harness, чтобы порог 80% был значимым — точное количество — суждение мейнтейнеров корпуса; начальный корпус поставляется с инструментом, растёт через вклад сообщества, и его метки сами являются версионированными артефактами.
- **Известное неизвестное #2 (этот документ):** репрезентативность корпуса для реальных распределений задач — разрыв между curated задачами и органической работой — именно то, что должны измерить полевые данные.

## Слой 6: Механизм верификации подписанного манифеста (отложен из governance-protocol)

Только дизайн возможности — **ни один профиль v1 не требует подписей** (формулировка governance-protocol v1.2.1 управляет; любое требование — накопленный CP, расширяющий FR-1.4 / затрагивающий NFR-3, второй рецензент обязателен при затрагивании NFR-3).

Где проверялась бы подпись, если бы возможность была включена:

- **Точка проверки:** шлюзы merge/archive читают поле подписи манифеста сессии; present-but-invalid подпись **валит шлюз** (tamper-evidence), absent подпись при non-requiring конфигурации **проходит** (возможность, не мандат).
- **Что подписывается:** содержимое манифеста (каноническая сериализация) — не журнал событий (append-only, NQ-L) и не артефакты (git objects уже несут целостность).
- **Обработка ключей:** вне области здесь — распределение ключей, отзыв и офлайн-ограничения (NFR-2, FR-6.7) специфицируются только если/когда CP сделает подписи нормативными; проектировать их сейчас было бы спекулятивной церемонией (P2).

## Интеграция прерываний и human-in-the-loop (FR-3.6)

Триггеры прерываний оцениваются tool-side в тех же точках вызова, что и шлюзы (обнаружение отклонения сравнивает состояние, на которое ссылается план, с состоянием артефактов — артефакты первичны). Поднятое прерывание останавливает и испускает `interrupt.raised` атомарно со своей записью; возобновление требует логированного ответа. В контекстах субагентов конфигурация прерываний наследуется (FR-3.3 item 4), поэтому дочерние сессии останавливаются идентично.

- Формат артефакта отчёта о стоимости

- Схема записи журнала событий и физическая дисциплина атомарности (single-commit, согласно механизму атомарной эмиссии выше; помечено как требование атомарности для data-formats.md)

## Известные неизвестные (этот документ)

1. **Достаточность двух каналов:** предоставляет ли каждый интерактивный harness tool-controllable точку инъекции для канала 1 (записывается per harness в профилях интеграции FR-6.1).
2. **Репрезентативность корпуса:** разрыв между curated задачами корпуса и органическими распределениями работы.
3. **Значения по умолчанию каденции SLA:** 72-часовой SLA арбитража и каденция повторных уведомлений требуют полевой калибровки.
4. **Независимость разметки (эпистемическая):** политика состязательного не-авторского слепого обзора — контроль процесса, а не эпистемическая независимость — долгосрочная валидация — накапливающаяся доля внешне авторских кейсов корпуса, которую должны отслеживать полевые данные.
