# Процесс предложений об изменениях

## Назначение

Этот документ определяет, как [ideal-tool-requirements.md](./ideal-tool-requirements.md) изменяется после его стабилизации в качестве базовой версии v2.0 (2026-10-02). Он реализует механизм предложений об изменениях, упомянутый в примечании о стабилизации базовой версии, и закрывает решение 8 пост-заморозочного обзора (2026-10-02).

## Область: что требует предложения об изменении

Предложение об изменении (CP) требуется **только когда меняется нормативный текст** — то есть когда идентификатор FR, NFR или PG приобретает, теряет или изменяет текст требования либо критерии приемки.

CP **не требуется** для:

- Архитектурных решений, которые реализуют требование без изменения его текста (выбор механизма, спецификации форматов, декомпозиция модулей)
- Дополнительной наблюдаемости или аудита, которые не запрещены ни одним требованием (например, аудит триггеров preemptive-vs-remedial, добавленный решением Q3)
- Уточнений, записанных в сопутствующих документах (архитектурный документ, заметки о будущей совместимости), которые не противоречат базовой версии
- Ненормативных правок прозы (опечатки, формулировки), которые применяются напрямую с записью в журнале изменений

**Операционный тест:** *ведёт ли себя какой-либо критерий приемки иначе после этого изменения?* Если да — это CP. Если никакая соответствующая реализация не может изменить статус pass/fail — это не CP.

Эта граница существует, чтобы заморозка не превратилась в бюрократию, против которой предупреждает сама базовая версия (P2, FR-7.4).

## Формат CP

```
# CP-YYYY-MM-DD-NNN: <Title>

## Motivation
Why the change is needed. What evidence or experience drives it.

## Affected identifiers
- FR-X.Y: <what changes>
- NFR-X: <what changes>
- PG-X: <what changes>

## Proposed change
Exact textual changes: additions / modifications / deletions.
For modifications: before / after.

## Impact on acceptance criteria
For each affected requirement: are ACs added, modified, or removed? How?

## Impact on cross-references
Which other FR/NFR/PG reference the affected identifiers? Do they require updates?

## Alternatives considered
What else was considered, and why it was rejected.

## Review
- Reviewer(s): <name(s)>
- Reviewed: <date>
- Second reviewer (required when NFR-3 is affected): <name or n/a>

## Decision
[Proposed | Accepted | Rejected | Withdrawn] — <date> — <owner>
- If Rejected: reason.
- If Withdrawn: replaced-by (CP id, or none).
- If Accepted: application mode — immediate (annotated) | accumulated (fold revision).
```

## Хранение и идентичность

- CP хранятся в `docs/research/spec-tools/proposals/` как `CP-YYYY-MM-DD-NNN.md`, версионируются как обычные артефакты репозитория согласно FR-6.2
- Номера CP никогда не переиспользуются; отозванный CP сохраняет свой номер с указателем `replaced-by`
- Более поздний принятый CP заменяет более ранний, затрагивающий тот же текст; оба остаются в реестре
- Ревизии во время обзора обрабатываются через историю git

## Владение и обзор

- **Утверждающий:** сопровождающий проекта или назначенный архитектурный руководитель
- **Второй рецензент:** требуется для любого CP, затрагивающего NFR-3 (безопасность/приватность)
- Подпись обзора фиксируется в разделе Review CP до внесения решения

## Жизненный цикл

**Proposed → In Review → Accepted | Rejected → Applied**

- Любой может подготовить CP
- In Review: привлечён как минимум один рецензент (два, когда затронут NFR-3)
- Решение фиксируется с датой и владельцем; отклонения записывают причину
- Применяется согласно правилу применения ниже

## Правило применения

Два режима:

- **Немедленный (аннотированный).** Разрешён только для уточнений, устраняющих неоднозначность, и ненормативных правок — случаев, когда никакая соответствующая реализация не может изменить статус pass/fail. Текст базовой версии обновляется на месте с завершающей аннотацией `[CP-YYYY-MM-DD-NNN]`.
- **Накопленный (свёрточная ревизия).** Требуется для любого изменения, которое может повлиять на поведение верификации, включая модификации, удаления и **дополнительные критерии приемки**. Принятые CP перечисляются в истории ревизий базовой версии как ожидающие и сворачиваются в следующую нумерованную ревизию (v2.1, v3.0, …) — редкое, намеренное событие.

Обоснование: перекрёстные ссылки на идентификаторы FR/NFR/PG должны оставаться стабильными для читателей. Дополнительный рост, который ужесточает верификацию, — это семантическая изменчивость, а не уточнение, и он относится к свёрточным ревизиям.

## Связь с открытыми вопросами

Открытый вопрос (в настоящее время Q2–Q6 базовой версии) может закрыться одним из трёх способов:

- **(a) Разрешён через CP** — когда решение меняет текст требования
- **(b) Отложен как архитектурное решение** — записан в архитектурном документе без изменения базовой версии
- **(c) Закрыт без изменений** — когда обсуждение приходит к выводу, что базовая версия уже покрывает вопрос

## Реестр отложенных проектных решений

Следующие вопросы намеренно направлены в архитектурный документ, а не в базовую версию (механизм (b) выше):

- **Протокол управления**: единый версионированный контракт с двумя гранями — схема событий и представление правил (Q2, Q6, NQ-C); синхронное мажорное версионирование
- **Механизм триггеров**: хуки + минимальный список триггеров + шлюзы уровня инструмента; middleware исключён из базовой комбинации, разрешён как отключённый по умолчанию плагин в рамках NFR-4 с подчинением kill-switch, анализом приватности и раскрытием обработки данных (Q3, NQ-A, NQ-K)
- **Вторичная метрика триггеров**: аудит preemptive vs remedial вызовов — только наблюдаемость для v1; цель отложена до появления базовой линии по референсному корпусу FR-3.1 (NQ-H)
- **Условия spec-as-source**: независимая верификация, маркировка сгенерированных артефактов, round-trip плюс property-test-компаньон, производный от спецификации (Q4, NQ-D)
- **Формат spec-tree**: адресуемость по идентификатору репозитория, чтобы избежать будущего кросс-репозиторного ломающего изменения; классы ссылок broken vs unresolvable (Q5, NQ-E)
- **Формат инъекции правил**: наследование управления в digest-форме, разрешение во время сборки, ключи кэша по content-digest (которые включают инвалидацию FR-5.5 для входов конфигурации) (Q6, NQ-B, NQ-I)
- **Область подтверждения**: «project» в FR-1.4 подтверждён как per-repository (NQ-F, подтверждено 2026-10-02): подтверждение vibe+Critical — это принятие политики на уровне проекта — записывается один раз в конфигурации репозитория (FR-6.2) и наследуется всеми модулями; команды с более строгими риск-аппетитами на уровне модулей выбирают более строгие профили per-task (FR-1.4), а не подтверждают заново. Подтверждение с областью пути и сброс на уровне модуля через переопределение FR-2.9 остаются будущими кандидатами в CP, актуальными в основном для монорепозиториев с сильной автономией модулей. Устаревание при смене команды — задокументированное ограничение v1
- **Каденция арбитража**: повторные уведомления без верхней границы для v1; состояние escalation-pending наблюдаемо через FR-4.2 (пункт обзора 2.3, принят как есть)
