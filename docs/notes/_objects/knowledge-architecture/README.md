# Идея: архитектура знаний — «контент стабилен, структура виртуальна»

## Проблема

База знаний проекта (research-заметки, спеки, ADR, идеи) должна быть удобна и человеку, и AI-агенту, и при этом не деградировать при эволюции. Три зафиксированные боли:

1. **Перемещение файлов ломает git diff и дорого.** При смене статуса/темы артефакта его перемещают (`inbox/ → active/ → decided/`): rename detection ломается («удалён + создан» вместо «перемещён + изменён»), а агент тратит 2000+ токенов на перемещение файла в 1000 строк (прочитать + переписать).
2. **Статус и тема не вписываются в иерархию.** Поиск (grep/rg) ищет по содержимому, не по путям — статус только в директории не находится поиском, только в frontmatter не виден в tree. Один файл часто относится к нескольким темам — жёсткая иерархия не позволяет поместить его в несколько каталогов.
3. **Навигация для человека и агента разнится.** Человек навигирует деревом (tree, IDE), агент — поиском по содержимому. Нужен механизм, работающий для обоих без дублирования контента.

## Почему готовые решения не закрывают

- **Физическое перемещение (inbox/active/decided)** — решает статус ценой сломанного diff и дорогих операций агента.
- **MOC (Map of Content)** — «документ, а не структура»: дополнительный шаг навигации, требует поддержки (вручную забывают, скриптом — ещё одна генерация), невидим для `ls`/`fzf`/IDE/`find`.
- **Только frontmatter** — статус невиден в оглавлении (tree); агенту нужен парсинг вместо `ls`.
- **Симлинки «в лоб»** — риски: Windows без Developer Mode, абсолютные пути, циклы, grep не следует. Отбрасываются поспешно без купирования.
- **Готовые SDD-инструменты** (Spec Kitty, specs.md) — организуют по mission/change, не по теме; не накапливают cross-mission knowledge.

## Ценность

Единая архитектура, снимающая все три боли одновременно:

- **Чистый diff**: файл не тронут, изменился только индекс/симлинк (1 строка).
- **Дёшево для агента**: смена статуса/темы — O(1) токенов (скрипт), не 2000+.
- **Один файл — много тем**: теги `topics:` + несколько симлинков, ноль перемещений.
- **Нативная навигация для обоих потребителей**: человек — tree/IDE, агент — `ls` (views/) или `rg` (notes/).
- **Source of truth один**: frontmatter; всё остальное — материализация, регенерируемая.

## Архитектура

**Принцип: контент стабилен (файлы не перемещаются), структура виртуальна (индексы, теги, симлинки), статус — данные (frontmatter), а не местоположение (директория).**

```
research/
├── notes/YYYY-MM-DD-<slug>/   # РЕАЛЬНЫЕ ФАЙЛЫ. Source of truth. Не перемещаются.
│   └── README.md              # frontmatter: status, topics, author, created, updated, decision?
├── views/                     # СИМЛИНКИ. Материализация frontmatter. Не редактируется вручную.
│   ├── by-status/<status>/<slug> -> ../../notes/…
│   └── by-topic/<topic>/<slug> -> ../../../notes/…
├── indexes/                   # (опц.) MOC, auto-generated _index.md
├── meta/insights.md           # журнал инсайтов о самом процессе
└── scripts/                   # research-status.py, research-index.py, research-link.py
```

**Механика**: frontmatter в `notes/` — единственный source of truth → `research-link.py sync` → `views/` перестраивается (идемпотентно). CI = `verify` (битые симлинки → exit 1). Симлинки всегда относительные; никаких симлинков на симлинки.

**Риски симлинков и купирование** (честный разбор): Windows — `core.symlinks=true` + WSL, fallback CI-генерируемые indexes/; абсолютные пути — запрещены скриптом; grep не следует — «фича, не баг» (notes/ для поиска, views/ для навигации); циклы — правило «только на notes/» + CI; merge conflicts — git хранит симлинк как однострочный blob (тривиально).

**Вердикт по навигации**: симлинки — primary (человек через tree, агент через ls); frontmatter — source of truth; MOC — опционально для аннотированных обзоров с контекстом («это документация, не навигация»).

## Мета-процесс: инсайт → правило

Знания о самом процессе эволюционируют по тому же pipeline: **инсайт** (журнал `meta/insights.md`, статусы `raw → confirmed → promoted`) → **практическая проверка** → **правило в CONVENTIONS.md**. Это механизм, при котором система улучшает сама себя: семь инсайтов пользователя (#1–7) превратились в эту архитектуру именно так.

**Таблица «инсайт → решение»** (основание): иерархия = оглавление → `notes/YYYY-MM-DD-<slug>/`; поиск не видит пути → frontmatter status/topics + auto-index; move+edit ломает diff → файлы не перемещаются; агенту дорого → скрипт O(1); много тем → теги + views; симлинки рискованны → купирование + правила; ссылка дешевле файла → индексы обновляются, файлы — нет.

## Переносимость за пределы research/

Принцип применим к любому эволюционирующему корпусу: KB-статьи (эта база — кандидат), спеки, ADR-коллекции, ideas/. Инвариант: никогда не перемещать контент ради статуса/темы; статус и темы — данные; навигация — материализация. Для малых корпусов S (< 100 файлов) допустима упрощённая модель `inbox/active/decided` (цена перемещения мала); notes/+views/ — рекомендуемая для M+.
