## 2. Целевые артефакты и их отношение

Предлагаемая структура (директории верхнего уровня репозитория):

```
research/                  # весь ресёрч: inbox + обработанное
  inbox/                   # зона не обработанного (как сейчас)
  kb/                      # ← БАЗА ЗНАНИЙ (атомарные, стабильные справочные статьи)
    landscape/             #   инструменты/фреймворки: 1 файл = 1 сущность или сравнение
    methods/               #   методологии и нотации: ADR, EARS, BDD, C4/arc42, SDD-подходы
    principles/            #   выделенные принципы (из критики и синтеза)
    meta.yaml              #   реестр KB-статей (см. §5)
guide/                     # ← РУКОВОДСТВО (нарратив, ссылается на research/kb)
ideas/                     # ← высокоценные идеи и принципы → зародыш новой системы
  <idea>/                  #   problem / decision-drivers / value / architecture / status
STATUS.md                  # трекинг обработки (см. §5)
```

Разделение по **типу изменчивости и читателю**:

| Артефакт | Тип | Читатель | Изменчивость |
|---|---|---|---|
| `research/kb/` | Справочный (descriptive): что существует, pros/cons, ссылки | Все, включая AI-агентов | Низкая-средняя; точечные обновления |
| `guide/` | Нарративный + прескриптивный: путь через ландшафт, как выбирать, на каких принципах строить | Архитекторы, CTO | Средняя; главы ревизуются целиком |
| `ideas/` | Генеративный: наши собственные идеи, проблемы, архитектурные эскизы | Мы сами | Высокая; живые документы |

Ключевое решение: **KB и guide — отдельные слои**. KB держит фактуру (сущности, сравнения, источники), guide — логику выбора и повествование, ссылаясь на KB. Это позволяет использовать KB и в других представлениях (ваш пункт 2), не дублируя фактуру в гайде. Если позже окажется, что гайд достаточен сам по себе, KB остаётся его фактическим приложением — слияние всегда дешевле разделения, поэтому начинаем с разделёнными.

## 3. Контуры руководства (проект глав)

Намечается по материалам inbox; детализация после обработки фаз 1–2:

1. **Введение: проблема** — фрагментированный ландшафт, документация отрывается от кода, AI меняет правила (из C/00, D).
2. **Принципы** — docs-first, git-as-source-of-truth, формат > инструмента, human approves / agent executes, масштабируемость overhead'а, durable context (из B/goals, C/00, D, E).
3. **Карта ландшафта** — таксономия: управление решениями (ADR/RFC), нотации требований (EARS, SbE), исполняемые спеки (BDD), архитектурная документация (C4/arc42), SDD-инструменты AI-эры, docs-as-code платформы, контракты API (из A, C/01, C/09).
4. **SDD и AI-агенты: что работает, что нет** — синтез критики: Plan Mode is Dead, провалы OpenSpec, DX-ловушки, контрактное программирование как альтернатива (из D + свежие источники из F).
5. **Проектирование процесса под масштаб** — уровни L0–L4, продвижение артефактов между уровнями, пайплайн Idea→PRD→RFC→Spec→ADR→Code (из B, C/02).
6. **Структура репозитория и toolchain** — раскладка директорий, реестр инструментов с альтернативами, критерии выбора и миграции (из C/06, C/09, C/04).
7. **AI-агенты в процессе** — AGENTS.md/CONSTITUTION.md, протоколы, approval-гейты, durable context (из C/05, B/ai-agent-workflows, E).
8. **Исследовательские процессы** — как вести research внутри проекта: шаблоны, хранение, связь с ADR (из E).
9. **Операционка** — CI/CD для документации, метрики, обучение/онбординг, review-коллаборация (из C/07, B/metrics, B/training, B/review).
10. **Открытые вопросы и трейдоффы** — честный раздел о нерешённом (из C/03, D).

## 4. Фазы обработки

Каждая фаза завершается коммитом и обновлением STATUS.md — точка безопасного прерывания сессии.

- **Фаза 0 (эта сессия).** План, STATUS.md, схемы метаданных. Готово к прерыванию в любой момент.
- **Фаза 1. KB-фундамент из готового (A → kb/methods, часть C/01 → kb/landscape).** Самое структурированное, быстрый результат, задаёт формат KB-статьи.
- **Фаза 2. Критика → kb/principles + черновик главы 4.** Три исследования D синтезируются в: (а) набор принципов с атрибуцией источников, (б) нарратив критики.
- **Фаза 3. Процессное ядро: синтез с нуля по сырью v2+v3 → главы 5–6 + kb-статьи уровней/пайплайна.** Ни v2, ни v3 не наследуются как каркас; конфликты (L0–L4 vs модульный процесс) решаются в пользу новой модели. Самая трудоёмкая часть.
- **Фаза 4. Исследовательские процессы (E → глава 8 + шаблоны в kb).** Расщепить research-process.md по его внутренним секциям.
- **Фаза 5. AI-collaboration + операционка (B-вертикали, C/05, C/07 → главы 7, 9).**
- **Фаза 6. Внешние источники (F) + свежий поиск.** Исследовать spec-weave, Spec Kitty, specs.md, Spec Kit; целевой свежий поиск по ландшафту SDD (сравнения инструментов, состояние BMAD/Kiro/OpenSpec, новая критика после 09.2026) — web_search + чтение первоисточников. Дополняет главы 3–4.
- **Фаза 7. Сборка гайда целиком: сквозное повествование, введение, заключение, перекрёстные ссылки.**
- **Фаза 8. Идеи (ideas/) — выделение высокоценных принципов.** Параллельно фазам 2–5 ведём журнал кандидатов; на фазе 8 оформляем. **Известные входы (указаны пользователем 2026-09-30):** инсайты #1–7 (E, строки 618–628), разбор «Симлинки против MOC» (E, строки 1096–1562, сравнительная таблица 1487–1500); v2/goals.md (Vision, Core Principles); v2/modular-process.md (модульность); v3/00-goals.md (G4 коллаборация, G5 масштабируемость, G2 docs-first, P1–P10); сквозной принцип «избегать ненужного трения». Фазы 1–2 независимы; фаза 3 — синтез, требует завершения фаз 1–2 как входа.

## 5. Трекинг прогресса между сессиями

Два механизма, взаимно проверяемые:

### 5.1 STATUS.md (уровень источников)

Таблица: одна строка = один исходный файл (или логический кусок большого файла, напр. секция E).

| source | группа | статус | куда выгружено | охват / остаток | сессия |
|---|---|---|---|---|---|
| documentation-process/reference/sdd-landscape.md | A | done | kb/landscape/sdd-tools.md | полный | 2026-09-30 |
| research-and-notes/research-process.md | E | partial | kb/methods/research-kb.md | §§1–5 извлечены; остаток: секции про шаблоны, сводные таблицы | … |

Статусы: `new` → `triaged` (прочитан, определено назначение) → `partial` → `done` → `archived` (выгружен полностью, источник можно убрать из inbox или пометить). Плюс `deferred` (сознательно отложен) и `rejected` (не несёт ценности — с причиной).

Правило частичной обработки: запись в STATUS обязана содержать «охват / остаток» в терминах секций источника, чтобы следующая сессия продолжила без перечитывания.

### 5.2 meta.yaml (уровень KB-статей)

Каждая KB-статья регистрируется: `id, title, status (stub|draft|reviewed), sources[] (какие inbox-файлы поглощены), last_touched, freshness_notes`. По sources[] можно машинно проверить покрытие: каждый inbox-файл со статусом done должен встречаться хотя бы в одном meta.yaml.

### 5.3 Протокол сессии

1. Начало: прочитать STATUS.md + этот PLAN.md → выбрать работу.
2. Конец: обновить STATUS.md (статусы, охваты), meta.yaml, журнал идей-кандидатов; коммит.

## 5.4 Работа с отклонениями от пути

План — это понимание направления, а не рельсы. Споткнулись (фаза оказалась больше ожидаемого, источник не даёт ожидаемого, гипотеза структуры KB/guide не подтвердилась, появились новые данные) — протокол:

1. **Фиксация.** Запись в `research/STATUS.md` (история сессий): что случилось, где именно, почему путь выглядит неоптимальным/тупиковым.
2. **Ориентация.** `PLAN.md` + `STATUS.md` отвечают на вопросы «где мы» (фаза, статусы строк, журнал), «что уже сделано и не надо переделывать» (done-строки — накопленный прогресс не теряется при смене пути), «какие пути есть» (оставшиеся фазы, deferred-строки, открытые вопросы).
3. **Шаг назад.** Любая фаза/строка откатывается до точки последнего согласованного состояния (коммиты после каждой фазы — чекпоинты). Частичная работа не обнуляется: «охват / остаток» в STATUS фиксирует, что из сделанного валидно при любом пути.
4. **Пересмотр пути.** `PLAN.md` обновляется явной правкой (что меняем и почему), а не молчаливым сдвигом; история сессий в STATUS сохраняет причину смены курса.
5. **Продолжение.** Ближайшее выполнимое действие по новому пути — в той же сессии, чтобы направление подтверждалось делом, а не только правкой документов.

Инвариант, который держит любые смены пути: STATUS всегда отражает фактическое состояние каждого источника; коммит после каждой фазы — точка возврата.

## 7. Принципы самой работы (мета)

- **Поглощение, а не копирование.** KB-статья пишется заново по источникам; источник помечается поглощённым. Дословные куски — только шаблоны/таблицы, где форма — суть.
- **Атрибуция.** Каждое утверждение о внешнем мире — со ссылкой на источник (в KB — обязательный раздел «Источники»).
- **Никаких «окончательных» версий.** Статусы reviewed не означают frozen; свежесть фиксируется в meta.yaml, пересмотр — по мере фазы 6 и новых поступлений.
- **Источник не удаляем**, пока его статус не `archived` — и тогда решаем: оставить в inbox как сырьё или убрать.
