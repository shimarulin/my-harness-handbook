# Принцип: требование живёт в самой дешёвой форме, способной его удерживать

| Параметр | Значение |
|---|---|
| Статус | draft |
| Обновлено | 2026-09-30 |

## Что это

Центральный принцип выбора формы спецификации: вместо единой текстовой спеки каждое требование выражается в самой дешёвой формализуемой форме, которая способна его удерживать. Словами остаётся только то, что «формализуется дороже, чем нарушается». Формулировка: **Dhwtj** (enterprise architect, тред Хабра, 2026-09-28/29); развито в материалах корпуса критики под влиянием Шапиро.

Следствие: текстовая спецификация сжимается до минимума; «море Markdown» — анти-паттерн: детальная проза-спека рискует стать «кодом, написанным прозой» и дрейфовать от реального кода.

## Таблица форм (требование → форма)

| Тип требования | Форма | Кто проверяет |
|---|---|---|
| Структурный инвариант домена | **Тип** («illegal states unrepresentable» — type-driven design, концепция Влашина; `Money` неотрицательным на уровне типа) | Компилятор |
| Граница систем | **Схема данных + контрактный тест** (OpenAPI + Pact) | Машина (CI) |
| Обобщённое намерение | **Property-based тест** («сумма долей равна единице») | Машина (CI) |
| Конкретное поведение | **Пример / unit-тест** (`calculateDiscount(500, gold) == 12%`) | Машина (CI) |
| Причины решений, разрешение конфликтов, триггеры пересмотра | **ADR** | Человек (форма текста дешевле нарушения) |

## Машинная проверка — фундамент, не надстройка

«Судьба SDD решится не качеством спек и не workflow, а появлением дешёвого машинного enforcement/доказательства: заранее созданных тестов, типов, контрактов… Спека словами не отменяется, она сжимается до минимума» (Dhwtj).

Подтверждение из практики: «If nothing blocks on spec/code divergence, divergence is the default outcome over time» (CodeMySpec, 2026-06-03).

Историческая проверка идеи «спека = исполняемые тесты»: BDD и Specification by Example Гойко Аджича (2011) взлетели частично — ценность оказалась в разговоре при построении сценариев, а артефакт (Gherkin + step definitions) стал вторым слоем поддержки, «который гнил быстрее кода» (Dhwtj).

## Verification vs Validation (различие Бёма)

Barry Boehm, «Software Engineering Economics» (1981):

| | Verification | Validation |
|---|---|---|
| Вопрос | «Правильно ли построен продукт?» | «Тот ли продукт построен?» |
| Что сверяется | Код с контрактом | Контракт с намерением |
| Кто | Машина | Человек (голова) |

Практика: не пытаться формализовать всё — для validation остаются разговор, ревью, ADR; для verification — машинно-проверяемые артефакты. Ограничения: (1) машинно проверяемо только дёшево формализуемое — либо полнота дорого, либо неполнота; (2) «если enforcement/доказательство создал LLM, то это фигня, надо писать самому — сложность из разработки перетекает в проектирование доказательства корректности» (Dhwtj).

## Сильные и слабые стороны

Сильные: устраняет главный драйвер спек-дрейфа (непроверяемая проза); каждая форма проверяется дешёвейшим доступным способом; текст остаётся там, где он незаменим (причины, контекст).

Слабые / открытые вопросы: требует компетенции в типах/контрактах/PBT (порог входа выше, чем Markdown); полнота формализации vs её стоимость — нет общего ответа (открытый вопрос корпуса); не решает validation (намерение) — только verification.
