## Что это

Нормативный каркас целей и ограничений, из которого выведено всё процессное ядро (уровни, пайплайн, структура, tooling). Синтез: 5 Core Principles (v2 goals) + 10 принципов P1–P10 (v3 00-goals) + constraints + риски + критерии успеха. Это слой «конституции» процесса — ответ на вопрос «почему процесс устроен именно так».

## Vision

Процессы разработки ПО, которые: начинаются с документации и спецификаций, затем переходят к коду; поддерживают совместную работу людей и AI-агентов; сохраняют все артефакты в репозитории (Git-native); используют открытые форматы (no vendor-lock); адаптируются под размер проекта.

## Core Principles (5, v2)

1. **Documentation-First** — документация создаётся до кода; документация — source of truth; код генерируется/пишется на основе спецификаций.
2. **Open Formats & Tools** — все артефакты в открытых форматах (Markdown, YAML, JSON, PlantUML, Mermaid); преимущественно OpenSource; экспорт и миграция данных.
3. **Git-Native** — все артефакты в репозитории; версионирование через Git; code review для документации; ветвление и merge.
4. **Human + AI Collaboration** — AI-агенты генерируют, ревьюят, верифицируют; люди принимают финальные решения; clear handoff.
5. **Scalability** — процессы для проектов любого размера; минимальный набор на старте; структура добавляется по мере роста; monorepo и multi-repo.

## Принципы проектирования P1–P10 (v3) со следствиями

| # | Принцип | Следствие |
|---|---|---|
| P1 | Git — единственный source of truth | Все артефакты — файлы в репо |
| P2 | Формат важнее инструмента | Markdown/YAML первичны, генераторы заменяемы |
| P3 | Один артефакт — одно решение (ADR) | Никаких «мегадокументов решений» |
| P4 | Структура предсказуема | Единая раскладка директорий во всех проектах |
| P5 | Автоматизируй проверку доков | CI линтит и собирает документацию |
| P6 | Минимальный overhead по умолчанию | Уровень процесса выбирается per-инициатива |
| P7 | Пишем для будущего читателя | ADR — «разговор с будущим разработчиком» |
| P8 | Человек утверждает, агент исполняет | Approval-гейты у людей |
| P9 | Обратная совместимость масштаба | L2-артефакт разворачивается в L3 без переписывания |
| P10 | Инструмент можно выкинуть | Никакой критической зависимости от одного OSS-проекта |

Соответствие: P1 ↔ Git-Native; P2/P10 ↔ Open Formats; P8 ↔ Human+AI; P6/P9 ↔ Scalability; P5 — операционное усиление Docs-as-Code. v2-принципы — декларативные «что ценим», P1–P10 — операционные «что из этого следует».

## Constraints (Must / Should / Nice to Have)

**Must Have**: открытые форматы; OpenSource инструменты (или open-core с полной функциональностью); Git-based workflow; поддержка AI-агентов (Claude, GPT, локальные модели); documentation-first.

**Should Have**: multi-repository support; cross-references между артефактами; metrics и dashboards; integration с IDE.

**Nice to Have**: visual editors для диаграмм; real-time collaboration; mobile access; advanced analytics.

**Запрещено (vendor-lock)**: бинарные/закрытые форматы как единственный носитель; сервисы без экспорта в открытый формат; трекинг задач без API (артефакт задачи дублируется в репо, внешний трекер — только зеркало).

## Критерии успеха (5 тестов, v3)

1. **Traceability-тест**: для любого non-trivial коммита можно по цепочке артефактов дойти до исходной идеи/PRD.
2. **Onboarding-тест**: новый участник (или AI-агент) может по репозиторию понять состояние проекта без устных объяснений.
3. **Vendor-exit-тест**: замена любого инструмента не требует конвертации артефактов.
4. **Scale-тест**: задача L1 — overhead ≤ 15 минут на документацию; L4 — полный набор артефактов.
5. **AI-тест**: агент, получивший только файлы репозитория (без истории чатов), корректно имплементирует задачу L1–L2 по спеке.

## Риски и митигации (5)

| Риск | Митигация |
|---|---|
| Over-engineering | Начинать с минимального набора артефактов, добавлять по необходимости |
| Tool fragmentation | Стандартные форматы, interoperability |
| Documentation debt | Регулярные ревью, автоматическая проверка соответствия |
| Resistance to change | Обучение, примеры успешных проектов, постепенное внедрение |
| AI hallucinations | Human-in-the-loop для критических решений, верификация outputs |

## Проблема (мотивация, v3 §2)

Разрозненность ландшафта: тяжеловесные enterprise-процессы (TOGAF, ISO 42010) избыточны для малых команд; лёгкие практики (ADR, BDD) не собраны в сквозной пайплайн «идея → продакшн»; AI-ассистированная разработка (SDD) привязана к экосистемам и закрытым форматам; документация отрывается от кода и устаревает. Требуется связная модель: проверенные практики в единый пайплайн; без vendor-lock; читаема человеком и машиной; деградирует изящно (минимальный overhead для малых задач — полный цикл для крупных).

## Связь с критикой (фаза 2)

Принципы целей не отменяются критикой SDD — они уточняются: Documentation-First не означает BDUF (уровни L0–L4 + итеративное уточнение артефактов); Git-Native имеет границу (upstream requirements work — вне репо, с зеркалированием: кейс Talk Think Do, `process-over-tool.md`); Human+AI Collaboration конкретизируется экономикой внимания и блокирующими gate (`attention-economy.md`, `invariants-and-gates.md`).
