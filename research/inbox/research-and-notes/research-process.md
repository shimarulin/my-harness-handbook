# Системы управления знаниями для процессов исследования в разработке ПО

Для ваших целей — doc-first, Git-native, human+AI collaboration, масштабируемость — наиболее рабочей комбинацией выглядит **гибридный подход: ADR/RFC для решений + Digital Garden (или иерархический Markdown-органайзер типа Foam/Dendron) для исследовательских заметок + "durable context" файлы (AGENTS.md, CLAUDE.md, LEARNINGS.md) для AI-агентов**. Research Compendium оправдан только там, где исследование включает runnable-код и данные (spike, PoC, бенчмарки), но как основа для всей базы знаний проекта он избыточен. Чистый Zettelkasten для командной разработки ПО действительно плохо переносится — об этом ниже.

## Почему классические подходы "не приживаются" в разработке ПО

### Research Compendium: сила в воспроизводимости, слабость в повседневности

Research Compendium задуман для академической воспроизводимости: data + code + text вместе, окружение зафиксировано (Dockerfile, Makefile, DESCRIPTION)【turn0search5】. Это отлично закрывает потребность G6 из ваших целей ("исследовательские задачи — принципы Research Compendium"), но у него есть ограничения для постоянного процесса:

- **Ориентация на "финальный артефакт", а не на процесс.** Compendium — это "упакованный" результат исследования, готовый к публикации. Ежедневные заметки "я посмотрел 5 библиотек, вот сравнение" в эту структуру не ложатся естественно.
- **Требует дисциплины к окружению.** Для каждого исследовательского цикла фиксировать Docker/Make — overhead, который оправдан только для runnable-исследований.
- **Не решает проблему навигации и связности.** Compendium хорош как единица публикации (один compendium = одно исследование), но не как база знаний, в которой нужно искать связи между десятками исследований.

**Где Research Compendium работает:** spike с кодом, бенчмарки алгоритмов, сравнение производительности библиотек. **Где не работает:** ландшафтные обзоры, сравнение подходов, накопление выводов между циклами.

### Zettelkasten: почему критика оправдана

Zettelkasten часто критикуется, и не без оснований. Основные проблемы, которые отмечают и практики, и сообщества (Hacker News, форумы Obsidian):

- **Самоцель вместо инструмента.** Люди, строящие сложные productivity-системы, часто тратят на их построение столько времени, что продуктивность не растёт, а падает【turn0search0】. Это наблюдение постоянно повторяется в дискуссиях о Zettelkasten.
- **Атомарность конфликтует с командной работой.** Zettelkasten требует атомарных заметок ("одна идея = одна заметка") с плотной сетью ссылок. Для личной рефлексии это работает; для команды, где заметки должны быть читаемы другим человеком (и AI-агентом) без контекста автора, атомарные фрагменты превращаются в кашу.
- **Wiki-links нестандартны и ломают toolchain.** `[[wikilinks]]` — это расширение Obsidian/Foam, не стандартный Markdown. При сборке документации через mdBook, Hugo или CI они ломаются【turn0search6】.
- **Плохо масштабируется для machine parsing.** AI-агенту нужно предсказуемо находить релевантный контекст. Граф из тысяч атомарных заметок со слабой структурой — худший сценарий для retrieval по сравнению с иерархией или курсорными файлами.

Zettelkasten полезен как **личный** инструмент мышления (для одного исследователя, ведущего рефлексию), но как **командная** база знаний для разработки ПО — не лучший выбор.

## Сравнение подходов для ваших целей

| Подход | Для человека | Для AI-агента | Git-native | Подходит для |
|---|---|---|---|---|
| **Research Compendium** | Высокая воспроизводимость, peer review | Хорошо, если окружение зафиксировано (Docker) | Да | Runnable spikes, бенчмарки, PoC |
| **Zettelkasten (чистый)** | Отличен для личной рефлексии, плох для команд | Плохо: нестандартные links, слабая структура | Частично | Личные исследовательские дневники |
| **Digital Garden** | Хорошо: заметки эволюционируют, публичный черновик | Средне: зависит от структуры | Да (если на Markdown) | Ландшафтные обзоры, обучение |
| **ADR + RFC** | Отлично: явные решения с контекстом | Отлично: предсказуемая структура, легко парсится | Да | Архитектурные решения, выбор технологий |
| **Dendron / Foam (иерархия)** | Хорошо: nested структура как в IDE | Хорошо: предсказуемая схема | Да (Markdown) | Организация большого корпуса заметок |
| **AGENTS.md / durable context** | Минимально (для человека не читается как docs) | Отлично: это и есть интерфейс для агента | Да | Правила, конвенции, "память" агента |
| **Agile Spike + findings** | Хорошо: timeboxed, результат — документ | Средне: если находки зафиксированы | Да | Точечные исследования перед фичей |

## Что хорошо работает для человека

**Иерархический Markdown + курсорные файлы.** Для человека лучшая метафора — не "граф идей" (Zettelkasten), а "проект в IDE" (Dendron, Foam). Dendron описывается как "local-first, schema-driven, hierarchical Markdown notes" — это ближе к тому, как разработчики уже мыслят【turn1search7】. Foam добавляет в VS Code backlinks, graph visualization, daily notes и templates, но остаётся в Markdown【turn0search8】.

**Digital Garden для исследовательских областей.** Digital Garden — подход, при котором заметки публикуются как "растущий черновик", а не финальный документ. Он хорошо ложится на ландшафтные обзоры ("вот что я знаю про X, вот что ещё unclear")【turn0search0】.

**Ритуалы вместо инструментов.** Критика сложных PKM-систем показывает: система работает, когда она проста и встроена в существующий workflow (Git, PR, code review), а не когда требует отдельного "садоводства"【turn4fetch0】.

## Что хорошо работает для AI-агента

**Durable context как интерфейс.** AGENTS.md и CLAUDE.md становятся стандартом для передачи контекста AI-агентам — это markdown-файл с инструкциями для агента, а не для человека【turn0search6】【turn0search9】. Файлы — один из самых ясных способов дать агенту durable context【turn0search12】.

**Предсказуемая структура важнее графа.** AI-агенту нужна иерархия с понятной схемой именования (`research/<дата>-<тема>/`, `adr/NNN-*.md`, `rfc/NNN-*.md`), а не семантическая сеть. Иерархия → проще → retrieval → меньше галлюцинаций.

**Markdown-first.** Инструменты типа owledge позиционируются как "Markdown-first durable memory for AI agents"【turn0search10】. Repomix упаковывает весь репозиторий в AI-friendly формат【turn3search1】. Всё это работает потому, что Markdown — общий знаменатель.

**AGENTS.md как точка входа.** В монорепозиториях AGENTS.md/CLAUDE.md размещают в корне и/или в подкаталогах, чтобы агент получал правильный контекст в зависимости от того, с какой частью кода работает【turn0search8】.

# Ответы на уточняющие вопросы

## 1. "Предсказуемая структура важнее графа" — что это значит

**Под "графом"** понимается модель знаний, где основная навигация — через сеть взаимных ссылок между атомарными заметками (как в Zettelkasten или Obsidian с wikilinks). Каждый узел — заметка, связи — `[[wikilinks]]`. Релевантный контент находится переходами по ссылкам, а не по иерархическому пути.

**Под "предсказуемой структурой"** — модель, где путь к информации можно вычислить из соглашения, не исследуя граф. Например: "информация о выборе ORM лежит в `research/decided/2026-09/orm-comparison/`" — это предсказуемо. "Информация о выборе ORM где-то в сети из 500 заметок, связанных backlinks" — непредсказуемо.

Критерии предсказуемости (проверяемые):

- По пути к файлу можно определить его тип и статус (research/decided vs research/active)
- По имени файла можно определить дату и тему (`2026-09-30-orm-comparison.md`)
- Иерархия не глубже 3–4 уровней
- На каждом уровне — ограниченное (менее ~50) количество элементов
- AI-агент, прочитав только структуру директорий (без содержимого), может предсказать, где искать

**Где это записать:** в `CONVENTIONS.md` или `AGENTS.md` в корне репозитория — как часть правил для агентов и людей. Ниже предложу конкретный файл.

## 2. Проблемы с research notes: масштаб, длина, параллельность

Вы правы — предложенный ранее формат `2026-09-30-<slug>.md` не масштабируется. Вот исправленная модель, решающая все четыре проблемы:

### 2.1. Несколько ресёрчей в одну дату → отдельная директория на ресёрч

Вместо файлов в `inbox/` — директория на каждый ресёрч, с уникальным ID:

```
research/
├── inbox/
│   ├── 2026-09-30-orm-comparison/     # один ресёрч = одна директория
│   ├── 2026-09-30-auth-libraries/     # второй ресёрч в ту же дату
│   └── 2026-10-01-caching-strategy/   # следующий день
```

Имя директории уникально по дате + slug. Если в один день два ресёрча про одно и то же — добавляем суффикс: `2026-09-30-orm-comparison-v2/`.

### 2.2. Десятки тысяч строк → иерархическое разбиение на под-файлы

Один файл `findings.md` на 30 000 строк нечитаем ни для человека, ни для агента. Решение — разбивать на под-файлы по мере роста, с `README.md` как точкой входа и индексом:

```
research/active/2026-09-30-orm-comparison/
```

### 2.3. Параллельная работа → изоляция по директориям + merge strategy

Проблема параллельной работы (человек + несколько агентов, возможно на разных машинах) решается тем, что **каждый ресёрч (и каждое под-направление) — отдельная директория**. Конфликты merge в Git возникают в двух случаях:

1. **Разные ресёрчи** — лежат в разных директориях, конфликтов нет.
2. **Один ресёрч, разные агенты** — работают в разных файлах внутри `findings/` (агент A пишет `01-sqlalchemy.md`, агент B — `02-peewee.md`). Конфликт возможен только в `README.md` (индексе) — решается через:
   - Каждый файл findings имеет своего "владельца" (в front-matter)
   - `README.md` обновляется атомарно в конце цикла, а не в процессе
   - Для реальной одновременной работы — использовать Git branches + PR

Front-matter в каждом findings-файле:

```yaml
---
author: "human:vasya"  # или "agent:claude-3"
created: 2026-09-30T14:30:00+03:00
updated: 2026-09-30T16:00:00+03:00
status: draft          # draft | review | final
parent: ../README.md
---
```

### 2.4. "Черновики, не требующие структуры" — в чём цель

Цель `inbox/` — **снизить порог входа для начала исследования**. Когда исследователь (человек или агент) начинает смотреть тему, он ещё не знает, выльется ли это в полноценный research-цикл или это просто "быстро глянул пару ссылок и понял, что не то".

Если требовать сразу структуру (README, question.md, findings/), то:
- Для мелких исследований overhead слишком велик
- Исследователи (особенно агенты) будут откладывать фиксацию находок
- База знаний будет пустеть

`inbox/` — это место, где можно начать с одного файла `notes.md` без какой-либо структуры. Если находок много и тема важная — промоут в `active/` со структурой. Если это были "две ссылки и вывод 'не подходит'" — остаётся в `inbox/`, но с минимальным README.

**Правило промоушена:** если в `inbox/<slug>/` больше 3 файлов или больше 500 строк — пора промоутить в `active/`.

# Инсайты: где жить и что из них следует

Ваши инсайты — это не просто заметки, это **эволюция архитектуры базы знаний**. Они ломают мою предыдущую модель (`inbox/ → active/ → decided/` через перемещение файлов) и указывают на более правильную. Разберу каждый и предложу, куда их записать.

## Куда записывать инсайты

Инсайты о процессе — это **мета-уровень** базы знаний. Они отличаются от "learnings" о технологиях. Предлагаю два места:

1. **`research/meta/insights.md`** — журнал инсайтов (сырой, растущий вниз)
2. **`CONVENTIONS.md`** — куда инсайт "промоутится", когда подтвердился и превратился в правило

Инсайт → практическая проверка → правило в CONVENTIONS.md. Это тот же pipeline, что и `inbox → active → decided`, но для знаний о самом процессе.

### `research/meta/insights.md`

```markdown
# Process Insights

Журнал озарений о том, как устроена база знаний.
Каждый инсайт: дата, автор, текст, статус (raw → confirmed → promoted).

---

## 2026-09-30 | author: human

### Insight #001: Иерархия файловой системы работает как оглавление
**Статус:** raw

Древовидная структура каталогов — естественный оглавление для человека.
Не нужно изобретать отдельный индекс — файловая система уже им является.

### Insight #002: Статус должен быть и в структуре, и в frontmatter
**Статус:** raw

Поиск (grep/ripgrep) ищет по содержимому, но не по именам файлов.
Если статус только в директории — его не найти поиском.
Если только в frontmatter — его не видно в оглавлении (tree).
Нужно дублировать: frontmatter для поиска, директория для навигации.

### Insight #003: Перемещение + редактирование ломает diff
**Статус:** raw

git rename detection ломается, когда файл одновременно перемещается
и изменяется. Diff показывает "удалён + создан" вместо "перемещён + изменён".
Решение: git mv отдельно, изменения отдельно. Или — не перемещать вообще.

### Insight #004: Перемещение агентом — дорого по токенам
**Статус:** raw

Если AI-агент перемещает файл, он читает содержимое и переписывает его
в новом месте. Для файла в 1000 строк это 2000+ токенов на одно перемещение.
Скрипт делает то же за O(1) по токенам.

### Insight #005: Один файл — много тем
**Статус:** raw

Иногда файл относится к нескольким темам одновременно.
Жёсткая иерархия файловой системы не позволяет поместить файл
в несколько каталогов. Нужен другой механизм для тем.

### Insight #006: Плоская структура + симлинки
**Статус:** raw

Хранить файлы в одном месте, создавать симлинки для организации.
Риск: симлинки теряются при копировании, не работают на Windows,
ломаются в некоторых инструментах.

### Insight #007: Перемещать ссылку, не файл
**Статус:** raw

Если файл остаётся на месте, а "перемещается" только ссылка на него
(в индексе, в MOC), то diff чистый: файл не тронут, изменился только индекс.
```

## Архитектурное следствие: пересмотр модели

Инсайты #3, #4, #5, #7 вместе указывают на принципиально другую архитектуру:

> **Файлы не перемещаются. Статус меняется в frontmatter. Навигация — через индексы.**

### Проблема с перемещениями (инсайты #3, #4)

Модель `inbox/ → active/ → decided/` требует физического перемещения файлов. Это:
- Ломает diff (#3)
- Дорого для агентов (#4)
- Создаёт шум в git log (commit "moved file" вместо полезной информации)

### Проблема с темами (инсайт #5)

Жёсткая иерархия не позволяет файлу быть в нескольких темах. Классическая проблема, для решения которой в Zettelkasten-мире придумали **MOC (Map of Content)** — индексные файлы, которые собирают ссылки на заметки по теме. MOC — это "виртуальная папка", реализованная как файл со ссылками.

### Предлагаемая архитектура: "Content stays, structure is virtual"

```
research/
├── notes/                          # ВСЕ файлы. Плоско или по дате создания.
│   ├── 2026-09-30-orm-comparison/  # Никогда не перемещается
│   │   ├── README.md
│   │   ├── question.md
│   │   ├── findings/
│   │   │   ├── 01-sqlalchemy.md
│   │   │   └── 02-peewee.md
│   │   └── comparison.md
│   └── 2026-10-01-auth-libraries/  # Тоже никогда не перемещается
│       └── ...
├── indexes/                        # Виртуальные коллекции (генерируются или ведутся вручную)
│   ├── by-status.md               # Автогенерируемый: активные, решённые, архивные
│   ├── topic-orm.md               # MOC: всё про ORM
│   ├── topic-auth.md              # MOC: всё про авторизацию
│   └── topic-async.md             # MOC: всё про async (пересекается с ORM)
├── meta/
│   └── insights.md                # Этот журнал
├── templates/
└── learnings.md
```

**Ключевые принципы:**

1. **`notes/` — единственное место, где живут файлы.** Директория = дата создания + slug. Файл не перемещается никогда.
2. **Статус — только в frontmatter.** Меняется скриптом, не перемещением.
3. **`indexes/` — виртуальные коллекции.** MOC-файлы со ссылками на `notes/...`. Один файл может быть в нескольких MOC.
4. **MOC ведутся вручную или генерируются.** Вручную — для тем (человек решает, что к чему относится). Автоматически — для статусов (скрипт сканирует frontmatter).

## Инструменты: скрипт для смены статуса

Решает инсайт #4 — агент вызывает скрипт, не тратит токены на чтение/переписывание файла:

### `scripts/research-status.py`

```python
#!/usr/bin/env python3
"""Change research note status without moving files.

Usage:
  research-status.py <path> --status active --author "agent:claude"
  research-status.py <path> --status decided --author "human:vasya"

Updates frontmatter only. File stays in place.
"""
import argparse
import re
import sys
from datetime import datetime, timezone
from pathlib import Path


def parse_frontmatter(content: str) -> tuple[dict, str, str]:
    """Split file into (frontmatter_dict, fm_raw, body)."""
    fm_match = re.match(r"^---\n(.*?)\n---\n", content, re.DOTALL)
    if not fm_match:
        return {}, "", content
    fm_raw = fm_match.group(0)
    body = content[fm_match.end():]
    props = {}
    for line in fm_match.group(1).split("\n"):
        if ":" in line:
            key, _, val = line.partition(":")
            props[key.strip()] = val.strip().strip('"').strip("'")
    return props, fm_raw, body


def serialize_frontmatter(props: dict) -> str:
    lines = ["---"]
    for key, val in props.items():
        lines.append(f'{key}: "{val}"')
    lines.append("---")
    return "\n".join(lines) + "\n"


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("path", help="Path to research note/directory")
    parser.add_argument("--status", required=True,
                        choices=["draft", "active", "review", "decided", "archived"])
    parser.add_argument("--author", default=None,
                        help="Author (e.g. 'human:vasya' or 'agent:claude')")
    args = parser.parse_args()

    path = Path(args.path)
    if not path.exists():
        print(f"Error: {path} not found", file=sys.stderr)
        sys.exit(1)

    # If directory, update all .md files with frontmatter
    if path.is_dir():
        files = list(path.rglob("*.md"))
    else:
        files = [path]

    now = datetime.now(timezone.utc).isoformat(timespec="seconds")
    updated = 0

    for f in files:
        content = f.read_text(encoding="utf-8")
        props, fm_raw, body = parse_frontmatter(content)
        if not props:
            continue  # No frontmatter, skip

        props["status"] = args.status
        props["updated"] = now
        if args.author:
            props["author"] = args.author

        f.write_text(serialize_frontmatter(props) + body, encoding="utf-8")
        updated += 1
        print(f"  Updated: {f}")

    print(f"\nDone: {updated} file(s) → status={args.status}")


if __name__ == "__main__":
    main()
```

### `scripts/research-index.py`

Генерирует `indexes/by-status.md` из frontmatter (решает инсайт #2 — поиск по содержимому):

```python
#!/usr/bin/env python3
"""Generate indexes/by-status.md from frontmatter in research/notes/.

Usage:
  research-index.py [--root research/]
"""
import argparse
import re
import sys
from collections import defaultdict
from pathlib import Path


def parse_frontmatter(content: str) -> dict:
    fm_match = re.match(r"^---\n(.*?)\n---\n", content, re.DOTALL)
    if not fm_match:
        return {}
    props = {}
    for line in fm_match.group(1).split("\n"):
        if ":" in line:
            key, _, val = line.partition(":")
            props[key.strip()] = val.strip().strip('"').strip("'")
    return props


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--root", default="research", help="Research root dir")
    args = parser.parse_args()

    root = Path(args.root)
    notes_dir = root / "notes"
    index_dir = root / "indexes"
    index_dir.mkdir(parents=True, exist_ok=True)

    by_status = defaultdict(list)
    by_topic = defaultdict(list)

    for md in notes_dir.rglob("*.md"):
        if md.name == "README.md":
            # Use parent dir name as title
            title = md.parent.name
        else:
            title = md.stem

        props = parse_frontmatter(md.read_text(encoding="utf-8"))
        if not props:
            continue

        status = props.get("status", "unknown")
        rel_path = md.relative_to(root)
        by_status[status].append((title, rel_path))

        topics = props.get("topics", "").split(",")
        for topic in topics:
            topic = topic.strip()
            if topic:
                by_topic[topic].append((title, rel_path))

    # Generate by-status.md
    lines = ["# Index: By Status", "", "<!-- Auto-generated. Do not edit manually. -->", ""]
    for status in ["active", "draft", "review", "decided", "archived"]:
        items = by_status.get(status, [])
        if not items:
            continue
        lines.append(f"## {status.title()} ({len(items)})")
        lines.append("")
        for title, path in sorted(items):
            lines.append(f"- [{title}]({path})")
        lines.append("")

    output = index_dir / "by-status.md"
    output.write_text("\n".join(lines), encoding="utf-8")
    print(f"Generated: {output}")

    # Generate per-topic indexes
    for topic, items in sorted(by_topic.items()):
        lines = [f"# Topic: {topic}", "",
                 "<!-- Auto-generated from frontmatter 'topics' field. -->", ""]
        for title, path in sorted(items):
            lines.append(f"- [{title}]({path})")
        lines.append("")
        output = index_dir / f"topic-{topic}.md"
        output.write_text("\n".join(lines), encoding="utf-8")
        print(f"Generated: {output}")


if __name__ == "__main__":
    main()
```

# Симлинки против MOC: честный разбор

Вы правы — я отбросил симлинки слишком поспешно, одной строкой "рискованны". Если файлы не перемещаются и не удаляются (что уже принято), главный риск симлинков — битые ссылки — исчезает. Давайте разберу подробнее.

## Что не так с MOC (ваша критика справедлива)

MOC — это Markdown-файл со списком ссылок. Проблемы при навигации:

1. **Дополнительный шаг.** Чтобы увидеть "что есть по теме ORM", нужно открыть MOC-файл, прочитать его, перейти по ссылке. Симлинк виден сразу в `tree` или file explorer — нулевой шаг.
2. **MOC нужно поддерживать.** Либо вручную (забывают), либо скриптом (нужна генерация, актуальность, запуск в CI).
3. **MOC не интегрируется с инструментами.** `ls`, `fzf`, IDE tree view, `find` — все работают с файловой системой, а не с содержимым Markdown. MOC для них невидим.
4. **MOC — это документ, а не структура.** Человек привык к навигации через директории; MOC заставляет его читать документ для навигации.

Симлинки возвращают нативную навигацию: `ls research/views/by-topic/orm/` — сразу видны все исследования по теме, без чтения чего-либо.

## Симлинки: полный разбор рисков и купирование

### Риск 1: Windows без Developer Mode

**Проблема:** Git на Windows без включённых симлинков (`core.symlinks=true` + Developer Mode или admin) превращает симлинки в текстовые файлы с путём внутри. Участник на Windows клонирует репо — и вместо директорий с ссылками получает текстовые файлы.

**Купирование:**
- Зафиксировать требование в `CONVENTIONS.md` и `README.md`
- CI-проверка: если платформа Windows и `core.symlinks=false` — warning при clone
- WSL — работает нативно без ограничений
- Fallback для Windows-участников: автогенерируемые индексы (см. ниже, гибрид)

**Оценка:** если вся команда на Linux/macOS/WSL — риска нет. Если есть Windows-участники без WSL — это реальная проблема, требующая дисциплины или fallback.

### Риск 2: Абсолютные пути в симлинках

**Проблема:** симлинк с абсолютным путём (`/home/user/project/research/notes/...`) ломается при клонировании в другую директорию.

**Купирование:** всегда использовать **относительные пути** при создании симлинков. `ln -s` с относительным путём создаёт симлинк с относительной ссылкой.

```bash
# ПРАВИЛЬНО — относительный путь:
ln -s ../../notes/2026-09-30-orm-comparison research/views/by-topic/orm/orm-comparison

# НЕПРАВИЛЬНО — абсолютный путь:
ln -s /home/vasya/project/research/notes/2026-09-30-orm-comparison research/views/by-topic/orm/orm-comparison
```

**Оценка:** полностью купируется дисциплиной или скриптом (скрипт всегда создаёт относительные пути).

### Риск 3: Поиск (grep/ripgrep) не следует симлинкам

**Проблема:** `grep -r` и `rg` по умолчанию **не следуют** симлинкам на директории. `rg "pattern" research/` найдёт содержимое в `notes/`, но не будет дублировать находки через `views/`.

**На самом деле — это фича, а не баг:**
- `rg "pattern" research/notes/` — ищет в реальных файлах, находит всё
- `rg --follow "pattern" research/views/` — если нужно искать через views
- Отсутствие дублирования — хорошо (grep не показывает один файл дважды)

**Купирование:** не требуется. Просто знать: `notes/` — для поиска, `views/` — для навигации.

### Риск 4: Циклические ссылки и симлинки на симлинки

**Проблема:** можно случайно создать симлинк на симлинк или цикл.

**Купирование:** правило в CONVENTIONS.md — симлинки указывают только на реальные директории в `notes/`, никогда на другие симлинки или на `views/`. CI-проверка верифицирует.

### Риск 5: Инструменты для AI-агентов

**Проблема:** агент читает симлинк — получает содержимое цели? Или путь? Зависит от инструмента.

**Реальность:**
- `cat`, `head`, `tail`, Python `Path.read_text()` — прозрачно читают цель ✅
- `ls`, `find`, Python `Path.iterdir()` — видят симлинк как элемент ✅
- Некоторые инструменты (например, `realpath`) показывают реальный путь — тоже полезно ✅
- Агенту нужно просто знать: "views/ — симлинки, notes/ — реальные файлы"

**Купирование:** указать в `AGENTS.md`. Для агента поиск — через `notes/` (grep по frontmatter), навигация — через `views/` (ls по директориям).

### Риск 6: Merge conflicts на симлинках

**Проблема:** два человека создают разные симлинки в одном месте.

**Реальность:** Git хранит симлинк как однострочный blob (путь). Merge conflict — как на обычном текстовом файле с одной строкой. Разрешается тривиально.

**Купирование:** не требуется. Даже проще, чем merge на MOC-файлах (где конфликт на несколько строк).

### Риск 7: Копирование/архивация вне Git

**Проблема:** `tar`, `zip`, `cp -r` без флагов могут дублировать содержимое симлинков или сохранять их как битые.

**Купирование:** для нашей задачи не критично — Git является единственным носителем (P1: Git = source of truth). Архивация вне Git — не наш сценарий.

## Скрипт для управления симлинками

Избавляет от ручного `ln -s` и гарантирует относительные пути:

### `scripts/research-link.py`

```python
#!/usr/bin/env python3
"""Manage symlinks in research/views/.

Commands:
  research-link.py add <note-path> --topic <topic>       # Add symlink to views/by-topic/<topic>/
  research-link.py add <note-path> --status <status>     # Add symlink to views/by-status/<status>/
  research-link.py remove <note-path> --topic <topic>    # Remove symlink
  research-link.py sync                                   # Sync all views from frontmatter
  research-link.py verify                                 # Check all symlinks resolve

Always creates relative symlinks (portable across clones).
"""
import argparse
import re
import shutil
import sys
from pathlib import Path


def parse_frontmatter(path: Path) -> dict:
    content = path.read_text(encoding="utf-8")
    fm_match = re.match(r"^---\n(.*?)\n---\n", content, re.DOTALL)
    if not fm_match:
        return {}
    props = {}
    for line in fm_match.group(1).split("\n"):
        if ":" in line:
            key, _, val = line.partition(":")
            props[key.strip()] = val.strip().strip('"').strip("'")
    return props


def get_note_dir(note_path: str, research_root: Path) -> Path:
    """Resolve note path (real dir under notes/)."""
    p = Path(note_path)
    if not p.is_absolute():
        p = Path.cwd() / p
    p = p.resolve()
    if not str(p).startswith(str(research_root / "notes")):
        print(f"Error: {note_path} is not under research/notes/", file=sys.stderr)
        sys.exit(1)
    return p


def add_symlink(note_dir: Path, views_subdir: Path, name: str = None):
    """Create relative symlink in views_subdir pointing to note_dir."""
    views_subdir.mkdir(parents=True, exist_ok=True)
    if name is None:
        name = note_dir.name

    # Date prefix for sorting: strip date from name if it starts with YYYY-MM-DD-
    # e.g., "2026-09-30-orm-comparison" -> link name "orm-comparison"
    link_name = re.sub(r"^\d{4}-\d{2}-\d{2}-", "", name)
    link_path = views_subdir / link_name

    if link_path.exists() or link_path.is_symlink():
        print(f"  Already exists: {link_path}")
        return

    # Calculate RELATIVE path from link location to target
    rel_target = Path("..") / Path(
        __import__("os").path.relpath(note_dir, views_subdir.parent)
    )

    link_path.symlink_to(rel_target, target_is_directory=True)
    print(f"  Created: {link_path} -> {rel_target}")


def remove_symlink(views_subdir: Path, link_name: str):
    link_path = views_subdir / link_name
    if link_path.is_symlink():
        link_path.unlink()
        print(f"  Removed: {link_path}")
    else:
        print(f"  Not found: {link_path}")


def cmd_sync(research_root: Path):
    """Rebuild views/ from frontmatter in notes/."""
    notes_dir = research_root / "notes"
    views_dir = research_root / "views"

    # Clear existing views
    if views_dir.exists():
        shutil.rmtree(views_dir)
        print(f"Cleared: {views_dir}")

    print("Rebuilding views/...")
    for readme in notes_dir.rglob("README.md"):
        props = parse_frontmatter(readme)
        if not props:
            continue

        note_dir = readme.parent
        name = note_dir.name

        # By status
        status = props.get("status", "unknown")
        add_symlink(note_dir, views_dir / "by-status" / status, name)

        # By topics
        topics = props.get("topics", "").split(",")
        for topic in topics:
            topic = topic.strip()
            if topic:
                add_symlink(note_dir, views_dir / "by-topic" / topic, name)

    print("Done.")


def cmd_verify(research_root: Path):
    """Check all symlinks resolve to existing directories."""
    views_dir = research_root / "views"
    if not views_dir.exists():
        print("No views/ directory.")
        return

    broken = 0
    for link in views_dir.rglob("*"):
        if link.is_symlink():
            if not link.resolve().exists():
                print(f"BROKEN: {link} -> {link.readlink()}")
                broken += 1
            else:
                # Check it points to notes/
                target = link.resolve()
                if "notes" not in target.parts:
                    print(f"WARN: {link} -> {target} (not in notes/)")

    if broken:
        print(f"\n{broken} broken symlink(s) found.")
        sys.exit(1)
    else:
        print("All symlinks OK.")


def main():
    parser = argparse.ArgumentParser(description=__doc__)
    sub = parser.add_subparsers(dest="command")

    # add
    p_add = sub.add_parser("add", help="Add symlink to views/")
    p_add.add_argument("note_path", help="Path to note directory under research/notes/")
    p_add.add_argument("--topic", help="Topic name (creates views/by-topic/<topic>/)")
    p_add.add_argument("--status", help="Status (creates views/by-status/<status>/)")

    # remove
    p_rm = sub.add_parser("remove", help="Remove symlink from views/")
    p_rm.add_argument("note_path", help="Path to note directory")
    p_rm.add_argument("--topic", help="Topic name")
    p_rm.add_argument("--status", help="Status")

    # sync
    sub.add_parser("sync", help="Rebuild all views/ from frontmatter")

    # verify
    sub.add_parser("verify", help="Verify all symlinks resolve")

    args = parser.parse_args()
    research_root = Path(__file__).parent.parent / "research"

    if args.command == "add":
        note_dir = get_note_dir(args.note_path, research_root)
        if args.topic:
            add_symlink(note_dir, research_root / "views" / "by-topic" / args.topic)
        if args.status:
            add_symlink(note_dir, research_root / "views" / "by-status" / args.status)
        if not args.topic and not args.status:
            print("Error: specify --topic and/or --status", file=sys.stderr)
            sys.exit(1)

    elif args.command == "remove":
        note_dir = get_note_dir(args.note_path, research_root)
        link_name = re.sub(r"^\d{4}-\d{2}-\d{2}-", "", note_dir.name)
        if args.topic:
            remove_symlink(research_root / "views" / "by-topic" / args.topic, link_name)
        if args.status:
            remove_symlink(research_root / "views" / "by-status" / args.status, link_name)

    elif args.command == "sync":
        cmd_sync(research_root)

    elif args.command == "verify":
        cmd_verify(research_root)

    else:
        parser.print_help()


if __name__ == "__main__":
    main()
```

### `cmd_sync` — ключевой сценарий

`sync` полностью перестраивает `views/` из frontmatter — это идемпотентная операция. Значит:

1. **Frontmatter в `notes/` — единственный source of truth** для статуса и тем
2. **Симлинки — просто материализация** frontmatter в файловую систему
3. **После любого изменения frontmatter** → `python scripts/research-link.py sync` → views актуальны
4. **Git diff после sync** — только изменённые симлинки (дёшево)
5. **CI может запускать sync + verify** — гарантия целостности

## Сравнение: симлинки vs MOC vs frontmatter-only

| Аспект | Симлинки (`views/`) | MOC (индексные файлы) | Только frontmatter |
|---|---|---|---|
| **Навигация человеком** | ✅ Нативная: `tree`, IDE, `ls` | ❌ Через чтение Markdown | ❌ Только через поиск |
| **Навигация агентом** | ✅ `ls views/by-topic/orm/` | ✅ Чтение MOC-файла | ⚠️ `rg "topics:"` + парсинг |
| **Поиск (grep/rg)** | ⚠️ Не следует симлинкам (и это ок) | ✅ Находит по содержимому | ✅ Находит по содержимому |
| **Git diff** | ✅ 1 строка на изменение | ⚠️ Несколько строк в MOC | ✅ Только frontmatter |
| **Windows** | ❌ Требует настройки | ✅ Работает везде | ✅ Работает везде |
| **Двойная привязка (файл в 2 темах)** | ✅ Два симлинка | ✅ Две записи в MOC | ✅ Тег `topics: "a,b"` |
| **Требует генерации** | ⚠️ Sync после изменения | ⚠️ Генерация или вручную | ✅ Нет |
| **Source of truth** | Frontmatter (sync) | MOC-файл | Frontmatter |
| **Нулевой overhead для чтения** | ✅ Файловая система = UI | ❌ Нужно открыть MOC | ❌ Нужно искать |

## Рекомендация: гибрид с симлинками как primary

**Симлинки — основной механизм навигации** (для человека через file tree и для агента через `ls`). **Frontmatter — source of truth** (для поиска и генерации views). **MOC — опционально** для аннотированных обзоров (когда нужно не просто "список ссылок", а "список с контекстом и выводами").

```
┌─────────────────────────────────────────────────────┐
│  notes/YYYY-MM-DD-<slug>/README.md                 │
│  frontmatter: { status, topics, author, ... }      │
│  ↑ SOURCE OF TRUTH (человек пишет, агент читает)   │
└─────────────────┬───────────────────────────────────┘
                  │
                  │  scripts/research-link.py sync
                  │  (генерация из frontmatter)
                  ▼
┌─────────────────────────────────────────────────────┐
│  views/                                             │
│  ├── by-status/active/<slug> -> ../../notes/...    │
│  ├── by-topic/orm/<slug> -> ../../../notes/...     │
│  └── by-topic/database/<slug> -> ../../../notes/...│
│  ↑ МАТЕРИАЛИЗАЦИЯ (для навигации)                  │
└─────────────────────────────────────────────────────┘
```

**Workflow:**
1. Создать ресёрч в `notes/`, заполнить frontmatter (`status`, `topics`)
2. Запустить `python scripts/research-link.py sync`
3. Commit: новые файлы + новые симлинки (чистый diff, всё в одном PR)
4. Изменить статус → обновить frontmatter → `sync` → commit
5. CI: `research-link.py verify` — гарантия, что нет битых ссылок

**Fallback для Windows-без-WSL:** CI генерирует `indexes/` (MOC-подобные файлы) из frontmatter — как альтернативный интерфейс для тех, у кого симлинки не работают. Это опционально, только если в команде есть такие участники.

## Что такое GitHub Spec Kit и как он устроен

[github/spec-kit](https://github.com/github/spec-kit) — открытый инструментарий для Spec-Driven Development, интегрирующий SDD в workflow AI-агентов (Copilot, Gemini CLI, Claude Code и др.)【turn1search2】.

**Ключевые факты из анализа репозитория:**

| Параметр | Значение |
|---|---|
| Язык | **Python** (`src/specify_cli/`, `pyproject.toml`)【turn1fetch0】 |
| CLI | `specify` |
| Установка | `uvx --from git+https://github.com/github/spec-kit.git specify init <PROJECT>`【turn0search2】 |
| Звёзды | 139k+ |
| Структура | scripts, templates, presets, extensions, bundles, workflows, integrations |
| AI-интеграция | AGENTS.md в корне репо, instructions для разных агентов |

**Как Spec Kit решает задачу "человек + агент":**

1. **CLI-интерфейс** (`specify init`, `specify spec new`, и т.д.) — и человек, и агент вызывают одни и те же команды через shell.
2. **Промпт-фреймворк** — Spec Kit генерирует инструкции (в `.specify/` и `AGENTS.md`), которые агент читает для понимания контекста проекта.
3. **Шаблоны + пресеты** — параметризация через переменные, которые можно передавать флагами (`--data key=value`).
4. **Расширения** — community-extensions для дополнительных сценариев.

Это тот же паттерн, что вы используете: **CLI → генерация/валидация артефактов → Markdown в Git**.

# Установка в проект vs внешний tool: архитектура кастомизации

## Короткий ответ

**Правильный ответ — гибрид: ядро как внешний пакет (через `uv`/`uvx` или как dev-dependency), кастомизация через project-local переопределения (`.research/` директория).** Это паттерн, который используют GitHub Spec Kit (presets + extensions), pre-commit (local hooks) и Husky (`.husky/` директория) — и он решает конфликт "единый инструмент ↔ кастомизация под проект".

## Три модели распространения

### Модель 1: Внешний tool (только uvx)

```bash
# Установка нулевая, вызов всегда через uvx:
uvx research-tools status notes/2026-09-30-orm --status active
```

**Как работает:** скрипты живут в отдельном пакете (PyPI или git), вызываются через `uvx` в изолированном окружении. В проекте — только данные (`research/notes/`, `research/views/`).

| Плюс | Минус |
|---|---|
| Одна версия для всех проектов | ❌ Нельзя кастомизировать |
| Автообновления (обновил пакет — все проекты получили) | ❌ Шаблоны фиксированы |
| Чистый проект (только данные) | ❌ Зависимость от внешнего пакета |
| Идеально для команд с одинаковыми процессами | ❌ Не подходит, если проекты разные |

**Когда достаточно:** все проекты следуют одному процессу, никаких вариаций.

### Модель 2: Vendoring (копия в проект)

```bash
# Копируем скрипты:
research-tools init --vendor
# → создаёт scripts/research-tools/ в проекте
```

**Как работает:** `research-tools init` копирует скрипты в `scripts/` проекта. Проект владеет всем кодом.

| Плюс | Минус |
|---|---|
| ✅ Полный контроль — правь что угодно | Обновления вручную (copy-paste) |
| ✅ Ноль внешних зависимостей | Дрейф между проектами |
| ✅ Проект самодостаточен | Дублирование кода |
| ✅ Можно менять под конкретный проект | ❌ Fix в одном проекте не попадает в другие |

**Когда достаточно:** один проект, никогда не будет второго, или кастомизация настолько глубокая, что ядро не узнаётся.

### Модель 3: Гибрид — ядро + переопределения (рекомендуемая)

```bash
# Ядро — внешний пакет (dev-dependency):
# pyproject.toml:
# [project]
# dependencies = ["research-tools>=0.1.0"]

# Или через uv:
uv add --dev research-tools

# Кастомизация — в проекте:
# .research/config.yaml, .research/templates/, .research/hooks/
```

**Как работает:** ядро логики (парсинг frontmatter, симлинки, sync) — внешний пакет. Шаблоны, конфигурация, hooks, extensions — в `.research/` директории проекта. Ядро ищет переопределения сначала в проекте, потом fallback на дефолт.

| Плюс | Минус |
|---|---|
| ✅ Кастомизация per-project | Чуть сложнее архитектура |
| ✅ Ядро обновляется централизованно | Нужно определить точки расширения заранее |
| ✅ Шаблоны можно переопределять | |
| ✅ Hooks для расширения поведения | |
| ✅ Extensions для новых команд | |
| ✅ Дефолты работают из коробки | |

**Когда нужна:** несколько проектов с общим ядром, но разными деталями (статусы, шаблоны, workflow).

## Как это делает GitHub Spec Kit

Из анализа [github/spec-kit](https://github.com/github/spec-kit) и его документации【turn3search2】【turn1search2】:

Spec Kit имеет **три уровня кастомизации**:

1. **Integrations** — подключение к AI-агентам (Copilot, Claude, Gemini)
2. **Extensions** — добавляют capabilities, commands, templates, scripts, hooks
3. **Presets** — кастомизируют или заменяют поведение (overriding templates, commands, terminology)

При `specify init <project>` Spec Kit создаёт `.specify/` директорию в проекте【turn1search4】, куда копируются шаблоны. Дальше команда может править эти шаблоны — они уже в проекте, версионируются вместе с ним. Presets позволяют переопределить терминологию и структуру, не меняя код инструмента.

**Ключевой инсайт Spec Kit:** templates копируются в проект при init (project-owned), но инструмент остаётся внешним (tool-owned). Extensions добавляются отдельно — как community-пакеты.

```python
# В ядре (research_tools/templates.py):

from importlib.resources import files
from pathlib import Path

def get_template(name: str, project_root: Path) -> str:
    """Lookup: project template → package default → error."""
    # 1. Project-local override
    project_template = project_root / ".research" / "templates" / f"{name}.md"
    if project_template.exists():
        return project_template.read_text(encoding="utf-8")

    # 2. Package default (fallback)
    package_template = files("research_tools.defaults") / "templates" / f"{name}.md"
    if package_template.is_file():
        return package_template.read_text(encoding="utf-8")

    raise FileNotFoundError(f"Template not found: {name}")
```

**Результат:** если в проекте есть `.research/templates/question.md` — используется он. Если нет — дефолт из пакета. Проект может переопределить один шаблон, не трогая остальные.

```python
# В ядре (research_tools/config.py):

from pathlib import Path
import yaml

DEFAULTS = {
    "paths": {
        "notes": "research/notes",
        "views": "research/views",
    },
    "statuses": ["draft", "active", "review", "decided", "archived"],
    "required_fields": ["status", "topics", "author"],
}

def load_config(project_root: Path) -> dict:
    """Merge: project config → defaults."""
    config = DEFAULTS.copy()

    config_file = project_root / ".research" / "config.yaml"
    if config_file.exists():
        project_config = yaml.safe_load(config_file.read_text())
        # Deep merge: project overrides defaults
        for key, value in project_config.items():
            if isinstance(value, dict) and key in config:
                config[key].update(value)
            else:
                config[key] = value

    return config
```

### Механизм 3: Hooks (pre/post точки расширения)

```python
# В ядре (research_tools/hooks.py):

import importlib.util
from pathlib import Path
from typing import Callable, Any

def run_hook(hook_name: str, project_root: Path, context: dict) -> Any:
    """Run project-local hook if it exists. Hooks are optional."""
    hook_path = project_root / ".research" / "hooks" / f"{hook_name}.py"

    if not hook_path.exists():
        return None  # Hook not defined — skip silently

    # Dynamic import
    spec = importlib.util.spec_from_file_location(f"hook_{hook_name}", hook_path)
    module = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(module)

    # Call the hook's main() function with context
    if hasattr(module, "main"):
        return module.main(**context)

    return None
```

#### Simple Flow

Только генерация спеков, без отслеживания выполнения:

```

1. Requirements → requirements.md (user stories, EARS criteria)

specs/

    └── tasks.md
```

#### FIRE Flow (Fast Intent-Run Engineering)

Адаптивное выполнение с brownfield и monorepo support:

```
/fire-orchestrator   # Entry point, routing
/fire-planner        # Intent capture, work item decomposition
/fire-builder        # Run execution, walkthrough generation
```

**Ключевые фичи FIRE:**
- **Adaptive checkpoints** — Autopilot (0), Confirm (1), или Validate (2) в зависимости от сложности
- **First-class brownfield** — auto-detect существующих паттернов и конвенций
- **Monorepo support** — иерархические standards с module-specific overrides
- **Walkthrough generation** — автоматическая документация каждого изменения

```
.specs-fire/
├── state.yaml           # Central state tracking
├── standards/           # Project standards
├── intents/             # Intent documentation
├── runs/                # Run logs
└── walkthroughs/        # Generated documentation
```

Полная методология с Domain-Driven Design:

```
/specsmd-master-agent       # Orchestrates & navigates
/specsmd-inception-agent    # Requirements, stories, bolt planning
/specsmd-construction-agent # Execute bolts through DDD stages
/specsmd-operations-agent   # Deploy, verify, monitor
```

**Три последовательные фазы:**
1. **Inception** — intents, requirements, decompose into units
2. **Construction** — bolts: Model → Design → ADR → Implement → Test
3. **Operations** — deploy, verify, monitor

```
    └── {topic-slug}-{YYYYMMDD}/

        ├── spark-bank.md         # All generated ideas, grouped by theme
        ├── flame-report.md       # Six Hats evaluations + shortlist
        └── concept-briefs/
            └── {concept-name}.md # One per shortlisted concept
```

**Когда использовать Ideation Flow (прямо из документации):**
- Starting a new feature, want novel angles → explore space before specs
- Stuck in an echo chamber → anti-bias engine pulls from non-tech domains
- Product discovery session → resumable, polished artifacts
- Concept brief for a meeting → fully-structured, no editing needed
- Stress-test an idea → Black Hat + Critic surface risks early

### Почему это меняет картину

Ideation Flow — это **не** delivery-инструмент. Это **research/ideation**-инструмент, встроенный в specs.md ecosystem. Он закрывает ровно ту задачу, которую мы обсуждали: "какой язык лучше, какие библиотеки, какие альтернативы" — через structured brainstorming с anti-bias.

Мой предыдущий тезис "все три фокусируются на delivery, не на research" был **неверен** для specs.md. specs.md покрывает оба: research (Ideation) → delivery (Simple/FIRE/AI-DLC).

## 2. Research knowledge management — часть software delivery

```
Ideation → Research → Specification → Planning → Implementation → Review → Deploy
   ↑          ↑           ↑            ↑           ↑           ↑
```

## 3. TypeScript vs Python — пересмотр

Вы правы, и мой аргумент "Python, потому что Spec Kit на Python" был слабым. Честное пересмотрение:

### TypeScript — сильные стороны для этой задачи

**TUI/CLI экосистема:**

| Библиотека | Что даёт | Аналог в Python |
|---|---|---|
| [**Ink**](https://github.com/vadimdemedes/ink) | React для CLI — компонентная модель, Flexbox layout через Yoga【turn1search4】 | Textual (но другой подход) |

| **Commander / Yargs / Oclif** | CLI framework, subcommands, аргументы | Typer/Click |
| **Chalk / Picocolors** | Цветной вывод | Rich/Colorama |

**AI harness экосистема:**

| Harness | TS extension mechanism |
|---|---|
| **Claude Code** | MCP servers (TS SDK official), slash commands в Markdown |
| **Cursor** | Rules в `.mdc` (TS-friendly) |
| **GitHub Copilot** | Agents в `.agent.md` |
| **OpenAI Codex** | Config в `.codex/` |
| **specs.md** | Сам построен на Node.js/TS |

**Практические преимущества TS:**

1. **Многие harness построены на TS** — specs.md, многие MCP servers, Copilot extensions
2. **Extension mechanisms на TS** — если вы расширяете существующий harness, TS — родной язык
3. **npm экосистема** — 2M+ пакетов, включая все нужные для CLI/TUI
4. **Type safety** — TypeScript строже, чем Python type hints (которые optional)
5. **Один language для full-stack** — если проект уже на TS/Node.js

### Честное сравнение

| Критерий | Python | TypeScript |
|---|---|---|
| **TUI frameworks** | Textual (зрелый, полный) | Ink (React-модель, зрелый), Clack (prompts) |
| **AI agent SDK** | ✅ Официальный MCP SDK | ✅ Официальный MCP SDK |
| **CLI frameworks** | Typer, Click, argparse | Commander, Yargs, Oclif, Citty |
| **Типизация** | Optional (mypy/pyright) | Строгая из коробки |
| **npm/pip экосистема** | pip (меньше) | npm (2M+, больше) |
| **AI harness extensions** | Хорошо | **Отлично** (многие на TS) |
| **Быстрота прототипирования** | ✅ Быстрее | ⚠️ Чуть медленнее (build step) |
| **Distribution** | `uvx` / pip | `npx` / npm install |
| **Для этой конкретной задачи** | Хорошо | **Возможно лучше** |

### Почему TS может быть лучше для research-tools

1. **Если target — specs.md ecosystem:** specs.md сам на Node.js. Расширять его — естественнее на TS.
2. **Если нужен TUI:** Ink + React — мощная модель для сложных интерфейсов (research browser, kanban view).
3. **Если AI-агенты — primary users:** многие harness extension mechanisms TS-friendly.
4. **Если проект full-stack TS:** один язык для всего — research-tools, web dashboard, MCP server.

### Почему Python всё ещё конкурент

1. **Spec Kit, Spec Kitty на Python** — если target эта экосистема
2. **Textual — самый зрелый TUI** (богаче Ink для complex interfaces)
3. **Data/ML экосистема** — если research включает анализ данных
4. **Быстрота итерации** — нет build step

### Честный вывод

**Для вашей задачи TypeScript — валидный и возможно лучший выбор.** Решающие факторы:

- Target ecosystem (specs.md → TS, Spec Kit → Python)
- Team expertise (какой язык знают лучше)
- TUI complexity (простой → оба, сложный → Textual/Ink на равных)
- AI harness integration (Claude Code/Canvas → TS-friendly)

## Research Mission в Spec Kitty — полный разбор

### Research как first-class mission type

Spec Kitty определяет **четыре mission types** как равноправные【turn0fetch0】:

| Mission Type | Primary Goal | Key Activities |
|---|---|---|
| `software-dev` | Working code | Write tests, implement features, review code |
| **`research`** | **Validated findings** | **Collect evidence, analyze data, synthesize conclusions** |
| `plan` | Actionable plan | Define architecture, map dependencies, write roadmaps |
| `documentation` | Clear docs | Audit gaps, create content, validate accessibility |

Ключевой аргумент из документации【turn0fetch0】:

> "A workflow designed for software development doesn't fit research:
> - 'All tests pass' makes no sense for a literature review
> - 'Documented sources' isn't relevant for code implementation
> - Phases like 'gather data' don't apply to feature development"

Это ровно та же проблема, которую мы решали: **разные типы работы требуют разных workflows**.

### Research workflow: state machine с циклом

```
scoping → methodology → gathering ↔ synthesis → output → done
```

Ключевая особенность — **цикл `gathering ↔ synthesis`**: можно вернуться к сбору данных после первичного синтеза【turn0fetch0】. Это отражает реальную research-практику (iterative evidence collection).

### Guards: evidence-gated transitions

Специфика именно research-миссии — переходы блокируются, пока не собрано достаточно evidence【turn0fetch0】:

| Переход | Условие |
|---|---|
| scoping → methodology | `spec.md` существует (research objectives определены) |
| methodology → gathering | `plan.md` существует (methodology описана) |
| **gathering → synthesis** | **Минимум 3 источника documented** |
| synthesis → output | `findings.md` существует |
| output → done | Publication approved |

Guard "минимум 3 источника" — это **evidence-based quality gate**, которого нет ни в specs.md, ни в GitHub Spec Kit.

### Research artifacts

Структура research-миссии【turn0fetch0】【turn1fetch0】:

```
kitty-specs/001-serverless-auth-study/
├── spec.md                      # Research objectives, hypothesis, scope
├── plan.md                      # Methodology, sources, criteria
├── tasks.md                     # WP breakdown
├── findings.md                  # Key discoveries, synthesis, recommendations
├── data-model.md                # Concepts, relationships, taxonomies
├── research/
│   ├── evidence-log.csv         # Structured source tracking
│   ├── source-register.csv      # Source registry
│   ├── comparison-matrix.md     # Side-by-side comparisons
│   └── synthesis-notes.md       # Integration insights
└── meta.json                    # Links to mission type "research"
```

### Evidence Log — структурированный, машиночитаемый

CSV-формат с confidence ratings【turn1fetch0】:

```csv
timestamp,source_type,citation,key_finding,confidence,notes
2025-01-15T10:30:00Z,paper,"Smith et al 2024, JWT Security","Token rotation reduces breach window",high,"Peer-reviewed"
2025-01-15T11:00:00Z,docs,"AWS Lambda Auth Docs","Sessions require external store",high,"Official docs"
2025-01-15T14:20:00Z,blog,"Auth0 Blog: Serverless Auth","Cold starts impact auth latency",medium,"Industry observation"
```

Поля: **timestamp, source_type, citation, key_finding, confidence (high/medium/low), notes**. Это структурированнее, чем наши `findings/NN-<name>.md` — CSV парсится агентами без NLP.

### Research patterns

Из документации【turn1fetch0】 — три типовых сценария:

**Technology Selection** (наш основной use case):
```
WP01-WP0N: One work package per option (одна технология = один WP)
WP Last: Comparison matrix and recommendation
```

**Literature Review:**
```
WP01: Search and source collection
WP02-WP0N: Analysis by theme/topic
WP Last: Synthesis and gaps analysis
```

**Best Practices Study:**
```
WP01: Industry standards research
WP02: Case studies collection
WP03: Pattern extraction
WP04: Recommendations for context
```

### Agent context для research

> "You are a research agent conducting systematic literature reviews. Document ALL sources."【turn0fetch0】

Это специфицирует поведение AI-агента под research-домен (в отличие от "TDD practices" для software-dev).

### Per-feature missions (0.8.0+)

Ключевая архитектурная особенность: **разные features в одном проекте могут использовать разные mission types**【turn0fetch0】:

```
kitty-specs/
├── 010-auth-system/
│   └── meta.json  # mission: "software-dev"
├── 011-library-comparison/
│   └── meta.json  # mission: "research"
└── 012-user-docs/
    └── meta.json  # mission: "documentation"
```

Это решает проблему "проект разного масштаба" — research-задача получает research-workflow, feature-задача — software-dev-workflow, без переконфигурации проекта.
