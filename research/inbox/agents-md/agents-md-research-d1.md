## 1. Что такое AGENTS.md

`AGENTS.md` — это открытый стандарт для файла инструкций, размещаемого в корне репозитория и помогающего ИИ-агентам, пишущим код, понять, как работать с проектом. Официальная спецификация описывает его как «README для агентов»: выделенное, предсказуемое место для команд сборки, тестирования и соглашений.

Стандарт используется более чем в **60 000 открытых проектов**. Более 30 агентов читают его, включая OpenAI Codex, GitHub Copilot, Cursor, Gemini CLI, Google Jules, Aider, Zed, Windsurf и Devin.

Ключевые свойства:

- **Plain Markdown** — никаких обязательных полей, YAML-фронтматтера или специального синтаксиса.
- **Кросс-инструментальность** — один файл работает для большинства агентов.
- **Иерархичность** — поддерживаются вложенные файлы; агент читает ближайший к редактируемому коду.

`AGENTS.md` дополняет `README.md`, а не заменяет его: README написан для людей, `AGENTS.md` — для агентов.

## 2. Официальная спецификация

Официальная спецификация `AGENTS.md` определяет файл как простой Markdown-документ **без обязательных полей или фиксированной схемы**. Спецификация предлагает информацию, которую стоит включить:

- структура проекта;
- команды сборки и тестирования;
- соглашения о коде;
- инструкции по тестированию;
- соображения безопасности.

При этом каждое проект решает самостоятельно, что именно нужно его агентам.

Спецификация не предписывает, как именно агенты или инструменты должны реализовывать поддержку формата — это остаётся на усмотрение разработчиков инструментов.

**Текущий статус:** по состоянию на середину 2026 года стандарт остаётся открытым и продолжает развиваться.

**Предложение v1.1** (обсуждается в issue #135) направлено на кодификацию существующих лучших практик: иерархическую область действия, приоритет и прогрессивное раскрытие. Цель — сделать неявные соглашения явными без внесения ломающих изменений.

## 3. Управление и стандартизация

`AGENTS.md` возник как кросс-вендорное соглашение в результате работы команд OpenAI Codex, Amp, Google Jules, Cursor и Factory.

**9 декабря 2025 года** Linux Foundation объявил о создании **Agentic AI Foundation (AAIF)** — нейтрального некоммерческого фонда, которому OpenAI передал `AGENTS.md` в качестве одного из трёх founding-проектов (наряду с MCP от Anthropic и goose от Block).

Управление под эгидой Linux Foundation означает:

- **Стабильность имени файла** — репозиторий, добавляющий `AGENTS.md`, не привязывается к дорожной карте одной компании.
- **Нейтральное управление** — спецификация остаётся намеренно тонкой, без вендор-специфичных полей.
- **Прозрачность и стабильность** — открытое управление обеспечивает долгосрочную предсказуемость.

Платиновые члены AAIF: Amazon Web Services, Anthropic, Block, Bloomberg, Cloudflare, Google, Microsoft и OpenAI.

## 5. Структура и рекомендуемые разделы

Спецификация не требует обязательных разделов, но большинство репозиториев используют следующие:

| Раздел | Содержание |
|---|---|
| **Project overview** | Краткое описание проекта и его назначения |
| **Build & test commands** | Точные команды с флагами |
| **Code style** | Форматтеры, линтеры, правила именования |
| **Testing instructions** | Как запускать тесты, какие фильтры использовать |
| **Security notes** | Обработка секретов, чувствительные пути |
| **Commit / PR rules** | Формат коммитов, правила ветвления, чеклист PR |
| **Boundaries** | Трёхуровневая защита: ✅ Always / ⚠️ Ask first / ❌ Never |
| **Gotchas** | Неочевидные подводные камни |

Полный набор рекомендуемых разделов из руководства mitchellfyi/documentation:

- **Project map** — высокоуровневая структура и «что где лежит»
- **Setup & environment** — точные шаги для локального запуска
- **Build & test** — единственно верный способ компиляции и валидации
- **Style & conventions** — форматтеры, линтеры, правила именования
- **Git & PR rules** — имена веток, формат коммитов, чеклист PR
- **Security & do not touch** — обработка секретов, чувствительные пути
- **Gotchas** — неочевидные подводные камни
- **Task workflow** — что делать до, во время и после каждой задачи
- **Scope limits** — что агент не должен пытаться делать

Рекомендуется использовать заголовки H2/H3 и маркированные списки команд в обратных кавычках — это легче для парсинга агентами, чем проза.

## 6. Руководства по составлению

### 6.1. Writing an Effective AGENTS.md (Agentic AI Foundation)

Официальное руководство AAIF. Ключевой принцип: **для каждой инструкции спросите, изменит ли она поведение агента**. Если нет — информация может принадлежать другому месту.

Что `AGENTS.md` решает: агент не может надёжно вывести из кода репозиторно-специфичное знание. Очевидная команда сборки может дать неполный бинарник. Директория может содержать генерируемый код, который нельзя редактировать. Два пакета могут выглядеть так, будто могут зависеть друг от друга, хотя архитектура это запрещает.

### 6.2. How to Write a Definitive AGENTS.md (mitchellfyi/documentation)

Практическое руководство, независимое от языка. Определяет `AGENTS.md` как «README для агентов» — предсказуемый Markdown-файл, который говорит инструментам, как работать с репозиторием: настройка, сборка, тестирование, линтинг, коммиты и соблюдение границ.

Ключевые результаты:

- **Снижение неоднозначности** — явные, копируемые команды
- **Повышение надёжности** — агенты проверяют изменения локально перед PR
- **Принудительные стандарты** — те же проверки, что используют люди
- **Масштабирование на монорепозитории** — локальные файлы переопределяют корневые

### 6.3. What Is AGENTS.md? How to Write One in 2026 (Tembo)

Обзор с примерами. Основные правила: **пишите команды, а не прозу**. Если вы перечислите тестовые команды в `AGENTS.md`, совместимые агенты попытаются выполнить эти проверки и исправить ошибки до объявления задачи завершённой.

### 6.4. Guides: AI Coding Agents (Next.js)

Пример использования `AGENTS.md` для направления агентов к встроенной документации, соответствующей версии фреймворка, вместо их тренировочных данных. Next.js автоматически генерирует `AGENTS.md` и `CLAUDE.md` при создании нового проекта или при запуске `next dev` (в версии 16.3+).

### 6.5. Harness Engineering (Software Mansion)

Рекомендует рассматривать `AGENTS.md` как **таблицу содержания**: по мере роста файла выносить блоки в отдельные файлы в `docs/` или в skills, оставляя в `AGENTS.md` только указатели.

## 8. Монорепозитории и вложенные файлы

В монорепозиториях рекомендуется размещать `AGENTS.md` в каждом пакете. Агент читает **ближайший файл** к редактируемому коду — ближайший `AGENTS.md` побеждает.

Официальный репозиторий OpenAI Codex использует **88 файлов `AGENTS.md`** по всему дереву директорий.

Рекомендуемая структура:

```
monorepo/
├── AGENTS.md                  # глобальные правила
├── apps/
│   ├── web/
│   │   └── AGENTS.md          # специфично для web
│   └── api/
│       └── AGENTS.md          # специфично для API
└── packages/
    ├── ui/
    │   └── AGENTS.md          # специфично для UI-пакета
    └── shared/
        └── AGENTS.md          # специфично для shared
```

Корневой файл — для глобальных правил, листовые — для технологически специфичных.

## 9. Прогрессивное раскрытие

**Проблема:** `AGENTS.md` загружается при каждом обращении к разговору — это полная стоимость промпта фреймворка до того, как модель напишет хоть слово.

**Решение — прогрессивное раскрытие:** вместо размещения всего в одном файле:

```
AGENTS.md                    # Таблица содержания (~100 строк)
├── docs/setup.md            # Детали настройки
├── docs/testing-patterns.md # Паттерны тестирования
├── docs/api-reference.md    # API-справочник
└── packages/backend/AGENTS.md  # Доменные правила для backend
```

**Паттерн:** корневой `AGENTS.md` выступает как указатель, ссылающийся на подробную документацию. Специфичные для директорий инструкции выносятся в отдельные `AGENTS.md` внутри поддиректорий, чтобы они загружались только при необходимости.

Предложение v1.1 рекомендует опциональный YAML-фронтматтер для поддержки прогрессивного раскрытия — он позволяет агентам строить лёгкие индексы доступного руководства без загрузки полного содержимого файлов.

## 10. Исследования эффективности

### 10.1. Исследование ETH Zurich (февраль 2026)

**Авторы:** Thibaud Gloaguen, Niels Mündler, Mark Müller, Veselin Raychev, Martin Vechev (ETH Zurich, LogicStar.ai).

**Публикация:** arXiv:2602.11988v1 [cs.SE], 12 февраля 2026.

**Методология:** построен новый бенчмарк **AGENTBENCH** из 138 реальных Python-задач из нишевых репозиториев с developer-committed context files. Протестированы четыре агента (Claude 3.5 Sonnet, Codex GPT-5.2, GPT-5.1 mini, Qwen Code) в трёх сценариях: без context file, с LLM-сгенерированным файлом и с human-written файлом.

**Ключевые результаты:**

| Метрика | LLM-generated | Human-written | Без файла |
|---|---|---|---|
| Успешность задач | −3% | +4% | baseline |
| Стоимость инференса | +20% | +20% | baseline |
| Количество шагов | больше | больше | baseline |

Исследование показало, что context files **снижают успешность задач** по сравнению с отсутствием контекста, одновременно увеличивая стоимость инференса более чем на 20%.

LLM-сгенерированные файлы оказали **маргинально негативный эффект** на успешность задач, в то время как developer-written файлы показали маргинальный выигрыш. Однако ни то, ни другое отличие от отсутствия context file не было статистически значимым. Developer-written файлы значимо превзошли LLM-generated.

**Рекомендации исследователей:**

- **Опустить LLM-сгенерированные context files полностью**
- **Ограничить human-written инструкции non-inferable деталями** — например, высокоспецифичным tooling или кастомными командами сборки
- Context files полезны для указания **нестандартных практик кодирования**, но должны содержать специфичную информацию, уже недоступную в репозитории

**Важная оговорка:** trace analysis показал, что агенты в целом следуют конкретным инструкциям в файлах, включая рекомендации использовать репозиторно-специфичные инструменты. Однако обзоры репозитория (repository overviews) **не помогали** им достичь релевантного кода более эффективно.

### 10.2. Эксперимент AAIF (пять запусков)

AAIF сравнил идентичные копии репозитория с коротким `AGENTS.md` и без него. На более сложной задаче два из пяти запусков **без файла** потратили время на переориентацию в репозитории или запуск незапрошенной production-сборки. **Ни один из запусков с файлом** не делал ни того, ни другого.

Эксперимент охватывал один репозиторий и один агент, поэтому является полезным свидетельством, а не общим бенчмарком.

### 10.3. Исследование Jai Lal Lulla et al.

Тестирование 124 pull-request задач в 10 репозиториях. Запуски с `AGENTS.md` имели **на 28,64% меньшую медианную продолжительность** и использовали **на 16,58% меньше медианных выходных токенов**.

Исследование фокусировалось на операционной эффективности, а не на комплексной оценке корректности патчей, поэтому эти цифры не следует читать как доказательство, что `AGENTS.md` автоматически производит лучший код.

### 10.4. Сводка по исследованиям

| Исследование | Выборка | Результат |
|---|---|---|
| ETH Zurich (2026) | 138 задач, 4 агента | Контекстные файлы снижают успешность; LLM-сгенерированные — негативно; human-written — маргинально позитивно |
| AAIF (5 запусков) | 1 репозиторий, 1 агент | Файл предотвращает дезориентацию и незапрошенные сборки |
| Jai Lal Lulla et al. | 124 задачи, 10 репозиториев | −28,64% времени, −16,58% токенов |

## 11. Лучшие практики

### 11.1. Принцип минимализма

**Каждая инструкция должна отвечать на вопрос: изменит ли она поведение агента?** Если нет — информация может принадлежать другому месту.

Исследование ETH Zurich показало, что **избыточные требования** из context files делают задачи сложнее. Human-written файлы должны описывать только **минимальные требования**.

### 11.2. Бюджет в 200 строк

Фронтальные LLM могут надёжно следовать примерно 150–200 инструкциям. Превышение этого лимита ведёт к снижению точности выполнения. Рекомендуется, чтобы ни один сгенерированный файл не превышал **200 строк**.

Корневой файл рекомендуется держать в районе **20–30 строк**, потому что контент, дублированный из README, измеримо ухудшает производительность агента.

### 11.3. Команды вместо прозы

Используйте точные, копируемые команды в обратных кавычках. Агент, который знает, что `pnpm test` существует, гораздо вероятнее отправит PR с проходящими тестами.

### 11.4. Правила с причинами

Правило с приложенной причиной обобщается на случаи, которые вы не перечислили. Правило с «оглядкой» (hedge) интерпретируется.

### 11.5. Non-inferable детали

Включайте только информацию, которую агент **не может вывести** из кода:

- Очевидная команда сборки может дать неполный бинарник
- Директория может содержать генерируемый код, который нельзя редактировать
- Два пакета могут выглядеть совместимыми, хотя архитектура это запрещает
- Маленькое изменение может требовать конкретной валидационной команды, неочевидной из тестов

### 11.6. Трёхуровневая система границ

Самая ценная секция по анализу GitHub (2 500+ репозиториев):

| Уровень | Значение | Пример |
|---|---|---|
| ✅ Always | Всегда делать | Запускать `pnpm lint` перед коммитом |
| ⚠️ Ask first | Спросить перед действием | Изменение схемы БД |
| ❌ Never | Никогда не делать | Редактировать `src/generated/` |

Этот раздел предотвращает деструктивные ошибки.

### 11.7. Приоритет ближайшего файла

В монорепозиториях агент читает ближайший `AGENTS.md` к редактируемому коду. Локальные файлы переопределяют корневые.

### 11.8. Таблица содержания

По мере роста файла выносите блоки в `docs/` или skills, оставляя в `AGENTS.md` только указатели.
