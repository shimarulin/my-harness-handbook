# RFC: Migrate Notifications to Event-Driven Architecture

## Status

**Approved** — Decision recorded in [adr-0007](../decisions/0007-use-kafka-for-notifications.md)

## Context and Scope

**Current State:**
- Notifications processed synchronously in API request handlers
- At peak load (> 1000 req/s), API p95 latency increases from 200ms to 3+ seconds
- 3 incidents in last quarter caused by notification system overload
- Team spends ~20% of time on notification-related performance issues

**Problem:**
- Sync processing couples API response time to notification delivery
- No retry mechanism for failed notifications
- No way to replay notifications after system failures
- Scaling requires scaling entire API service

**Scope:**
- All notification types: email, SMS, push, in-app
- Notification triggers: user actions, system events, scheduled
- NOT in scope: notification content templates, user preferences (remain unchanged)

**Related:**
- [prd-012](../../prd/012-notify-reliability.md) — Product requirements for notification reliability
- [adr-0003](../../decisions/0003-current-notification-architecture.md) — Current architecture decision

## Goals and Non-goals

**Goals:**
- Decouple notification processing from API request handling
- Achieve 99.9% notification delivery within 5 minutes
- Enable replay of failed notifications
- Scale notification processing independently from API
- Reduce API p95 latency to < 300ms even at peak load

**Non-goals:**
- Changing notification content or templates
- Adding new notification channels
- Real-time notifications (< 1 second delivery)
- Cross-region notification replication
- Notification analytics or A/B testing

## Proposal

### Recommended: Apache Kafka as Event Backbone

Миграция на event-driven architecture с Apache Kafka как message broker.

**Architecture:**

```
[API Service] → [Kafka Producer] → [Kafka Topic: notifications]
                                          ↓
                              [Notification Consumer Service]
                                          ↓
                              [Email/SMS/Push/In-App Senders]
```

**Key Design Decisions:**
1. **Kafka** over RabbitMQ/Redis/SQS (see Alternatives)
2. **At-least-once delivery** with idempotent consumers
3. **Schema Registry** with Avro for event schemas
4. **Consumer groups** for scaling notification processing
5. **Dead letter queue** for failed notifications after max retries

### Implementation Phases

**Phase 1 (Week 1-2):** Infrastructure
- Deploy Kafka cluster (3 brokers, replication factor 3)
- Set up Schema Registry
- Create topics: `notifications`, `notifications-dlq`, `notifications-retry`

**Phase 2 (Week 3-4):** Producer Side
- Add Kafka producer to API service
- Dual-write: write to both sync processor and Kafka
- Monitor: verify events in Kafka match sync processing

**Phase 3 (Week 5-6):** Consumer Service
- Deploy Notification Consumer Service
- Implement consumers for each notification type
- Add retry logic with exponential backoff
- Implement dead letter queue handling

**Phase 4 (Week 7-8):** Cutover
- Switch from dual-write to Kafka-only
- Remove sync processing code
- Monitor for 1 week before declaring success

## Alternatives Considered

### Alternative 1: RabbitMQ

- **Description:** Use RabbitMQ as message broker with work queues
- **Pros:**
  - Simpler to operate than Kafka
  - Lower latency for single messages
  - Built-in retry and dead letter exchanges
  - Team has some RabbitMQ experience
- **Cons:**
  - Message persistence is optional (default: in-memory)
  - No built-in replay capability
  - Scaling consumers requires manual configuration
  - No schema registry integration
- **Why not chosen:** Lack of replay capability is critical for compliance. Team evaluated and decided replay is a hard requirement.

### Alternative 2: Redis Streams

- **Description:** Use Redis Streams as lightweight message queue
- **Pros:**
  - Already using Redis (no new infrastructure)
  - Very low latency
  - Simple API
  - Minimal operational overhead
- **Cons:**
  - Memory-bound (limited by Redis instance size)
  - No built-in partitioning for consumer scaling
  - Persistence requires configuration (AOF/RDB)
  - No consumer groups in same way as Kafka
- **Why not chosen:** At current scale (10M notifications/day), Redis memory requirements would be excessive. Also, consumer scaling is limited.

### Alternative 3: AWS SQS + SNS

- **Description:** Use AWS managed messaging services
- **Pros:**
  - Fully managed (no infrastructure to operate)
  - Infinite scaling
  - Built-in DLQ and retry
  - Pay-per-use pricing
- **Cons:**
  - Vendor lock-in to AWS
  - Message size limit (256KB)
  - No replay capability
  - Higher latency than Kafka (typically 10-100ms vs < 10ms)
  - Cost at scale can be significant
- **Why not chosen:** Team preference for cloud-agnostic solution. Replay capability not available.

### Alternative 4: Keep Sync + Add Async Sidecar

- **Description:** Keep current sync processing but add async retry mechanism
- **Pros:**
  - Minimal change to existing code
  - Fastest to implement
  - No new infrastructure
- **Cons:**
  - Doesn't solve core problem (sync processing in request path)
  - API latency still affected during notification processing
  - No true decoupling
  - Technical debt increases
- **Why not chosen:** This is a band-aid, not a solution. Core problem is architectural.

## Trade-offs and Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Kafka operational complexity | High | Managed Kafka (Confluent Cloud) or dedicated SRE ownership |
| Learning curve for team | Medium | Training sessions, pair programming, documentation |
| Migration bugs during dual-write | Medium | Extensive monitoring, feature flags, rollback plan |
| Schema evolution challenges | Medium | Schema Registry with backward compatibility checks |
| Latency increase (10-50ms) | Low | Still well within 5-minute target |
| Kafka cluster downtime | High | 3-broker setup with replication factor 3, monitoring, alerting |

## Open Questions

1. ~~Should we use managed Kafka or self-hosted?~~ **Resolved:** Start with Confluent Cloud, evaluate self-hosting after 6 months
2. ~~What serialization format?~~ **Resolved:** Avro with Schema Registry
3. How to handle notifications during Kafka downtime? **Open:** Fall back to sync processing or queue locally?
4. Should we use Kafka Streams for processing or separate consumer service? **Open:** Evaluate in Phase 3
