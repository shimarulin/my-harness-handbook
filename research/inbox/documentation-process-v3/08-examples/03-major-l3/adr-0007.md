# 0007. Use Apache Kafka for Event-Driven Notifications

Date: 2026-09-22

## Status

Accepted

## Context and Problem Statement

Текущая система уведомлений обрабатывает notifications синхронно в API request handlers. При пиковой нагрузке (> 1000 req/s) это вызывает:

- API p95 latency рост с 200ms до 3+ секунд
- 3 инцидента за последний квартал
- ~20% времени команды на performance issues

Нужна event-driven architecture для:
- Decoupling notification processing от API
- 99.9% delivery guarantee в течение 5 минут
- Replay capability для failed notifications
- Independent scaling notification processing

Подробный анализ: [rfc-0031](../rfc/0031-event-driven-notifications.md)

## Decision Drivers

- **Replay capability:** Hard requirement from compliance team
- **Scalability:** Must handle 10M+ notifications/day
- **Cloud-agnostic:** No vendor lock-in
- **Team expertise:** Some Kafka experience, no RabbitMQ in production
- **Operational overhead:** Prefer managed solution initially
- **Latency budget:** < 5 minutes end-to-end (not real-time requirement)

## Considered Options

- **Apache Kafka** (Confluent Cloud initially)
- **RabbitMQ**
- **Redis Streams**
- **AWS SQS + SNS**
- **Keep sync + add retry sidecar**

Подробное сравнение: [RFC §Alternatives](../rfc/0031-event-driven-notifications.md#alternatives-considered)

## Decision Outcome

Chosen option: **"Apache Kafka (Confluent Cloud)"**, because:
- Only option with built-in replay capability (compliance requirement)
- Proven at our scale and beyond (10M+ messages/day)
- Schema Registry provides schema evolution guarantees
- Consumer groups enable horizontal scaling
- Cloud-agnostic (can self-host later)
- Team has some experience

### Consequences

**Good, because:**
- True decoupling of notification processing from API
- At-least-once delivery with idempotent consumers
- Replay capability for failed notifications
- Independent scaling of notification consumers
- Schema Registry ensures compatibility during evolution
- Dead letter queue for poison messages

**Bad, because:**
- Additional infrastructure to operate (Kafka cluster)
- Learning curve for team (Kafka-specific patterns)
- Latency increase of 10-50ms per notification
- Schema evolution requires discipline
- Confluent Cloud adds cost (~$500/month at current scale)

**Neutral, because:**
- Kafka is industry standard, hiring easier
- Avro schemas are self-documenting
- Monitoring ecosystem is mature

### Confirmation

Implementation will be verified by:
- [ ] API p95 latency < 300ms at peak load
- [ ] 99.9% notifications delivered within 5 minutes
- [ ] Replay of failed notifications succeeds
- [ ] No data loss during broker failure (replication factor 3)
- [ ] Consumer lag monitoring shows healthy processing

## Pros and Cons of the Options

### Apache Kafka (Confluent Cloud)

- Good, because built-in replay capability (offset-based)
- Good, because consumer groups for horizontal scaling
- Good, because Schema Registry integration
- Good, because proven at massive scale
- Good, because cloud-agnostic (can migrate to self-hosted)
- Bad, because operational complexity (if self-hosted)
- Bad, because learning curve for team
- Bad, because additional infrastructure component
- Bad, because Confluent Cloud cost (~$500/month)

### RabbitMQ

- Good, because simpler to operate than Kafka
- Good, because built-in retry and dead letter exchanges
- Good, because team has some experience
- Good, because lower latency for single messages
- Bad, because no built-in replay capability
- Bad, because scaling consumers requires manual config
- Bad, because no schema registry integration
- Bad, because message persistence optional (default: in-memory)

### Redis Streams

- Good, because already using Redis (no new infra)
- Good, because very low latency
- Good, because simple API
- Good, because minimal operational overhead
- Bad, because memory-bound (limited by Redis instance)
- Bad, because limited consumer scaling (no consumer groups like Kafka)
- Bad, because persistence requires explicit configuration
- Bad, because not suitable for 10M+ messages/day scale

### AWS SQS + SNS

- Good, because fully managed (zero infra to operate)
- Good, because infinite scaling
- Good, because built-in DLQ and retry
- Good, because pay-per-use pricing
- Bad, because vendor lock-in to AWS
- Bad, because no replay capability
- Bad, because message size limit (256KB)
- Bad, because higher latency than Kafka (10-100ms vs < 10ms)
- Bad, because cost at scale can be significant

### Keep Sync + Add Retry Sidecar

- Good, because minimal change to existing code
- Good, because fastest to implement
- Good, because no new infrastructure
- Bad, because doesn't solve core problem
- Bad, because API latency still affected
- Bad, because no true decoupling
- Bad, because increases technical debt
