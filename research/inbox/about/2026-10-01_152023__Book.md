`````markdown
## Часть 2. Execution Layer

Движок: цикл, рассуждения, tools, маршрутизация.

- 01. Обзор execution-слоя.
- 02. Agent Loop — от наивного while-loop до state machine.
- 03. Reasoning patterns — ReAct, Plan-and-Solve, Reflexion, LATS, ToT.
- 04. Tool calling — JSON Schema, идемпотентность, retry-политики.
- 05. MCP — универсальный стандарт инструментов.
- 06. Routing — router-агенты, semantic routing, классификация намерений.
- 07. Multi-agent — иерархия, дебаты, supervisor/worker.

## Часть 3. Infrastructure Layer

Память, знания и состояние.

- 01. Обзор инфраструктуры.
- 02. Vector stores — Qdrant, pgvector, Pinecone, гибридный поиск.
- 03. Graph databases — Neo4j, NetworkX, Knowledge Graphs.
- 04. State management — LangGraph, Temporal, Redis для long-running агентов.
- 05. Memory systems — short-term, long-term, episodic, semantic.
- 06. RAG pipelines — re-ranking, query transformation, agentic RAG.

## Часть 4. Production

Эксплуатация, надёжность, стоимость.

- 01. Обзор продакшена.
- 02. Evaluation — LLM-as-a-Judge, offline/online метрики, golden datasets.
- 03. Observability — LangSmith, Arize Phoenix, OpenTelemetry.
- 04. Guardrails — prompt injection, output filtering, PII redaction.
- 05. Cost optimization — кэширование, batching, routing моделей.
`````

`````markdown
# Архитектура AI-агентных систем

Это расширенное руководство для разработчиков, которые уже запускали свой первый harness, работали с tool calling и понимают, чем RAG отличается от fine-tuning. Здесь мы не будем учить вас писать `client.chat.completions.create()`. Мы будем говорить об архитектуре, контрактах и надежности.

## Почему «слои», а не «фичи»?

Агентная система — это не монолит. Это **стек ответственности**, где каждый слой решает свой класс проблем:

```text
┌─────────────────────────────────────────┐
│  СЛОЙ 4: Production                     │ ← Как это живет в реальности
│  (Evaluation, Observability, Cost)      │
├─────────────────────────────────────────┤
│  СЛОЙ 3: Data Layer                     │ ← Где хранится контекст
│  (Vectors, Graphs, State, Memory)       │
├─────────────────────────────────────────┤
│  СЛОЙ 2: Execution Layer (Harness)      │ ← Как агент думает и действует
│  (Agent Loop, Reasoning, Routing, MCP)  │
├─────────────────────────────────────────┤
│  СЛОЙ 1: Contract Layer                 │ ← Что агенту разрешено делать
│  (Specs, BDD, ADR, AGENTS.md, SDD)      │
└─────────────────────────────────────────┘
```

> **Ключевой инсайт книги:** Большинство проблем с AI-агентами (галлюцинации, неконтролируемое поведение, «дрейф» логики) возникают не в Слое 2 (harness), а в Слоях 1 и 3. Вы не можете починить ненадежного агента, просто добавив ему еще одну модель. Вам нужно начать со спецификации и памяти.

## С чего начать?

### Если вы начинаете новый проект с нуля
Начните с **Части 1 (Contract)**. Прочитайте про [EARS](part-1-contract/ears-requirements.md) и [ADR](part-1-contract/adr-workflow.md), выберите SDD-инструмент ([Kiro](part-1-contract/sdd-tools/kiro.md) или [Spec Kit](part-1-contract/sdd-tools/spec-kit.md)) и зафиксируйте требования ДО того, как напишете первую строчку Python-кода.

Идите в **Часть 2 (Execution)**. Разберитесь с [reasoning patterns](part-2-execution/reasoning-patterns.md) (возможно, вам нужен LATS, а не ReAct), изучите [MCP](part-2-execution/mcp-protocol.md) и [мультиагентные паттерны](part-2-execution/multi-agent.md).

### Если агент «теряет контекст» между сессиями
Ваша проблема в **Части 3 (Infrastructure)**. Вам нужны главы про [графовые БД](part-3-infrastructure/graph-databases.md) (для связей между сущностями) и [state management](part-3-infrastructure/state-management.md) (для long-running процессов).

### Если агент работает на демо, но вы боитесь выкатывать его в прод
Вам нужна **Часть 4 (Production)**. Читайте про [evaluation](part-4-production/evaluation.md) (без него вы не узнаете, что агент деградировал), [observability](part-4-production/observability.md) и [guardrails](part-4-production/guardrails.md).
`````

`````markdown
> Если артефакт читает агент до начала работы и он определяет **что делать**, — он здесь. Если он определяет **как делать** — это [Execution](../part-2-execution/index.md).
`````

`````markdown
# EARS (Easy Approach to Requirements Syntax)

## Зачем эта глава

Модель не умеет читать мысли. EARS даёт **фиксированные шаблоны**, которые модель понимает однозначно. Применённые к агентам, они превращают «хочу фичу» в проверяемый контракт.

## Пять паттернов

- **Ubiquitous**: «The system shall …»
- **Event-driven**: «When <trigger>, the system shall …»
- **State-driven**: «While <state>, the system shall …»
- **Optional feature**: «Where <feature>, the system shall …»
- **Unwanted behaviour**: «If <condition>, the system shall …»

## Пример для агента

```text
When пользователь запрашивает code review,
the agent shall return комментарии в формате JSON
с полями: file, line, severity, message.

If агент не может прочитать файл,
the agent shall вернуть ошибку с кодом FILE_UNREADABLE
и не продолжать ревью.
```

## Архитектурная схема

```text
[Идея] → EARS → [Требование] → Prompt / Spec / Test
```

## Почему это критично для LLM

- Модель не различает «должно» и «может», если не сказать явно.
- EARS убирает двусмысленность, снижает дрейф задачи.
- EARS-требования напрямую конвертируются в acceptance-тесты.

## Чеклист

- [ ] Каждое требование имеет один из пяти паттернов EARS.
- [ ] Нет слов «быстро», «удобно», «правильно» без критерия.
`````

`````markdown
# BDD / Gherkin

## Зачем эта глава

Gherkin-сценарии — это **исполняемые спецификации**: они одновременно описывают поведение агента и служат acceptance-тестами. Мост между «что просим» и «как проверяем».

## Пример

```gherkin
Feature: Code review agent

  Scenario: Ревью простого PR
    Given PR содержит изменения в одном файле
    When агент получает запрос на ревью
    Then он возвращает список комментариев
    And каждый комментарий содержит file, line, severity
    And severity ∈ {info, warning, error}

  Scenario: Файл недоступен
    Given файл был удалён до старта ревью
    When агент пытается его прочитать
    Then он возвращает ошибку FILE_UNREADABLE
    And не продолжает ревью
```

## Архитектурная схема

```text
[EARS] → [Gherkin] → [Feature files] → [Agent prompt + tests]
```

## Как использовать с агентом

- `.feature` файлы передаются агенту как часть контекста.
- Агент может сам генерировать Gherkin-сценарии из EARS.
- В CI — прогон сценариев через step definitions.

## Чеклист

- [ ] Каждое требование EARS имеет хотя бы один Gherkin-сценарий.
- [ ] Сценарии покрывают happy path и edge cases.
`````

`````markdown
# Agent Loop

## Зачем эта глава

Все агенты работают по одному циклу. Понять его устройство — значит понимать, где вставлять свои улучшения и как отлаживать.

## Эволюция

1. **Naive loop**: `while not done: response = llm(context); context += response`.
2. **Tool-aware loop**: `while not done: response = llm(context); if tool_call: result = run(tool); context += result`.
3. **State machine**: явные состояния, переходы, условия выхода.
4. **Durable loop**: чекпоинты, восстановление после сбоя.

## Архитектурная схема

```text
[perceive] → [plan] → [act] → [observe] → (loop)
   ↑                                        │
   └──────────── exit conditions ───────────┘
```

## Условия выхода

- Цель достигнута (агент сам сообщил).
- Tool вернул терминальный результат.
- Бюджет исчерпан (шаги, токены, время).
- Внешний сигнал (HITL, cancel).

## Чеклист

- [ ] Явные условия выхода.
- [ ] Чекпоинты в долгих задачах.
- [ ] Логирование каждого шага.
`````

`````markdown
# Reasoning patterns

## Зачем эта глава

«Подумай шаг за шагом» — это только один из паттернов. Здесь разбираем семейство и то, когда какой выбирать.

## Паттерны

- **ReAct**: think → act → observe. База.
- **Plan-and-Solve**: сначала план, потом исполнение. Для длинных задач.
- **Reflexion**: self-critique после шага.
- **LATS**: tree search по действиям. Для задач с ветвлением.
- **Tree-of-Thought**: ветвление на уровне рассуждений.

## Архитектурная схема

```text
ReAct:       [T]→[A]→[O]→[T]→[A]→[O]→...
Plan-Solve:  [Plan]→[Step1]→[Step2]→...
Reflexion:   [Act]→[Critique]→[Act]→...
LATS:        [Act]⇄[Rollout]⇄[Backprop]
```

## Как выбрать

| Задача | Паттерн |
|---|---|
| Быстрый Q&A с tools | ReAct |
| Многошаговая с чётким планом | Plan-and-Solve |
| Ошибки в рассуждениях | Reflexion |
| Игровые / поисковые задачи | LATS |

- [ ] Паттерн выбран под тип задачи.
`````

`````markdown
# Vector stores

## Зачем эта глава

Vector store — самый распространённый способ дать агенту доступ к знаниям. У него есть пределы, которые нужно понимать.

- Эмбеддинги: модель, размерность, стоимость.
- Similarity: cosine, dot, euclidean.
- Qdrant, pgvector, Pinecone, Weaviate — когда что.
- Chunking: как резать документы.
- Ограничения: семантический шум.

## Архитектурная схема

```text
[Документы] → [Chunker] → [Embedder] → [Vector DB] → [Agent]
```
`````

`````markdown
# Memory systems

## Зачем эта глава

«Память агента» — это не одна сущность, а как минимум четыре. Здесь разбираем их роли и как их не путать.

- **Short-term**: рабочая память в рамках задачи.
- **Long-term**: проектные знания, переживают сессии.
- **Episodic**: история взаимодействий.

## Архитектурная схема

```text
[Session] → [Short-term]
[Project] → [Long-term]
[Events]  → [Episodic]
[Facts]   → [Semantic]
```

## Чеклист

- [ ] Типы памяти разделены.
- [ ] Есть стратегия очистки.
- [ ] Episodic → Semantic переход осмыслен.
- [ ] PII не утекает в long-term.
`````

`````markdown
# RAG pipelines

## Зачем эта глава

RAG — не одна техника, а семейство. Здесь разбираем эволюцию: от naive retrieve-then-generate до agentic retrieval.

## Эволюция

1. **Naive RAG**: embed → retrieve top-k → generate.
2. **Advanced RAG**: query rewriting, reranking, compression.
3. **Agentic RAG**: агент сам решает, что и как искать.

## Архитектурная схема

```text
[Query] → [Rewrite] → [Retrieve] → [Rerank] → [Compress] → [LLM]
```

## Чеклист

- [ ] Retrieval измеряется (recall@k, MRR).
- [ ] Reranking — не опционально, если качество важно.
- [ ] Agentic RAG не используется без нужды.
- [ ] Generation отделён от retrieval в eval.

## Что дальше
`````

`````markdown
## Зачем эта глава

Без трассировки отладка агента превращается в гадание.

[Task] ─┬─ [Step] ─┬─ [LLM call]
        │          ├─ [Tool call]
        │          └─ [Result]
        └─ [Step] ─ ...
```

## Чеклист

- [ ] Каждый шаг трейсится.
- [ ] Prompt и response логируются.
- [ ] Есть связь trace ↔ task.
- [ ] PII редактируется.
`````

`````markdown
# ADR-0001: Разделение книги на четыре слоя

## Status
Accepted

## Context

Первоначальная структура книги была линейной: Foundations → Harness → Orientation → Extensions → Practice. По мере роста стало понятно, что читатели приходят с разными болями и не хотят читать линейно.

## Decision

Разделить книгу на четыре слоя ответственности:

1. Contract — текстовые артефакты (EARS, BDD, ADR, AGENTS.md, SDD).
2. Execution — harness (agent loop, reasoning, tools, MCP).
3. Infrastructure — память и данные (vector, graph, state, memory, RAG).
4. Production — эксплуатация (eval, observability, guardrails, cost).

## Consequences
+ Читатель заходит с нужной стороны.
+ Каждый артефакт имеет однозначное место.
+ Легче добавлять главы.
− Требуется явная навигация между слоями.
− Некоторые темы пересекают слои (например, MCP), приходится выбирать.
`````

`````markdown
# Spec 001: Code Review Agent

## EARS-требования

- **Ubiquitous**: The agent shall return comments in JSON format.
- **Event-driven**: When a PR is opened, the agent shall start review within 30s.
- **State-driven**: While the PR is in draft, the agent shall not post comments.
- **Optional feature**: Where the repo has ADRs, the agent shall check compliance.
- **Unwanted behaviour**: If a file is unreadable, the agent shall return error `FILE_UNREADABLE` and stop.

## BDD-сценарии

```gherkin
Feature: Code Review Agent

  Scenario: Простой PR
    Given PR содержит один изменённый файл
    When агент получает запрос на ревью
    Then он возвращает JSON с комментариями
    And каждый комментарий имеет severity ∈ {info, warning, error}

  Scenario: Draft PR
    Given PR в статусе draft
    When агент получает запрос на ревью
    Then он не публикует комментарии
    And логирует "skipped: draft"

  Scenario: ADR violation
    Given в репозитории есть ADR-0007
    And PR нарушает ADR-0007
    When агент ревьюит PR
    Then он добавляет комментарий со ссылкой на ADR-0007
```
`````

## 📌 Что получилось

Полный репозиторий по четырёхслойной архитектуре:

| Слой | Папка | Файлов |
|---|---|---|
| Корень | `.` | 6 (README, OUTLINE, CONTRIBUTING, AGENTS.md, mkdocs.yml, шаблон) |
| Вход | `docs/` | 1 (index.md) |
| **Contract** | `docs/part-1-contract/` | 5 + 5 SDD-глав |
| **Execution** | `docs/part-2-execution/` | 7 глав |
| **Infrastructure** | `docs/part-3-infrastructure/` | 6 глав |
| **Production** | `docs/part-4-production/` | 5 глав |
| Сквозные | `decisions/`, `specs/`, `examples/` | 4 файла |

**Ключевые принципы, которые теперь явно зафиксированы:**

1. **Спецификация — это код.** EARS, BDD, ADR, AGENTS.md, specs живут в Contract Layer и проектируются с той же строгостью, что API-контракты.
2. **Harness — только механика.** Execution Layer не знает про текстовые артефакты и хранилища.
3. **Data Layer — под Execution.** Storage вынесен отдельно, чтобы его можно было менять независимо от движка.
4. **Production — обратная связь.** Eval, observability и cost замыкают цикл: они сообщают в Contract и Execution, что нужно менять.

Дальше можно:
- **расписать полноценно одну главу** (например, `docs/part-1-contract/ears-requirements.md` или `docs/part-2-execution/reasoning-patterns.md`) как эталон стиля;
- **добавить CI** (GitHub Actions) для `mkdocs build --strict` и деплоя на Pages;
- **собрать `examples/code-review-agent/agent.py`** как runnable reference-реализацию.
