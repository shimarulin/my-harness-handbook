# Идея: ядро процесса — уровни масштаба × модульность × дешевая форма

| Параметр | Значение |
|---|---|
| Статус | core-candidate (претендент на ядро системы) |
| Обновлено | 2026-09-30 |
| Происхождение | Синтез фаз 2–3 (критика SDD + процессное ядро v2/v3) |

## Проблема

Процессы разработки через документацию ломаются о две крайности:

1. **Overhead не окупается.** Полный процесс (PRD → RFC → spec → tasks → ADR) для простой задачи — «хирургия вилочным погрузчиком»: затраты на документацию превышают ценность (подтверждено: BMAD Full 6 дней/$200 против лёгкого 1 день; кейс, где простой Instructions.md победил OpenSpec).
2. **Лёгкий процесс не масштабируется.** Отсутствие структуры для крупной инициативы — потеря трассировки, невозможность onboarding, хаос при росте.
3. **Форма артефактов навязана шаблоном.** Тяжёлые текстовые спеки дрейфуют от кода, потому что проза не проверяется машиной; требование живёт не в той форме, которая способна его удерживать дёшево.

## Почему готовые решения не закрывают

- **Жёсткие pipelines (Spec Kit, BMAD)** — константный overhead независимо от размера задачи; «too opinionated», waterfall-like.
- **Лёгкие (OpenSpec)** — нет уровней governance; advisory verification не удерживает соответствие.
- **Уровни v2/v3 по отдельности** — v3 даёт L0–L4 (per-инициатива), v2 — S1–S5 (per-организация), но ни одна не связывает их и не соединяет с формой артефактов.
- **Шаблонные спеки** — навязывают форму (Markdown-проза) вместо выбора по цене удержания.

## Ценность

Единая модель, делающая overhead пропорциональным риску, а форму артефактов — минимально достаточной:

- **Две оси масштаба** — разделяют «сколько документов на изменение» (уровень инициативы) и «сколько governance» (уровень организации). Снимают ложную дилемму «лёгкий vs строгий процесс».
- **Модульность** — процесс собирается из блоков под задачу, а не выбирается целиком; core всегда, optional по критериям.
- **Дешевая форма** — требование живёт в самой дешёвой удерживающей форме (тип/контракт/PBT/пример/ADR); проза — только для дорогоформализуемого.
- **Экономика внимания** — человек решает только по квалифицированным расхождениям; масштаб процесса = f(сложность, цена ошибки).
- **Продвижение вверх** — артефакты не рождаются «правильного уровня», а растут (idea → task → prd → rfc → adr), не выбрасываясь.

## Архитектура

### Две оси масштаба

| Ось | Что определяет | Диапазон |
|---|---|---|
| **Инициатива (L0–L4)** | Набор артефактов и gates для одного изменения | L0 trivial → L1 small → L2 feature → L3 major → L4 platform |
| **Организация (S1–S5)** | Governance-контекст | S1 solo → S2 small → S3 growing → S4 large → S5 enterprise |

Уровни как механизм экономики внимания: L0 — ~0 overhead; L1 — ≤ 15 мин; L2 — ~2–4 ч; L3 — ~1–2 дня; L4 — дни. Overhead пропорционален риску.

### Модульный пайплайн

Core (всегда): Problem Statement → Requirements (EARS) → Approach → Tasks → Implementation + ADR при каждом решении. Optional по критериям: PRD, RFC, BDD, API Specs, discovery, Formal Methods, Research Compendium. «Не выбирайте pipeline — соберите его».

### Дешевая форма требования (критерий выбора артефакта)

| Тип требования | Форма | Проверяет |
|---|---|---|
| Структурный инвариант домена | Тип | Компилятор |
| Граница систем | Схема + контрактный тест | Машина (CI) |
| Обобщённое намерение | Property-based тест | Машина (CI) |
| Конкретное поведение | Пример (unit-тест) | Машина (CI) |
| Причины решений | ADR | Человек |

Принцип отбора: словами — только то, что формализуется дороже, чем нарушается. Это корень устойчивости: текстовая спека сжата до минимума, всё формализуемое дёшево — машинное.

### Promotion-цепочка

`idea → task → prd → rfc → adr` со статусом `promoted`: артефакт нижнего уровня разворачивается в верхний (Job Story → PRD; design notes → RFC; RFC-серия → arc42) без переписывания и потери следа. Сочетается с «контент стабилен» (см. `../knowledge-architecture/`): продвижение — через данные (frontmatter `traces`), не перемещение.

## Связь с остальными кластерами

- Форма артефактов проверяется машиной → `../enforcement/` (блокирующие gate: EARS → coverage → architecture → tests).
- Экономика внимания + durable context для агента → `../agent-governance/` (агент читает артефакты нужного уровня, человек — approval gates).
- Хранение и навигация артефактов → `../knowledge-architecture/` (notes/+views/, frontmatter `traces`, `level`).
