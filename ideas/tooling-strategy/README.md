## Проблема

Инструменты процесса создают три риска:

1. **Vendor-lock принимает разные формы.** Не только лицензионный: знаниевый (Tessl — 10K+ specs в закрытом registry), экосистемный (Kiro — AWS, Antigravity — Google Cloud), форматный (проприетарные форматы). Открытость ≠ отсутствие проблем (Spec Kit — MIT, но проблемы дизайна при 90K звёзд).
2. **Инструмент навязывает процесс.** Команда принимает workflow «из коробки» вместо проектирования под свой контекст; при смене инструмента ломаются привычки.
3. **Преждевременное «своё» или «готовое».** Либо строят своё, когда есть рабочее готовое (over-engineering), либо принимают готовое там, где оно не закрывает нужное (компромисс функциональности).

## Почему готовые решения не закрывают (мета-проблему выбора)

- **Готовые инструменты** — решают свою задачу, но не вопрос «как остаться независимым от них» (знаниевый/экосистемный lock, bus factor, форк-модель).
- **«Roll your own» полностью** — 4 custom slash-команды + AGENTS.md дают ~80%, но остальные 20% (presets, delta-маркеры, handoffs) приходится достраивать; риск переизобретения.
- **Чек-листы лицензий** — проверяют лицензионный lock, но не знаниевый/экосистемный.

## Ценность

Стратегия, делающая процесс независимым от инструментов и выбор — осознанным:

- **Процесс переживает инструменты**: процесс проектируется владельцем; инструмент — заменяемая реализация, обёрнутая в собственную абстракцию.
- **Vendor-exit как операционная практика**: реестр с exit strategies и quarterly health check; любой инструмент заменим ≤ 1 sprint.
- **Осознанный adopt/adapt/build**: критерии, когда adopt готового, когда adapt, когда build своё.
- **Распространение tooling без lock-in**: ядро + project-local кастомизация с fallback chain.

## Архитектура

### Принцип: процесс проектируется владельцем

«Design the experience you want, not the one the tool ships»: шаги, артефакты, форматы, review gates — под контекст владельца; инструмент это реализует, но не определяет. Оборачивание в абстракцию: свои команды (`my-company-sdd start feature` вместо `openspec create-feature` — разработчики учат команды компании, не инструмента), свои форматы, свой PROCESS.md отдельно от инструмента.

### Таксономия vendor-lock и чек-лист

4 формы: лицензионный, знаниевый, экосистемный, форматный. Чек-лист оценки (7 пунктов): лицензия MIT/Apache/BSD; код форкабелен; нет обязательных облачных сервисов; основные возможности бесплатны; открытый формат данных; экспорт 100%; активное сообщество (не bus factor 1). Красные флаги: «AWS Content»-лицензии; ключевая функциональность в закрытом реестре; требование конкретных облаков; платный доступ к сообществу; проприетарный формат без экспорта.

### Vendor-exit как практика

Реестр инструментов: primary + ≥1 альтернатива на категорию, скоринг, exit strategy заранее, **quarterly health check** (last commit, stars, contributors; red = > 30 дней без коммита или < 3 contributors → «Consider alternative»; триггер смены — альтернатива score > current + 0.5). Смена инструмента = ADR. Правило T5: заменимость ≤ 1 sprint; критическая зависимость запрещена.

### Adopt / Adapt / Build (критерии)

| Решение | Когда |
|---|---|
| **Adopt** (готовое как есть) | Готовое закрывает нужное без компромиссов; принять его модель (напр., Spec Kitty Research Mission для research в delivery) |
| **Adapt** (готовое + доработка) | Готовое закрывает основу, но нужны расширения: template overrides, hooks, extension-скрипты (напр., Spec Kitty + extract-learnings) |
| **Build** (своё) | Нужны механизмы, которых нет у готовых (cross-mission learnings, topic-views, cross-tool handoff); независимость от bus factor/форк-модели; нестандартный пайплайн |

Комбинация допустима: adopt/adapt для закрытых функций + build для дифференцирующих. Собственная система и есть «своя абстракция» поверх готовых частей.

### Распространение: ядро + project-local кастомизация

Гибрид (паттерн Spec Kit/pre-commit/Husky): ядро — внешний пакет (dev-dependency, централизованные обновления); кастомизация — project-local `.research/` (templates / config.yaml / hooks / extensions) с **fallback chain** «project → package default». Дает: обновления ядра в одном месте + вариации per-project + graceful degradation (проект без `.research/` работает на дефолтах) + Git-friendly. Путь роста: скрипты в проекте → вынос ядра при втором проекте → publish + uvx.

### Инструменты для двух потребителей (dual-mode)

Один инструмент, два режима: интерактив (wizard/TUI) для человека; флаги + `--json` для агента. Ядро логики отделено от интерфейса (CLI → dual-mode → MCP → TUI добавляются без переписывания ядра; ядро можно переписать на другом языке, сохранив CLI).

### Граница Git-Native: место артефактов

Репо — source of truth для **артефактов решений**; upstream requirements work (discovery, scope, stakeholder alignment) может жить в доступных всем ролям системах (BA, delivery, QA, клиент — не workspace репо) с **зеркалированием** в репо. Граница по доступности ролям, не по догме «всё в git».
